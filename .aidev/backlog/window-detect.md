# ウィンドウ判定（罫線推測をやめて受信データで決める）

ウィンドウ装飾（`windowFrame` / `windowBackdrop`）を出す範囲を、**画面に描かれた罫線から
推測**している。この推測に誤検出があるという報告を受け、2026-07-28 に現状を実測した。
**判定材料そのものを変えないと直らない**と分かったので、調査結果と方針をここへ積む。

## 現状の仕組み

`packages/web-ui/src/composables/fkeyLegend.ts:205` の `detectWindowRect` が 2 段構え。

1. `snap.gui.windows` があればそれを使う（`CREATE_WINDOW(51)` 構造化フィールド由来＝**ホストの宣言**）
2. 無ければ**罫線から推測**する。同ファイルの `detectReverseFrame`（反転で描く ATNPGM の窓）も併用

呼び出し側は `packages/web-ui/src/components/ScreenGrid.vue` の `decoWindow`。
ホストが枠を送っている場合は推測を止める作りになっており、**そこは正しい**。

問題は 2 の側で、コメントにあるとおり**通常のヘルプ窓は `gui.windows` に出ない**
（文字で描かれる）ため、**実際はこの推測経路がほとんどを占める**。

推測の条件が緩い（`fkeyLegend.ts:35-47`）:

- `BORDER_H`（`. - ─ ━ ═ _ ＿`）が **8 桁以上連続**する行が 2 本、80% 以上重なる
- 間の行の**左右どちらか**に `BORDER_V`（`: ： | ｜ │ ┃ ║`）が**半数以上**ある

「どちらか」「半数以上」なので、罫線で囲っていない画面でも成立してしまう。

## 実測（2026-07-28）: 誤検出を再現した

| 画面 | 判定 | 枠の外側の非空白セル数 |
|---|---|---|
| ① 本物の窓（F1 ヘルプ相当。上下 `.`・左右 `:`） | 検出（正） | **130** |
| ② 一覧画面（PDM 風。`---` 区切り 2 本） | null（正） | — |
| ③ 表（左右に `:` が並ぶ帳票） | **誤検出** | 176 |
| ④ 反転バナー（見出し行＋末尾行が反転） | **誤検出** | **0** |

③ は罫線経路、④ は反転経路で誤る。**両方の経路に誤検出がある**。

## 却下: 「枠の外に何も無ければ窓」は逆効果（再検討しないこと）

「背景なしの全画面ウィンドウなら枠の外に何も無いはず」という条件を検討したが、
**上の実測で否定された**。

- **本物の窓ほど外側に内容がある**（① は 130 セル）。窓は背景の上に開くので当然で、
  背景が残るのが窓の一般形
- 誤検出の ④ はむしろ外側が **0**

つまりこの条件で絞ると**本物を弾いて誤検出を通す**。「背景なしの全画面ウィンドウに限る」と
限定しても、④ のような偽物が同じ条件を満たすため判別材料にならない。

## 本命: 受信データの書き込み範囲で決める

**窓かどうかは描画結果ではなく受信データに出ている。**

- 本物の窓: 背景を消さずに**窓の領域だけ**書く → 書き込み範囲＝窓
- ③④ のような通常画面: 画面全体を書く → 書き込み範囲＝全画面 → 窓ではないと判定できる

**この情報は現在捨てられている。** `packages/core/src/protocol/wtd-applier.ts:10-33` の
`ApplyResult` には書き込み範囲も「CLEAR したか」も無く、`ScreenBuffer` も dirty 領域を持たない。
判定が見た目しか見られないのは、そもそも材料が渡っていないからで、
**推測条件をいくら調整しても限界がある**。

## 着手の順番

core 改修が入るので、いきなり判定を切り替えない。

1. 書き込み範囲を snapshot に載せるところまでやり、**既存テストが通ることだけ**確かめる
   （`window-view` / `stacked-window` / `reverse-frame-window` / `pane-cursor-window`）
2. 上の実測 4 画面を回帰テストに起こす（③④ が窓と判定されないことを固定）
3. そのうえで判定を切り替える

## 本命: 前画面との差分——「枠の外に新しい内容が出ていないなら窓」

**実機 34 対（窓 9・通常 25）で検証済み（2026-07-29）。窓 9/9 を保ち、誤検出 0。**

窓は背景の上に開くので、**枠の外側は前の画面のまま**であるはず。通常画面への遷移なら
枠の外にも新しい内容が現れる。`lastWrite`（1 レコード内の書き込み）と違い、
**画面と画面の差分**を見るのが肝で、ヘルプ窓が全画面書き直しで来ても成立する。

### 測り方の注意（両方とも実測で踏んだ）

1. **`detectWindowRect` は枠の「内側」を返す。** そのまま外側を測ると**新しく描かれた枠自体**が
   変化として数えられ、窓 9 件中 8 件を取りこぼす。**外周（±1 行・±1 桁）を含めた矩形**で測ること
2. **「文字→空白」は変化に数えない。** 窓の枠が DBCS 文字の片割れを潰すと、縁の 1〜3 桁に
   `文字→空白` が出る（実測: WRKACTJOB 3・WRKOBJPDM 3・WRKSPLF 14 セル。すべてこれ）。
   **枠外に新しい内容が現れた場合だけ**を変化とみなすと窓 9/9 が通る

### 残る穴と対処

**同じ画面が無変化で再描画されると、枠外も無変化なので窓と誤判定する**（合成データで再現済み）。
→ **画面全体が前回と完全一致なら「判定し直さず前回の結論を保つ」**。
情報が増えていないのに判定を変える理由が無い、という整理で筋も通る。

    無ければ従来どおり。判定は `ScreenGrid.vue` の watch が持つ（computed だと設定 OFF→ON で
    古い画面と比較してしまう）
  - **表示設定（SO/SI マーク・表示コード）は watch しない。** 含めると設定変更時に

## 制限事項: 大きい窓から小さい窓へ戻ると判定が外れる

**直さない。原理的に前画面 1 枚では区別できない**（利用者判断 2026-07-29）。

ヘルプ窓 → `F2` 拡張ヘルプ（より大きい窓）→ 元のヘルプ窓、と戻ったときに窓と判定されない。
大きい窓が占めていた領域は、戻るときに背景で描き直される。それが**小さい窓の枠の外**に当たるため
「新しい内容が現れた」と数えられる——**通常画面への遷移とまったく同じ形**になる。

この判定は「窓は背景の上に開く＝枠の外は前のまま」という前提に立っており、
**窓が縮む方向の遷移はその前提の外**にある。直すには前画面 1 枚ではなく
**窓の履歴（スタック）**を持つ必要があり、費用に見合わないと判断した。

`window-prev-diff.test.ts` の「既知の制限」節で**この挙動を固定してある**——
誰かが「直った」と思って挙動を変えたら、そのテストが落ちて気づける。

### 却下: RESTORE SCREEN を合図に使う（**実機で否定済み。再検討しないこと**）

「ホストは窓を閉じるとき RESTORE SCREEN を送るので、`WriteExtent.restored` を
『1 つ前の窓へ戻った』合図に使えるのでは」という案を実機で測った（2026-07-29 / 実機・~~IBM i 7.5~~ **7.3**）。
`WRKMBRPDM` → `F1` ヘルプ → `F2` 拡張ヘルプ → `F12` で戻る:

| 段 | cleared | restored | rect | cells |
|---|---|---|---|---|
| 1) WRKMBRPDM 一覧 | true | false | 全画面 | 3053 |
| 2) F1 ヘルプ窓 A | true | false | 全画面 | 1702 |
| 3) F2 拡張ヘルプ B（大） | true | false | 全画面 | 1921 |
| 4) **F12 で A へ戻る** | true | **false** | 全画面 | 1702 |

**4 段すべて `restored=false`。** ホストは毎回クリアしてから全画面を描き直しており、
**RESTORE SCREEN は来ない**。合図として使えない。

実機の遷移を fixture 化してある（`win-help-shrink-back`）。
`window-prev-diff.test.ts` の「既知の制限」節が、**判定が外れること**と
**`restored` が false であること**の両方を固定している。
