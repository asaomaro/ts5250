# セッションの寿命（アイドルタイムアウト・永続）

**セッション設定でタイムアウト時間を選べるようにし、そこに「永続（切らない）」を含める。
設定した値のとおりに動くこと。** 2026-07-28 に「無操作で切れるのか」という問いから現状を
調べ、既定値そのものを見直すべきだと分かったので、調査結果とあわせて積む。

## 調査済み（2026-07-28）: 現状

- `packages/server/src/session-manager.ts:312` の `idleTimeoutMs` は**既定 30 分**、
  `startIdleSweep()` が **60 秒間隔**で `sweepIdle()` を回し、超過したエントリを
  `session.disconnect()` して削除する（表示・プリンターとも）
- **どこからも設定できない。** コンストラクタに口はあるが `main.ts:172` が
  `new SessionManager()` と引数なしで生成しており、CLI にも設定ファイルにも項目が無い
  （`config-types.ts` の `timeoutMs` は PC Organizer の `PAUSE(*YES)` 待ち上限で別物）
- `lastActivity` を更新するのは `get()` / `getPrinter()` を通る操作だけ＝
  `key` / `gui-select` / `gui-submit` / `printer-output`
- プリンターは `deliverReport()` でも更新される（push 型・救出型の両方が同じ道を通る）ため、
  **帳票が届いている限り生き続ける**。表示セッションとはここが違う

### 決定的: WebSocket が切れた時点で既に破棄している

`ws-handler.ts:87-89` の `onSocketClose()` → `dispose()` → `sessions.close()`。
ブラウザを閉じる・タブが落ちる・回線が切れると**その場でセッションは破棄される**
（ファイル冒頭にも「切断でセッションを破棄する」と明記）。**孤児セッションは残らない。**

つまり `sweepIdle` が実際に殺しているのは **WS が繋がったまま＝ブラウザが開いている
セッションだけ**で、reaper 本来の目的（放置された孤児の回収）とは逆に、
**在席している利用者を切っている**。

## 判断: 既定は「永続」が妥当

- **ACS は長時間放置しても切れない。** このリポジトリは ACS 準拠を基準にしている
- **アイドル対話ジョブの扱いは本来ホストの管轄**（`QINACTITV` / `QINACTMSGQ`）。
  多くの環境で `*NONE`（切らない）。こちらが 30 分で切るのは、
  **ホストが持つ方針を先取りして上書きしている**ことになる。
  retro で自分たちが見つけた「ホストが送っている情報を無条件に上書きしていた」と同じ型
- 孤児回収は `onSocketClose` が担っているので、**壁時計タイマーは重複**であり、
  既定を永続にしても安全性は落ちない

## やること

- [ ] **セッション設定にタイムアウト項目を足す（永続を含む）**
  - 置き場は `packages/server/src/config-types.ts` の **`sessionBase`**。
    サーバー設定・個人設定の両方が共有する。**信頼設定ではない**
    （サーバー上のパス書き込み・コマンド実行・秘密のいずれにも触れない）ので、
    `watermark` と同じ理屈で `sessionBase` に置ける
  - 「永続」の表し方（`0` / `null` / `"never"` のどれにするか）は実装時に決める。
    **未設定と永続を取り違えない**表現にすること
- [ ] **配線**: 設定 → `OpenOptions` → `open()` / `openPrinter()` でエントリに保持
- [ ] **`sweepIdle()` をエントリごとの値で判定する**
  - 現在はマネージャ共通の `cutoff` を 1 つ作って全エントリと比較している。
    `sweepIdle` は**既にエントリを 1 件ずつ回している**ので、
    エントリごとの値で判定し直すだけで済む。永続のエントリは対象外にする
- [ ] **既定値を永続にする**（上の判断のとおり）

## 「設定どおりに動く」ために塞ぐ穴

**有限値を選んだときに、設定した時間より早く切れる経路がある。**

利用者が入力欄に文字を打っても、値はクライアント内の `edits` に溜まるだけで、
**AID キー（Enter・F キー等）を押すまで WS に何も流れない**
（`packages/web-ui/src/session-controller.ts:296-311` の `sendKey`）。
コピー・範囲選択・画面スクロール・読んでいる時間も同様にサーバーからは見えない。

つまり長いコマンドを組み立てている・大きな入力画面を埋めている最中でも、
サーバーから見れば無操作のまま時間が進む。**在席しているのに切られ、
打ち込み途中の未送信入力（`edits` はクライアントにしか無い）は消える。**

- [ ] **在席の証拠をクライアントから拾う**
  - 入力・カーソル移動などの操作時に軽い活動通知を WS で送る。
    **値は送らないこと**——`edits` の中身を早く送ると秘密（マクロの `secretRef` 等）の
    扱いが変わってしまう
  - 永続を選べばこの穴は無害化されるが、**有限値を選ぶなら塞がないと「設定どおり」にならない**

### ホスト発の画面更新は活動に数えない（現状のままでよい）

ホストからの画面更新は `entry.session.on("screen", ...)` 直結で `get()` を通らないため
数えられていないが、**これは設計として正しい**ので変えないこと。
測るべきは利用者の在席であってホストの活動ではない。IBM i には中断メッセージ・ATNPGM・
READ を伴わない WRITE ループなど**利用者が居なくてもホストが書いてくる経路**があり、
これを活動に数えると閉じ忘れたタブが永久に生き残る。

## 残る論点

- [ ] **異常系の死活監視**
  - `onSocketClose` が拾えない場合（ソケットが半開きで残る等）に備えるなら、
    壁時計のアイドルではなく **WS の ping/pong** が本筋。
    **現在クライアント・サーバーとも実装が無い**（`ws-client.ts` / `ws-handler.ts` に定期送信なし）
- [ ] **プリンターの常駐用途との関係**
  - ブラウザを閉じている間も帳票を受け続ける「常駐」は `pc-command.md` /
    `hostserver.md` に挙がっている。そちらは WS 非依存の寿命管理が要るため、
    ここでの結論（WS 切断＝破棄）と噛み合うか確認してから決めること
- [ ] **永続セッションの本数に上限が要るか**
  - 永続は装置記述を掴み続ける。共有サーバーでは管理者が上限を掛けたくなる可能性がある。
    セキュリティというより資源の問題として、要否を判断する
