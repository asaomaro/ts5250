# セッションの寿命（アイドルタイムアウト・永続）

**セッション設定でタイムアウト時間を選べるようにし、そこに「永続（切らない）」を含める。
設定した値のとおりに動くこと。** 2026-07-28 に「無操作で切れるのか」という問いから現状を
調べ、既定値そのものを見直すべきだと分かったので、調査結果とあわせて積む。

**→ 2026-07-29 に `20260729-session-lifetime-timeout` で全項目を着地。このファイルは閉じた。**

## 調査済み（2026-07-28）: 現状

- `packages/server/src/session-manager.ts:312` の `idleTimeoutMs` は**既定 30 分**、
  `startIdleSweep()` が **60 秒間隔**で `sweepIdle()` を回し、超過したエントリを
  `session.disconnect()` して削除する（表示・プリンターとも）
- **どこからも設定できない。** コンストラクタに口はあるが `main.ts:172` が
  `new SessionManager()` と引数なしで生成しており、CLI にも設定ファイルにも項目が無い
  （`config-types.ts` の `timeoutMs` は PC Organizer の `PAUSE(*YES)` 待ち上限で別物）
- `lastActivity` を更新するのは `get()` / `getPrinter()` を通る操作だけ＝
  `key` / `gui-select` / `gui-submit` / `printer-output`
- プリンターは `deliverReport()` でも更新される（push 型・救出型の両方が同じ道を通る）ため、
  **帳票が届いている限り生き続ける**。表示セッションとはここが違う

### 決定的: WebSocket が切れた時点で既に破棄している

`ws-handler.ts:87-89` の `onSocketClose()` → `dispose()` → `sessions.close()`。
ブラウザを閉じる・タブが落ちる・回線が切れると**その場でセッションは破棄される**
（ファイル冒頭にも「切断でセッションを破棄する」と明記）。**孤児セッションは残らない。**

つまり `sweepIdle` が実際に殺しているのは **WS が繋がったまま＝ブラウザが開いている
セッションだけ**で、reaper 本来の目的（放置された孤児の回収）とは逆に、
**在席している利用者を切っている**。

### 追記（2026-07-29）: この結論は**ブラウザ経路に限って**正しかった

`sessions.open()` の入口は 2 つある（`ws-handler.ts:106` と `mcp-tools.ts:287`）。
**MCP には切断の通知が無い**（`StreamableHTTPTransport` のツール呼び出しごとの HTTP）ため、
MCP セッションを回収していたのは `sweepIdle` の壁時計タイマー**だけ**だった。
既定を一律に永続にすると `maxSessions`（既定 8）を食い潰して新規接続ができなくなる。
→ **既定は入口ごとに決める**という結論に落ちた（下記「やること」参照）。

## 判断: 既定は「永続」が妥当

- **ACS は長時間放置しても切れない。** このリポジトリは ACS 準拠を基準にしている
- **アイドル対話ジョブの扱いは本来ホストの管轄**（`QINACTITV` / `QINACTMSGQ`）。
  多くの環境で `*NONE`（切らない）。こちらが 30 分で切るのは、
  **ホストが持つ方針を先取りして上書きしている**ことになる。
  retro で自分たちが見つけた「ホストが送っている情報を無条件に上書きしていた」と同じ型
- 孤児回収は `onSocketClose` が担っているので、**壁時計タイマーは重複**であり、
  既定を永続にしても安全性は落ちない

## やること

- [x] **セッション設定にタイムアウト項目を足す（永続を含む）**
  - 置き場は `packages/server/src/config-types.ts` の **`sessionBase`**。
    サーバー設定・個人設定の両方が共有する。**信頼設定ではない**
    （サーバー上のパス書き込み・コマンド実行・秘密のいずれにも触れない）ので、
    `watermark` と同じ理屈で `sessionBase` に置ける
  - **`idleTimeout: "never" | 1..1440`（分）で実装**。`0` も `null` も使わない——
    未設定（＝サーバー既定に従う）・永続・有限を型で三分する（spec 方針2）
  - UI からも選べる（`ConfigCard` の「無操作で切る」。「サーバー既定に従う」と「切らない」は別項目）
- [x] **配線**: 設定 → `OpenOptions` → `open()` / `openPrinter()` でエントリに保持
  - 分 → ms の変換は `config-resolver.buildConnect` の**1 か所だけ**。
    プリンター経路（`ws-handler.onOpenPrinter`）はキーごとの手写しなので明示転記が要る
- [x] **`sweepIdle()` をエントリごとの値で判定する**
  - `expired(entry)` が `entry.idleTimeoutMs ?? this.idleTimeoutMs` を見る。永続は対象外
- [x] **既定値を永続にする**（上の判断のとおり）
  - `SessionManagerOptions.idleTimeoutMs ?? "never"`。運用者は `--idle-timeout <分|never>` で戻せる
  - **MCP 経由だけは既定 30 分**（`orphanSafeIdleTimeoutMs`）。設定の有限値は尊重するが
    `"never"` は通さない。回収する者が居ないため。曲げたときは warn に出す

## 「設定どおりに動く」ために塞ぐ穴

**有限値を選んだときに、設定した時間より早く切れる経路がある。**

利用者が入力欄に文字を打っても、値はクライアント内の `edits` に溜まるだけで、
**AID キー（Enter・F キー等）を押すまで WS に何も流れない**
（`packages/web-ui/src/session-controller.ts:296-311` の `sendKey`）。
コピー・範囲選択・画面スクロール・読んでいる時間も同様にサーバーからは見えない。

つまり長いコマンドを組み立てている・大きな入力画面を埋めている最中でも、
サーバーから見れば無操作のまま時間が進む。**在席しているのに切られ、
打ち込み途中の未送信入力（`edits` はクライアントにしか無い）は消える。**

- [x] **在席の証拠をクライアントから拾う**
  - `{type:"activity"}`（**payload なし**）を `EmulatorPane.onEdit` / `onCursor` から出す。
    15 秒に間引き、サーバーは `SessionManager.touch()` で `lastActivity` を進める
  - **値は送らない**（型に何も持たせない＝将来足せない形にした）。
    操作ログ・監査ログにも出さない（心拍で本来の記録を押し流さないため）

### ホスト発の画面更新は活動に数えない（現状のままでよい）

ホストからの画面更新は `entry.session.on("screen", ...)` 直結で `get()` を通らないため
数えられていないが、**これは設計として正しい**ので変えないこと。
測るべきは利用者の在席であってホストの活動ではない。IBM i には中断メッセージ・ATNPGM・
READ を伴わない WRITE ループなど**利用者が居なくてもホストが書いてくる経路**があり、
これを活動に数えると閉じ忘れたタブが永久に生き残る。

## 残る論点

- [x] **異常系の死活監視** → **実装した**（永続を既定にする代償として必要と判断）
  - `onSocketClose` が拾えない場合（半開きソケット）に備える。既定が永続になった以上、
    拾えなければセッションは**永久に**残る
  - **アプリ層のハートビート**にした（`{type:"ping"}` / `{type:"pong"}`。30 秒間隔・無応答 90 秒で死判定）。
    プロトコル層の ping（`ws.raw.ping()`）を使わないのは、`WsSender` が `send`/`close` だけの
    薄い境界でモックを差し込める形になっており、生ソケットを掴むと単体テストが書けなくなるため
  - 死活の更新は**任意の受信**で行う（pong 専用にしない。キー送信中に心拍を 3 回落としただけで
    生きている接続を切らないため）
- [x] **プリンターの常駐用途との関係** → **噛み合う。ここでは変えない**
  - 今回の「永続」は「**WS が繋がっている間は切らない**」の意味で、
    「ブラウザを閉じても生きる」ではない。`onSocketClose` の破棄は据え置いた
  - 常駐（`hostserver.md` の「サービス型セッションの常駐化」/ `pc-command.md`）は
    **WS 非依存の寿命管理**が要る別の話で、そちらを実装するときは
    「WS 切断＝破棄」そのものを見直すことになる。今回の結論はその前提を壊していない
  - 常駐セッションを作るときは、**壁時計タイマーが唯一の安全網になる**点に注意
    （MCP と同じ構図。`orphanSafeIdleTimeoutMs` の考え方を再利用できる）
- [x] **永続セッションの本数に上限が要るか** → **要らない。既にある**
  - `maxSessions`（既定 8）が本数の上限で、超えると `CONNECT_FAILED` を返す。
    永続にしたことで新しい漏れ口が増えたわけではない（切断で破棄・半開きは心拍で破棄）
  - 共有サーバーで時間を切りたい運用には `--idle-timeout` を用意した。
    資源の問題としてはこの 2 つで足りるので、**専用の上限は足さない**
    （設定が増えるほど「どれが効いているか」が分からなくなる）
