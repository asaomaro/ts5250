# 3270 で IBM i に繋いだときの差（実機で測った・2026-08-18）

同じ IBM i（実機）のサインオン画面を **5250 と 3270 の両方**で受けて突き合わせた。
差は 3 つあり、**3 つともこちら側の問題**だった。1 つは直した（属性桁の下線）。
残る 2 つをここに置く。

⚠ **どちらも IBM i 限定の話。** メインフレーム（z/OS / TK4-）では成り立たないので、
**無条件に適用してはならない**。見分けは交渉で付く——IBM i は `DO NEW-ENVIRON` を出して
5250 流のシード交換をするが、TK4- / z/OS は出さない（実測）。

## F1〜F12 を `PA1` ＋ `PFn` で送る（IBM i のとき）

- [x] **2026-08-18 完了** — `20260818-tn3270-ibmi-keys` / PR #332（`453c1b15`）。
  読み替えは**送信の一本道**に置いた: `packages/tn3270/src/session/session.ts:702` の
  `sendFunctionKey`（`PA1` で施錠されるので、解けるのを待ってから `PFn` を送る）。

**いま F キーが実質使えない。** 実機で `PF3` を送ると
「**機能キーは使用できません。**」と返る。5250 で同じ画面に F3 を送ると受理される。

送っているバイトは正しい——`f3 c7 c4 ff ef`（AID＋カーソル＋EOR）で、
受理される Enter（`7d c7 c4 ff ef`）と**AID しか違わない**。端末タイプを
3278/3279・±E で振っても変わらない。

原因は **IBM i の対応表がこちらの想定と違う**こと。IBM i 自身が
「ヘルプ－ 3270 キーボード・マッピング」という画面を持っており（3270 で繋いで `PF2`）、
そこにこう書いてある:

| 3270 キー | IBM i での機能 | | 3270 キー | 機能 |
|---|---|---|---|---|
| PF1 | 5250 ヘルプ・テキスト | | PF7 | 前ページ・キー |
| PF2 | 3270 ヘルプ・テキスト | | PF8 | 次ページ・キー |
| **PF3** | **画面の消去** | | PF9 | **アテンション** |
| PF4 | 画面の印刷 | | PF10 | 取り消し |
| PF5 | 表示属性 | | PF11 | **システム要求** |
| PF6 | テスト要求 | | PF12 | レコード後退 |
| PF13〜PF24 | **F13〜F24** | | | |

> **PA1 ＋ PF1..PF12 → F1..F12**
> **PA2 ＋ PF1..PF12 → F13..F24**

**直し方は実機で確かめてある**:

```
PA1+PF4（F4=プロンプト） → 「活動ジョブ処理 (WRKACTJOB)」   ← 効いた
PA1+PF12（F12=取り消し） → メインメニューへ戻る            ← 効いた
素の PF3                → 拒否
```

**ついでに直すもの**: いま `aidFor3270`（`web-ui/src/session-controller.ts`）は
**Attn / SysReq / Help / Print を「3270 端末にはありません」と断っている**が、
IBM i では使える（PF9 / PF11 / PF1 / PF4）。断り方が誤り。
PageUp / PageDown → F7 / F8 の読み替えは PF7 / PF8 と一致しており、**そのままでよい**。

読み替えは**送信の一本道**（`sendKey`）に置くこと——キーボード・状態バーのボタン・
マクロが同じ関数を通るので、片方だけ直すと「キーボードでは動くのにボタンでは動かない」になる。

## 装置名

- [x] **2026-08-18 完了**（**`DEVNAME` で通る。ホストの設定次第**）
  — `20260818-tn3270-devname` / PR #332（`453c1b15`）。
  `packages/tn3270/src/telnet/telnet.ts:349`（NEW-ENVIRON の `DEVNAME`。実測は pub400）、
  渡し方の分岐は `packages/server/src/tn3270-manager.ts:44`（IBM i は `DEVNAME` / それ以外は `@名前`）。

⚠ **一度、社内機 1 台だけで測って「IBM i は受け付けない」と誤結論した。**
pub400 で測り直したら通ったので差し戻した。**1 台の測定を一般化しない。**

| 渡し方 | pub400 | 実機 |
|---|---|---|
| 端末タイプに `@名前` | **時間切れ（15 秒）** | **時間切れ** |
| NEW-ENVIRON の `DEVNAME` | **効く**（Display name が要求どおり） | 画面を送らずに閉じる |

**やったこと**: IBM i には `DEVNAME` だけ送る（`@名前` は付けない）。
断られたら**閉じる理由に装置名を添える**（素の `socket closed` では辿り着けない）。
`@名前` は NEW-ENVIRON を使わないホスト（TK4- 等）には従来どおり。

**実機がなぜ断るかは未解明。** `QAUTOVRT` が怪しいが値を取れていない
（`QSYS2.SYSTEM_VALUE_INFO` の BigInt でこちらの直列化が落ちる）。

## IBM i に TN3270E を提示させられるか測る

- [x] **2026-08-18 完了（できない）** — `20260818-tn3270-devname` の調査中に実測
  （`requirement.md`「72」／`review.md`「2. TN3270E は 2 台とも断られる」）。**実装変更なし**。
  提示の前提は `packages/tn3270/src/telnet/constants.ts:37`——**サーバから `DO` で提示される**もので、
  こちらから `WILL` を出しても IBM i は断る。

こちらから `WILL TN3270E` を先に出しても、**pub400 / 実機の 2 台とも
`DONT TN3270E`** で断る。TLS の 992 番も閉じている（社内機）。

```
TX WILL TN3270E
RX DO NEWENV / DO TT / **DONT TN3270E**
```

装置名は `DEVNAME` で足りるので実害は無い。応答モードなど TN3270E の機能は使えない。



## 測り直すときの手順

```
node --env-file=.env <スクリプト>   # tn3270 の Tn3270Session と tn5250 の Session5250 を
                                    # 同じホストに繋いで、同じ画面・同じキーで並べる
```

⚠ **s3270 は物差しに使えない。** docker は開発コンテナの外で動くため、
社内ホストへ到達できない（`not-connected` になる）。TK4- 相手なら使える。
