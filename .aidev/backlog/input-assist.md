# 入力支援 UI（datepicker / timepicker ほか）

5250 の入力欄に、ブラウザらしい入力支援を出せないかという検討。
発端は **datepicker / timepicker を出したい**という要望（2026-07-28）。
実装の可否は「**何が材料として届いているか**」で決まるので、まずそこを整理してから積む。

## 前提: 材料として届くもの・届かないもの

**届かない**（→ 詳細は `field-input.md`。再調査しないこと）:

- **EDTCDE / EDTWRD / EDTMSK そのもの**。DDS のコンパイル時キーワードで、ワイヤには載らない。
  EDTMSK は SF が `[FFW][FCW*][attr][length]`（フィールドは連続 1 区間・FCW は固定 2 バイト）
  である以上、構造的に表現できない

**届く**:

- FFW 由来の欄の性質（`numeric` / `length` / `protected` / `hidden` / `dbcsType`）
- **EDTMSK の痕跡**＝分解された欄の並びと、その間の保護された区切り文字
- 画面の文字（ラベル・凡例）
- 拡張 5250 の GUI 構造体（`gui.selectionFields` / `gui.scrollBars`）
- ホストサーバー（SQL が実装済み）経由のシステム値

## 本題: datepicker / timepicker → **作らない（2026-07-30 に実機で前提が崩れた）**

判定材料は **EDTMSK の分解形から作る署名**（同一行の連続する数値欄＋間の 1 桁の区切り文字）で、
2026-07-28 に**合成データストリーム**で `2/2/2` / `2:2:2` / `3-2-4` / `6` という値を得ていた。

- [x] ~~**署名から「日付らしい欄 / 時刻らしい欄」を導く**~~
      **← 前提が実機で崩れた。作らない**（`20260730-input-assist-datetime`）
  - **`EDTMSK` は欄を分解しない。** 実機（IBM i 7.5）に 8 通りの DDS を作って実測した
    （`scripts/build-dttest.mjs` / `scripts/research-edtmsk.mjs`）:

    | DDS | 画面 | 実際に届いた形 |
    |---|---|---|
    | `EDTCDE(Y)` ＋ `EDTMSK('&& && &&')` | `0/00/00` | **1 欄**・長 8・`value=" 0/00/00"` |
    | `EDTCDE(Y)` ＋ `EDTMSK('  /  /  ')` | `0/00/00` | **1 欄**・長 8・同 |
    | `EDTCDE(Y)` ＋ `EDTMSK('&&/&&/&&')` | `0/00/00` | **1 欄**・長 8・同 |
    | `EDTCDE(Y)` のみ（対照） | `0/00/00` | **1 欄**・長 8・同 |
    | `EDTWRD('  :  :  ')` ＋ `EDTMSK` | （空） | **1 欄**・長 8・`value=""` |
    | `EDTWRD('  :  :  ')` のみ | （空） | **1 欄**・長 8・`value=""` |
    | `EDTWRD('   -  -    ')`（SSN） | （空） | **1 欄**・長 11 |
    | 素の `6 0`（対照） | （空） | **1 欄**・長 7・shift=signed-num |

  - **どの構成も 1 欄で来て、編集文字は欄の中の値に入る**（`" 0/00/00"`）。
    PR #212 で `EDTCDE`/`EDTWRD` について実測した結論と同じ形
  - `EDTMSK` のマスクは **3 通りとも `CRTDSPF` が通る**。つまり
    「書けるか」では分解の有無を判別できない（通っても効果がワイヤに出ない）
  - **代替も成立しない**（`20260730-input-assist-datetime/research.md` F4 の表）:
    - 「現在値に `/` があるか」は**値があるときだけ**効く。`EDTWRD` の 0 は全桁空白で来るので、
      **新規入力の空欄では材料ゼロ**。出たり出なかったりは無いより悪い
    - 長 8 の num-only を日付とみなす → 金額（`EDTCDE(1)`）と区別できない
    - ラベルの文字（「日付」「DATE」）で判定 → 位置も対応も保証されない＝推測を真実として扱う
    - FFW に日付を示すビットは無い
  - **再調査しないこと。** やるなら「欄ごとのオプトイン」（利用者が指定して覚えさせる）しかない
    ——数値スピナーで出したのと同じ結論（下記「見送り: 数値スピナー」）
- [x] ~~**桁順・区切りをシステム値で解釈する**~~ **← 引き方は確かめた。使う先が無い**
  - `QSYS2.SYSTEM_VALUE_INFO` は**実在した**（`scripts/research-sysval.mjs` で実測）。
    値は `CURRENT_CHARACTER_VALUE` に入る（`CURRENT_NUMERIC_VALUE` は null）:
    **`QDATFMT=YMD` / `QDATSEP=/` / `QTIMSEP=:`**。`QDECFMT` / `QDATE` / `QYEAR` も同じ表から引ける
  - **実装はしていない**（日付欄を見分けられないので消費側が無い）。
    将来使うときはこの事実から始められる

## 他にできそうなこと

- [x] ~~**オプション欄のドロップダウン**（**一番効きそう**）~~
  - **対応済み**（`.aidev/works/20260729-opt-field-dropdown`）。設定 `optHints`（既定 OFF）。
  - 実機 5 画面（WRKOBJPDM / WRKSPLF / WRKACTJOB / DSPLIBL / WRKUSRJOB）で Opt 欄の形を実測し、
    **同じ桁・同じ長さ（1〜2）の非保護欄が連続 3 行以上**を条件にした（5/5 で成立）
  - 凡例はその列より上の行から拾う（複数行にまたがる）。**両方揃ったときだけ発火**する
  - **矩形選択・コピー＆ペーストを妨げないこと**が利用者指示。ポップオーバーは
    `mousedown.stop.prevent` で伝播とフォーカス移動を止め、**キーイベントを 1 つも購読しない**
    （`fkeyLegend.ts` / `ScreenGrid.vue` の注記と `opt-hints-ui.test.ts` を参照）
  - `WRKxxx` / PDM 系の画面は、1〜2 桁の Opt 欄の上に
    `2=Edit 3=Copy 4=Delete 5=Display` という凡例が必ず出る。これを拾って
    Opt 欄に選択肢を出せば、番号を覚えずに操作できる
  - **既存の機能キー凡例の仕組みがそのまま使える。** `fkeyLegend.ts` は `F<n>=` を
    `LEGEND_RE` で拾っているので、`<数字>=` を拾う兄弟を足すだけで済む。
    実績のある仕組みなので確度が高い（`<数字>=` 単体は誤検出しやすいので、
    Opt 欄の存在・凡例行との位置関係で絞ること）
- [x] ~~**`inputmode` の指定**（安価。**現在どこにも設定されていない**）~~
  - **対応済み**（`.aidev/works/20260729-field-inputmode`）。
  - 訂正: **`f.numeric` 全体に付けてはいけない**。`field-validate.ts` の許容集合は
    **digits-only（0x0600）だけが `/^[0-9]*$/`** で、numeric-only / signed-numeric は
    `/^[0-9.,+-]*$/`＝ `.` `,` `+` `-` を通す。全体に付けるとそれらのキーが消えて
    **打てるはずの文字が打てなくなる**
  - `Field.digitsOnly` を core に足し、**その欄にだけ** `inputmode="numeric"` を付けた。
    絞っても打てる文字が 1 つも減らないので「塞がない」ことが保証できる
  - `f.numeric` の欄に `inputmode="numeric"` を付ければ、モバイル・タブレットで
    数字キーパッドが出る。**推測を一切含まず**ホストの申告だけで決まる
- [x] ~~**F4=Prompt の導線**~~ — **廃止した**（2026-08-01。利用者判断で不要）

### 既にあるので作らないこと

- **拡張 5250 の選択部品**（`gui.selectionFields`）＝ラジオ・チェック・メニュー・
  プッシュボタン・リスト/プルダウンは**ホストが宣言したとおりに描画済み**
- **機能キー凡例のボタン化**（`buttons` 設定）、**スクロールバー**（`gui.scrollBars`）も実装済み

### 見送り: 数値スピナー

数量欄には効くが、**金額・コード値では邪魔になる**。

分けられない理由がはっきりしている: **FFW からは「数量か金額かコード値か」を区別する情報が
出ない。** `SIGNED_NUMERIC` は符号の有無であって用途ではなく、桁数でも分離できない
（3 桁の数量も 3 桁のコード値もある）。ADJUST（右寄せゼロ埋め）も金額・数量の双方に付く。

やるなら**欄ごとのオプトイン**（利用者が「この欄はスピナー」と指定して覚えさせる）に
するしかない。自動判定は狙わないこと。

## 見せ方・有効無効は画面設定から選べるようにする

**ここに積んだ機能はすべて、他の項目と同様に画面設定から有効/無効とデザインを選べること。**
勝手に有効化しない。

- [x] ~~**`ViewSettings` に項目を足し、`VIEW_ITEMS` に定義を足す**~~
      **対応済み**（`optHints` で実施済み。`promptHint` も同じ形で足したが後に廃止）
  （`packages/web-ui/src/stores/viewSettings.ts`）
  - `VIEW_ITEMS` は「**画面設定メニューとキー設定で共有する単一の出どころ**」なので、
    ここへ足せば**メニューにもキー設定（順送り `view:*`）にも自動で出る**。
    2 か所に書かないこと
  - デザイン候補が多い項目は `expandable` で畳み、`group` / `groupLabel` で
    既存の「入力項目設定」（`controls`）と同じ群にまとめるのが素直
  - ON/OFF だけで足りる項目（`inputmode` など、見た目の候補が無いもの）は
    `linkify` と同じ 2 択でよい。**全部にデザイン候補を作らない**
- [x] ~~**既定は無効（`none` / OFF）にする**~~ **対応済み**
      （`optHints: "none"`。`inputmode` は推測を含まないので既定 ON にした）
  - datepicker / timepicker / オプション欄のドロップダウンは**推測を含む**機能なので、
    既定で出すと誤判定がそのまま利用者に見える。
    `windowFrame` / `windowBackdrop` の既定が `none` なのと同じ扱いにすること
  - 逆に `inputmode` は推測を含まない（ホストの申告だけ）ので、既定 ON でも筋は通る。
    判断は実装時に
