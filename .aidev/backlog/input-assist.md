# 入力支援 UI（datepicker / timepicker ほか）

5250 の入力欄に、ブラウザらしい入力支援を出せないかという検討。
発端は **datepicker / timepicker を出したい**という要望（2026-07-28）。
実装の可否は「**何が材料として届いているか**」で決まるので、まずそこを整理してから積む。

## 前提: 材料として届くもの・届かないもの

**届かない**（→ 詳細は `field-input.md`。再調査しないこと）:

- **EDTCDE / EDTWRD / EDTMSK そのもの**。DDS のコンパイル時キーワードで、ワイヤには載らない。
  EDTMSK は SF が `[FFW][FCW*][attr][length]`（フィールドは連続 1 区間・FCW は固定 2 バイト）
  である以上、構造的に表現できない

**届く**:

- FFW 由来の欄の性質（`numeric` / `length` / `protected` / `hidden` / `dbcsType`）
- **EDTMSK の痕跡**＝分解された欄の並びと、その間の保護された区切り文字
- 画面の文字（ラベル・凡例）
- 拡張 5250 の GUI 構造体（`gui.selectionFields` / `gui.scrollBars`）
- ホストサーバー（SQL が実装済み）経由のシステム値

## 本題: datepicker / timepicker

判定材料は **EDTMSK の分解形から作る署名**（同一行の連続する数値欄＋間の 1 桁の区切り文字）。
2026-07-28 に合成データストリームで実測した値:

| 画面上の欄 | 取れる署名 |
|---|---|
| 日付（EDTMSK あり） | `2/2/2` |
| 時刻（EDTMSK あり） | `2:2:2` |
| SSN（日付ではない） | `3-2-4` |
| **日付（EDTMSK なし・単一 6 桁）** | **`6`** |

- [ ] **署名から「日付らしい欄 / 時刻らしい欄」を導く**
  - `2/2/2` `2:2:2` は材料として十分に強い。`3-2-4` のような別物とも分かれる
  - **断定はしない。** このリポジトリの原則（ホストが送る情報を UI 側で上書きしない／
    同じ事実の導出元を 2 つ持たない）に照らし、推測を真実として扱わないこと
- [ ] **桁順・区切りをシステム値で解釈する**
  - `2/2/2` を見ても **YMD / MDY / DMY は決まらない**。EDTCDE の `Y` はシステム値
    **QDATFMT** に従うため、同じ画面でも設定次第で意味が変わる。区切りは QDATSEP・QTIMSEP
  - ホストサーバーの SQL で `QSYS2.SYSTEM_VALUE_INFO` から引けるはず（**ビュー名は実機で要確認**）。
    これは推測ではなくシステムの申告なので、署名判定と組み合わせる価値が高い

### 限界（実装前に織り込むこと）

- **EDTMSK が付いていない日付欄は判定できない。** 上表の `6` がそれで、ただの 6 桁数値と
  区別が付かない。EDTMSK は必須ではないので**取りこぼしが一定量出る**
- 逆に `2/2/2` が必ず日付とも限らない（強い材料ではある）
- 用途で線を引くこと。**入力補助（カレンダー・書式ヒント）なら誤判定の害は小さい**が、
  **バリデーションや自動変換に使うと取りこぼしと誤判定がそのまま実害**になる

## 他にできそうなこと

- [ ] **オプション欄のドロップダウン**（**一番効きそう**）
  - `WRKxxx` / PDM 系の画面は、1〜2 桁の Opt 欄の上に
    `2=Edit 3=Copy 4=Delete 5=Display` という凡例が必ず出る。これを拾って
    Opt 欄に選択肢を出せば、番号を覚えずに操作できる
  - **既存の機能キー凡例の仕組みがそのまま使える。** `fkeyLegend.ts` は `F<n>=` を
    `LEGEND_RE` で拾っているので、`<数字>=` を拾う兄弟を足すだけで済む。
    実績のある仕組みなので確度が高い（`<数字>=` 単体は誤検出しやすいので、
    Opt 欄の存在・凡例行との位置関係で絞ること）
- [ ] **`inputmode` の指定**（安価。**現在どこにも設定されていない**）
  - `f.numeric` の欄に `inputmode="numeric"` を付ければ、モバイル・タブレットで
    数字キーパッドが出る。**推測を一切含まず**ホストの申告だけで決まる
- [ ] **F4=Prompt の導線**
  - 凡例に `F4=Prompt` がある画面では、フォーカス中の欄にプロンプト操作の導線を出せる。
    これも既存の凡例解析の応用

### 既にあるので作らないこと

- **拡張 5250 の選択部品**（`gui.selectionFields`）＝ラジオ・チェック・メニュー・
  プッシュボタン・リスト/プルダウンは**ホストが宣言したとおりに描画済み**
- **機能キー凡例のボタン化**（`buttons` 設定）、**スクロールバー**（`gui.scrollBars`）も実装済み

### 見送り: 数値スピナー

数量欄には効くが、**金額・コード値では邪魔になる**。

分けられない理由がはっきりしている: **FFW からは「数量か金額かコード値か」を区別する情報が
出ない。** `SIGNED_NUMERIC` は符号の有無であって用途ではなく、桁数でも分離できない
（3 桁の数量も 3 桁のコード値もある）。ADJUST（右寄せゼロ埋め）も金額・数量の双方に付く。

やるなら**欄ごとのオプトイン**（利用者が「この欄はスピナー」と指定して覚えさせる）に
するしかない。自動判定は狙わないこと。

## 関連

- FFW の未使用ビット（`MANDATORY_ENTER` の必須表示・`MONOCASE` の欄単位大文字化・
  `ADJUST` の右寄せ）も**推測なしで見せ方を良くできる**材料だが、実装項目としては
  `field-input.md` 側に積んである。UI として出すときはそちらとセットで進めること
