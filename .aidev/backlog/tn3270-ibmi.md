# 3270 で IBM i に繋いだときの差（実機で測った・2026-08-18）

同じ IBM i（SR-OSAKA）のサインオン画面を **5250 と 3270 の両方**で受けて突き合わせた。
差は 3 つあり、**3 つともこちら側の問題**だった。1 つは直した（属性桁の下線）。
残る 2 つをここに置く。

⚠ **どちらも IBM i 限定の話。** メインフレーム（z/OS / TK4-）では成り立たないので、
**無条件に適用してはならない**。見分けは交渉で付く——IBM i は `DO NEW-ENVIRON` を出して
5250 流のシード交換をするが、TK4- / z/OS は出さない（実測）。

## - [x] F1〜F12 を `PA1` ＋ `PFn` で送る（IBM i のとき）— 2026-08-18 完了

**いま F キーが実質使えない。** 実機で `PF3` を送ると
「**機能キーは使用できません。**」と返る。5250 で同じ画面に F3 を送ると受理される。

送っているバイトは正しい——`f3 c7 c4 ff ef`（AID＋カーソル＋EOR）で、
受理される Enter（`7d c7 c4 ff ef`）と**AID しか違わない**。端末タイプを
3278/3279・±E で振っても変わらない。

原因は **IBM i の対応表がこちらの想定と違う**こと。IBM i 自身が
「ヘルプ－ 3270 キーボード・マッピング」という画面を持っており（3270 で繋いで `PF2`）、
そこにこう書いてある:

| 3270 キー | IBM i での機能 | | 3270 キー | 機能 |
|---|---|---|---|---|
| PF1 | 5250 ヘルプ・テキスト | | PF7 | 前ページ・キー |
| PF2 | 3270 ヘルプ・テキスト | | PF8 | 次ページ・キー |
| **PF3** | **画面の消去** | | PF9 | **アテンション** |
| PF4 | 画面の印刷 | | PF10 | 取り消し |
| PF5 | 表示属性 | | PF11 | **システム要求** |
| PF6 | テスト要求 | | PF12 | レコード後退 |
| PF13〜PF24 | **F13〜F24** | | | |

> **PA1 ＋ PF1..PF12 → F1..F12**
> **PA2 ＋ PF1..PF12 → F13..F24**

**直し方は実機で確かめてある**:

```
PA1+PF4（F4=プロンプト） → 「活動ジョブ処理 (WRKACTJOB)」   ← 効いた
PA1+PF12（F12=取り消し） → メインメニューへ戻る            ← 効いた
素の PF3                → 拒否
```

**ついでに直すもの**: いま `aidFor3270`（`web-ui/src/session-controller.ts`）は
**Attn / SysReq / Help / Print を「3270 端末にはありません」と断っている**が、
IBM i では使える（PF9 / PF11 / PF1 / PF4）。断り方が誤り。
PageUp / PageDown → F7 / F8 の読み替えは PF7 / PF8 と一致しており、**そのままでよい**。

読み替えは**送信の一本道**（`sendKey`）に置くこと——キーボード・状態バーのボタン・
マクロが同じ関数を通るので、片方だけ直すと「キーボードでは動くのにボタンでは動かない」になる。

## - [x] 装置名 — 2026-08-18 完了（**IBM i には通せないと分かった**）

当初は「届けられるはず」として積んだが、**測ったらどの道も通らなかった**:

| 渡し方 | 結果 |
|---|---|
| 端末タイプに `@名前` | **交渉が 15 秒で時間切れ** |
| NEW-ENVIRON の `DEVNAME` | 交渉は通るが**直後にソケットを閉じる**（画面 0 文字） |
| TN3270E の `CONNECT`（3270 本来の道） | **IBM i が TN3270E を提示しない**ので使えない |

名前を 4 通り試して全て同じ。`DEVNAME` の 1 行を止めるだけで通った。
ホスト側も見たが **3270 の装置記述は 0 件**で、表示装置は全て `DSPVRT`（自動採番）。

`DEVNAME` は RFC 4777 の**5250 向け**の仕組み。3270 の装置名は TN3270E の
`CONNECT`（RFC 2355）で渡すのが筋で、IBM i がそれを提示しない以上、道が無い。

**やったこと**: どちらの経路にも載せない（＝指定しても壊れない）。
指定されていて使えないときは**警告を出す**（黙って無視しない）。
`@名前` は NEW-ENVIRON を使わないホスト（TK4- 等）には従来どおり付ける。

## - [ ] IBM i に TN3270E を提示させられるか測る

上の根っこ。**こちらから `WILL TN3270E` を先に出すとどうなるか**を測っていない
（いまの実装はホストの `DO` を待つだけ）。提示させられれば `CONNECT` で装置名が通り、
応答モードなど TN3270E の機能も使えるようになる。

⚠ 「IBM i は装置名を受け付けない」は **SR-OSAKA（V7R5M0）1 台でしか測っていない**。
`QAUTOVRT` の値は取れていない（SQL の BigInt 直列化で落ちた）ので、
自動作成の上限が効いている可能性も排除できていない。

## 測り直すときの手順

```
node --env-file=.env <スクリプト>   # tn3270 の Tn3270Session と tn5250 の Session5250 を
                                    # 同じホストに繋いで、同じ画面・同じキーで並べる
```

⚠ **s3270 は物差しに使えない。** docker は開発コンテナの外で動くため、
社内ホストへ到達できない（`not-connected` になる）。TK4- 相手なら使える。
