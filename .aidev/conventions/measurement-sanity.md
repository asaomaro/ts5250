# measurement-sanity

<!-- 条項の本文。PJ ドキュメントへ移送(promote)するまではここが唯一の在処。 -->

## 規約

**実測値を記録に残す前に、計測器そのものを疑う。** 数字を research・台帳・PR に書く前に、次の 3 つを確かめる。

1. **もう一度取る。** 同じ条件で 2 回目を取り、桁が変わらないことを見る。変わるなら、変わった理由が分かるまで記録しない。
2. **計測の道具が結果を作っていないか。** 中継・ラッパー・エミュレーターを挟んで測るときは、**その道具が本物には無い経路を作っていないか**を見る。
   道具が「検出した」と言っているのか、対象が検出したのかを区別する。
3. **測っている間の負荷を見る。** 並行してテストやビルドを回していたら、その値は使わない（load average と、他に走っているものを確かめる）。

**時計の取り方も疑う。** 別プロセス越し（CDP・SSH・リモートのログ）の時刻は、届くまでに遅れが乗る。
遅れが結果と同じ桁なら、**測る対象の側の時計**（ページ内の `performance.now()`、ホストのトレースの到着時刻）で取り直す。

**記録には、どの条件で取った値かを書く。** 「直す前の中継での値」「負荷の高いときの値」を、条件を書かずに並べない。
次に測る人は、その数字を基準線として使う。

## 背景

`20260919-backlog-acs-triage` で 2 回続けて、最初の実測値が使えなかった。

- **負荷**（同 work の `decisions.md` D4）: 打鍵から描画までを p50 465ms と測ったが、並行して委譲先が vitest を回していた（load average 最大 25）。
  落ち着いてから測り直すと 72〜137ms で、3〜6 倍の開きがあった。そのままなら「全体的に遅い」と誤って結論していた。
- **計測器**（同 work の `decisions.md` D10）: 半開きの検証で、ブラウザとサーバーの間に挟んだ中継が、サーバー側の閉鎖をブラウザへ伝えていた。
  そのため「120.1 秒で検出した」と出たが、本物の半開き（回線が死んでいる）ではその閉鎖は届かない。
  中継を直すと 130 秒たっても検出せず、**欠陥（見張りが最初の ping まで張られない）は中継に隠されていた**。
- **時計**（同 work の research F0-4）: Playwright の `framesent` / `framereceived` は CDP 経由で約 200ms 遅れて届く。
  測ろうとしていた値（数十 ms）と同じ桁なので、ページ内の時計で取り直した。
