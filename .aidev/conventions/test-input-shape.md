# test-input-shape

## 規約

**外から来る入力を弾くコードにテストを足すときは、「値」ではなく「形」を振る。**

同じ項に対して、少なくとも次の形を 1 つずつ通す:

1. **想定の型で中身が不正**（`{field: "LEAK"}` のような、よくある形）
2. **その項が `null` / `undefined`**
3. **その項が配列**（`[]`）
4. **要素そのものがプリミティブ**——配列や object の**要素**を受け取る API では、
   `{field: x}` に包まずに `"文字列"` / `42` をそのまま入れる
5. **容れ物そのものが違う型**——`fields` のような配列を受け取る項に、
   文字列・`{length: 1, 0: …}`（配列風オブジェクト）・数値を入れる

**とくに 4 と 5 を落としやすい。** テストを書く人は「正しい形の中の、間違った値」を思い浮かべるので、
`{ 正しいキー: 不正な値 }` ばかり並べてしまう。しかし実装が壊れるのは
`"key" in f` や `f.map(...)` のように**形を前提にした 1 行**なので、
中身だけ振っていても**その行に一度も到達しない**。

**「実装を戻すと落ちる」（`verify-by-mutation`）と対で使う。** あちらは
**実装を変えて**テストが捕まえるかを見る。こちらは**入力を変えて**捕まえるかを見る。
**前者を全部通しても後者は抜ける**——実際にそうなった（下記）。

## 背景

`20260920-field-error-no-value`（PR #408）で、**同じ欠陥を 2 ラウンド続けて見逃した**。

ws の `fields[].field` にクライアントの任意文字列が入ると、素の `TypeError` の文言
（`Cannot use 'in' operator to search for 'value' in <その文字列>`）がブラウザへ返る欠陥。
回帰テストはこう書いてあった:

```ts
for (const field of [marker, { index: marker }, { row: marker, col: 1 }, null, []])
  applyFields(session, [{ field, value: "x" }]);   // ← いつも {field, value} に包んでいる
```

`field` の**中身**は 5 通り振っているのに、**要素そのもの**（`applyFields(session, [marker])`）も
**容れ物**（`fields: "LEAK"`）も一度も試していない。実装が壊れるのは
`if (!("value" in f))` と `fields.map(...)` なので、この 5 通りではその行に届かない。

- review ラウンド 3 が 4 の形で 1 件（3270 側で検証より前に `in` が走っていた）
- review ラウンド 4 が 5 の形で 1 件（`fields` の容れ物が素通し。しかも
  5250 と 3270 が**同じ入力に別の答え**を返していた）

を見つけている。**その時点までの変異注入はすべて通っていた**（最終的に 14 件。
`test-result.md` の表）——実装を戻せば落ちるテストは揃っていたのに、
入力の形が狭いせいで**別の壊れ方**を一度も見ていなかった。
