## 改善提案

### 製品 / コード（→ issue 候補）

この軸は各 work の retro と deliver で既に backlog へ落ちている（直近 3 works で 9 件）。
**横断で新しく足すものは無い**——重複を避ける。

### PJ プロセス / 規約（→ `.aidev/conventions/`。AGENTS.md 本体には書かない）

1. **既存 2 条項に `scope` を宣言する**（判定の前提。上の「判定案」参照）。
   宣言せずに母集団を数え続けると、**対象外の work で薄まった分母**のまま `ready` になり続ける。
2. **`paired-artifact-sync` は条項を足さず、層を下げる。**
   3 works で再発し、索引にも載っている（＝届いている）以上、散文の追記は効かない。
   `20260920-field-error-no-value` の retro が提案した
   「共有型から対になる呼び出し元を引く走査テスト」を PJ 側の資産として作る
   （backlog 起票済み）。
3. **`comment-provenance` の scope に「同一 work 内での陳腐化」を含める。**
   再発パターン 3 のとおり、実際に効いているのは work をまたぐ腐敗ではなく
   **work の中で自分が書いた注記が偽になる**場面。scope をそう書けば、
   母集団の取り方も判定の意味も変わる。

### ハーネス自体（→ `aidev-*` への提案・適用は人間）

1. **【最優先】ハーネスを git 管理下に置く。**
   いま `harnessRev` が全 work で `unknown` のため、**ハーネス改修の効果は原理的に測れない**。
   `aidev harness new` で登録しても、母集団を版で層別できないので `ready` にならない。
   縦断分析の片翼が丸ごと機能していない状態。
2. **cross 点検のログを、review ラウンドの指摘と別の書式にする。**
   いまは同じ `- [must][conv:…]` で同じファイルに並ぶため、
   **条項の `violations` が母集団の違うものを合算している**（上の (3) で実測。差 8 件）。
   `protocol.md`「8.」が「数を混ぜるな」と定めている以上、**書式で分けて機械が分離できる**ようにする
   （例: `- (check)[must][conv:…]`）。現状は人間が `approve` に手で正しい数を渡すことでしか分離できていない。
3. **差し戻しの「拒否」を記録に残す。**
   `aidev event <phase> sent_back` がガードで exit 2 になったとき **metrics には何も残らない**ので、
   後から見ると単に「差し戻しが少ない work」になる（今回 1 件実際に発生）。
   `event: sent_back_refused` を刻めば、**記録の欠落が「跡」として見える**。
4. **`unplanned_lookups` の数え忘れを検知する。**
   全 works の 8 割が 0 で、0 でない 3 件はいずれも「意識して数えた」work。
   指標として死んでいるので、**数えさせる仕掛け**（coding 終了時に「アンカーを外れた回数は？」を
   明示的に問う等）か、**指標を捨てる**かのどちらかに倒す。中途半端な現状がいちばん悪い。
5. **`sharedFiles` の未宣言を doctor の WARN 止まりにしない。**
   `declared=0` のまま「常連 2 件」を指摘し続けているが、
   **その結果 `aidev-40-coding` 手順 5 のタスク点検が一度も発火していない**（直近 3 works の
   `task_checks` がすべて 0）。doctor が常連を検出できているなら、**初期値を提案して書き込む**
   （`aidev doctor --fix` 相当）ところまでやるほうが、発火条件が死んだままより良い。
