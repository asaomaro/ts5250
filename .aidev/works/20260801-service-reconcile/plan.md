# 計画: 定義の変更をサービスに反映する

## 実装方針

**反映するロジックを先に単独で書く**（`service-reconcile.ts`）。配線から書くと、
CRUD の経路に実体の知識が滲む。

## 作業順序と依存関係

1. `service-reconcile.ts`（何をどう扱うかの表を関数に落とす）
2. 材料を差し替える口（`updatePrinterOptions` / `WatchRegistry.update` / `remove`）
3. `WatchEvent.list`（行の増減は `state` で伝わらない）
4. `config-routes` のコールバック → `app.ts` で配線
5. `stale` を行と画面へ
6. 単体テスト → 実機 E2E

## リスク / 留意点

- **`WatchRegistry` の生成順**。`app.ts` では CRUD 登録より後に作られていたので、先へ動かす。
- **`subscribe` の絞り込み**が `ev.watch` を前提にしている。`list` には無いので分岐が要る。
- **削除で解決しに行かない**——必ず失敗する経路を通してはいけない。
- 動いているものを落とさない、が全体の軸。テストで「止めていない」ことを**呼び出し列**で確かめる。

## テスト方針

- **単体**: 足す / 直す / 消す × プリンター / 待ち行列 × 動いている / いない。
  偽のマネージャで**呼び出し列**を突き合わせる（「止めていない」を直接見る）。
- **実機 E2E**: 保存で立ち上がる／保存で切れない／「要再起動」が出て開始で消える／
  サービス ☐ と削除で止まる。
