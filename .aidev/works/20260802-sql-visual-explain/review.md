### この差し戻しの意味

ラウンド 1 で「確かめていないこと」として残した 3 点（実ブラウザ・MCP・記録種別）を、
利用者の指示で全部埋めた。**結果として欠陥が 4 件出た。**

| # | 欠陥 | 深刻度 | どこで出たか |
|---|---|---|---|
| A | 画面から計画を採ると**必ず 400**（`source` の形） | **致命的**——機能がまったく使えない | 実ブラウザ |
| B | 画面からの索引作成も同じ形で壊れていた | **致命的** | 実ブラウザ |
| C | `host_sql_explain` を MCP から呼ぶと**必ず失敗**（出力スキーマの宣言漏れ） | **致命的** | MCP を実行 |
| D | **既存の全 MCP ツール**がエラー時にクライアントを壊す | 重大（既存・本作業の範囲外） | 同上 |

**「REST が通っているから画面も動く」は成り立たなかった。** A/B は web-ui とサーバーの境界で、
単体テストは偽 `fetch` を使っていたため**要求の形が一度も検証されていなかった**。
C/D は MCP SDK の検証が `listTools()` を呼んだクライアントでだけ効くため、
一覧を取らないテストでは素通りしていた。

→ **回帰テストを足した**（要求ボディの形／エラー応答の形）。同じ抜け方を繰り返さないため。

### D の扱い（範囲外だが直した）

`errorResult` は 17 本すべての MCP ツールが使う共通処理で、修正の影響は全ツールに及ぶ。
本作業の範囲外だが:

- **自分の新しいツール 2 本が同じ欠陥を踏む**ため、直さないと機能が完成しない
- 現状は**すべてのツールが壊れている**ので、構造化エラーを落としても失う機能は無い
  （クライアントは受け取る前に例外を投げている）

よって直し、既存テスト 20 件を更新した。PR では別コミットに分けてある。

### 記録種別の命名について

**名前を与える基準を「IBM の文書化された名称と、こちらの実測の一致」に置いた。**
どちらか一方だけでは付けない:

- 文書だけ → 実物と食い違っていても気づけない
- 実測だけ → 出現条件からの推測になる（`3026` が UNION でだけ出た、は「集合演算」の証明ではない）

一致した 18 種に名前を与え、**`5002` / `5005` / `3018` は名前を与えないまま残した**。
「分からないものは分からないと出す」方針は変えていない。
