## 統合テストで見つけて直した欠陥（2 件）

### 1. `GET /api/host/plans` が必ず 400 になっていた

`source` をクエリ文字列から**オブジェクトとして**パースしようとしていた。
クエリ文字列は文字列しか運べないので、`sourceSchema`（オブジェクト）を当てると必ず失敗する。
**単体テストでは偽 `fetch` を使っていたため気づけなかった**——REST を実際に通して初めて出た。

→ `system` / `session` の 2 つのクエリパラメータで受け、内部で `source` の形に戻す。
web-ui 側（`planApi.ts`）も揃えた。

### 2. **ODP 再利用で 3 回目以降の計画が空になっていた**（実運用に響く）

統合検証の「explain → SQL → explain」が `404/200/404` になった。実機で切り分けた:

```
1 回目: OK nodes=12
2 回目: OK nodes=12
3 回目以降: OK nodes=0     ← 記録が出ない
別の文にすると: OK nodes=13  ← また出る
```

**同じ接続で同じ文を 2 回完全オープンすると、以降 IBM i がオープン済みデータパス（ODP）を
再利用して完全オープンを避けるため、最適化記録が出なくなる。**

さらに悪いことに、**`QQ1000` を持つ記録は引けてしまう**ので、
`records.length === 0` だけを見ていた実装は **0 ノードの空の計画を「成功」として返していた**
（spec「空の計画を成功として返さない」に反する）。

**直した内容:**

- `plan-capture.ts`: **ノード数 0 も失敗として弾く**。理由に「オープン済みデータパスを再利用」と書く。
- `host-plan.ts`: **使い回した接続で計画が採れなかったら、新しい接続で 1 度だけやり直す**
  （新しいジョブには ODP のキャッシュが無いので必ず採れる）。
  既存 SQL 経路の「切れていたら 1 度だけ張り直す」と同じ作法。`reused` のときだけ試す。
- 回帰テストを 2 件追加。

修正後、両実機とも「explain → SQL → explain」が **200/200/200** になった。

## 2. MCP の実行（`scripts/verify-visual-explain-mcp.mjs`）

**実機 15/15・PUB400 16/16。** 叩いて初めて分かった欠陥が 2 件。

### 欠陥 A: `host_sql_explain` の `outputSchema` 宣言漏れ（自分の作り込み）

`captured` / `at` / `job` / `warnings` を宣言しておらず、**MCP クライアントから呼ぶと必ず
`Structured content does not match the tool's output schema` で落ちていた。**

### 欠陥 B: **`outputSchema` を持つ全 MCP ツールがエラー時に壊れる**（既存・リポジトリ全体）

`errorResult` が返す `structuredContent: { error: … }` はどのツールのスキーマにも合わない。
SDK は **`isError` に関わらず** `structuredContent` があれば検証する
（`client/index.js` はコメントに「エラー時は検証しない」と書きつつ `if (result.structuredContent)` だけを見ている）。

**`listTools()` を呼んだクライアントでだけ起きる**（検証子はツール一覧から作られる）ため、
一覧を取らないテストでは素通りしていた。実クライアントは必ず一覧を取る。
`host_sql` に誤った SQL を渡して**既存ツールでも再現することを確認**した。

→ `errorResult` から `structuredContent` を落とし、追加情報（SQLCODE 等）はテキストに併記した。
既存テスト 20 件をテキスト検証に更新。
