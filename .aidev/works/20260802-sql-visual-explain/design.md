前提: `spec.md`、`research.md`（F1〜F17）。

## design で確定させた事実（実機 7.3・QTEMP 上の検証表で実測）

結合・集約・副問合せ・UNION を監視下で流し、階層を表しうる列を全て見た。

> ⚠ **2026-08-08 訂正**: この節の「階層を表しうる列を全て見た」は事実ではなかった。
> 見たのは `QQQDTN` / `QQQDTL` の 2 列で、**ダンプ表は 282 列ある**。
> **結合の順位は `QQJNP`（Join position）が持っている。** 下の「確定した 3 点」4. と
> A1 の訂正を参照。利用者から「ACS では 2 つの表が別の枝から 1 つにまとまる」と
> 指摘を受けて全列をダンプし直して分かった。

| 流した形 | `QQQDTN` | `QQQDTL` | 出た記録種別（3000 番台） |
|---|---|---|---|
| 単純走査 | `1` | `1`（3019 のみ `0`） | 3000, 3006, 3014, 3019, 3020, 3028 |
| 結合 | `1` | 同上 | 3000×2（**表ごと**）, 3006, 3014, 3019, 3020×2, 3023, 3028 |
| 集約＋整列 | `1` | 同上 | 3000, **3003**, 3006, 3014, 3019, 3020×2, 3023, 3028 |
| 副問合せ | `1` | 同上 | 3000×2, 3006, 3014, 3019, 3020×3, 3023×2, 3028×2 |
| **UNION** | **`1` と `2`** | 同上 | 3000×2（各ブロック）, **3026**（`dtn=2`）, 3023×3, 3028×3 |

**確定した 3 点:**

1. **`QQQDTN` は「クエリブロック」の番号**。UNION で `1`/`2` に割れ、集合演算の記録（`3026`）が
   後続ブロックに付いた。~~**演算子の親子ではない。**~~
   → **`QQQDTN` がブロック番号だという事実は正しい。** ただし「だから親子は無い」は誤り（4. を見よ）。
   副問合せ（`K IN (SELECT …)`）は `dtn=1` のまま＝**オプティマイザが平坦化**しており、
   ブロックは増えなかった。
2. **`QQQDTL` は階層に使えない**。ほぼ全て `1` で、`3019` だけ `0`。
   → `3019` は**文レベルの要約であってノードではない**、という区別にだけ使う。
3. **`3000` は「表ごと」に出る**（結合で 2 件、対象表が `QVQTBL` に入る）。
   → 走査対象の一覧は `3000` から作れる。
4. **【2026-08-08 追記】`QQJNP` が結合の順位（ダイヤル）を持つ。** 実機 7.3 で実測:

   | 流した形 | `QQJNP` | `QQC21`（結合方式） | `QVFILES` |
   |---|---|---|---|
   | 2 表の内部結合 | `3000`=1, `3001`=2 | `NL` | 2 |
   | 3 表の内部結合 | `3000`=1, `3001`=2, `3001`=3 | `NL` | 3 |
   | 左外部結合 | `3000`=1, `3001`=2 | `NL` | 2 |
   | UNION ALL | 各ブロックで 1 | （空） | 1 |
   | 副問合せ（結合へ書き換え） | `3000`=1, `3023`=1, `3028`=1, `3001`=2 | `NL` | 2 |

   `3007`（オプティマイザの打ち切り）は `QQJNP=0`＝**参加していない**。
   ⚠ **`QQC22`（結合種別）は当てにならない**。`LEFT OUTER JOIN` を流しても `IN` のままだった。
   内部/外部は名乗らせない。
5. **【2026-08-08 追記】ACS が出している残り 2 つも記録から導ける。**
   利用者から「ACS だと同じ SQL でオブジェクトがもっと多い」と実画面を見せてもらい、
   差分（テーブル・プローブ／最終選択／索引名）の出どころを追い込んだ。

   | ACS の表示 | 出どころ | 確かめ方 |
   |---|---|---|
   | **テーブル・プローブ** | `QVC14`（索引のみアクセス）が `N` | 同じ結合を `SELECT *` と「索引のキー列だけ」で流して**全 279 列の差分**を採ったところ、意味のある違いは `QVC14`（`N` → `Y`）**1 列だけ**だった |
   | **最終選択（8）** | `3019` の `QQI7`＝返した行数 | 実測 8。ACS の「最終選択」の数字と一致 |
   | **索引名 `Q_TESTLIB_M_MENU_MENUCD_00001`** | `3001` の `QQ1000`（＋ライブラリは `QQILNM`） | `QVINAM` は索引が載る**ファイル名**（`M_MENU`）で、ACS が出しているアクセスパス名ではない |

   位置は**ネステッドループの内側の行が確定した直後**（結合の出力側）。2 表の実機比較で
   ACS と同じ位置・同じ表になった。3 表以上は同じ規則の外挿（ACS 未照合）。
   ⚠ **プローブに行数は載せない**。ダイヤルの `QQREST` は「1 回の突き合わせで当たる行数」で、
   ACS が出している通過行数（8）とは意味が違う（実測 1）。数えられるのは `3019` だけ。
6. **【2026-08-08 追記】詳細情報は「読む列を選ばない」形にした。**
   利用者から ACS の詳細ダイアログ 5 枚（PDF）を貰い、項目の出どころを追った。

   - **ACS は 1 ノードに 40〜60 項目**出す。手で選んだ 21 列では原理的に足りない。
     → **`QSYS/QAQQDBMN` の列一覧をホストから引いて、読める列（279/282）を全部読む**。
     列名を焼き込まないのは版数差があるため（無い列を `SELECT` に並べると採取ごと落ちる）。
     引けなければ従来の固定列に落とす。
     ⚠ `CCSID <> 65535` だけで絞ると**数値列が落ちる**（数値列の CCSID は NULL）。実際に踏んだ。
   - **列の意味はホストからは取れない。** `QSYS2.QQQ3000` 系のビューは**存在しない**（実測 0 件）。
     `QAQQDBMN` の `COLUMN_TEXT` は名前付きの列にしか入っておらず、
     ACS が名前を付けている `QQI*` / `QQC*` / `QVC*` は**空**だった。
   - **ACS の値との突き合わせで一意に決まった列だけ**に名前を付けた:
     `3000.QQI3`＝テーブル・サイズ / `3001.QQIA`＝索引論理ページ・サイズ /
     `3001.QVP156`＝テーブル・サイズ / `3014.QQC83`＝QRO ハッシュ /
     `3014.QQI5`＝最適化時間 / `3019.QQI7`＝返した行数。
     ⚠ **同じ `QQI5` が `3001` では 213（索引の項目数）、`3014` では 9（最適化時間）**。
     記録種別で分けないと必ず嘘になる。
   - **一致しなかった値**（`使用されたメモリー 4,096` / `平均入出力読み取り時間 2.891` /
     `処理された行数の合計 1,704` 等）は、(a) ACS 側の計算（1,704 = 213 × 8）か、
     (b) ACS の実行が別条件（`最適化ゴール *FIRSTIO` / `N行の最適化 30`）だったため。
     **推測で名付けない**——残りは列名のまま出す。
   - **ACS の「最終選択」の中身は `3014`（クエリ情報）**。QAQQINI・環境・クライアント情報まで、
     あの長い一覧の大半がここにある。`3019` は行数など数項目だけ。
   - 全列を持つと計画 1 件が **110KB** になる。localStorage（履歴 20 × 保存 20）は
     容量に届くので、**保存時は「列名のままの属性」を落とす**（`planStore.slim`）。
7. **【2026-08-08 追記】列の論理名はホストの catalog から取れる（ただし 71 列だけ）。**
   「列の ID では何を表しているか分からない」という指摘への対応。

   - `QSYS2.SYSCOLUMNS` の `COLUMN_TEXT` / `COLUMN_HEADING` に IBM の論理名が入っている。
     **282 列中 71 列**（`QQTFN`＝照会されたテーブルの名前、`QQQDTN`＝副選択番号 …）。
     残り（`QQI9` / `QQF1` / `QVC13` …）は**説明そのものが空**で、どこにも論理名が無い。
     ＝ACS のラベルは ACS の中にしかない。**推測で名付けない**方針は変えない。
   - ⚠ **日本語システムでは、その説明が壊れて届く。** DBCS 混在の文字列が
     SBCS（カタカナ）表で 1 バイトずつ変換されていて、SO/SI が文字として残る:
     `QQTFN` → `"｣ﾃ｣ｰ｣J…"`。**1 文字 = 元の 1 バイト**なので、カタカナ表を逆に引いて
     CCSID 5026 の混在として読み直せば「照会されたテーブルの名前」に戻る
     （`plan-column-text.ts`）。
   - ⚠ **完全には戻らない。** カタカナ表に無いバイト（29 個）はホスト側で潰れていて
     元の値が残っていない。**戻せない行は論理名として採用しない**——半端に欠けた
     日本語より列名の方が誤解が無い。`COLUMN_TEXT` が駄目なら `COLUMN_HEADING` を見る
     （`QQTIME` は説明が駄目で、見出しから「作成 時刻」が取れた）。
   - **`DSPFFD` の出力ファイルから読む道は駄目だった**（実測）。こちらの復号が
     さらに崩れる（「照会されたテーブルの名前」→「算材高気佐こ…」）。catalog 経由が良い。
   - 画面は**確かめた項目を先に出し、モニターの全列は畳んで後ろ**に置く。
     100 項目を超えると読みたい数行が埋もれるため。論理名の脇に列の ID を小さく添える
     （ACS や IBM の資料と突き合わせるのに要る）。

~~**結論: 真の演算子木は組めない。**~~
**結論（2026-08-08 訂正）: 結合の木は組める。** `QQJNP` がダイヤルの順位そのもので、
IBM i の結合は**左深**（`((ダイヤル1 ⋈ ダイヤル2) ⋈ ダイヤル3)`）。推定は入らない。
「文 → クエリブロック（`QQQDTN`）→ ダイヤル（`QQJNP`）→ ノード」の 4 層になる。
結合していない計画は従来どおり 3 層のまま並べる——**無い階層をでっち上げない**方針は変えない。

**なぜ間違えたか（手法の反省。ここは残す価値がある）**: 「階層を表しうる列」を
`QQQDTN` / `QQQDTL` という**名前から当たりを付けた 2 列**に絞ってしまい、
282 列を実際には見ていなかった。列名から意味を推し量るのは、原典を読まずに
書き始めるのと同じ誤り（AGENTS.md「原典を直読してから設計する」）。

## インターフェース / データモデル

### 3 層モデル（design で確定）

```ts
export interface QueryPlan {
  statement: string;
  captured: "run" | "no-rows" | "plan-cache";
  at: string;
  job?: string;
  /** クエリブロック（QQQDTN 単位）。UNION 等で複数になる */
  blocks: PlanBlock[];
  /** 索引助言（3020 由来。ブロックをまたいで集約） */
  advice: IndexAdvice[];
  summary: PlanSummary;
  /** 畳めなかった記録種別（版数差の可視化。7.5 の 3015 等） */
  unknownRecordTypes: number[];
}

export interface PlanBlock {
  /** QQQDTN の値 */
  number: number;
  nodes: PlanNode[];
}

export interface PlanNode {
  id: string;                 // `${block}-${index}`
  kind: PlanNodeKind;
  /** 元の記録種別（QQRID）。未知でも必ず持つ */
  recordType: number;
  label: string;
  table?: { schema: string; name: string };
  index?: { schema?: string; name: string };
  totalRows?: number;         // QQTOTR
  estimatedRows?: number;     // QQREST
  estimatedMs?: number;       // QQEPT
  /** QQRCOD。オプティマイザの理由コード（T1/T3/I1/I2/F7/A0 を実測） */
  reasonCode?: string;
  /** 属性パネル用。**値が入っていた列だけ**を並べる */
  attributes: PlanAttribute[];
}

/** **実測で中身を確かめた種別だけ名前を持つ。** それ以外は "other" */
export type PlanNodeKind = "table-access" | "access-method" | "advice" | "other";
```

### 記録種別の写像（`planNodeKind`）

**名前を与えてよいのは、この作業で中身を実測した種別だけ**とする。
推測でラベルを付けない（AGENTS.md「仕様・決定・標準を参照する」＝出所の無い断定を書かない）。

| QQRID | 実測した中身 | `kind` | 表示 |
|---|---|---|---|
| `3000` | 対象表（`QVQTBL`）・総行数・推定行数・理由コード。**表ごとに 1 件** | `table-access` | 「表アクセス: `<表>`」 |
| `3001` | 対象表＋**使った索引**（`QVINAM`。実測 `QADBILLB`）・総行数・推定行数 | `access-method` | 索引あり=「索引使用: `<索引>`」／なし=「表全体の走査」 |
| `3020` | 対象表・`QQIDXA='Y'`・`QQIDXD`＝助言キー列 | `advice` | 「索引の助言」 |
| 上記以外 | 未実測 | `other` | 「記録 `<QQRID>`」＋理由コード＋埋まっていた列 |

- `3019`（`QQQDTL=0`）は**ノードにしない**（文レベルの要約）。`summary.rowsReturned` 等に使う。
- **`other` でも情報は落とさない**——`attributes` に値の入っていた列を全部載せる。
- **観測した種別の記録**: 3003（集約時）/ 3006（常時 `A0`）/ 3010（ホスト変数）/ 3014 / 3018 /
  3023（集約・副問合せ・UNION）/ 3026（**UNION のみ**）/ 3028 / 5002 / 5005、7.5 のみ 3015。
  → **どれも `other`。** 意味を足すのは、実測で中身を確かめてからにする（後続作業でよい）。

## 処理フロー / シーケンス

### 採取と後始末（`plan-capture.ts`）

```mermaid
stateDiagram-v2
  [*] --> 接続取得: explain 専用プール
  接続取得 --> 残骸掃除: ENDDBMON（失敗は無視）
  残骸掃除 --> 監視開始: STRDBMON OUTFILE(QTEMP/一意名)
  監視開始 --> 文の実行: run / no-rows
  監視開始 --> 失敗: STRDBMON が失敗<br/>**文は実行しない**
  文の実行 --> 監視終了: ENDDBMON（finally）
  文の実行 --> 監視終了: SQL エラーでも通す
  監視終了 --> 読み出し: SELECT 明示列 FROM QTEMP/一意名
  読み出し --> 後始末: DROP TABLE（finally）
  後始末 --> [*]
  失敗 --> [*]
```

**不変条件（回帰テストで固定する）**

- `STRDBMON` が成功したら、**どの経路を通っても `ENDDBMON` が 1 回呼ばれる**。
- 作った QTEMP 表は、**どの経路を通っても `DROP` される**。
- `no-rows` で **1 行も読まなくても、カーソルと接続が解放される**（research F9 の修正）。
- **`SELECT *` を使わない**——読み出しは常に列を明示する（research F8 の CCSID 65535 を踏まないため。
  F8 自体も直すが、明示列は「必要な列だけ運ぶ」意味でも正しい）。

### F8 / F9 の直し方

- **F8**: `db-decode.ts` の `decodeText` を `isBinaryCcsid` 経由にする。
  CCSID 65535 の CHAR / VARCHAR / LONGVARCHAR は **BLOB と同じくバイト列**で返す
  （同ファイルの `:275` が既にその扱い＝**片側だけ取り残されていた**のを揃える）。
  `RangeError` を投げない。
- **F9**: `openQuery` の戻り値に**冪等な `close()`** を足し、`iterate()` の `finally` も同じ `close()` を呼ぶ。
  ジェネレータを 1 度も回さずに捨てても解放されるようにする。
  `no-rows` はこの `close()` を使う（`openQuery` → 即 `close()`）。
  **既存呼び出し側の契約は変えない**（`columns` / `rows` はそのまま。`close` は追加）。

### 権限が無いときの分岐

```mermaid
flowchart LR
```
