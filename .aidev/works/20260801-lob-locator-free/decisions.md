# 自律実行中の判断記録

## D1: 実装するが、**`fillLobs` には組み込まない**

**判断**: `freeLob` をライブラリの口として実装・公開するが、`fillLobs` が
取得直後に自動で解放することは**しない**。

**理由**:

- **単発接続では要らない**。実測（`research.md` F3 / F4）で、接続を閉じれば
  ロケーターは消え、次の接続では**同じ番号が配り直される**。
  このプロジェクトの接続は呼び出しごとに開いて閉じるので、後始末はホスト任せで足りる
- **組み込むと直前の決定と矛盾する**。`20260801-sql-lob-failed-state` で
  「失敗したセルも `locator` を残す——**取り直す手がかりを消さない**」と決めたばかり。
  取得直後に解放すると、その手がかりが**必ず死ぬ**
- それでも**長い接続の中で大量の LOB を引く**利用者にとっては要る資源なので、
  `index.ts` から公開して呼べるようにしておく

## D2: 「既に解放済み」の戻りコードは実測を優先する

原典のコメントは `7 / -401` を挙げるが、**実機（7.3）は `2 / -816`** を返した。

**判断**: 両方を「もう無い」として同じ扱いにする（`ALREADY_FREED`）。

**理由**: 原典自身が `host now has various errors if locator is already freed` と書いており、
**値がホスト・版数で変わることを原典も認めている**。片方だけ見ると、
別のホストで benign な二重解放が `warn` になって騒がしくなる。
AGENTS.md「規格どおりより既存クライアントと同じ挙動」の趣旨——
原典が「値は一定でない」と言っているなら、こちらもそう作る。

## D3: 解放の失敗で投げない。ただし `debug` に落とさない

後始末なので、失敗しても呼び出し側は落とさない（値は既に取れている）。
ただし**理由は `warn` で残す**——`debug` は既定の sink で消えることを
`20260801-sql-lob-failed-state` で踏んでいる。「解放が効いていない」ことに
誰も気づけないのが一番困る。

**二重解放だけは `debug`**（目的は達しているので騒ぐ意味が無い）。
