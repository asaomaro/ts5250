# 要件: LOB ロケーターの明示的な解放を入れるか決める

## 背景 / 課題

backlog `hostserver.md`「ロケーターの明示的な解放（接続を閉じれば消えると見込んでいるが未確認）」。

要求形式は `20260801-lob-batch-retrieval-research`（PR #243）で**原典から確定済み**:
**`FUNCTIONID_FREE_LOB = 0x1819`**、パラメータは**ロケーターハンドル（`0x3818`）1 つだけ**、
ORS ビットマップは **RETURN_DATA のみ**。原典は**戻りのエラーを握り潰している**
（`7,-401` が「既に解放済み」）。

残っているのは**実装と実機確認**、そして**入れる価値があるかの判断**。
こちらの接続は**単発完結**（呼び出しごとに開いて閉じる）なので、
閉じれば消えるなら明示的な解放は要らないかもしれない——**それを確かめていない**。

## 目的 / ゴール

**「解放が要るのか」を実機で確かめ、要るなら入れる。**

確かめること:

1. `0x1819` を送ると**実際に解放されるか**（解放後に同じロケーターを引くと何が返るか）
2. **接続を閉じれば消えるのか**（＝明示的な解放が要らないと言えるか）
3. 既に解放したロケーターをもう一度解放すると何が返るか（原典が握り潰している状況の実物）

## スコープ

### 対象

- `freeLob`（`0x1819`）の実装
- 上の 3 点の実機実測と記録
- 実測に基づく**採否の判断**（`fillLobs` に組み込むかどうかを含む）
- 再現スクリプト

### 対象外

- **LOB の書き込み**（`0x1817`）
- ロケーター経由の DBCLOB の欠陥（`20260801-lob-threshold-realhost` F5。**別項目**）
- 接続プールの導入（`20260730-sql-fetch-limit` で「要らない」と結論済み）

## 機能要件

- 要求は原典と同じ形（ロケーターハンドルのみ・ORS は RETURN_DATA のみ）
- **解放の失敗で呼び出し側を落とさない**。解放は後始末であって、
  それ自体が目的の操作ではない（原典も握り潰している）。ただし**黙らせない**
  ——理由はログに残す（`20260801-sql-lob-failed-state` で `debug` は消えると分かっている）
- 組み込むと決めた場合、**既定の挙動を壊さない**

## 非機能要件 / 制約

- 実資格情報を成果物・コミット・PR に書かない（`.env` のみ）
- 実機に副作用を残さない（ロケーターは接続を閉じれば消える見込み。表は作らない）
- 既存テストが通ること

## 完了条件 (受け入れ基準)

- [ ] `0x1819` の要求が実装され、原典と同じ形になっている
- [ ] **解放後に同じロケーターを引くと何が返るか**が実測で記録されている
- [ ] **接続を閉じたら消えるか**が実測で記録されている
- [ ] 二重解放の応答が実測で記録されている
- [ ] 採否の判断と理由が `decisions.md` に残っている
- [ ] 再現スクリプトがあり、`scripts/README.md` に載っている
- [ ] `npm run build` / `npm run lint` / `npm test` が通る
- [ ] backlog の該当項目が更新されている

## 未確定事項 / 確認したいこと

- **`fillLobs` に組み込むか**。取得後すぐ解放すれば接続中のメモリを早く手放せるが、
  **同じロケーターを再取得できなくなる**（`20260801-sql-lob-failed-state` で
  「ロケーターは取り直す手がかりとして残す」と決めたばかり）。**実測を見て spec で決める**
