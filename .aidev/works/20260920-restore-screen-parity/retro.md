## うまくいった点

- **「ACS のワイヤを無人で記録する」手立てを作れたこと。** `scripts/tap-proxy.mjs` を中継として上げ、
  **ECL プローブ（`scripts/acs-probe.mjs`）の接続先をそこへ向ける**と、利用者の操作なしに
  ACS が出す 5250 レコードをそのまま採れる。これで「ACS はこう返す」が**推測から実測に変わった**
  ——SAVE 応答が zlib（`78 9c`）であること・opcode が受信の写しであること・
  `0x66` の応答が 1,920 バイトちょうどであることは、どれもこの手立てが無ければ分からなかった。
  前 work が「ACS を実機に当てられる」を作り、この work が「そのワイヤを見られる」を足した。
- **1 回の観測で決めなかったこと。** RESTORE SCREEN の積荷の後ろに READ が続くかは、
  Attn→F12 では「続かない」、QSH→F3 では「続く」だった（research F9・F9b）。
  1 例で決めていれば「レコードの残りを捨てる」を実装し、**QSH から戻ると施錠が解けなくなる**
  欠陥を入れていた。`measurement-sanity` が効いた場面。
- **退行を「注入して落ちること」まで確かめたこと。** 主要な修正 5 つ（積荷の段の取り違え／
  `b < 0x40`／`errShape` の 3 世代／`msgLineRow` の復元／`ll` を壊したレコード）について、
  実装を元に戻すとテストが落ちることを確認した。**「テストを足した」と「欠陥を固定した」は別**で、
  この work では実際に 3 回、前者だけで後者になっていなかった。
- **過去の決定を破棄できたこと。** opcode `0x05` 固定・フラグキーに欄を載せない・
  「ACS のやり方は当 PJ では真似できない」の 3 つを、一次資料と実測を根拠に覆した（decisions D6〜D8）。
  利用者が原則 3 を明文化してくれたおかげで、**迷わず破棄に倒せた**。

## 課題 / 手戻り

### 1. must 11 件のうち 6 件が「自分の修正・自分のテスト」由来だった

| ラウンド | 指摘 | must の性質 |
|---|---|---|
| 1 | 29 | 製品コードの欠陥（退避段のずれ・逃げ道が塞がる・lint が落ちる） |
| 2 | 10 | **直前の修正が生んだ退行**（`String(e)` → 秘密がログに出る） |
| 3 | 12 | **同上**（`stack` の 1 行目だけ落とす → 複数行 message が残る） |
| 4 | 9 | **自分が足したテストが構造的に落ちない**（`msgLineRow`） |
| 5 | 8 | **同上**（`b < 0x40` と fail-closed。委譲先が変異注入で実証） |

**原因は 1 つに収束する**——`AGENTS.md` の判断の原則 2（推測せず実機・実測で確かめる）を、
**私が繰り返し外した**。利用者がその原則を明文化した直後の work で、である。

- ラウンド 2 の must: 「`String(e)` では `code` とスタックが落ちる」という nit に応じて `err: e` にした。
  **`FIELD_TYPE` の文言に打鍵値が埋まることを確かめずに**変えた。
- ラウンド 3 の must: 「`stack` の 1 行目は `<name>: <message>`（V8 の書式）」と JSDoc に書いた。
  **測っていなかった。** message は複数行になりうる。
- ラウンド 4 の must: `msgLineRow` の往復テストに入れた SOH の `0x18`＝24 が**既定値**で、
  SAVE と RESTORE の間の操作も `msgLineRow` に触れない。**落ちないことを確かめずに**「往復を固定した」と書いた。
- ラウンド 5 の must: `b < 0x40` と fail-closed のどちらも、**テストを足していなかった**のに
  「直した」と扱った。

**前段で防げたか: 防げた。** どれも「書く前に 1 回動かす」で分かった。
実際、ラウンド 4 以降は**先に測ってから直す**ようにしたら、自分で must を 2 件先に見つけられた
（`at ` 行頭の漏れ・`msgLineRow` の無防備）。

### 2. `comment-provenance` は「規約はあるのに守られていない」類型

- 違反（`!` 付き）**18 件**。条項の仮説は「次の 5 works で work あたり 3 件以下」で、**6 倍**。
  baseline（32 件）からは減っているが、**同じ work の中で 3 ラウンド連続で再発**した
  （ラウンド 1 で直した「work 未修飾」が、ラウンド 2・3 の隣の行で再発）。
- **追記しても効かない類型**（`protocol.md`「12.」の表）。打ち手は層を下げること。
  前 work が起票した「work をまたぐ参照の無修飾を走査で検知する」は `code-quality-checks.md` に
  **まだ未着手のまま**で、この work でもその穴をそのまま踏んだ。

### 3. 「テストを足した」が「欠陥を固定した」になっていない

- ラウンド 4・5 の must はどちらもこれ。**委譲先が変異注入で実測して初めて分かった**
  （`b < 0x20` に戻して 682 件緑／fail-closed に戻して 34 件緑）。
- 根っこは **tn5250 / hostserver のテストが型検査されない**ことにもある——
  `buildReadScreenExtendedResponse` に引数を足したのに、テスト 7 か所が 2 引数のまま
  `undefined` を渡して通っていた（ラウンド 2 で発見）。

### 4. review が 5 ラウンドかかった

- 件数は 29 → 10 → 12 → 9 → 8 と逓減したが、**上限（3 回）を 2 回超えた**。
  `debug skip` を 2 回記録して進めた——原因は毎回特定済みで再現もできていたので、
  「原因究明」ではなく「修正」の工程だったという判断。
- ただし**5 ラウンドかかった事実は、上流で防げたことの裏返し**でもある。
  ラウンド 1 の 29 件のうち 22 件が should で、その多くが**コメントと実装の食い違い**だった
  ——実装を変えるたびに、周辺のコメントを読み直していなかった。

## 改善提案

### 製品 / コード（→ backlog に起票済み）

- **`sendError` が検証文言をブラウザへ返す**（優先度 高）——`validateFieldContent` は文言に
  `JSON.stringify(value)` を埋めるので、マクロの `secretRef` を型の合わない欄へ再生すると
  **復号済みの秘密が平文でクライアントへ返る**。`AGENTS.md`「API/ブラウザには平文も暗号文も返さない」違反。
  既往で、この work はフラグキーの経路だけを塞いだ → `code-quality-checks.md` に起票済み。
- **tn5250 / hostserver のテストを型検査の対象にする** → 同上に起票済み。

### PJ プロセス / 規約（→ `.aidev/conventions/` の条項）

- **条項を起こす**: `verify-by-mutation`（「固定した」と言う前に、実装を戻して落ちることを確かめる）
  - 仮説: 回帰テストを足したとき**実装を元に戻して落ちることを 1 回確かめれば**、
    「テストは足したが欠陥は固定されていない」が review の must になる件数が減る。
  - baseline: この work で 3 件（`msgLineRow` / `b < 0x40` / `errShape` の fail-closed）。
    いずれも**委譲先が変異注入して初めて**分かり、それまで「固定した」と記録していた。
- **条項を起こさない**（規約はあるが守られていない類型）: `comment-provenance` の違反 18 件と、
  判断の原則 2（推測せず実測）を外した must 4 件。**どちらも追記しても効かない**
  ——前者は走査（起票済み）、後者は下の「ハーネス」側の促しで層を下げるべき。

### ハーネス自体（→ aidev-* への提案・適用は人間）

- **`aidev event <工程> sent_back` の促しに「直前の修正由来か」の次を足す。**
  いまの促しは「同じ不変条件を支える項をすべて列挙して壊してみる」で、**列挙は効いた**
  （ラウンド 2 で 3 つの不変条件を機械的に洗えた）。だが**「壊してみる」が実行されなかった**
  ——列挙して直しただけで、戻して落ちるかは確かめなかった。
  「**列挙したら、1 つを元に戻してテストが落ちることを確かめる**」まで促せば、
  この work の must 3 件はラウンド 2 で止まっていた。
- **`review` の差し戻し上限に達したとき、`debug` 以外の出口を用意する。**
  この work は 5 回差し戻したが、原因は毎回特定済みで再現もできており、`debug` は的外れだった
  （`debug skip` を 2 回打った）。**「収束しているか」を件数の推移で判定する出口**——
  例えば「件数が単調減少で、かつ must が製品コードでなくテストに寄っている」なら
  「締めてよいか人に聞く」——があると、`skip` の乱発にならない。
- **`aidev metrics` の `reworks` が 14 と出るが、内訳が読めない。**
  差し戻し 5 回に対して手戻り 14 は「coding → test → review を 5 周した」結果で、
  **1 周あたり 3 工程が数えられている**。工程ごとの再開回数が分かれば
  「どの工程を何周したか」が読め、insights で work をまたいで比べられる。
