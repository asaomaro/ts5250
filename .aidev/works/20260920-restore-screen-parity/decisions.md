# 決定記録

## D1: 三層の判定は full（aidev-00-start 手順 0）

- 背景: backlog `acs-parity.md` の「Attn・SysReq・ヘルプから戻ると、打鍵した文字と MDT が消える」に着手するにあたり、
  対象外 / light / full のどれかを決める必要があった。
- 決定: **full**。利用者に確認した（2026-09-20）。
- 理由 / 代替案: 振る舞いを変える変更であり、`@ts5250/tn5250` の共有モジュール
  （`wtd-applier.ts` / `buffer.ts` / `save-screen.ts`）と `packages/web-ui` にまたがる。
  light の 4 条件（振る舞い不変・小規模）を満たさない。
- 影響: 上流 3 工程をそれぞれのゲートで回す。research も挟んだ。

## D2: 積荷は「レコードの残り」ではなく「送った長さ」で読み飛ばす

- 背景: ホストは RESTORE SCREEN（`ESC 0x12`）で、こちらが SAVE SCREEN 応答として送った積荷を
  そのまま返してくる。当 PJ の解析ループは積荷を読み飛ばさないので、積荷の中の
  `ESC 11`（WTD）を次のコマンドとして適用し、打鍵と MDT を潰していた（research F5・F10）。
- 決定: **退避スタックの各段に「送った積荷の本体」を添え、復元時に、直後のバイト列がその積荷と
  一致する限り読み飛ばす。** 一致しなければ 1 バイトも読み飛ばさない（現状の振る舞いのまま）。
- 理由 / 代替案:
  - **退けた案 (a)「レコードの残りを捨てる」**（ACS `DS5250.processRestoreScreen` の `n2 - 2` と同じ）。
    **実機で反例が出た**——QSH から F3 で抜けるときの RESTORE SCREEN レコードは
    `04 12` ＋ 積荷 793 バイト ＋ **`04 52 00 00`（READ MDT）**で、READ が同じレコードに続いていた
    （research F9b）。捨てると READ を失い、施錠が解けなくなる。
    ACS がこれで平気なのは `Save5250Net` が `pending_read` / `pending_aid` / 施錠を退避しており、
    復元時に戻すから（research F9c）。**当 PJ にはその復元が無いので、同じ真似はできない。**
  - **退けた案 (b)「積荷に 2 バイトの長さを付ける」**（ACS の SAVE PARTIAL と同じ）。
    ホストは積荷を不透明な保管物として扱うので長さを付けること自体は可能だが、
    **0x02 の応答形式を変えると、長く実機で動いている経路（SEU の F1・PDM の F1・QSH）を
    まとめて危険にさらす**。`20260730-tn5250-cross-check` で「自分が付けた前置きを
    ホストのパラメータと誤解する」自作自演を一度やっているので、前置きを増やす方向は採らない。
  - 採った案の利点: **0x12 と 0x13 の両方に同じ仕組みで効く**。積荷が無い（退避スタックが空・
    一致しない）ときは 0 バイト読み飛ばしなので、既存テストが固定している
    「RESTORE PARTIAL はパラメータを読まない／後続のコマンドを捨てない」
    （`packages/tn5250/test/save-partial-screen.test.ts:135`・`:196`）を**壊さない**。
  - 一致の確認を入れるのは、ホストが積荷を改変して返す場合に**黙って別物を読み飛ばさない**ため。
    2 回の採取では長さ 793 バイトで一致しており、改変の兆候は無い（research F9・F9b）。
- 影響: `ScreenBuffer` の退避スタックの型に 1 項目増える。`Session5250` が SAVE 応答を組み立てた後、
  その本体をバッファへ渡す配線が要る（今は buffer が応答を知らない）。

## D3: ブラウザの編集差分は「復元由来の画面」では捨てない（サーバーへ打鍵を送る案は退ける）

- 背景: 利用者が打った文字は**ブラウザの `SessionState.edits` にしか無い**。AID を送る瞬間に
  初めてサーバーへ渡る（research F6）。そして `packages/web-ui/src/stores/sessions.ts:481` が、
  ホスト発の画面が来るたびに `edits.clear()` する。
  **Attn / SysReq には欄を載せない**ので（`packages/web-ui/src/session-controller.ts:1161`）、
  退避の時点でサーバーは打鍵を知らない。**サーバー側（D2）を直しても、利用者の画面は空のまま。**
- 決定: **`updateScreen()` の `edits.clear()` を、復元由来の画面（`lastWrite.restored`）では行わない。**
- 理由 / 代替案:
  - **退けた案「フラグキーでも欄をサーバーへ送る」**（ACS の構造に合わせ、打鍵を表示バッファへ入れる）。
    `packages/server/src/ws-handler.ts:1031-1034` に**意図的な決定として反対のことが書いてある**——
    「フラグレコードには欄を書かない。Attn / SysReq のレコードは画面の MDT を載せないので書いても
    送られない。それどころか `setField` は施錠中に `KEYBOARD_LOCKED` を投げるので、
    **逃げ道であるはずの SysReq が、未送信の入力が残っているだけで使えなくなる**」。
    この決定を覆すには `assertReady` を迂回する必要があり、逃げ道を壊す危険が実害を上回る。
  - **退けた案「打鍵ごとにサーバーへ送る」**。ACS の構造（表示バッファ＝打鍵の置き場）には最も近いが、
    1 打鍵ごとの往復を増やす設計変更で、この work の範囲を大きく超える。
  - 採った案は web-ui 側の局所的な条件追加で、`lastWrite.restored` は**既に snapshot に載っている**
    （`packages/tn5250/src/screen/buffer.ts:1256`）。
  - MDT は壊れない——打鍵は次の AID 送信で `fields` として渡り、`setFieldValue` が MDT を立てる
    （`buffer.ts:942-949`）。**復元の時点でサーバー側の MDT が false なのは、実際に何も送っていないから**で、
    5250 の意味として正しい。
- 影響: `updateScreen()` は全セッションの画面更新の要。条件を誤ると「ホストが書き直した欄に
  古い編集が残る」退行になるので、テストで両方向を固定する。

## D4: 積荷とイメージ応答の文字は、`rawByte` が無ければコードページで符号化して出す

- 背景: `packages/tn5250/src/protocol/save-screen.ts:243` の `writeCell` は `cell.rawByte ?? 0x40`。
  `setFieldValue` で入れた文字は `rawByte` を持たない（`buffer.ts:939-940`）ので**空白になる**。
- 決定: `rawByte` が無いときは、セルの文字をコーデックで符号化して出す。符号化できないときだけ `0x40`。
- 理由 / 代替案: D2 により**積荷は二度と自分で適用しない**ので、積荷の中身だけなら実害は消える。
  しかし**同じ `writeCell` が画面イメージ応答にも使われ、`0x66` / `0x6A` は実機に到達する**
  （research F12。DSM の `QsnPutInpCmd(0x66)` で実証済み）。ACS は `HostPlane` を返すので
  打鍵した文字が載る（research F3・F4）。**ACS に合わせる。**
  - `rawByte` を意図的に付けていない箇所（`setUnmappable` / `setShift` / ORDER 0x1C・0x1E）は、
    カタカナ表示モードでの再解釈による化けを避けるためなので、**そのまま `0x40` でよいかを個別に見る**。

## D5: 画面イメージ応答の形式差（前置・opcode）は、実機で測れる範囲だけ動かす

- 背景: ACS は前置なし・opcode は受信したものの写し。当 PJ はカーソル 2 バイトを前置し、opcode を
  PUT_GET にする（research F3 と `save-screen.ts:100-119`）。
- 決定: **`0x62` は「実機に到達しないので変更しない」と根拠付きで記録して閉じる。**
  `0x66` / `0x6A` は DSM で到達させられるので、**実機で測ってから**判断する（test 工程）。
- 理由 / 代替案: `0x62` は国勢調査 2 回（83 レコード・142 レコード）で 1 件も出ず、当 PJ は
  設定に関わらず常に拡張 5250 を申告する（`packages/tn5250/src/protocol/query-reply.ts:45`・`:88-89`）ため
  ホストは `0x64` を送ってくる（research F12）。**測れないものを推測で変えない**
  ——`READ SCREEN EXTENDED` の形式を 9 通り試して確定させた経緯（`save-screen.ts:160-176`）と同じ態度。

## D6: D3 を差し替える——フラグキーでも、施錠されていないときに限り欄をサーバーへ渡す

- 背景: D3 では「ブラウザの編集差分を復元画面で捨てない」を採ったが、利用者の判断（2026-09-20）で
  **ACS の構造に合わせる**ことになった。ACS は打鍵した文字を表示バッファ（`PS5250` の
  `HostPlane` / `TextPlane`）へ即座に書き（research F4）、それが `Save5250Net` に退避される（research F1）。
  当 PJ で同じ形にするには、退避が起きる前に打鍵がサーバーの `ScreenBuffer` に在る必要がある。
- 決定: **Attn / SysReq でも `fields` をサーバーへ渡す。ただしサーバーは、施錠されていないときだけ
  `setField` する**（施錠中は黙って見送り、フラグレコードはそのまま送る）。
  `edits.clear()`（D3 で触ろうとしていた `packages/web-ui/src/stores/sessions.ts:481`）は**変更しない**。
- 理由 / 代替案:
  - `packages/server/src/ws-handler.ts:1031-1034` の既存の決定が守っているのは
    「**`setField` が施錠中に `KEYBOARD_LOCKED` を投げるので、逃げ道であるはずの SysReq が、
    未送信の入力が残っているだけで使えなくなる**」という一点。
    **施錠中だけ同期を見送れば、この一点はそのまま守られる。**
  - **施錠中に失われる打鍵は無い**——web-ui は施錠中の入力自体を止めている
    （`packages/web-ui/src/components/ScreenGrid.vue:202` ほか、`inputInhibited`）。
    打って Attn を押す場面では `state === "ready"` なので、同期は成立する。
  - もう一方の理由「フラグレコードは欄を載せないので書いても送られない」は**そのまま正しい**
    （`buildFlagRecord`）。今回書くのは**ホストへ送るため**ではなく、**退避に載せるため**。
    この意図の違いをコメントに残す。
  - **退けた案（D3 の元案）**「復元画面では `edits` を捨てない」。web-ui だけで閉じるが、
    サーバーの `ScreenBuffer` は打鍵を知らないままなので、`READ SCREEN TO PRINT`(0x66/0x6A) の応答・
    MCP の画面表示・`format.ts` の整形が ACS と食い違ったままになる。**差異の根が残る。**
  - **退けた案**「打鍵ごとにサーバーへ送る」。ACS に最も近いが往復が増え、この work の範囲を超える。
    フラグキーと AID 送信の 2 点で同期すれば、退避が起きる場面はすべて覆える。
- 影響:
  - Attn 後にホストが READ MDT を送ってくると、**これまで送らなかった打鍵済みの欄を送るようになる**。
    これは ACS と同じ振る舞い（ACS も打鍵で FFT の MDT が立つ）なので、**差異を埋める側の変更**。
    ただし観測可能な変化なので test で確かめる。
  - `assertWritable` の検査はフラグキーでも通す（権限の扱いを変えない）。

## D7: D2 の「ACS のやり方は当 PJ では真似できない」を破棄する。ACS と同じ状態一式を退避・復元する

- 背景: `AGENTS.md`「判断の原則」1（ACS を聖典とする）と 3（矛盾したら過去の決定を破棄する）を
  利用者から明示された（2026-09-20）。D2 は ACS の「レコードの残りを消費する」を
  「**当 PJ にはその復元が無いので、同じ真似はできない**」と書いて退けていた。
  **これは聖典より当 PJ の現状を上位に置いた誤り。** 破棄する。
- 決定: **ACS が `Save5250Net` で退避している状態を、当 PJ の退避にも入れる。**
  ACS の一覧（research F1）のうち、当 PJ に対応物があるもの:
  - 欄の定義（MDT 込み）＝ `fields`（**既にある**）
  - セル＝プレーン群（**既にある**）／画面サイズ（**既にある**）／GUI 構造（**既にある**）
  - カーソル位置（**既にある**）
  - **保留中の READ**（ACS `pending_read`）— 当 PJ の `Session5250.readCommand` と施錠状態
  - **保留中の AID**（ACS `pending_aid`）— 当 PJ の `pendingAid`
  - **施錠**（ACS `keyboardLocked`）— 当 PJ は `state` から導出
  - **メッセージ行番号**（ACS `SOH_msgline_num`）— 当 PJ の `msgLineRow`
  - **CA マスク**（ACS `SOH_Byte5/6/7`）— 当 PJ の `aidNoDataMask`
  - **挿入モード**（ACS `insertMode`）— 当 PJ はブラウザ側が持つ（対応箇所を design で確かめる）
  - ホーム位置・`WTD_IC_addr`・ENPTUI/PMB — 当 PJ の対応物を design で確かめ、無ければ「未対応」と書く
- 理由 / 代替案: 聖典に従う。ACS が退避している項目は、**退避する理由があって入っている**と考える。
  当 PJ に対応物が無い項目は、無いこと自体を記録する（推測で「要らない」と決めない）。
- 影響: 退避の型が広がる。`ScreenBuffer` の外（セッション層）に在る状態を退避するため、
  退避・復元の呼び口をセッション層に用意する必要がある。

## D8: SAVE SCREEN 応答の opcode を「受信した opcode の写し」にする（過去の決定を破棄）

- 背景: ACS のワイヤ実測（research F14）で、ACS の SAVE SCREEN 応答は **opcode `0x04`**
  （＝受信した SAVE SCREEN レコードの opcode の写し）だった。
  当 PJ は `OPCODE.RESTORE_SCREEN`(0x05) を固定で使っている
  （`packages/tn5250/src/protocol/save-screen.ts:29`）。
- 決定: **ACS に合わせ、受信した opcode を写す。** 既存テスト
  `packages/tn5250/test/save-screen.test.ts:32`（「opcode … が RESTORE SCREEN になっている」）が
  固定している過去の決定は、**原則 3 により破棄**して書き替える。
- 理由 / 代替案: 聖典が `WorkHeader.Opcode` の写しであることは、デコンパイル結果とワイヤの両方で一致。
  当 PJ の 0x05 でもホストは受理する（実測で往復している）が、**受理されることは「同じである」ことではない**。
- 影響: `buildSaveScreenResponse` / `buildSavePartialScreenResponse` が受信 opcode を受け取る必要がある。
  **変更後に実機で往復を確かめる**（SEU の F1・PDM の F1・QSH・Attn→F12）。

## D9: D6 の「影響」の記述を破棄する——ACS は F12 でも欄データを送らない（実測）

- 背景: D6 で「Attn 後にホストが READ MDT を送ってくると、これまで送らなかった打鍵済みの欄を
  送るようになる。これは ACS と同じ振る舞い」と書いた。**これは推測だった。**
- 決定: 破棄する。ACS のワイヤ実測（research F17）では、
  - **Attn** は 10 バイトのフラグレコード（flags `0x40`・本体空）＝欄データ無し
  - **F12** は本体 `14 1a 3c`（カーソル 20,26 ＋ AID `0x3C`）＝**欄データ無し**
  ——ACS の画面には `WRKACTJOB` が残っていた（research F11）のに、である。
  **打鍵を表示バッファに持つことと、それをホストへ送ることは別。**
- 理由 / 代替案: `AGENTS.md`「判断の原則」2（推測せず実機で確定する）。
- 影響: **D6 の変更（フラグキーで欄をサーバーへ渡す）は、ホストへ送るバイト列を変えてはならない。**
  これを受け入れ基準に入れ、**実機のワイヤで確かめる**（`tap-proxy` ＋ 当 PJ のクライアント）。
  変わるなら D6 自体を見直す。

## D10: 積荷の読み飛ばしは「長さ」で行う（D2 の手立ては維持。理由を実測で置き換える）

- 背景: D2 は「レコードの残りを捨てると QSH の READ を失う」を理由にしていた。
  D7 で ACS の状態復元を入れるなら、末尾の READ を失っても保留 READ が復活する——
  **ACS と同じ理屈が成り立つ**ようにも見える。
- 決定: **それでも「長さで読み飛ばす」を採る。**
- 理由 / 代替案: ACS のワイヤ実測（research F16）で、**同じ QSH→F3 でも
  ACS のときは READ が別レコード、当 PJ のときは同一レコード**だった（当 PJ 側は 2 回とも再現）。
  ＝**ホストのレコードのまとめ方が、積荷の形式によって変わっている。**
  聖典の「残り全部を消費する」は **ACS の積荷形式を前提にした境界**であって、
  当 PJ の積荷形式ではそのまま当てはまらない。
  **状態を復元できるからといって、ホストが同じレコードに載せてきた READ を捨ててよい理由にはならない**
  ——捨てれば、退避時とは別の READ（QSH 終了後の画面に対するもの）を失う。
  なぜ積荷の形式でホストのまとめ方が変わるのかは**未確認**（設計には不要）。
- 影響: D2 の手立て（退避スタックに積荷の本体を添え、一致を確かめて読み飛ばす）はそのまま。

## D11: 実機で確定する 5 タスクは coding ではなく test 工程で消化する

- 背景: `AGENTS.md`「判断の原則」2 により、実機で確定できることは実機で確定する。
  T13〜T17 はいずれも実機での計測・突き合わせで、coding の中では閉じられない。
  T18（片付けと点検）は deliver で行う。
- 決定: **T13〜T17 は test 工程、T18 は deliver で消化する。** coding の承認時には未チェックで残る
  （`aidev-30-tasks` 手順 6 の「coding ではなく test / deliver で消化する」に当たる）。
- 理由 / 代替案: coding の中で実機を叩くこともできるが、**実装が固まる前に測ると測り直しになる**。
  とくに T15（DSM で `0x62`/`0x66`/`0x6A` を出させて ACS と突き合わせる）は、
  T8（`writeCell`）の結果を含めて測る必要がある。
- 影響: coding の完了の目安（全タスクがチェック済み）と形の上で食い違う。この記録がその証跡。

## D12: セッションの `state`（施錠）は退避・復元しない——ACS の `SaveKeyboardLocked` に対応物が無い

- 背景: D7 で「ACS が `Save5250Net` に入れている状態は当 PJ も退避する」と決め、`readCommand`（ACS の
  `pending_read`）と `state`（ACS の `keyboardLocked`）を積んだ。cross 点検が**実害を指摘**した——
  `pushInputState()` が捉える `this.state` はそのレコードの施錠／解錠が適用される**前**の値なので、
  READ を伴わない RESTORE レコードが来ると **`ready` のセッションが `locked` に戻り、
  次の READ が来るまで入力が死ぬ**。
- 決定: **`state` は退避・復元しない。** 退避するのは `readCommand` だけ。
- 理由 / 代替案: ACS の `keyboardLocked` は `PS5250.isKeyboardLocked()`＝**表示（OIA）の施錠**に近く、
  復元しても「入力を受け付けるか」の判断そのものは `pending_read` 側が担う。
  当 PJ の `Session5250.state` は**`sendAid()` の門番も兼ねる**（`assertReady()`）ので、
  同じものとして扱うと「送れるはずのセッションを送れなくする」side effect が出る。
