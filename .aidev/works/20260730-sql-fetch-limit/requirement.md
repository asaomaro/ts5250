# 要件: 取得する行数を実際に抑える（早期打ち切り）

## 背景 / 課題

`host_sql`（MCP）と `/api/host/sql`（ページングを使わない経路）の `maxRows` は
**応答に載せる行数の上限であって、ホストから取得する行数の上限ではない**。
`query()` が結果セットを全件取得してから返すため、大きな表では**全行がメモリに載る**。

現状のツール説明は正直にそう書いてある（「大きな表では SQL 側に `FETCH FIRST n ROWS ONLY`
を付けること」）が、これは**利用者に回避を押し付けている**状態である。とくに MCP は
AI が自律的に叩く入口なので、`SELECT * FROM 大きな表` が来たときに
プロセスのメモリを持っていかれる。

抑えられなかった理由は backlog に書かれている:

> 早期打ち切りには `stream` が要るが、**カーソルを途中で閉じる経路が未検証**

`openQuery` はジェネレータを返し、`return()` で `closeCursor` が走る形になっており、
画面のページング（`ResultSetStore.close`）が実際にそれを呼んでいる。
つまり**実質は動いている**が、「途中で閉じたあとホストが健全か」を測っていない。
測っていないので採用できず、`maxRows` が名前どおりに働かないまま残っている。

## 目的 / ゴール

- **`maxRows` を「ホストから取ってくる行数の上限」にする。** 名前どおりに働かせる
- そのために「**途中でカーソルを閉じても、その接続でそのまま次の SQL が通る**」ことを
  実機（）で確かめ、記録する（backlog の未検証項目を閉じる）

## スコープ

### 対象

- 早期打ち切りで行を取る入口を core に用意する（`query` の上限つき取得）
- MCP `host_sql` をそれに載せ替える。**ツール説明の「取得量は減らない」を実態に合わせる**
- `/api/host/sql` の `pageSize` を指定しない経路（単発取得）も同じ扱いにする
- 「**まだ続きがあるか**」を正直に返す（切ったのに黙らない）
- 実機で早期打ち切り後のホストの健全性・取得量の減少・所要時間を実測する

### 対象外

- 画面のページング経路（`pageSize` 指定）は既に結果セットを保持する形で正しい。触らない
- SQL 結果表の仮想化（描画性能。別項目）
- LOB のまとめ取得（別項目）

## 機能要件

- 上限を超える結果セットでも、**上限＋α までしか取得しない**（往復回数で確認できること）
- 「続きがある」ことを利用者に伝える（`truncated` 相当）。**推測で立てない**
- 途中で打ち切った接続を**そのまま使い続けられる**（画面の接続プールに戻せる）
- 打ち切りに失敗したとき（カーソルが閉じられない等）は、その接続を**使い回さない**
- 既存の全件取得の呼び出し（CSV ダウンロード・アップロード前の検査など）は挙動を変えない

## 非機能要件 / 制約

- **推測で実装しない。** カーソルの途中終了はホスト側の状態を残しうるので実測で確かめる
- ブロッキング係数（既定 100 行）を跨ぐ位置・跨がない位置の両方で確かめる
- 秘密を成果物に書かない（実機検証は環境変数名だけを設定に書く）

- [ ] 既存テストが通る（全件取得の経路は変わらない）
