# 決定記録

## D1: `openQuery` が失敗したときに占有を解く（潜在バグの修正をこの作業に含める）

- 背景: `openQuery` は `conn.acquire()` の直後に `prepareAndOpen` を呼んでおり、
  **prepare が失敗すると `release()` が呼ばれなかった**。実機で確かめた:
  存在しない表を 1 度指定すると、以降その接続のすべての SQL が
  「another query is in progress」で失敗する（＝接続が二度と使えない）。
- 決定: `prepareAndOpen` を `try`/`catch` で包み、失敗時に `release()` してから投げ直す。
- 理由 / 代替案: spec の対象範囲には入っていないが、
  **`queryLimited` が `openQuery` と同じ土台（`prepareAndOpen`）に乗る**ため、
  この穴を残すと新しい入口も同じ性質を持つ。単発接続では接続ごと閉じるので隠れていたが、
  接続を使い回す経路（`/api/host/sql` のプール）では致命的になる。
  修正は 4 行・テスト可能・既存の挙動を壊さないので、別 work に切らず含めた。
- 影響: `query.ts` の `openQuery`。テスト 2 件（`openQuery` / `queryLimited` の両方）と
  空振り検証のミュータント 1 本で固定した。

## D2: `queryLimited` は `openQuery` の上には乗せず、`query` と同じ形で書く

- 背景: 当初は `openQuery` を呼び、返ってきたジェネレータを上限で `break` する実装にした。
  しかし**ブロッキング係数を要求ごとに変えられない**ため、
  「あと 1 行ほしい」ときにブロック 1 つぶん（既定 100 行）が丸ごと届いていた
  （上限 200 で **300 行**取得＝100 行が無駄）。
- 決定: `fetchAll` に `maxRows` を足し、**1 回ごとのブロッキング係数を「残り」に合わせる**。
  `queryLimited` は `query` と同じ形（`acquire` → `prepareAndOpen` → `fetchAll` → `closeCursor`）で書く。
  上限 200 なら要求は **100 / 100 / 1**（最後の 1 行は続きの有無を見るため）。
- 理由 / 代替案: 「上限＋1 をブロックにする」案は、上限が大きいと 1 往復の応答が
  上限ぶん丸ごと載る（抑えたい相手そのもの）。残りに合わせる形なら両端で無駄が出ない。
- 影響: `fetchAll` の引数が 1 つ増える（既定 `undefined` で従来と同じ）。
  ブロック終端の判定を `blockSize` から**その回に要求した数**（`want`）へ変えた。
  なお `want` は最後の要求でしか `blockSize` を下回らないため、この 2 つの比較は
  **観測上は等価**（ミュータントにしても落ちない）。それでも `want` と比べるのは
  「要求した数と返った数を比べる」ほうが意図として正しく、
  将来ブロック幅を動的に変えたときに壊れないため。

## D3: 「続きがあるか」は上限＋1 行**読んで**決める（推測しない）

- 背景: `rows.length === limit` を「続きがある」と見なすと、
  **上限ちょうどの結果セットで嘘になる**（`truncated: true` と言ってしまう）。
- 決定: 上限＋1 行目まで読み、読めたら `truncated: true`、その 1 行は**捨てる**。
- 理由 / 代替案: 追加コストは最後の 1 往復（1 行ぶん＝実測 184 バイト）だけ。
  嘘の `truncated` は「まだ続きがあるのでは」と利用者に無駄な追い読みをさせるか、
  逆に取り切ったのに切られたと誤解させる。
- 影響: `LimitedResult.truncated` の意味が「測った事実」になった。
  MCP の説明文と `/api/host/sql` のコメントもその意味に書き換えた。

## D4: 画面のページング経路は載せ替えない

- 背景: `/api/host/sql` は `pageSize` を指定すると結果セットを保持し、
  続きを `/next` で返す（接続を掴み続ける）。上限つき取得に寄せることもできる。
- 決定: 触らない。
- 理由 / 代替案: あちらは「続きを読む」という別の要求で、
  保持しないと続きが読めない。混ぜると規律（期限切れ・手放し）が壊れる。
  ただし「1 ページ見て閉じる」使い方が多いなら打ち切る方が接続を掴まないので、
  **使われ方を見てから決める**旨を backlog に残した。
- 影響: なし（テストで「ページング経路は変えていない」ことを固定した）。
