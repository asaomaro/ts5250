## 空振り検証（mutation）: 12/12

上限＋1 を読まない / 余りの 1 行を捨てない / `truncated` を `rows.length === limit` で決める /
ブロッキング係数を残りに合わせない / ブロッキング係数を上限＋1 固定にする /
`limit <= 0` を黙って通す / **LOB の解決を落とす** / **打ち切り時にカーソルを閉じない** /
**`openQuery` 失敗時に占有を解かない** / **MCP が全件取得に戻る** /
REST 単発が上限を渡さない / REST 単発が `truncated` を捏造する。

**初回は 2 本が空振りした**:

1. **LOB の解決を落とす** → `queryLimited` が `fillLobs` を通すことを見るテストが無かった。
   CLOB ロケーターを返す偽の接続を作って塞いだ（本体の要求＝`0x1816` にも答えさせる）
2. **MCP が全件取得に戻る** → MCP 経路は実機スクリプトでしか見ておらず、
   単体では往復を数えていなかった。**実際の登録コードを通してハンドラを呼ぶ**テストを足した

（もう 1 本、`fetchAll` の終端判定を `want` から `blockSize` に戻すミュータントも検討したが、
`want` が `blockSize` を下回るのは最後の要求だけなので**観測上等価**と分かった。
ミュータントには数えず、なぜ `want` と比べるのかを decisions D2 に書いた。）

## 実装中に見つけて直したこと

1. **`openQuery` の占有漏れ**（decisions D1）。prepare の失敗で `release()` されず、
   **SQL の誤り 1 回で接続が二度と使えなくなっていた**。実機で確認して直した
2. **最初の実装は 100 行を無駄に取っていた**（decisions D2）。`openQuery` の上に乗せた形では
   ブロッキング係数を要求ごとに変えられず、上限 200 で 300 行取得していた。
   `fetchAll` に上限を渡し、要求ごとに「残り」へ合わせる形に書き直した
3. **腐った説明の是正**: `host_sql` の説明文（「maxRows は応答に載せる行数の上限であって、
   ホストから取得する行数の上限ではない」「大きな表では FETCH FIRST を付けること」）と
   `host-sql.ts` の同旨のコメント
