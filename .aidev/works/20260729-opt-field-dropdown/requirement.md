# 要件: オプション欄に選択肢のドロップダウンを出す

出典: `.aidev/backlog/input-assist.md`「他にできそうなこと」→ **オプション欄のドロップダウン**
（backlog 自身が「**一番効きそう**」と記載）。

## 背景 / 課題

`WRKxxx` / PDM 系の一覧画面は、1〜2 桁の Opt 欄の上に**必ず選択肢の凡例が出る**。
利用者は番号を覚えるか、毎回凡例を目で追って入力するしかない。

実機（IBM i 7.5）で採った `WRKOBJPDM TESTLIB` の画面
（`packages/web-ui/test/fixtures/window-prev-diff/nrm-wrkobjpdm-testlib.json`）:

```
 6|  オプションを入力して，実行キーを押してください。
 7|   2=変更      3=コピー      4=削除      5=表示      7=名前の変更
 8|   8=記述の表示              9=保管     10=復元     11=移動  ...
10| OPT  オブジェクト   タイプ    属性        テキスト
11|      ADJPGM      *PGM        RPGLE
12|      EMPSFR      *PGM        RPGLE
```

凡例（r7-8）と Opt 欄（r11 以降の行頭）が揃っている。**材料は画面にすべて出ている。**

**既存の機能キー凡例の仕組みがそのまま使える**（backlog の見立て）。
`fkeyLegend.ts` は `F<n>=` を `LEGEND_RE` で拾い、`ScreenGrid` が桁位置に重ねてボタン化している。
`<数字>=` を拾う兄弟を足せば、実績のある仕組みの応用で済む。

## 目的 / ゴール

一覧画面の Opt 欄にフォーカスしたとき、**その画面の凡例から作った選択肢**を
ドロップダウンで選べるようにする。番号を覚えなくても操作できる状態にする。

## スコープ

### 対象

- 画面から**オプション凡例**（`<数字>=<ラベル>`）を検出する
- 検出した凡例を**どの入力欄に結び付けるか**を決める（Opt 欄の特定）
- 対象欄にドロップダウンの導線を出し、選ぶと欄へ番号が入る
- **画面設定（`ViewSettings` / `VIEW_ITEMS`）に項目を足し、既定は無効（OFF）**

### 対象外

- **datepicker / timepicker**（同じ backlog の別項目。署名判定とシステム値の解釈が要る）
- `inputmode` の指定、F4=Prompt の導線（同上・別項目）
- **拡張 5250 の選択部品**（`gui.selectionFields`）。ホストが宣言したとおりに描画済み
- 数値スピナー（backlog で見送り済み）
- 機能キー凡例（`F<n>=`）のボタン化。実装済み

## 機能要件

- **凡例の検出**: 同一行の `<数字>=<ラベル>` を拾う。`F<n>=` は対象外（機能キー側が扱う）
- **誤検出を抑える**: `<数字>=` は `F<n>=` よりはるかに紛れやすい。
  backlog も「**Opt 欄の存在・凡例行との位置関係で絞ること**」と明記している
- **対象欄の特定**: 凡例と結び付ける入力欄を決める。実機の PDM では
  「凡例行より下」「行頭付近」「桁数 1〜2」「同じ桁に縦に並ぶ」という形をしている
- **選択の反映**: 選んだ番号が対象欄に入り、通常の入力と同じ扱い（MDT が立つ）になる
- **画面設定**: `VIEW_ITEMS` に項目を足す。**既定は無効**（推測を含む機能なので勝手に出さない。
  `windowFrame` / `windowBackdrop` の既定が `none` なのと同じ扱い）
- 窓が開いているときは窓の中だけを対象にする（`detectFkeyLegends` と同じ考え方）

## 非機能要件 / 制約

- **既存テストを壊さない**（特に `fkeyLegend` 系・`ScreenGrid` 系）
- 検出は画面更新ごとに 1 回。入力のたびに再検出しない（`legendsByRow` と同じ設計）
- UI は `docs/UI-DESIGN.md` に従う。利用者に見えるメッセージは
  `composables/opMessages.ts` に置き、テストは**定数を参照**する（AGENTS.md）
- **ホストが送る情報を UI 側で上書きしない**。ドロップダウンは入力の補助であって、
  欄の値・様式の解釈を書き換えるものではない
- web-ui のテストは**パッケージ dir から**実行する（AGENTS.md）

## 追加要件（利用者指示 2026-07-29）: 既存の選択・クリップボード操作を妨げない

**矩形（ブロック）選択とコピー＆ペーストに一切影響を与えないこと。**

実装を読んで確認した干渉点:

| # | 経路 | 干渉の中身 |
|---|---|---|
| 1 | `@mousedown="onGridMousedown"` は**グリッド直下**に付いており、`cellAt()` は座標から桁を算出する | **グリッド内のどこを押しても** `clearRectSel()` が走りドラッグ開始点が置かれる＝選択が消える |
| 2 | `onGridDragMove` はドラッグ開始時に**入力欄を blur** する | 逆に言えば、矩形選択が始まればフォーカスは Opt 欄から外れる |
| 3 | `onGridDblclick` の語選択 | グリッド内の要素がヒット領域に入ると誤爆する |
| 4 | 貼り付けは入力欄の `@paste` | **フォーカスを奪うと貼り付け先が変わる** |
| 5 | コピーは `document` の `copy` を購読し、`rectText()` が `charAtForClipboard`（**モデル**）から組む | DOM の内容は混入しない＝この経路は安全 |

→ 受け入れ基準に「矩形選択・コピー・貼り付けが従来どおり動く」を追加する。

## 完了条件 (受け入れ基準)

- [ ] 実機 PDM 画面の fixture から、凡例 `2=変更` `3=コピー` … が正しく抽出できる
- [ ] 同じ fixture で Opt 欄が特定でき、凡例と結び付く
- [ ] 選択すると対象欄に番号が入る
- [ ] **既定では何も出ない**（設定 OFF）
- [ ] 誤検出を抑える条件が効いている（凡例らしくない `<数字>=` を拾わない）
- [ ] **ドロップダウンを出した状態で矩形選択が従来どおりできる**
- [ ] **ドロップダウンを出した状態でコピー・貼り付けが従来どおり動く**
- [ ] 既存テストが通る
- [ ] テストが空振りでない

## 未確定事項（spec で解消する。必要なら research を挟む）

- **Opt 欄をどう特定するか**。実機 1 画面（PDM）しか手元に無い。
  `WRKACTJOB` / `WRKSPLF` / `DSPLIBL` など他の一覧画面でも同じ形かは**未確認**。
  実機で採って確かめる価値が高い（`WRKSPLF` の fixture は既にある）
- **凡例の切れ目**。`2=変更      3=コピー` のように空白区切りで並ぶが、
  ラベルに空白が入る場合（`7=名前の変更`）の終端をどう決めるか。
  `F<n>=` 側の `TRAILING_BORDER` 相当の処理が要る見込み
- **10 以上の番号**（`10=復元` `11=移動`）と 1 桁の混在
- **ドロップダウンの出し方**。欄の中に `<select>` を重ねるか、フォーカス時にポップオーバーを出すか。
  `docs/UI-DESIGN.md` と既存の `InfoPopover` を踏まえて決める
- **複数の Opt 欄**（一覧の各行に 1 つずつある）への対応。行ごとに出すか、フォーカス中の欄だけか
