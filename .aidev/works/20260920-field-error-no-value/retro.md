# 振り返り: 欄の検証エラーが値をブラウザへ返さないようにする

## サマリ

マクロの秘密を型の合わない欄へ再生すると**復号済みの平文がブラウザへ返っていた**欠陥を塞ぎ、
PR #408 で着地した。実装は 20 ファイル・+1,169 / −78。

**本題そのものは早く片付いた。**時間を使ったのは「同じ欠陥が、最初に洗った経路の外にも
並んでいた」ことと、**その取りこぼしを自分の修正の中で 2 回繰り返した**ことだった。

| 指標 | 値 |
|---|---|
| リードタイム / 実作業 | 11,530 秒 / 9,257 秒（待ち 4,044 秒） |
| 差し戻し（review → coding） | **3 回**（記録は 2 回。下記「記録漏れ」） |
| review の指摘（通算） | must 3 / should 18 / nit 24 |
| coding 内の cross 点検 | 16 件（母集団が違うので上の数には含めない） |
| 変異注入 | 14 件すべて「戻すと落ちる」を確認 |
| タスク | 計画 11 → 最終 15（差し戻しで 4 追加） |
| `ac_drift` | 0 |

## うまくいった点

- **先に測ってから書いた**（`AGENTS.md` 判断の原則 2）。requirements に実測の文言を貼ったので、
  「何が漏れているか」で揉めることが一度も無かった。design も「値を外す」ではなく
  「**位置と理由に置き換える**」と決められた。
- **変異注入を全部の修正に掛けた**（条項 `verify-by-mutation`）。これが**この work の主産物**で、
  「テストが在るのに落ちない」を **4 件**見つけた:
  - ws の漏れ検査が**直した経路を通っていなかった**（18 文字の秘密が 10 桁の欄で桁あふれし、
    型検証まで届いていなかった）
  - 位置の配線（`at`）が**どこからも固定されていなかった**（第 5 引数を削っても 3 パッケージ全緑）
  - 反射をやめた 4 か所のうち**固定されていたのは 1 か所だけ**
  - 自分で書いた契約テストが**コメントに当たって**素通りした
- **独立点検を厚くしたことが効いた。** cross 点検が must 2 件、review 4 ラウンドが must 3 件。
  **どのラウンドも手ぶらで帰ってこなかった。**
- **「pass」と書いた主張を、証拠の範囲に戻した。** ラウンド 4 が AC9 の反例を 10 通り実測したとき、
  requirements の側を狭めて事実に合わせた（decisions D11）。
  `AGENTS.md` 判断の原則 3 がこういう場面のためにあると実感した。

## 課題 / 手戻り

### 1. 5250 に足したら 3270 を忘れる、を 3 回

`paired-artifact-sync` の `!` 付きが**この work だけで 7 件**。しかも**同じ修正の中で 2 回繰り返した**:

| | 起きたこと |
|---|---|
| ラウンド 1 | `fields[].field` の検証を `resolveField` に足し、「値がホストへ向かう 1 本の漏斗」と書いた。**それは 5250 の漏斗だった**（3270 は `applyFields` という別の漏斗） |
| ラウンド 2 | 検証を共有モジュールへ寄せ「両方の入口から呼ぶ」ようにした。**呼ぶ位置が違った**——3270 は `"value" in f` を検証より前に置いており、要素がプリミティブだと素の `TypeError` に文字列が載った |
| ラウンド 3 | 要素は守ったが**容れ物**（`fields` そのもの）が素通し。しかも 5250 と 3270 が**同じ入力に別の答え**を返していた |

**前段で防げたか**: 防げた。research F2 の棚卸しが `type:"key"` の 5250 経路だけを見ており、
**3270 の同型を数えていない**。design も「対象範囲」の表に 3270 を 1 行も書いていない。
`tn3270-adapt.ts` は `WsKeyField` を共有しているので、**型を共有している資産は対にして数える**
だけで気づけた。

### 2. テストの入力の「形」が狭く、同じ欠陥を 2 ラウンド見逃した

上の 2 回目・3 回目を見逃した**直接の原因**はこれ。回帰テストは

```ts
for (const field of [marker, { index: marker }, { row: marker, col: 1 }, null, []])
  applyFields(session, [{ field, value: "x" }])   // ← いつも {field, value} に包んでいる
```

と `field` の**中身**だけを振っており、**要素そのものがプリミティブ**な形も、
**容れ物が配列でない**形も一度も試していなかった。コードは正しく見えるのに、
テストが見ている面が狭いので緑になる。

**前段で防げたか**: tasks の「テスト方針」は「値が 1 文字も含まれない」「位置が入る」という
**性質**しか書いておらず、**どんな入力を流すか**を書いていない。ここに
「壊し方の形（プリミティブ / 配列 / null / 型違い / 容れ物）」を入れていれば防げた。

### 3. 棚卸しが自分で範囲を狭め、その狭さが後段まで残った

decisions D4 は「`type:"key"` 経路の例外を洗った」と**経路を限定して**書いた。
一方 AC9 は経路を限定していない。この食い違いが `gui-select` / `gui-submit` /
`macro-store` / `sessionId` / `watchId` を**「棚卸し済み」に見せたまま**外に置いた。
ラウンド 3・4 はどちらも**この隙間**を突いている。

**教訓**: 棚卸しの範囲を狭めるのは構わないが、**受け入れ基準の側と範囲を揃える**か、
揃わないなら**その差を基準に書く**。今回は最後に D11 で揃えた（が、4 ラウンド遅れた）。

### 4. 「AC9 pass」を 4 ラウンド書き続けた

`test-result.md` に pass と書いたとき、**欄の経路しか試していなかった**。
経路を限定していない基準に対して、限定した証拠で pass と書いた——
`AGENTS.md`「主張が証拠の範囲を超えていない」に反する。
ラウンド 4 が生 JSON を流して初めて反例が出た。

### 5. 記録漏れ: 差し戻し 1 回が metrics に残っていない

**`sent_backs` は 2 だが、実際には 3 回差し戻している**（08:21:33 の 1 回が欠けている）。

原因は**自分のコマンドの書き方**。`aidev event review sent_back >/dev/null 2>&1;` と
**出力を捨てて `;` で繋いだ**ため、ガードが exit 2 で止めたことに気づかなかった。
ガードは正しく働いている——`review.md` に**そのラウンドの指摘を書く前に**記録しようとしたので、
「理由が残らない順序」として拒否された（`aidev` の `sb_marks_at_start` 検査）。

**後から打ち直して辻褄を合わせない**（`protocol.md`「8.」）。
この retro に**欠落そのものを事実として残す**に留める。
以後の所要時間・手戻りの集計では、この work の `sent_backs` は**実際より 1 少ない**と読むこと。

## 改善提案

### 製品 / コード（→ backlog）

deliver で 5 件を起票済み（AC9 の範囲外・3270 のキー案内・`msg.cursor`・`INTERNAL_ERROR` の語彙・
`msg.selected`・監査ログの `key`・既存 flake）。**この retro から 1 件追加する**——
ws の入力検証を**網羅的に走査するテスト**（下記で `aidev backlog add` 済み）。

### PJ プロセス / 規約（→ `.aidev/conventions/`。AGENTS.md 本体には書かない）

**(a) `paired-artifact-sync` は条項を足さない。層を下げる。**

`!` 付きが**この work だけで 7 件**、条項の母集団は 11（`need` 5 を超えて `ready`）。
これは「**規約はあるのに守られていない**」であって、文章を足しても効かない
（`protocol.md`「12.」の判別）。打ち手は**機械で止める**こと:

- `WsKeyField` のように **5250 と 3270 が共有する型**を入口に持つ関数を走査し、
  **片方にしか検証が掛かっていない**組み合わせを落とすテスト。
- 実際、この work で 3 回とも「**共有している型の、対になる呼び出し元**」が抜けていた。
  対象は型で機械的に引けるので、散文より確実。

**(b) 新しい条項を 1 つ起こす: `test-input-shape`（テストの入力の形を振る）**

- **仮説**: 回帰テストを足すとき、**壊し方の形**（プリミティブ / 配列 / `null` / 型違い /
  容れ物そのもの）を振ると、同じ欠陥を別の形で見逃す差し戻しが減る。
- **baseline**: この work では must 3 件のうち **2 件**が「入力の形を振っていなかったため
  1〜2 ラウンド見逃した」もの。以後の work で
  「入力の形が狭かったことに起因する差し戻し」の件数を数える。
- `verify-by-mutation` と**対になる**——あちらは「実装を戻すと落ちるか」、
  こちらは「**入力を変えても捕まえるか**」。今回は前者だけ掛けて後者が抜けていた
  （変異注入は全部通ったのに、入力の形を変えたら穴が出た）。
- **既存ドキュメントとの重複は機械的に確かめていない**——`.aidev/config.yml` に
  `docsRoots` が未設定で、`aidev convention new` が確認できない旨を警告した。
  目視では `docs/` に同趣旨の記述は見当たらなかったが、**走査はしていない**
  （`protocol.md`「8.」——捏造で埋めない）。

**(c) `comment-provenance` は効いている側**

`!` 付き 2 件・言及 5 件で、いずれも**この work が書いた注記が work の途中で偽になった**もの
（`JSON.stringify(value)` の参照が 4 か所・`wsErrorNotice` の注記が 3 か所）。
条項が無ければ気づかれずに残っていた。母集団は 11 で `ready`。
**効果判定は retro の範囲外**なので `/aidev-util-insights` へ送る。

### ハーネス自体（→ `aidev-*` への提案・適用は人間）

- **差し戻しの「拒否」を記録に残せないか。** 今回 `event review sent_back` はガードが
  正しく exit 2 で止めたが、**metrics には何も残らない**ので、後から見ると
  「差し戻しが 2 回だった work」にしか見えない。
  **拒否そのものを `event: sent_back_refused` として刻む**と、記録の欠落が
  「静かに 1 減る」のではなく「**拒否された跡**」として見える。
  今回は自分が出力を捨てたのが直接の原因だが、**出力を捨てても残る**のが記録の価値。
- **`aidev verify` が review のラウンド数と `sent_back` の数を突き合わせられないか。**
  `review.md` に「## ラウンド N」が 5 つあるのに metrics の `review sent_back` が 2 件、
  という食い違いは機械で見える。WARN で足りる。
- **`approve review` の件数を手で渡すのをやめられないか。** いまは
  `must=3 should=18 nit=24` を人が数えて渡すが、`review.md` の行頭タグを数えれば出せる。
  今回、手で数えた値と `grep -cE '^- \[should\]'` の値が食い違った
  （cross 点検の指摘が同じファイルに同じ書式で並んでいるため）。
  **母集団が違うものが同じファイルに同じ書式で並んでいる**のが原因なので、
  cross 点検のログは書式を分ける（例: `- (check)[...]`）ほうが機械にも人にも読める。
