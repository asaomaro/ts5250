# 仕様: 認証を有効にしたときのサービスの見え方・操作可否

## 概要

**検証が主で、修正は検証が見つけたものだけ**にする。認可の設計は動かさない。

## 検証の作り

`scripts/verify-service-auth.mjs`——`buildApp` に `auth: { enabled: true, ... }` を渡して
**認証ありのサーバーを 1 本立て**、admin と一般ユーザーの 2 つのブラウザ文脈で見る。

資格情報は**この検証専用の使い捨て**（`UserStore` にメモリで足す）。実機のものとは無関係。

### 4 番目が要点

ボタンを消しただけなら、開発者ツールから叩けば通ってしまう。**画面を迂回して WS へ直接送り**、
サーバーが断ることを見る。さらに**サーバー側の状態が変わっていないこと**まで確かめる
——「エラーが返った」だけでは、止めたうえでエラーを返した可能性を潰せない。

## 検証が見つけたもの（＝この作業の修正）

### 1. 一般ユーザーはサービス一覧に辿り着けない

ランチャーの「アプリ」段は**システムを選んだ後**にしか出ない。ところが
サーバー設定のシステムは admin にしか見えないので、**一般ユーザーは選べるシステムが 0 件**で
「システムがまだありません」から先へ進めなかった。

**アプリ段はシステムの選択に依存しない**——扱うのは IBM i のデータではなくこのアプリだから。
段を外へ出す。

### 2. `printer-stop` の拒否が返らず、プロセスが落ちる

```ts
private onPrinterStop(msg): void {
  void withAudit({ op: "ws_printer_stop" }, async () => { ... });  // ← 捨てている
}
```

`void` で promise を捨てると 2 つ壊れる:

- 拒否が**利用者に返らない**（`handle()` の catch が `error` を送る経路を迂回する）
- **未処理の rejection でプロセスが落ちる**

`async` にして `await` する。**「認可が効いている」だけでは足りない——効いたことが呼んだ側に届く**
必要がある。

### 3. `UserStore` / `SessionStore` が公開されていない

認証ありのサーバーを外から組めなかった。**認可が効いているかは認証を有効にしないと測れない**
ので、実体を `@as400web/server` から出す。
