## 受け入れ基準ごと

| 基準 | 結果 |
|---|---|
| UTF-8（1208）で新規保存 → タグ 1208 | **合格**（実機） |
| EBCDIC（1399）で新規保存 → タグ 1399 | **合格**（実機） |
| 既存ファイルの上書きでタグが変わらない | **合格**（1208 のまま） |
| 修正前の挙動を実測として記録 | 合格——**実機の既定は 1041**（backlog の「850」は PUB400 の値） |
| `writeFile` のコメントが実態と合う | 合格（「通常経路は指定しない」を削除） |
| build / lint / test | 合格 |

## テストが「指定を落としたこと」を検出できるようにした

偽の接続の `writeFile` は**長さしか記録していなかった**。`dataCcsid` を渡し忘れても
書き込み自体は成功するので、**長さだけ見ていると気づけない**。
`ccsid=…` まで記録するようにして、経路が渡していることを固定した。

- utf8 の既定 → `write /d/f 3 ccsid=1208`
- `ccsid: 37` 指定 → `write /d/f 4 ccsid=37`
- base64 → `write /d/f 2`（**タグを付けない**）

## 未検証の穴

- **効果は新規作成に限られる**。既存の嘘タグ（実機に既にあるファイル）は直らない。
  `dataCcsid` は置き換えでは効かず、**それは望ましい性質**（他人のファイルを勝手に
  付け替えない）なので回避していない
- **アップロード経路（`entries` の一括置き）は触っていない**。バイト列をそのまま置く
  経路で、文字コードが分からないため
- **base64（バイナリ）にタグを付けるか**は決めていない。65535（バイナリ）で
  タグ付けする案はあるが、既存のアップロード物の扱いにも影響するので別の判断
- **PUB400（7.5）では未確認**。既定タグが機械ごとに違う（1041 / 850）ことは分かったが、
  `dataCcsid` の採用が版数に依るかは測っていない
- **画面（web-ui）からの保存では通しで確かめていない**。API の単体テストと
  ライブラリ経由の実機確認まで
