# 要件: IFS に新規作成するファイルのタグを中身と合わせる

## 背景 / 課題

backlog `hostserver.md`:

> IFS の書き込みで `dataCcsid` を明示し、新規作成ファイルのタグを中身と合わせる
> → 現状は 0（サーバー既定）で開くため、UTF-8 を書いても **850 のタグ**が付く。
> 読む側は決定表①（中身推定）で救えているが、**他ツールから見ると嘘のタグのまま**。

`IfsConnection.writeFile` には `dataCcsid` の受け口が**既にある**（`20260723` decisions D5）が、
サーバー（`/api/host/ifs/write`）が渡していない。テキスト保存の経路は
**どの CCSID で符号化したかを知っている**（`body.ccsid ?? 1208`）のに、
それをタグに反映していない。

`IfsTextFile.ccsid` のコメント自身がこう書いている——
**「タグは中身を説明しているとは限らない——我々が書いた UTF-8 のファイルに 850 が付く」**。
自分で嘘のタグを付けている側を直す。

## 目的 / ゴール

**新規作成するテキストファイルのタグを、実際に書いた文字コードに合わせる。**

## スコープ

### 対象

- サーバーのテキスト保存経路が `dataCcsid` を渡すようにする
- 実機でタグを確認する（修正前後）
- `writeFile` の「通常経路では指定しない」というコメントを実態に合わせる

### 対象外

- **既存ファイルのタグの付け替え**。`dataCcsid` は新規作成時にしか効かない
  （置き換えでも実機は元のタグを保つ——`20260723` で確認済み）。
  **他人のファイルのタグを勝手に変えない**のは望ましい性質なので、そのままにする
- **base64（バイナリ）経路**。文字コードの概念が無い。
  バイナリを 65535 でタグ付けするかは別の判断
- CSV アップロード経路（バイト列をそのまま置く）
- 読む側の決定表（既に中身推定で救えている）

## 機能要件

- テキストで保存した**新規**ファイルのタグが、符号化に使った CCSID と一致する
- **既存ファイルのタグは変わらない**（置き換え保存でも）
- 保存できる文字コードの範囲・行末・BOM の扱いは変えない

## 非機能要件 / 制約

- 実機に置いたファイルは消す
- 実資格情報を成果物・コミット・PR に書かない
- 既存テストが通ること

## 完了条件 (受け入れ基準)

- [ ] 実機で、UTF-8（1208）で新規保存したファイルに **1208 のタグ**が付く
- [ ] EBCDIC（例 1399）で新規保存したファイルに **1399 のタグ**が付く
- [ ] **既存ファイルを上書きしてもタグが変わらない**ことを実機で確認
- [ ] 修正前の挙動（850 が付く）を実測として記録している
- [ ] `writeFile` のコメントが実態と合っている
- [ ] `npm run build` / `npm run lint` / `npm test` が通る
- [ ] backlog が更新されている

## 未確定事項

- **実機が本当にタグを付けてくれるか**。`dataCcsid` は要求に載せているが、
  新規作成時にホストがそれを採用するかは**実測していない**（受け口があるだけ）
