# 調査: host_call_program の正常系（実機）

実機 **実機（IBM i 7.3）**。再現は `scripts/research-call-program.mjs`（**副作用なし**）。

## 選んだ API

| API | 書式 | 検証できること |
|---|---|---|
| `QUSROBJD` | `OBJD0100` | `QSYS/QCMD (*PGM)` の**名前・ライブラリ・種別**が受け取り変数から読める |
| `QSYRUSRI` | `USRI0100` | **サインオンしているユーザー名**が読める |

どちらも読み取り専用で、**返った値を外部の事実（呼んだ対象そのもの）と突き合わせられる**。
「エラーが出ない」だけの確認では、**間違った位置を読んでいても気づけない**。

## F1. 正しいパラメータ列なら通る

```
### QUSROBJD（オブジェクト記述）
  rc=0x0 success=true
  bytesReturned=90 bytesAvailable=90
  object=QCMD library=QSYS type=*PGM
```

`MCH0802`（パラメータ数不一致）は出ない。**受け取り変数の中身が期待どおり**。

`QUSROBJD` のパラメータ列（6 個）:

1. 受け取り変数（**出力**・長さ 200）
2. 受け取り変数の長さ（入力・`Binary(4)`）
3. 書式名（入力・`Char(8)` = `OBJD0100`）
4. 修飾オブジェクト名（入力・`Char(20)` = 名前 10 ＋ ライブラリ 10）
5. オブジェクト種別（入力・`Char(10)` = `*PGM`）
6. エラーコード（入力・先頭 4 バイトを **0** ＝「例外で知らせる」）

**文字列は EBCDIC・右空白詰めの固定長**。長さは 4 バイトのビッグエンディアン。

## F2. 書式の違う API でも同じ形で通る

```
### QSYRUSRI（ユーザー情報）
  rc=0x0
  user=USER
```

`USRI0100` でもオフセット 8 から 10 バイトがユーザー名。**1 つだけだと偶然かもしれない**ので
2 つ目で確かめた。

## F3. 出力の位置合わせは説明どおり

```
outputs = [<100B>, null, null, null, null, null]
```

- **要求したパラメータ数だけ返る**（6 個）
- **出力パラメータの位置に中身がある**（1 番目）
- **入力パラメータの位置は null**

MCP ツールの説明「出力パラメータは要求した順で返る前提で位置合わせしている」は
**実機で裏づいた**。

## 結論

**実装は正しい。コード変更は不要。** 足りなかったのは成功例だけだった。
