## うまくいった点

- **「利用者の協力が前提」という制約を、測れる形に変えた。** ACS の HACL（ECL）を自作の Java から呼べば、GUI 無しで ACS のコアを実機に当てられると分かった。
  これで `acs-parity.md` の 2 項目（CURSORCL3 の実測比較・ヒューリスティックの是非）が「利用者に ACS を起動してもらう」前提から外れ、その場で判定できた。
  **調査の手段を先に作ると、止まっていた項目がまとめて動く。**
- **判定を「現物」に寄せた効果が大きかった。** 16 件のうち 9 件が対応不要で、そのうち 3 件は起票時の前提が現状と食い違っていた。
  works や backlog の記述を根拠にしていたら、どれも「対応要」のまま残っていた。
- **委譲の結果に「検証の深さ」（◎ ○ ◐ △）を付けたこと。** 3 領域を 3 つの委譲先に分けて調べさせたが、主エージェントが再確認した範囲と、報告だけに拠る範囲を区別して記録できた。
  △ の項目には「着手時に両側を再確認」と書いてあるので、次の work が誤った前提から始まらない。
- **タスクをまたぐ点検（cross）が 15 件を拾った。** タスク単位の点検は 1 件も発火しなかった（発火条件に当たらなかった）ので、この work で欠陥を拾った層は cross だけだった。
- **計測を疑って取り直したこと。** 2 回とも、最初の値のままなら誤った記録を残していた（decisions D4・D10）。

## 課題 / 手戻り

- **review の差し戻し 2 回（should 14 件）は、すべて新しく足したスクリプトに対するものだった。**
  台帳・突き合わせ表（この work の主目的）への指摘は 0 件。
  - 原因: スクリプトは scratchpad の試作をそのまま整えたもので、**coding の中で点検を受ける機会が無かった**。
    タスク単位の点検（`aidev-40-coding` 手順5）の発火条件は「`対象: 未特定`／アンカーが外れた／共有モジュール・公開 API」で、
    **新しく足した実行可能な資産（`scripts/`）はどれにも当たらない**。
  - 前段で防げたか: 防げた。design の時点で「scratchpad の試作を移す」と決まっていたので、そこで点検の対象に含めると決めておけばよかった。
- **ラウンド 1 の修正が、ラウンド 2 の should 2 件（退行）を生んだ。**
  `catch (Exception)` と、サインオンの成否を見ない `signon` は、どちらも「偽の合格を出さない」という同じ不変条件を支える箇所だった。
  ラウンド 2 で protocol の促し（「同じ不変条件を支える項をすべて列挙して壊してみる」）に従って 5 箇所をまとめて直した結果、ラウンド 3 は should 0 になった。**促しが実際に効いた。**
- **最初の実測が 2 回とも使えなかった。**
  - 負荷の高い最中に測った待ち時間（p50 465ms）は、落ち着いてから 72〜137ms だった（decisions D4）。
  - 半開きの検証は、中継がサーバー側の閉鎖をブラウザへ伝えていて、**欠陥を隠していた**（decisions D10）。
  - どちらも「計測器そのものが正しいか」を確かめる前に値を記録しかけた。
- **台帳の出典に、リポジトリの外にしかないラベルを書いた**（`委譲先 D の L1〜L15` など）。
  `comment-provenance` の違反 2 件はこれと、research に無い数値の引用。**条項は既にあるのに守れなかった**ので、追記ではなく層を下げる（走査で検知する）べき類型。
- **backlog の陳腐化が速い。** sharedFiles の項目は、起票から 9 日で対象の 4 ファイルが常連から外れていた（0〜1 回まで低下）。
  「未着手の項目は、時間が経つほど前提が崩れる」ことが数字で出た。

### PJ プロセス / 規約（→ `.aidev/conventions/` の条項）

- **条項を起こす**: `measurement-sanity`（実測値を記録する前に、計測器そのものを疑う）
  - 仮説: 実測値を記録する前に「同じ条件でもう一度取る」「計測器（中継・時計・負荷）が結果を作っていないか」を確かめれば、誤った値を記録に残す事故が減る。
  - baseline: この work で 2 件（decisions D4・D10）。どちらも最初の値のままなら、誤った事実が research と台帳に残っていた。
  - 根拠にした指摘: `[conv:-]` の 52 件のうち、計測の妥当性に関わるもの（review ラウンド 1 の「S4 の値がどちらの中継のものか読み取れない」ほか）。
- **条項を起こさない**（規約はあるが守られていない類型）: `comment-provenance` の違反 2 件。
  追記しても効かないので、**層を下げる**（上の走査の起票がその手当て）。

### ハーネス自体（→ aidev-* への提案・適用は人間）

- **タスク単位の点検の発火条件に「新しく足した実行可能な資産」を加える**（`aidev-40-coding` 手順5）。
  - この work では、指摘 22 件（should 14・cross の一部）がすべて `scripts/` に集中したのに、タスク単位の点検は 1 件も発火しなかった（`task_checks=0`）。
  - 共有モジュール・公開 API と同じく、**新しく足した実行可能なファイル**（`scripts/` / `tools/` / `bin/`）は、その場で点検する価値が高い。review まで持ち越すと、差し戻しが 1 往復増える。
- **`aidev status` に「起票からの経過」を出す**（または `doctor` が古い未着手項目を催促する）。
  - 根拠: 16 件中 9 件が対応不要で、うち 3 件は前提が崩れていた。sharedFiles は 9 日で対象が総入れ替えになった。
  - 「未着手のまま N 日経った項目は、着手前に前提を確かめる」を機械が促せる。
- **委譲した調査の結果に「検証の深さ」を付ける形を、protocol の側に置く**（`protocol.md`「2.6」）。
  - この work では research の中で独自に定義した（◎ ○ ◐ △）。同じ問題（一次資料との照合を委譲に任せ切らない）は他の work でも起きるので、書式を共通化すれば、次の work が「どこまで確かめた結果か」を読み違えない。
- **`aidev metrics` の `idle_sec` の扱い**（参考）。
  - この work は待ち 75,247 秒（全体の 94%）で、その大半は実機の計測（1 回 2〜7 分）と委譲の待ちだった。
  - `work_sec` と `idle_sec` を分けて出しているのは正しいが、**実機を伴う work は「待ちが長い」ことが常態**なので、横断で比べるときは実機の有無で層を分けないと読み違える（insights への申し送り）。
