# 要件: backlog 全件の要否判定と ACS との差異の洗い出し

## 背景 / 課題

- 未着手の backlog が 16 件ある（`session-lifecycle.md` 8・`code-quality-checks.md` 4・
  `acs-parity.md` 3・`pc-command.md` 1。2026-09-19 の `aidev status`）。いずれも起票時の見立てのままで、
  **今も本当に対応が要るのかを誰も確かめていない**。
  - **backlog は現状より遅れる。** 2026-08-01 の棚卸し（`20260801-backlog-audit`）では 41 件中、閉じ忘れが 5 件、
    一部だけ済んでいたものが 2 件あった。
  - **起票時の前提が誤っていたこともある。** `acs-parity.md` の SEU PageUp/PageDown の件は
    「ACS に未知のロジックがある」と見立てたが、実際は当 PJ の分岐（PR#387）が誤って発火していた。
    「この開発環境に ACS が無い」という記述も誤りだった。
- ACS 本体（`IBMiAccess_v1r1/acsbundle.jar`）がプロジェクトのルートに置かれ、デコンパイルして読めるようになった。
  ACS との突き合わせはこれまでに 5 つの領域で行い、**その都度、実害のある欠陥が見つかっている**:
  - WTD のオーダー（0x1E の未対応）
  - 入力検証（数値欄の空白）
  - IC/MC の確定単位
  - DBCS / 自己点検の FCW
  - 表示設定

  これら以外の領域は**まだ突き合わせていない**。同じ種類の欠陥が残っていても、利用者が遭遇するまで気づけない。
- 本 PJ は ACS / 5250 端末の**代替**である。仕様上は正しくても ACS と挙動が違えば、利用者には不具合に見える
  （`AGENTS.md`「既存クライアントと同じ挙動を優先する」）。

## 目的 / ゴール

- 未着手の backlog 16 件それぞれについて、**「今も対応が必要か」が現物の根拠付きで決まっている**状態。
  台帳もその判定どおりに更新されている。
- ACS のコアのうち、まだ突き合わせていない領域について**実害のある差異が洗い出されている**状態。
  差異は次の作業の requirements にそのまま使える粒度で台帳に並んでいる。

## ユーザーストーリー

- US1: 保守者（利用者）として、backlog の各項目が今も対応を要するのかを根拠付きで知りたい。
  なぜなら、台帳は遅れたり前提が誤っていたりするので、そのまま選ぶと完了済みの項目や
  前提の崩れた項目に着手して手戻りするから。（受け入れ: AC1, AC2, AC3, AC4）
- US2: ACS から移行する利用者として、ACS と挙動が違う箇所のうち実害のあるものが先に見つかっていてほしい。
  なぜなら、未発見の差異は遭遇するまで気づけず（WEA・0x1E の実例）、遭遇したときには
  業務画面が壊れて見えるから。（受け入れ: AC5, AC6, AC7）
- US3: 次の作業に着手する開発者（AI エージェントを含む）として、対応が要る項目が優先度・再現条件・根拠付きで
  台帳に並んでいてほしい。なぜなら、そのまま次の work の requirements に使えれば、
  同じ調査をやり直さずに済むから。（受け入れ: AC8）

### 対象外

- **対応が要ると判定した項目の修正**: 項目ごとに別の work として起こす。この work では優先度を付けて台帳に残すまでにとどめる。
  再接続周りは影響範囲が広いので、判定と修正を 1 つの PR に束ねない。
- 既に突き合わせを終えた領域の再調査。既存の結果を参照するのはよい。対象となる領域:
  - WTD のオーダーと `PS5250.addChar()`
  - `Field5250` の文字種の検査
  - IC/MC の確定
  - FCW（DBCS / 自己点検）
  - `ScreenText` の表示設定と配色
  - PR #404 で実測を取り込んだ項目
- 旧形式（schema 3）の work 14 件の整理と、deliver 済みでマージ待ちの HELD 項目。
- TN3270・VT: ACS 5250 の代替という主題の外にある。

## 機能要件

- FR1: 16 件それぞれに、次のいずれかの判定を付ける。
  - **対応要**: 欠陥や差異が現物に今もあり、利用者か開発者に実害が及ぶ経路がある
  - **対応不要（解決済み）**: 後の作業で既に解消している
  - **対応不要（差異なし・実害なし）**: 起票時の前提が誤っていた、または到達する経路が無い、あるいは費用に見合う効果が無い
  - **保留（外部条件）**: 本 PJ から届かない条件が要る。その条件を明記する
- FR2: 判定の根拠は現物で取る。
  - 根拠に使えるもの: 現在のコード（`file:line`）、テストの実行結果、実測値、ACS のクラスとメソッドの名前
  - works や backlog の記述は手掛かりとして読むだけで、根拠にしない
- FR3: 実測が要る項目は実測する。実測できなかった場合は、理由と必要な条件を記録する。
- FR4: 新規洗い出しの進め方
  - 突き合わせる領域（ACS 側のクラス・メソッド ↔ 当 PJ 側のモジュール）を一覧にし、領域ごとに結果を記録する
  - 見つかった差異には次の 2 点を付ける
    - 利用者から見た影響（どの操作・画面で、どう見えるか）
    - FR1 と同じ区分の判定
- FR5: 判定結果を台帳へ反映する（`AGENTS.md`「記録の同期」に従う）。
  - 対応不要の項目
    - `- [x]` にして根拠を併記する
    - 事実と食い違う記述は取り消し線で残す
  - 対応要の項目: 確かめた事実で書き直し、優先度を付ける
  - 一部だけ済んでいる項目: 分割して兄弟として並べる
  - 新しく見つかった差異: 適切な backlog ファイルに `- [ ]` で起票する

## 非機能要件 / 制約

- **製品コード（`packages/*`）は変更しない。** 修正は対象外のため。
  調査用のスクリプトは scratchpad に置く。リポジトリに残す価値がある検証スクリプトは、design で判断する。
- **ACS の原典をリポジトリに入れない**（`AGENTS.md`「ライセンスと出典」）。
  - 対象: `IBMiAccess_v1r1/`（`.git/info/exclude` 済み）と、デコンパイルした結果（scratchpad に置く）
  - 記録には、ACS のクラスとメソッドの名前、および振る舞いを自分の言葉で書く。コードの逐語的な引き写しはしない
- **実機の作法**
  - 装置名は使い回す
  - 作った検証用オブジェクトは片付ける
  - 利用者の実機ライブラリに手を入れる必要が出たら、事前に確認する
  - 実機の識別子は `.env.verify` から取り、`.env` は読まない
- 記録に秘密（パスワード・鍵）や実機の固有名詞を書かない（`AGENTS.md`「セキュリティ」「実機の識別子」）。
