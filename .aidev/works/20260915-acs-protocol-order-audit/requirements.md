# 要件: ACS のコア実装（DS5250/PS5250）と突き合わせた5250プロトコル処理の棚卸し（第1弾）

## 背景 / 課題

利用者から「全体的に ACS を手本に見直しを図ってください」との要望（2026-09-15）があり、
スコープが大きいため、まず対象範囲を絞り込むことにした
（`.aidev/backlog/acs-parity.md`）。絞り込みの結果、**最も着手しやすい対象**として
「プロトコル仕様そのものの突き合わせ」（実機・ACS 起動のどちらも不要、ACS のデコンパイル済み
コア実装との机上比較で完結する）を選び、この work の対象とする。

具体的には、`20260914-dspfmt-field-underline-instability` で見つかった WEA（0x12）のような
「未実装のまま `default:`（未知オーダー）節に落ちているオーダー」が他に無いかを、ACS の
デコンパイル済みコア（`DS5250.processWriteToDisplay()` のオーダー switch、`PS5250.addChar()`
の文字書き込み処理）と、このリポジトリの `wtd-applier.ts` を1バイト値ずつ突き合わせて
機械的に洗い出す。ACS のデコンパイル自体は `20260914-seu-page-cursor-hold`
（`decisions.md` D6）で実施済みで、`20260914-dspfmt-field-underline-instability` は
その成果（デコンパイル済みソース）を使って WEA の欠陥を1件見つけた——この work は
**同じ成果物を使って対象範囲を広げた第2弾**にあたる。

### 判明した事実（この work の事前調査。requirements 承認前に実施済み）

- F1: ACS の `DS5250.processWriteToDisplay()` のオーダー switch は
  `case 1, 2, 3, 16, 17, 18, 19, 20, 21, 29`（10進）＝ `0x01, 0x02, 0x03, 0x10, 0x11,
  0x12, 0x13, 0x14, 0x15, 0x1D`（16進）を扱う。これは `wtd-applier.ts` の
  `ORDER` 定数（`SOH, RA, EA, TD, SBA, WEA, IC, MC, WDSF, SF`）と**完全に1:1で一致**する
  （確認場所: 決定コンパイル済みソースの該当 switch 文、`wtd-applier.ts` の
  オーダー switch 全体）。
- F2: ACS の switch に一致しなかったバイト値は、`default` 相当の処理として
  `var21_13`（表示データのバッファ）へ蓄積され、`PS5250.writeString()`→`addChar()` で
  画面へ書き込まれる（＝**「未知オーダー」として捨てるのではなく、表示データとして
  扱う**）。`addChar()` 内の文字変換処理に次の特殊な置換がある:
  `this.TextPlane[n + n3] = sArray[n3] == 28 ? 42 : (sArray[n3] == 30 ? 59 : (char)this.codepage.sb2uni(...))`
  ——**バイト値 28（0x1C）は文字コード 42（`*`）へ、バイト値 30（0x1E）は文字コード
  59（`;`）へ置換して表示する**。0x1C はこのリポジトリの `ORDER.UNKNOWN_1C` として
  既に対応済み（過去に ACS の表示結果とのスクリーンショット突き合わせで発見・実装
  済みだったが、当時はソースコードでの裏付けが無く「正体未確認」と記録されていた）。
  **0x1E は現在このリポジトリで一切対応しておらず、`wtd-applier.ts` の main loop の
  どの分岐にも該当せず `default:`（未知オーダー扱い）に落ちる**——WEA と同種の、
  同じ WTD 内の以降の全データが失われる欠陥になっている
  （確認場所: 上記デコンパイル済みソースの `addChar()` 該当行、
  `wtd-applier.ts` の main loop 全体）。

## 目的 / ゴール

WTD（Write To Display）データストリーム中に現れうる各バイト値（オーダーコード・表示データ）に
対する処理が、ACS の実際の実装と機能的に整合している状態。特に、「未対応のバイト値に遭遇すると
同じ WTD 内の以降の全データが失われる」という `default:` 節の破壊的な復旧処理に、
本来は対応が要るバイト値が誤って落ちていない状態。

## ユーザーストーリー

- US1: 実機の様々な画面を操作する利用者として、まだ見つかっていない「特定のバイト値が
  混ざると画面の続きが表示されなくなる／応答待ちで固まる」不具合が無い状態を望む。
  なぜなら、WEA（`decisions.md` D1、`20260914-dspfmt-field-underline-instability`）のような
  未実装オーダーによる取りこぼしは、遭遇するまで気づけない潜在的な不具合であり、
  同種のものが他に残っていれば同じように利用者の操作を妨げるから。（受け入れ: AC1, AC2）
- US2: 開発者として、ACS のコア実装という信頼できる比較対象が手に入った今、
  推測ではなく実際のソースコードの突き合わせによって、このプロジェクトの
  プロトコル処理の正確性を体系的に検証したい。なぜなら、5250 の公式仕様書
  （SC30-3533）に直接アクセスできない中、ACS の実装こそが「実機が本当に送ってくる
  可能性のあるバイト列に対して、実際に動いている実装がどう振る舞うか」を示す
  最も信頼できる参照だから。（受け入れ: AC3, AC4）
- US3: 開発者として、この修正が既存の実機トレース・合成テストで確認済みの
  他の挙動（0x1C の表示、実機 fixture の再生等）を壊さないことを確認したい。
  なぜなら、`wtd-applier.ts` の main loop は多くの既存シナリオが通る共有経路であり、
  0x1E を新たに特別扱いする変更が意図せず他のバイト値の処理へ波及するリスクが
  あるから。（受け入れ: AC5）

## スコープ

### 対象

- ACS のデコンパイル済みコア（`DS5250.processWriteToDisplay()` のオーダー switch 文、
  `PS5250.addChar()` の文字書き込み処理）と、`packages/tn5250/src/protocol/wtd-applier.ts`
  のオーダー処理・表示データ処理を、バイト値単位で突き合わせる机上調査
  （「判明した事実」F1・F2 の通り実施済み）。
- 上記調査で見つかった具体的な欠陥（F2 の 0x1E 未対応）の修正。

### 対象外

- ACS の UI 描画層（Swing 側）の調査（コアのデコンパイルでは追えない。
  `.aidev/backlog/acs-parity.md` の別項目——見た目のヒューリスティックの是非——の対象）。
- 実機・ACS の同時比較によるトレース採取（この work は机上調査に閉じる）。
- AID キー処理・キーボードからホストへの応答生成（この work は WTD＝ホストからクライアントへの
  データストリームの受信処理に閉じる）。
- FFW（Field Format Word）ビットの詳細な突き合わせ、属性バイト表（`ATTR_TABLE`）の
  網羅的な再検証（`.aidev/backlog/acs-parity.md` の DSPFMT 項目で個別に扱う）。

## 機能要件

- ACS の `DS5250.processWriteToDisplay()` のオーダー switch と `wtd-applier.ts` の
  `ORDER` 定数・switch 文の対応関係を確認する（F1 の通り完了済み、両者は1:1で一致）。
- WTD 中にバイト値 0x1E が現れたとき、`default:`（未知オーダー扱い）に落とさず、
  ACS と同じくセミコロン `;` へ置換した表示データとして扱う処理を追加する（F2）。
- 既存の `ORDER.UNKNOWN_1C`（0x1C）の実装はそのまま維持しつつ、F2 で判明した
  事実（ACS の `addChar()` における文字置換であり、「未知オーダー」の一種ではない）を
  踏まえてコードコメントを更新する。

## 非機能要件 / 制約

- 修正は `packages/tn5250` 内部実装に閉じ、公開 API・型シグネチャの破壊的変更を
  伴わない見込み（design で確認し、AC5 の回帰確認テストで裏付ける——公開 API の
  破壊的変更は既存テストの型検査・実行時失敗として現れるため、専用の AC は立てず
  AC5 に含める）。
- 推測のみでの修正をしない——全ての判断は ACS のデコンパイル済みソースコードの
  該当箇所（クラス名・メソッド名・行の抜粋）を根拠として明記する。

## 完了条件 (受け入れ基準)

  同一 WTD 内の全オーダーが失われる）。

  更新する。
- [ ] AC3: ACS のオーダー switch（`DS5250.processWriteToDisplay()`）と `wtd-applier.ts`

## 未確定事項 / 確認したいこと

- 0x1E がこのリポジトリの既存の実機トレース（`packages/tn5250/test/` の各種 fixture・
  診断スクリプトのログ）で実際に観測されたことがあるかは未確認——0x1C と異なり、
  この work の事前調査時点では実機での目撃例が無い（ACS のソースコードの読解のみに
  基づく発見）。design/coding で確認する。
