# 判断記録

## D1: `ORDER.UNKNOWN_1C`/`ORDER.UNKNOWN_1E` の実装構造は作り替えず、
既存のオーダー switch の枠組みのまま維持する

- 背景: `research.md` F2・F3 で、ACS のデコンパイル済みコア（`PS5250.addChar()`）を
  確認したところ、0x1C・0x1E は実は「オーダー」ではなく、表示データを書き込む際に
  行われる固定の文字置換（0x1C→`*`, 0x1E→`;`）であることが判明した。一方、
  このリポジトリでは `ORDER.UNKNOWN_1C` として `constants.ts` の `ORDER` オブジェクトに
  定義し、`wtd-applier.ts` のオーダー switch の1ケースとして実装している——
  「オーダー」という位置づけ自体が実態と食い違っている。
- 判断: この実態と実装の食い違いを、`ORDER` オブジェクトから切り離して
  新しい専用の定数群・処理経路（表示データ判定チェーンへの統合）へ作り替える
  ことは**この work では行わない**。`ORDER.UNKNOWN_1E` も `UNKNOWN_1C` と同じ
  「オーダー switch の1ケース」という構造のまま対称的に追加する。doc コメントで
  実態（オーダーではなく文字置換であること）を明記するに留める。
- 理由 / 代替案:
  - 代替案（`ORDER` から切り離し、新しい `CHAR_SUBSTITUTE` 等の専用経路へ
    再配置する）は、実態により忠実な設計になる。しかし `ORDER.UNKNOWN_1C` は
    既存の公開定数であり、これを削除・移動すると `constants.ts` を参照する
    他のコードへの影響範囲を洗い出す必要が生じる（`requirements.md`
    「非機能要件」: 破壊的変更を避ける）。
  - `ORDER.UNKNOWN_1C` の既存実装（オーダー switch の1ケースとして扱う）は、
    実機シナリオ（`WRKOBJPDM`/`DSPSPLF` 系、`research.md` F6）で既に検証済みの
    実績があり、触ると新たな回帰リスクを持ち込む。
  - この work の主目的は「0x1E という具体的に確認された1件のギャップを塞ぐ」
    ことであり、アーキテクチャ上のより正確な再設計は目的を超える
    （`design.md`「対象範囲」の対象外にも明記済み）。
- 影響:
  - `packages/tn5250/src/protocol/constants.ts`・`wtd-applier.ts` は、
    `UNKNOWN_1C` と対称的な `UNKNOWN_1E` を追加するのみに留めた。
  - 将来、`ORDER` オブジェクトの位置づけを見直す機会があれば、この決定記録を
    出発点にできる。
