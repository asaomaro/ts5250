# 決定記録

## D1: full で進め、0x22 を DSM で出させて測ってから着手する（着手時の判断）

- 背景: `aidev-util-batch` で `acs-parity.md` の「窓の中のエラーメッセージ（WRITE ERROR CODE TO WINDOW）」を autonomous で起こした（利用者の指示「残りもすべて autonomous で」。2026-09-27）。
  台帳は「0x22 そのものは実機で観測できていない。出す画面が見つかったら着手」としていた。
- 決定: profile は full。**0x22 は DSM の `QsnPutOutCmd(0x22, …)` で任意に出させられる**（`scripts/host-src/dscmd.c` は第 1 引数のコマンドバイトを何でも出せる）ので、
  「見つかるまで保留」の前提は当たらない（AGENTS.md「判断の原則」2 と 3——過去の決定より実測を上位に置く）。実機の ACS のコアと当 PJ に同じ 0x22 を当てて比べる。
- 影響: 台帳の「保留」の記述は、deliver で取り消し線にする。

## D2: 0x21（WRITE ERROR CODE）の行の差は別項目に起票する

- 背景: research F1。ACS は 0x21 も SOH が申告したメッセージ行に書くが、当 PJ は常に最下行に重ねる。requirements では 0x21 の行を対象外にしていた（測定で差が見つかれば割る）。
- 決定: この work では直さず、`acs-parity.md` に起票する（deliver で）。原典で差が確かめられたので「測定で見つかれば」の条件は満たした。
- 理由: 0x21 は全画面のエラーで使われる経路で、SOH で行を申告する画面の実例（と実測）を足してから直すべき。0x22 と同じ位置の仕組みを使えば小さく直せる見込み（起票に書く）。

## D3: T4（実機の測定と片付け）は test 工程で消化する

- 背景: T4 は実装ではなく、実装を実機に当てて確かめ、試験プログラムを消す作業。
- 決定: coding では消化せず test 工程で行う。coding の承認時に T4 は未チェックのまま残る。

## D4: RESTORE SCREEN と上限の境界の扱いは未確認として残す

- 背景: T1 の独立点検。(1) RESTORE SCREEN は `systemMessage`（と位置）を消さない（既存の寿命を引き継いだ）。窓の中で 0x22 を受けたあと RESTORE が来ると、窓の無い画面に古い位置で重なりうる。
  (2) 上限の境界に IC・SBA・MC や DBCS の組がまたがると、当 PJ は組を読み切る。ACS が添字の終わりで組をどう扱うかは原典の読みでも実測でも確かめていない。
- 決定: どちらもこの work では変えず、未確認としてコードのコメント（(2)）と、0x21 の起票（D2）の本文（(1)）に残す。
- 理由: (1) は 0x21 と共通の寿命の規則で、ACS の RESTORE とエラー状態の関係を測ってから直すべき。(2) は実例（DBCS の本文を上限いっぱいに送る画面）が無い。
