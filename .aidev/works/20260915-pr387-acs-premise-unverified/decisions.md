# 判断記録

## D1: `packages/tn5250/test/cursor-default.test.ts` にも
`cursorIsUnenterable()` の単体テストがあり、削除が漏れかけた

- 背景: `research.md`「依拠する既存の事実」で `cursorIsUnenterable()`／
  `isEnterableAt()` の呼び出し元を確認した際、`grep -rn "cursorIsUnenterable\|
  isEnterableAt" packages/tn5250/src` と **`src/` だけ**を検索対象にしており、
  `test/` を含めていなかった。T2（`buffer.ts` からの削除）実装後、T4（既存
  テストの実行）で `cursor-default.test.ts` の「カーソルが入力できない桁に
  あるかを見分ける」describe ブロック（4テスト）が `buf.cursorIsUnenterable
  is not a function` で失敗し、この見落としが発覚した。
- 判断: このブロックは `cursorIsUnenterable()` の単体テストそのものであり、
  メソッドを削除した以上、テストブロックごと削除する。撤去の理由（旧
  `PR#387` 分岐専用のヘルパーだったこと）を示すコメントに置き換えた。
- 理由 / 代替案: メソッドのシグネチャだけを残してテストを通す、という選択肢は
  無い——死んだコードを残すことになり、`requirements.md`「非機能要件」の
  「死んだコードを残さない」という方針に反する。
- 影響: `research.md`「依拠する既存の事実」の grep 結果の記述は、対象範囲を
  `src/` に限定していたことを踏まえて読む必要がある（`test/` を含めた確認は
  T4 で事後的に行われた、という経緯として残す）。tasks.md の T2・T4 の記述
  そのものは変更不要——T4 の「green のままであることを確認する」という
  目的は、この発見と修正を経て結果的に満たされた。

## D2: `PR#387` の削除は、ACS コアで確認できる事実に矛盾しないという基準で
判断した——ACS の実際の見た目の挙動と完全に一致する保証はしていない

- 背景: `requirements.md`「非機能要件」「未確定事項」、`design.md`「エラー処理 /
  異常系」の通り、~~この開発環境には ACS 実機が無く、実際に ACS を動かして
  CURSORCL3 のシナリオでどう見えるかを確認する手段が無い。~~
  **訂正（2026-09-17）**: 「ACS が無い」は誤り。ACS の jar（`acshod2.jar`）も、それを
  そのまま使って実機を操作する 5250-operator MCP も手元にあり、中継タップ
  （`scripts/tap-proxy.mjs`）で送信バイトの比較もできる。以後の ACS 準拠化
  （PA0100J のカーソル・YB0140R の窓）はこの方法で実測と突き合わせた。
  **ACS の挙動はコードの読みだけで決めず、必ず実測と突き合わせる。**
  ただし CURSORCL3 のシナリオそのものは、この訂正の時点でも実測していない。
  同じ誤りは `requirements.md` / `research.md` / `test-result.md` の「ACS が無い」にも及ぶ。
- 判断: `PR#387` の分岐を撤去し、ACS のデコンパイル済みコア
  （`DS5250.preprocessWCC2()`、`.aidev/works/20260915-pr387-acs-premise-unverified`
  research.md F3）が確認上そうする（IC/MC の指定にそのまま従う）という事実に
  一致させる。これは「ACS の実際の見た目の挙動を正しく再現している」という
  確認ではなく、「確認できる唯一の一次資料と矛盾しない」という、より弱い
  基準での判断である——この違いを requirements/design/decisions のどこにも
  「確認済み」と書かず、一貫して明示する。
- 理由 / 代替案:
  - 代替案「`PR#387` 分岐を残す（現状維持）」は、未検証の前提
    （`research.md` F1・F2・F4）に基づく挙動を維持し続けることになり、
    利用者の指摘（「こちらの報告がソースなら誤報告かもしれない」）に応える
    ことにならない。
  - 代替案「実機 ACS が手に入るまで判断を保留する」も検討したが、
    この開発環境には ACS が無く、いつ手に入るか見通しが立たない
    （`.aidev/works/20260914-seu-page-cursor-hold` decisions.md D6）。
    確認できる事実（ACS コアのコード）に基づいて暫定的に判断し、将来
    実機同時比較が可能になった時点で再検証する余地を残す方が、
    未検証の前提を無期限に放置するより誠実である。
- 影響:
  - `PR#387` が元々解決しようとした症状（Enter 確定後、保護化された欄に
    カーソルが取り残され Tab を押すまで入力できない）が再び起きる
    ——ACS コアの確認済み挙動に合わせるための意図的な変更であり、
    単純な退行ではないと `design.md`「振る舞いの詳細」に明記済み。
  - `.aidev/backlog/acs-parity.md` に、実機 ACS による再確認が今後の課題
    として残っていることを記録する（T6、deliver 工程で実施）。
  - もし将来、実機同時比較で「ACS は実際に CURSORCL3 で下の欄へ寄せる」
    ことが確認された場合は、この work の変更を差し戻し、真の判別軸を
    実機で確認した上で `PR#387` 相当の分岐を再実装する必要がある。
