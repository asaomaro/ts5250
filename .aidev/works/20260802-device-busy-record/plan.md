# 計画: 起動応答の失敗コードを表示セッションでも受け止める

## 実装方針

**プリンター側に揃えるだけ**なので、正解の形は既にリポジトリの中にある。
`PrinterSession.handleStartup` を読み、同じ判断（コードで見る）を表示へ持ち込む。

実機では症状が再現しないので、**失敗応答は合成して**単体で固定する
（形式は `parseStartupResponse` の docstring に実機の 1 レコードがある）。

## 作業順序と依存関係

1. `isKnownStartupCode` を `startup-record.ts` に置く（`CODE_MEANING` が唯一の出所）
2. 表示セッションの判定を「コード or 装置名」に変え、失敗コードで接続を断る（依存: 1）
3. 単体テスト——成功 / 失敗 / 未知＋装置名 / 未知＋装置名なし（依存: 2）
4. 実機で回帰（正常接続・装置名の重複が従来どおり良い文言）（依存: 3）
5. `scripts/README.md` ＋ build / lint / test（依存: 4）

## リスク / 留意点

- **通常の画面を起動応答として食べると画面が出なくなる**（元のコメントの懸念）。
  既知コードの照合は `device !== ""` より厳しいので後退しないが、
  **`device !== ""` の枝は必ず残す**。
- **失敗を投げる場所**。`handleRecord` は受信経路にいるので、
  そこで throw しても接続待ちに届かない可能性がある。**待ち合わせの作りを読んでから**決める。
- 実機は共用の本番機。**装置は作らない**（採番させる手も使わない——auto-config を誘発しうる）。
  使うのは自分の設定にある `DEV1` だけで、必ず切断する。
- 接続条件は設定と揃える（**CCSID 5026 / 27x132**）。既定のままだと交渉で切られる。

## テスト方針

- 単体: `isKnownStartupCode`（成功・失敗・未知）。
  合成した起動応答レコードを `Session5250` に食わせ、
  **失敗コードで `SESSION_REJECTED` になる / 成功で従来どおり / 未知＋装置名で従来どおり /
  未知＋装置名なしはデータストリーム扱い**を固定する。
- 既存の 5250 解析テストが緑のまま（正常時を変えていない）。
- 実機: 正常接続（`I902`）と、装置名の重複が従来どおり断られること。
