# 要件: 装置名が使用中のときの `expected ESC, got 0xc0` の由来を突き止める

## 背景 / 課題

`.aidev/backlog/datastream-commands.md` の未着手項目（「その他」）。

> 装置名が使用中で接続を断られるとき、`expected ESC, got 0xc0 — discarding rest of record`
> が出る。5250 のレコードでないものを読んでいる（ホストが閉じる前に何か送っている）。
> **接続はどのみち失敗する**ので実害は無いが、由来は未解明

`packages/tn5250/src/protocol/wtd-applier.ts:100` の警告。**「実害は無い」は利用者から見た話ではない。**

- 装置名の重複は**利用者が普通に踏む**（同じ設定を 2 回開く／別のクライアントが掴んでいる）。
  ランチャーには `deviceNameInUse` の先回りがあるが、**このアプリの外**で掴まれていれば当たらない。
- そのとき操作ログに出るのは `expected ESC, got 0xc0 — discarding rest of record`
  ——**こちらの解析器が壊れているように読める**。本当の理由（装置が使用中）はどこにも出ない。
- `SESSION_CLOSED: closed during negotiation` のような一般的な文言に落ちるため、
  利用者は「なぜ切れたのか」を推測するしかない。

**由来が分かれば、警告を出さずに理由を出せる**可能性がある。まず何が届いているのかを実測する。

## 目的 / ゴール

- **装置名が使用中のときにホストが送ってくるバイト列を実機で捕まえ、記録する。**
- それが 5250 のレコードでないなら、**5250 として解析しようとするのをやめる**。
- 可能なら**利用者に理由を示す**（「装置が使用中です」）。

## スコープ

### 対象

- 実機で装置名の重複を起こし、**受信バイトを生で採る**。
- `wtd-applier` がその列を 5250 レコードとして食べに行っている経路の見直し。
- 判明した理由の**利用者への出し方**（操作ログ／エラー文言）。

### 対象外

- **接続を成功させること。** 装置が使用中なら断られるのが正しい。
- 装置名の自動採番・付け替え。
- ランチャーの先回り判定（`deviceNameInUse`）の改修——あれはアプリ内の重複だけを見る。

## 機能要件

- 装置名が使用中のとき、**解析器の警告（`expected ESC, got 0x…`）を出さない**。
  出すのは「なぜ切れたか」であること。
- 判明した理由を**操作ログに残す**。可能なら接続失敗のメッセージにも載せる。
- **正常な 5250 レコードの扱いを変えない**（この経路は異常時にしか通らないこと）。

## 非機能要件 / 制約

- 追加の依存を入れない。
- 実機は**共用の本番機**。**装置は作らない・消さない**。
  重複させるのは**自分の設定にある装置名**（`DEV1` / `PRT_TEST`）に限る。
  掴んだ接続は必ず閉じる（`finally`）。
- 検証スクリプトに内部 IP を書かない。資格情報は `.env` のみ。

## 完了条件 (受け入れ基準)

- [ ] 装置名が使用中のときにホストが送るバイト列が**実測で記録**されている
      （何のレコードか・どこから 0xc0 なのか）。
- [ ] その状況で **`expected ESC, got 0x…` が出ない**。
- [ ] **本当の理由が利用者に届く**（操作ログ／エラー文言）。
- [ ] 正常時の 5250 の解析が変わっていない（既存テスト緑）。
- [ ] 実機で「2 本目を同じ装置名で開くと、理由が出て切れる」を通している。

## 未確定事項 / 確認したいこと

- **0xc0 が何か。** EBCDIC の `{` でもあり、5250 の GDS ヘッダーの一部でもありうる。
  レコードの**どこから**読み始めているのかを含めて実測で決める。
- ホストが送っているのが **TN5250E の応答**（装置名の否認）なのか、
  **通常のメッセージ**なのか。前者なら交渉層で扱うべきで、5250 の適用層まで来るのが誤り。
- 直し方が「交渉層で受け止める」になるか「適用層で無視する」になるかは、
  実測してから決める（推測で書かない）。
