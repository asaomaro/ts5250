# 調査: メッセージの待ち受け

**実機（IBM i 7.3）で仕組みを確かめてから書いている。**

## 調査の問い

- Q1: **ポーリングせずに待てるか**（既存の監視の設計に合わせられるか）
- Q2: 待ち受けてメッセージを消さずに済むか
- Q3: 同じものを二度出さない方法は
- Q4: 既存の `WatchRegistry` に載るか

## 判明した事実

### F1: **`QSYS/QMHRCVM` でブロックして待てる**（ポーリング不要）

実測:

```
空の待ち行列 / 待ち 0 秒 → 実測 0.0 秒 返=8
空の待ち行列 / 待ち 4 秒 → **実測 4.0 秒** 返=8（8 = 見出しだけ＝何も無い）
1 件ある     / 待ち 4 秒 → 実測 0.0 秒 返=181
```

**指定した秒数ちょうど待つ。** 既存のデータ待ち行列の監視（`read({ wait: -1 })`）と
同じ「無通信で待つ」形にできる。

### F2: パラメータの並び（**実機で当てた**）

```
0 メッセージ情報   char(*)  out
1 その長さ         bin(4)   in
2 形式名           char(8)  in   RCVM0100 / 0200 / 0300
3 修飾名           char(20) in   待ち行列(10) ＋ ライブラリー(10)
4 **メッセージ種別** char(10) in   *ANY / *FIRST / *NEXT …
5 **メッセージキー** char(4)  in
6 **待ち時間**      bin(4)   in   秒。-1 で無限
7 メッセージ動作   char(10) in   *SAME / *OLD / *REMOVE
8 エラーコード     char(8)  inout
```

**踏んだ間違いが 2 つ:**

1. **待ち時間を種別の前に置いた** → `CPF24B3: Message type <空白 4 個>*ANY not valid`。
   **先頭の空白 4 個**が、直前の `bin(4)` を種別として読んでいる証拠だった
   ——**エラー文の空白が位置ずれを教えてくれた**
2. **キーを 0 埋めにした** → `CPF2551: Message key and message type combination not valid`。
   **キーは空白（0x40）4 バイト**。使わないときも 0 ではなく空白

### F3: **消さずに待てる**——`*SAME`

メッセージ動作に `*SAME` を渡すと**状態を変えない**。待ち受けても一覧に残り、
照会には後から応答できる。

### F4: **カーソルは `*NEXT` ＋ 直前のキー**

```
1 回目（*FIRST）→ キー=00000180
2 回目（*NEXT） → キー=000001f0
3 回目（*NEXT） → キー=00000260
4 回目（*NEXT） → 何も無い（2.0 秒待った）
```

**同じものが二度出ない。** 最後に見たキーを持ち回ればよい。

`RCVM0200` の並び（実測した hex から）:

```
0-3   返ったバイト数      4-7   利用可能なバイト数
8-11  重大度             12-18 メッセージ ID
19-20 メッセージ種別      21-24 **メッセージキー**
```

### F5: `WatchRegistry` は 2 つ目の種類を想定した作りになっている

```ts
/** サービス型の種類。今は `"dtaq"` だけ（プリンターの常駐化は別作業） */
kind: "dtaq";
```

ただし中身は**データ待ち行列に固く結び付いている**（`openDtaq` / `DtaqConnection` /
`dtaqDecodeEbcdic`）。**種類ごとの「待つ処理」を差し替えられる形へ広げる**必要がある。

寿命・状態・バックオフ・履歴の規則は**そのまま使える**（変えない）。

### F6: `RCVM0100` では**読める本文が返らない**（実装中に判明）

置換データしか入っていない。実機の `CPI1466`:

```
RCVM0100 → "SRBKUP    SUZUKI    081399"     ← 素の値
RCVM0200 → "Job holds large number of locks."  ← 読める文
```

**`RCVM0200` を使う。** 固定部は **176 バイト**、可変部は `176` から
**置換データ → 本文 → 二次レベル**。長さは `152 / 160 / 168` に対で並ぶ
（実機 5 件で `176 ＋ 3 つの長さ ＝ 返り` が成り立つことを確認）。

### F7: **即時メッセージは「置換データ」の側に本文が入る**（実装中に判明）

`SNDMSG MSG('...')` はメッセージファイルを使わないので ID を持たず、

```
本文の長さ = 0 / 置換データの長さ = 打った文字数
```

になる。本文の欄だけを読むと**空文字**になり、「何かが届いた」ことしか分からない。
最初これを踏んで、実機検証で本文が全部空になった。

### F8: **無限に待つと待ち行列が消せなくなる**（実装中に判明。設計を変えた）

待ち時間 `-1` にすると、**ホスト側のジョブが待ち行列を掴んだまま**になる。
こちらが接続を切っても、ジョブは `QMHRCVM` の中なので気づかない:

```
DLTMSGQ MSGQ(TESTLIB/WCHMSGQ) → CPF2451「in use」が**永久に**続く
SNDMSG で 1 通投げる           → 待っていたジョブが返って終わり、直後に消せた
```

**待ち行列の保守が、誰かが待ち受けているだけで止まる**のは割に合わない。
30 秒で区切って掛け直す形に変えた——**通知の速さは変わらない**（届いた瞬間に返る）。
何も来ないときに 1 分 2 往復するだけ。

## 影響範囲

- `packages/server/src/watch-registry.ts` — 種類を 2 つにする
- `packages/server/src/config-types.ts` — 待ち受けの設定
- `packages/server/src/ws-messages.ts` / `ws-handler.ts` — 種類の追加ぶん
- web-ui の `WatchPane` — 表示

## 実現性 / リスク

- **ポーリングを避けられる**ので、既存の設計思想を崩さずに済む
- リスクは **`WatchRegistry` の作り替え**——寿命の規則を壊さないこと。既存の検査で守る
- **実機を荒らさない**（専用の待ち行列で検証する）

## spec への申し送り

- **`*SAME` で消さない**（待ち受けは観測であって消費ではない）
- カーソルは**最後に見たキー**。取りこぼしと二重表示のどちらも避ける
- `WatchRegistry` の**寿命・状態・バックオフは変えない**
