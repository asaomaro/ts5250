# 決定記録

## D1: `hasRowCount` は SQLCA の件数ではなく**文の先頭語**で決める

- 背景: spec は「DDL では `updateCount` が 0 になるので `hasRowCount` を添えて区別できるようにする」
  としていたが、実装当初は `ca.updateCount >= 0` で判定していた。
  **research F3 の実測では DDL も `updateCount: 0` を返す**ので、この判定では
  「DDL の完了」と「0 行に影響した DML」が同じ `true` になり、
  `CREATE TABLE` に「**0 行に影響しました**」と出る（消えたのか作られたのか分からない）。
- 決定: `isRowCountStatement(sql)`（先頭語が `INSERT` / `UPDATE` / `DELETE` / `MERGE`）で決める。
  `updateCount` は負値なら 0 にそろえる（負の件数を画面に出さない）。
- 理由 / 代替案: SQLCA からは決められない（測って確かめた）。ホストに聞く手が無いので
  文の側から決めるしかない。「負値を行数なしの申告と見る」案は、実機がその値を返さないので
  **試していない振る舞いに頼る**ことになる。
- 影響: `statement-kind.ts` に `isRowCountStatement` を追加（`headOf` を切り出して共有）。
  空振り検証のミュータント「`hasRowCount` を件数から決める」で回帰を固定した。

## D2: 非クエリ文でも `hasParameterMarker` はコメントの `?` を数えない

- 背景: spec は「文字列リテラルの中の `?` は数えない」までを求めていた。
  実装後に気づいたが、`DELETE FROM T -- 本当に消す?` のような**コメント内の `?`** も拾ってしまい、
  **正しい文を実行前に断ってしまう**。
- 決定: 行コメント（`--`）とブロックコメント（`/* */`）の中も飛ばす。
  引用符の判定より後に置く（`'--'` は文字列であってコメントではない）。
- 理由 / 代替案: 断る側に倒す（安全側）案もあるが、**断られた利用者に打つ手が無い**
  （コメントを消すしかない）。マーカーの検出漏れは起きない
  ——飛ばすのはコメントと文字列の中だけで、実行に影響する `?` は必ず外にある。
- 影響: `statement-kind.ts` の `hasParameterMarker`。テストで両方向を固定した。

## D3: 書き込みの失敗では接続を**張り直さない**

- 背景: クエリ経路は「使い回した接続が相手側で切れていた」場合に 1 度だけ張り直している
  （`host-sql.ts` の既存の処理）。同じことを非クエリ経路でやると、
  `execute` が届いた後に応答だけ失われた場合に**同じ INSERT が 2 度走る**。
- 決定: `runNonQuery` では再試行しない。失敗はそのまま失敗として返す。
  ただし **`SqlError`（SQL の誤り）なら接続は健全**なのでプールへ戻す
  ——捨てると誤字のたびに次の実行が 6 秒待たされる。それ以外は状態が分からないので捨てる。
- 理由 / 代替案: コミットメント制御を使っていないので、二重実行は取り消せない。
  「速さ」より「取り消せない操作を 2 度走らせない」を選ぶ。
- 影響: `host-sql.ts` の `runNonQuery`。空振り検証のミュータント
  「失敗した接続もプールへ戻す」で固定した。

## D4: MCP の `host_sql` は **SELECT 専用のまま**にする

- 背景: 画面（`/api/host/sql`）は非クエリ文を実行できるようになった。
  MCP の `host_sql` は同じ core を使えるので、技術的には広げられる。
- 決定: 広げない。spec の対象範囲に入っていないうえ、
  **AI から取り消せない書き込みを撃たせるかは方針の判断**なので、実装の都合で決めない。
  `host_command` の `RUNSQL` で既に更新はできる。
- 理由 / 代替案: 「同じ機能なら同じ入口に」という一貫性の議論はあるが、
  入口ごとに危険度が違う（人が見て押す画面と、AI が自律的に叩く MCP）。
  判断材料を backlog に残して次の人に渡す。
- 影響: `host_server_tools.ts` は変更なし（その説明文は依然として正しい）。
  backlog に「MCP から非クエリ文を実行させるか決める」を追加。

## D5: `host-sql.ts` 冒頭の「構造的に読み取り専用」の説明を**書き換えて残す**

- 背景: この経路の docstring は「`query` が結果セットの無い文を実行できないので安全」
  という説明を長く持っていた。今回それが**事実でなくなった**。
  さらに `app.ts` と `host-upload.ts` がその説明を参照していた。
- 決定: 消さずに「2026-07-30 に読み取り専用ではなくなった」節に書き換え、
  当時の警告（更新系を通すときは方針を再検討せよ）に対する**結論**を書く。
  参照していた 2 箇所も同時に直す。既存テストの節名（「読み取り専用の不変条件」）も改める。
- 理由 / 代替案: 消すと次の変更で同じ検討をやり直すことになる。
  残すだけでは腐った説明が残る（この PJ が繰り返し踏んできた失敗）。
- 影響: `host-sql.ts` / `app.ts` / `host-upload.ts` / `host-sql.test.ts`。
