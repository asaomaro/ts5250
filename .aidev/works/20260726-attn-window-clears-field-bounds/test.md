## テストが本当に欠陥を捕まえているか

**先にテストを書き、修正前に落ちることを確認した。**

```
× **SOH でフォーマットテーブルが消えても下線は伸びない**
    → expected [ 11, 12, ..., 80 ] (70 桁) to deeply equal [ 11..16 ] (6 桁)
× フォーマットテーブルを消したあと別の場所に欄が定義されても、元の境界は残る
    → 同上
✓ 前提: フィールドがあれば下線は欄の終端で止まる         （基準線・最初から通る）
✓ CLEAR UNIT では境界も消える
✓ SAVE / RESTORE SCREEN で境界も退避・復元される
✓ 同じ開始アドレスの再定義で境界が新しい長さに追従する
✓ **新しい欄と重なる古い境界は捨てる**
```

**下線が 6 桁 → 70 桁に伸びる**という報告どおりの症状を数値で捉えている。

  報告にあった右への伸び・次行への回り込みが消えた。

  ヘルプ窓自体も点線枠・本文とも正常。

## ラウンド 2: 実機報告による差し戻しと再検証

当初案（境界を無条件に保持）は**窓のタイトル帯の反転を 29 桁目で切っていた**（利用者報告）。
引き継ぎを「ホストがその行を書き直したら捨てる」方式へ改めた（decisions D4）。

実機（#160 と併用）で 3 点を同時に確認:

```
行間隔=[27.5]                          ← 縦ずれなし（#160 の効果）
3〜4 行目の下線要素数=[2,1]            ← 背面の下線は収まったまま（本 PR の目的）
タイトル行=18 の反転スパン: 24-78      ← 窓幅いっぱい（改訂前は 24-29 で切れていた）
```

追加テスト 2 件で回帰資産化。core 868 件・全体 2184 件が通過。

## 未検証・残る懸念

- ホストが**同じ行を書き直さずに**その行へ新たな下線を引く経路があれば、古い境界が効きうる。
  行単位の失効なので当初案よりずっと狭いが、理屈上は残る。実機では観測していない。
- ZIP 書き出しの外部互換性（上記・環境要因）。
