# 要件: セッションの寿命（アイドルタイムアウト・永続）

## 背景 / 課題

`.aidev/backlog/session-lifetime.md` の項目。2026-07-28 に「無操作でセッションが切れるのか」という
問いから現状を調べたところ、**既定値そのものが間違っている**と分かった。

- `SessionManager` のアイドルタイムアウトは**既定 30 分**で、60 秒間隔の `sweepIdle()` が
  超過エントリを切断・削除する。**どこからも設定できない**（コンストラクタに口はあるが
  `main.ts` は引数なしで生成しており、CLI にも設定ファイルにも項目が無い）
- `ws-handler.ts` の `onSocketClose()` が **WS 切断でセッションを破棄している**ため、
  孤児セッションはそもそも残らない。つまり `sweepIdle` が実際に殺しているのは
  **ブラウザが開いているセッションだけ**で、reaper 本来の目的とは逆に**在席している利用者を切っている**
- 利用者が入力欄に文字を打っても、値はクライアント内の `edits` に溜まるだけで
  **AID キーを押すまで WS に何も流れない**。長いコマンドを組み立てている最中は
  サーバーから見れば無操作のまま時間が進み、**打ち込み途中の未送信入力ごと切られる**

このリポジトリは ACS 準拠を基準にしている。**ACS は長時間放置しても切れない**。
アイドル対話ジョブの扱いは本来ホストの管轄（`QINACTITV` / `QINACTMSGQ`。多くの環境で `*NONE`）であり、
こちらが 30 分で切るのは**ホストが持つ方針を先取りして上書きしている**ことになる。
これは retro で自分たちが見つけた「ホストが送っている情報を無条件に上書きしていた」と同じ型の誤り。

## 目的 / ゴール

**セッション設定でタイムアウト時間を選べるようにし、そこに「永続（切らない）」を含める。
既定を永続にする。そして設定した値のとおりに動くこと。**

「設定どおりに動く」を字面で終わらせない。**有限値を選んだときに設定した時間より早く切れる経路**
（未送信の入力・カーソル移動・読んでいる時間がサーバーに見えない）を塞いで初めて要件を満たす。

## スコープ

### 対象

- セッション設定（`sessionBase`）にアイドルタイムアウト項目を足す。「永続」を含む
- 設定 → `OpenOptions` → エントリ保持 → `sweepIdle()` の**エントリごと判定**まで配線する
- 既定を永続にする
- **在席の証拠をクライアントから拾う**（入力・カーソル移動で軽い活動通知を WS に流す。**値は送らない**）
- **WS の死活監視**（アプリ層のハートビート）。既定を永続にする代償として要る——
  半開きソケットが残ると `onSocketClose` が発火せず、セッションが**永久に**残る
- backlog の「残る論点」3 件に結論を出す（コード変更を伴わないものは判断を文書に残して閉じる）

### 対象外

- **ブラウザを閉じても生き残る「常駐セッション」**（`hostserver.md` / `pc-command.md` の項目）。
  ここでの結論は「WS 切断＝破棄」を変えないこと。永続は「**WS が繋がっている間は切らない**」の意味で、
  「ブラウザを閉じても生きる」ではない
- ホスト側のアイドル管理（`QINACTITV`）への介入。ホストの管轄には触らない
- セッション本数上限の新設（`maxSessions` が既にある）

## 機能要件

1. セッション設定に**アイドルタイムアウト**を持てる。値は「分」または「永続」。
   **未設定と永続を取り違えない**表現にする
2. 設定はサーバー設定・個人設定の両方が持てる（**信頼設定ではない**——サーバー上のパス書き込み・
   コマンド実行・秘密のいずれにも触れないので `watermark` と同じ理屈で `sessionBase` に置ける）
3. 表示セッション・プリンターセッションの両方に効く
4. `sweepIdle()` はエントリごとの値で判定する。永続のエントリは対象外
5. 設定が無いときの既定は**永続**
6. 利用者の在席（入力・カーソル移動）がサーバーに伝わり、有限値でも「設定した時間の無操作」で
   初めて切れる。**入力値そのものは送らない**
7. WS が半開きで残った場合は死活監視で検出して破棄する（永続でも取り残されない）
8. 運用者が**サーバー全体の既定**を有限値に戻せる（共有サーバーで永続が困る運用のため）

## 非機能要件 / 制約

- 活動通知は**値を運ばない**。`edits` の中身を早く送ると秘密（マクロの `secretRef` 等）の扱いが変わる
- ホスト発の画面更新は活動に**数えない**（現状のまま）。測るべきは利用者の在席であってホストの活動ではない。
  IBM i には利用者が居なくてもホストが書いてくる経路（中断メッセージ・ATNPGM・READ を伴わない
  WRITE ループ）があり、これを活動に数えると閉じ忘れたタブが永久に生き残る
- 活動通知・ハートビートは**通信量を増やしすぎない**（間引く）
- 既存の `SessionManagerOptions.idleTimeoutMs` を使っているテストを壊さない

## 完了条件 (受け入れ基準)

- [ ] セッション設定にアイドルタイムアウト項目があり、「永続」を選べる。未設定と永続が区別できる
- [ ] 設定値が `open()` / `openPrinter()` を通ってエントリに保持される
- [ ] `sweepIdle()` がエントリごとの値で判定し、永続のエントリを切らない
- [ ] 既定（設定なし）で開いたセッションが、無操作のまま時間が経っても切られない
- [ ] 有限値を設定したセッションが、その時間の無操作で切られる
- [ ] 入力・カーソル移動が活動として数えられ、有限値でも操作中は切られない。**送信内容に値が含まれない**
- [ ] 半開きソケットが死活監視で検出され、セッションが破棄される
- [ ] サーバー全体の既定を運用者が有限値に戻せる
- [ ] backlog の「残る論点」3 件（死活監視・プリンター常駐との関係・永続本数の上限）に結論がある
- [ ] `.aidev/backlog/session-lifetime.md` の未着手が 0 になる

## 未確定事項 / 確認したいこと

- **MCP 経由で開いたセッションには WS が無い**。`onSocketClose` による孤児回収が効かないため、
  既定を永続にすると回収する者が居なくなる（→ research で確認する）
- 「永続」の表し方（`0` / `null` / `"never"` / 別キー）
- 死活監視の実現手段（WebSocket プロトコルの ping/pong に手が届くか、アプリ層のメッセージにするか）
- 活動通知の間引き間隔
