# 決定記録

## D1: アイドルタイムアウトの既定は入口ごとに決める（MCP には永続を通さない）

- 背景: backlog の調査は「孤児回収は `onSocketClose` が担っているので壁時計タイマーは重複」と
  結論していた。しかし `sessions.open()` の入口は 2 つあり（`ws-handler` と `mcp-tools`）、
  **MCP には切断の通知が無い**（`StreamableHTTPTransport` のツール呼び出しごとの HTTP）。
  MCP セッションを回収していたのは `sweepIdle` の壁時計タイマー**だけ**だった。
- 決定: マネージャ既定は `"never"`（永続）。**MCP 経由の open は `orphanSafeIdleTimeoutMs()` を
  通し、`"never"` と未設定を 30 分（従来の既定）に落とす**。設定の有限値は両方の入口で尊重する。
- 理由 / 代替案:
  - 一律に永続にすると、落ちた MCP クライアントのセッションが残り続け `maxSessions`（既定 8）を
    食い潰して新規接続が `CONNECT_FAILED` になる。装置記述も掴んだまま
  - MCP 側にもハートビートを作る案は、トランスポートが要求単位の HTTP なので置き場が無い
  - 「設定どおりに動く」の例外はここ 1 点だけなので、**黙って曲げず warn に出す**
- 影響: requirement の「設定どおりに動く」に例外が 1 つ生まれた。README と backlog に明記した。

## D2: 「永続」は `"never"`、有限は「分」。`0` / `null` は使わない

- 背景: backlog は「`0` / `null` / `"never"` のどれにするかは実装時に決める。**未設定と永続を
  取り違えない**表現にすること」としていた。
- 決定: 設定スキーマは `z.union([z.literal("never"), z.number().int().min(1).max(1440)])`。
  内部表現は `IdleLimit = number | "never"`（ms）。未設定は `undefined` のまま運ぶ。
- 理由 / 代替案: `0` を永続の印にすると、転記漏れ・初期化漏れ（数値の既定 0）と区別が付かない。
  `null` は JSON では表せるが、`undefined`（未設定）との違いが呼び出し側で潰れやすい。
  `sessionBase` の他の値も素の値型なので、`null` の意味付けを新しく持ち込まない。
- 影響: 分 → ms の変換が要る。**変換は `config-resolver.buildConnect` の 1 か所だけ**に置いた
  （入口ごとに書くと片方が分のまま流れる）。

## D3: 死活監視はアプリ層のハートビート（プロトコル層の ping を使わない）

- 背景: backlog は「`onSocketClose` が拾えない場合に備えるなら、壁時計のアイドルではなく
  **WS の ping/pong** が本筋」としていた。既定を永続にした以上、半開きソケットを拾えなければ
  セッションが永久に残るので、今回の範囲に入れた。
- 決定: `{type:"ping"}` / `{type:"pong"}` のアプリ層メッセージ。30 秒間隔・無応答 90 秒で死判定。
  生存の更新は**任意の受信**で行う（pong 専用にしない）。
- 理由 / 代替案: `@hono/node-server` の `WSContext` から生ソケット（`raw.ping()`）に手を伸ばすと、
  `WsSender`（`send` / `close` だけの薄い境界。モックを差し込める形にしてある）が壊れて
  `WsConnection` の単体テストが書けなくなる。半開きの検出はアプリ層で足りる
  （`send` はローカルで成功するので送信失敗では気づけない、という性質は同じ）。
  pong 専用にしないのは、キー送信が流れている最中に心拍を 3 回取りこぼしただけで
  生きている接続を切ってしまうため。
- 影響: クライアントに自動応答が要る（`ws-client.ts` で完結。上の層へは渡さない）。

## D4: 在席の合図は payload を持たない型にする

- 背景: 有限値を選んだとき、**打鍵中はサーバーから無操作に見える**（値は AID キーまで送らない）。
  塞がないと「設定した時間より早く切れ、未送信の入力が消える」。
- 決定: `WsActivity { type: "activity" }`。フィールドを持たせない。15 秒に間引く。
  操作ログ・監査ログには出さない。
- 理由 / 代替案: `edits` の中身を早く送る案は、秘密（マクロの `secretRef`）の扱いが変わるので却下。
  カーソル位置だけ載せる案も、**将来値を足す入口**になるので取らない（型で不可能にした）。
  ログに出さないのは、15〜30 秒間隔の往復で利用者が読む操作ログが埋まるため。
- 影響: 間引きの記憶は `SessionState.activitySentAt` に持つ（モジュール側の Map だと
  閉じた id の記憶が残り、テスト間でも漏れた——実際に最初の実装で踏んだ）。

## D7: 合図の出所は合成イベントではなく DOM の生イベント（capture）

- 背景: spec は research F6 に従い `EmulatorPane.onEdit` / `onCursor` から合図を出す設計にしていた
  （`edits` への唯一の書き込み・カーソル調停の単一点）。実装後、**既存テストが 15 件落ちた**ことで
  `ScreenGrid.onInputFocus` が `cursor` を emit していると判明した。つまり
  **ホスト発の画面更新でも `onCursor` が呼ばれる**（新画面 → `reconcileFocus` → input focus → emit）。
- 決定: 合図は `.pane` の `@keydown.capture` / `@pointerdown.capture` から出す。
  `onEdit` / `onCursor` からは出さない。
- 理由 / 代替案:
  - ホストの活動を在席と数えると「閉じ忘れたタブが永久に生き残る」——requirement の非機能要件が
    明文で禁じている状態そのものになる（IBM i には利用者が居なくてもホストが書いてくる経路がある）
  - `onCursor` の呼び出し元を「利用者由来」だけに絞る案は、`reconcileFocus` を経由する経路が
    多く（Tab・矢印・語ジャンプ・クリック・ホスト新画面）判別を分岐で書くことになる。
    **生イベントなら分岐が要らない**
  - capture にしたのは、子（入力欄・機能キーボタン）が伝播を止めても必ず通るため
- 影響: research F6 の結論は**採らなかった**（合成イベントの出所を調べ切れていなかった）。
  回帰テストに「画面を開いただけでは出ない」「ホスト発の画面更新では出ない」を入れた。
  既存テスト 6 件は `sent` に `activity` が混ざるようになったので、集める側で除外した
  （ホストへ送ったかを見るテストなので、WS の内部往復は数えない）。
  併せて `client: {} as WsClient` と偽っていた既存の seed 7 箇所に `send` を足した——
  そのままだと Vue のエラーハンドラが例外を飲み込み、**テストは緑のまま 34 件の
  unhandled error が出る**（false green）状態になっていた。

## D5: 「永続」は「常駐」ではない。`onSocketClose` の破棄は変えない

- 背景: backlog の残る論点「プリンターの常駐用途との関係」。
- 決定: 今回の永続は「**WS が繋がっている間は切らない**」の意味に限定し、
  WS 切断時の破棄はそのまま残す。
- 理由: ブラウザを閉じても帳票を受け続ける「常駐」は WS 非依存の寿命管理が要る別の設計
  （`hostserver.md` / `pc-command.md`）。そちらを作るときは
  「壁時計タイマーが唯一の安全網になる」ので、D1 の考え方（`orphanSafeIdleTimeoutMs`）を再利用する。
- 影響: 常駐は対象外として requirement に明記した。

## D6: 永続セッションの本数に専用の上限は足さない

- 背景: backlog の残る論点「共有サーバーでは管理者が上限を掛けたくなる可能性がある」。
- 決定: 足さない。`maxSessions`（既定 8）が既に本数の上限で、時間で絞りたい運用には
  `--idle-timeout` がある。
- 理由: 永続にしたことで新しい漏れ口は増えていない（切断で破棄・半開きは心拍で破棄・
  MCP は有限）。設定が増えるほど「どれが効いているか」が分からなくなる。
- 影響: backlog の当該項目は「要らない」という結論で閉じた。
