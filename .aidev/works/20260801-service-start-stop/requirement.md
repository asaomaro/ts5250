# 要件: 待ち受けの開始/停止と `stopped` 状態

## 背景 / 課題

`20260801-service-lifecycle-model`（PR #253）で設定モデルと 4 状態の語彙は入ったが、
**状態機械そのものは未実装**。PR #253 の `decisions.md` D1 で次に送った分を実装する。

いま合っていないところ:

| 箇所 | 問題 |
|---|---|
| `WatchRegistry.stop()`（`watch-registry.ts:211`） | **レジストリから削除する**。停止すると一覧から消え、**再開できない** |
| `WatchState` | `watching / reconnecting / error`。`stopped` が無く、`ServiceState` とも語が違う |
| `PrinterEntry.session`（必須） | 「エントリがある＝接続がある」前提。**停止中を持てない** |
| `openPrinter` | 開いた瞬間に接続する。`autoStart ☐` を反映できない |
| 上限 | **存在する数**で数える。停止中は資源を持たないのに枠を食う |

## 目的 / ゴール

**プリンターと待ち行列が、同じ状態機械で開始/停止できる。**

## スコープ

### 対象

- `ServiceState`（`stopped / listening / reconnecting / error`）を**両者が使う**
  ——`WatchState` は `ServiceState` に寄せる（`watching` → `listening`。**破壊的変更**）
- **停止しても消えない**（一覧に残り、再開できる）
- **停止は接続を手放す**
- **上限は「待ち受け中」で数える**
- **`autoStart ☐` なら開いても待ち受けない**（プリンター）
- WS から開始/停止を指示できる
- 実機で 開始 → 受信 → 停止 → 再開 の往復

### 対象外（さらに次）

- **定義ベースの一覧 API**（`/api/printers` は実行中しか出さない）
- **サーバー起動時の自動開始**（`autoStart` を起動時に読む処理）
- **`ref` による attach**
- **画面（UI）**——利用者が設計中
- 待ち行列 UI の能動/受動の分離、サービスの sink

## 機能要件

- 停止したプリンター／監視が**一覧に残り、再開できる**
- **停止と再接続中が状態で区別できる**（意思と障害）
- 停止で**ホスト側の資源を手放す**（装置・接続）
- `autoStart ☐` のプリンター定義は、開いても**待ち受けを始めない**
- どちらの状態からでも**停止できる**
- **既定の挙動を変えない**（`autoStart` 既定 ✅ なので、いままでどおり開いたら待ち受ける）

## 非機能要件 / 制約

- 状態の語彙は `service-state.ts` の 1 か所（両者が使う）
- **`watching` → `listening`** は WS の外向き文字列が変わる。web-ui も直す
- 既存テストが通ること（挙動が変わる分は実態へ寄せる）
- 実機で往復が確認できること
