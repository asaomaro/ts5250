# 計画: 待ち受けの開始/停止

## subtask 分割の判定

**分割しない**。監視側とプリンター側は別レジストリだが、
**同じ状態機械を共有させるのが目的**なので、割ると片方だけの語彙になって食い違う。

## 作業順序と依存関係

1. **T1** `WatchState` を `ServiceState` に寄せる（`watching` → `listening`）
2. **T2** `WatchRegistry.stop()` が削除をやめ、`resume()` を足す（依存: T1）
3. **T3** 監視の上限を待ち受け中で数える（依存: T2）
4. **T4** web-ui の表示を追随（依存: T1）
5. **T5** `PrinterEntry.session` を省略可能に・状態を持たせる
6. **T6** `startPrinter` / `stopPrinter` と `autoStart` の尊重（依存: T5）
7. **T7** プリンターの上限を待ち受け中で数える（依存: T6）
8. **T8** WS メッセージとハンドラ（依存: T6）
9. **T9** テスト（依存: T1〜T8）
10. **T10** 実機で 開始 → 受信 → 停止 → 再開（依存: T9）
11. **T11** build / lint / test

## リスク / 留意点

- **停止で本当に装置を手放したか**は単体テストで測れない（偽の接続）。
  **再開できることが証拠**になるので、実機で往復させる
- **状態を先に立てる**（D3）。順序を誤ると明示停止が「障害」になる
- **上限の数え方**（D2）。登録済みを数えると自分で自分を締め出す
- **既定を変えない**。`autoStart` 既定 ✅ なので、いままでどおり開いたら待ち受ける
- 既存テストが「停止＝一覧から消える」を固定している。**実態へ寄せる**のが正しい
