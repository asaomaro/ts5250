# 要件: 転送が落ちてもセッションを失わない（猶予保持と再接続）

## 背景 / 課題

実機で次の 2 つが報告された。**同じ事象の表と裏**である。

1. **応答待ちのローディングが解除されない。** その状態の画面から見える操作ログの最後は
   `closed`（切断）だった。`WsClient` の `close` は操作ログに 1 行書くだけで
   `session-controller` へ伝わらず、`busy` / `loading` が立ったまま残っていた。
   覆いが残ると Attn / SysReq の逃げ道も押せず、タブを開き直す以外に手が無い。
2. **開き直すと「前回のセッションが閉じられた（こちらから切断した）」警告が出る。**
   ブラウザ ↔ サーバーの WebSocket が閉じると、`ws-handler.dispose` が
   **その場でホストセッションを閉じる**（`ws-handler.ts` の `onSocketClose` →
   `dispose` → `sessions.close`）。閉じるのは**そのタブが自分で開いたセッションで、他に見ている
   人が残っておらず、常駐でもない場合**——制約の節に挙げる既存の 3 判断はこのときも効いていて、
   通常のブラウザ 1 タブでの利用がちょうどこの条件に当たる。つまり操作ログに「切断」が出た時点で IBM i 側の
   対話ジョブは既に終わっており、利用者がタブを閉じたことが原因ではない。

現状は「転送が一瞬でも落ちたら、ホストの対話ジョブごと失う」設計になっている。
5250 の対話ジョブは画面遷移の途中状態を持つので、失う代償が大きい。

ここでいう**操作員メッセージ**とは、画面下部の状態表示に出すこちら発の 1 行の通知
（既存の `opMessages` 群。ホストが送ってくるメッセージとは別枠）を指す。

なお 1 の応急修正（`close` を `session-controller` へ伝えて待ちを解き、切断を通知する）は
本 work の作業ツリーに投入済み（`decisions.md` D2）。本 work はそれを含めて仕上げる。

## 目的 / ゴール

- **回線やサーバーの瞬断でホストの対話ジョブが失われない状態**にする。繋ぎ直せば
  同じセッションの続きから操作できる。
- **切れたこと・戻ったことが画面から分かる状態**にする。黙って固まらない。
- **孤児セッションが溜まらない状態**を保つ（保持は有限。装置と接続枠を握り続けない）。

## ユーザーストーリー

- US1: **エミュレーターの利用者**として、Wi-Fi の瞬断やサーバー再起動があっても
  **入力途中の画面から続けたい**。なぜなら 5250 の対話ジョブは画面遷移の途中状態を持ち、
  やり直すと最初のメニューから辿り直しになるため。（受け入れ: AC1, AC2, AC3, AC7）
- US2: **エミュレーターの利用者**として、**繋がっていないことがその場で分かってほしい**。
  なぜなら「ホストが遅い」と「切れている」を見分けられないと、応答を待ち続けて時間を失うため。
  （受け入れ: AC4, AC5, AC10, AC-I1〜AC-I5）
- US3: **サーバーを共有する運用者**として、**落ちたクライアントのセッションが残り続けない**ことを
  保証したい。なぜなら表示セッションは既定 `maxSessions` が 8 で、掴んだままだと
  他の利用者が繋げなくなり、ホスト側の装置記述も解放されないため。（受け入れ: AC6, AC8）

## スコープ

### 対象

- **5250 表示セッション**の転送断時の**猶予保持**
  （3270 は design 着手時に対象外へ移した。research F1・`decisions.md` D3）。
- ブラウザ側の **WebSocket 自動再接続と、生き残っているセッションへの再アタッチ**。
- クライアント側の**半開き検出**（サーバーの `ping` が途絶えたら自分から畳む）。
- 既投入の応急修正（切断で `busy` / `loading` を解き、切断を通知する）の仕上げ。

### 対象外

- **VT セッション**：画面のやり取りが別経路（`vt-*`）で、セッションを共有する仕組みが無い。
- **3270 セッション**：同じ理由（共有・再取得の経路が無く、`WsOpen.sessionId` の attach も
  5250 専用）。含めると attach 相当の新設が主題になるため別 work とする（`decisions.md` D3）。
- **プリンターセッション**：常駐（`resident`）として既に転送断で閉じない扱いになっている。
- **監視（DTAQ / メッセージ）**：レジストリが所有し、元からブラウザを閉じても続く。
- **MCP / HLLAPI 経路**：切断を通知しない入口なので孤児回収の前提が違う
  （`orphanSafeIdleTimeoutMs`）。今回の猶予はブラウザ経路の話に閉じる。
- **認証セッション（ログイン）の維持**：ログインが切れていれば再ログインが要る。
- **ホストとの TCP が切れた場合の復旧**：ホスト側セッションが死んだのなら保持する対象が無い。
  今回守るのは**ブラウザ ↔ サーバー**が切れた場合。

## 機能要件

- 表示セッションを見ていた最後の WebSocket が閉じても、**一定時間はホストセッションを閉じない**。
- 猶予が尽きたら**確実に閉じる**（放置しない）。
- ブラウザは切断を検知したら**自動で繋ぎ直し**、生き残っていれば**同じセッションへ再アタッチ**する。
- 再アタッチできたら、**切断中にホストが送ってきた最新の画面**を反映して操作を再開できる。
- 再アタッチできなかった（猶予切れ・別要因で閉じた）ときは、**理由を示して**切断状態にする。
- クライアントは、サーバーの `ping` が一定時間途絶えたら**自分から接続を畳んで**再接続へ回す
  （`close` イベントが来ない半開きでも固まらない）。

## 非機能要件 / 制約

- **孤児を作らない**：ブラウザ経路のアイドル上限は既定 `"never"` で、
  「WS の切断とハートビートが孤児を回収する」ことが前提になっている
  （`session-manager.ts` の `orphanSafeIdleTimeoutMs` 周辺）。猶予保持はこの前提を壊すので、
  **猶予そのものが有限で、期限で必ず回収される**こと。
- **1 装置 1 接続**：猶予中のセッションは装置記述を掴んだままなので、再接続は
  **新規に開くのではなく既存セッションへ attach する**（`WsOpen.sessionId`）。
  新規に開くと「装置使用中」で失敗する。
- **所有者検査を通す**：`sessionId` 指定の attach は自分のセッションだけ
  （`SessionManager.get` の所有者検査）。他人のセッションを拾えないこと。
- **既存の共有経路を壊さない**：`dispose` は 5250 / 3270 / VT / プリンター / 監視が通る合流点。
  「attach しただけのタブは閉じない」「他に見ている人が残っていれば閉じない」「常駐は閉じない」の
  既存の判断（以降**既存の 3 判断**と呼ぶ）を変えないこと。
- **再接続が嵐にならない**：再試行は有限かつ間隔を空ける（サーバー再起動時に全タブが
  同時に叩き続けない）。
- 既存テストがすべて緑であること（`packages/web-ui` は `cd packages/web-ui && npx vitest run`）。

## 完了条件 (受け入れ基準)

- [ ] AC1: 表示セッションを見ていた最後の WebSocket が閉じても、猶予時間内はホストセッションが
      閉じられない（サーバー側の単体テストで、閉じられていないことを確認できる）。
- [ ] AC2: 猶予時間内に、**ログインが有効なまま**同じ `sessionId` で繋ぎ直すと、
      **同じホストセッション**に再アタッチでき、直前の画面から操作を続けられる
      （ログインが切れていれば再ログインが要る＝スコープ対象外。そのときは AC10 の扱いになる）。
- [ ] AC3: 切断中にホストが画面を送っていた場合、再アタッチ後に**その最新画面**が表示される。
- [ ] AC4: WebSocket が閉じたら、応答待ち（`busy` / `loading`）が解け、状態表示が「切断」になり、
      切れたことが操作員メッセージで示される。
- [ ] AC5: 再接続を試みている間はその旨が画面から分かり、成功したら通常表示へ戻る。
- [ ] AC6: 猶予時間を過ぎても誰も繋ぎ直さなければ、ホストセッションは確実に閉じられ、
      `maxSessions` の枠と装置記述が解放される。
- [ ] AC7: サーバーの `ping` が途絶えたまま `close` イベントが来ない（半開き）場合でも、
      クライアントが自分で切断と判断し、再接続へ回る。
- [ ] AC8: 猶予保持は**表示セッションのブラウザ経路だけ**に効き、MCP / HLLAPI が開いた
      セッションや、既存の「attach しただけのタブ」「他に見ている人が残っている」場合の
      判断を変えない。
- [ ] AC9: 既存のテストがすべて緑のまま、本件の回帰テストが追加されている。
- [ ] AC10: 再アタッチできなかったとき（猶予切れ・ログイン切れ・別要因で閉じた）は、
      **なぜ繋ぎ直せなかったか**を操作員メッセージで示して切断状態にする。黙って諦めない。
- [ ] AC11: 他人が開いたセッションの `sessionId` を指定しても再アタッチできない
      （既存の所有者検査が効き、拒否される）。

## 相互作用の受け入れ基準

**AC-I1〜AC-I5 は US2 に紐づく横断的な基準**——個々の部品ごとではなく、再接続まわりの表示と
操作すべてに掛かる。

- [ ] AC-I1 開く / 閉じる: 再接続中であることは**画面を覆わずに**示す（応答待ちの覆いとは別物。
      覆うと復帰後に押せるはずのキーが押せない）。復帰したら表示は自動で消える。
- [ ] AC-I2 確定 / 取り消し: 自動再試行が尽きたら**手動で繋ぎ直す口**を出す。押せば再試行が再開する。
- [ ] AC-I3 キーボードだけで完結するか: 手動の繋ぎ直しはフォーカス移動＋Enter で押せる。
- [ ] AC-I4 フォーカスの行き先: 再接続の表示はフォーカスを奪わない。復帰後のフォーカスは
      画面（入力欄）に戻る——奪ったままだと打鍵が画面へ届かない。
- [ ] AC-I5 既存の操作を妨げないか: 切断中も操作ログの閲覧など、ホストを要さない操作は
      これまでどおり使える（応答待ちの覆いが残って画面全体を塞ぐ、という状態にしない）。

## 未確定事項 / 確認したいこと

- クライアント側の半開き判定のしきい値（AC7 / 機能要件の「一定時間」）。サーバーの心拍間隔と
  死判定との関係を design で決める。
- 猶予時間の既定値（design で決める）。長いほど復帰しやすいが、装置と接続枠を掴む時間も延びる。
- 猶予時間・再接続の試行回数を設定可能にするか、固定値にするか。
- 「切断中にホストが送った画面」をサーバーがどこまで保持するか（最新 1 枚で足りるか）。
