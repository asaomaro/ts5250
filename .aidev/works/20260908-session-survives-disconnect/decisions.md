# 判断の記録

## D1: 三層判定は full（light にしない）

- **背景**: 実機報告「応答待ちのローディングが解除されない／開き直すと前回セッションが
  閉じられた警告が出る」を aidev で対応するにあたり、`aidev-00-start` 手順 0 の三層判定が要る。
  判定は `aidev new` より前なので autonomous の自動承認が及ばない。
- **決定**: **full**（`aidev new --mode autonomous`、profile は既定の full）。
- **理由・代替案**: light の 4 条件（`protocol-light.md`）のうち少なくとも 3 つを満たさない。
  (1) **振る舞いを変える**——転送が落ちたときにホストセッションを閉じるかどうかという
  ライフサイクルそのものを変える。(2) 触るファイルが 3 個を超える（server の
  `ws-handler` / `session-manager`、web-ui の `ws-client` / `session-controller` ほか）。
  (3) **共有モジュールに触る**——`ws-handler.dispose` は 5250 / 3270 / VT / プリンター /
  監視のすべてが通る合流点。対象外（typo 等）でないことは自明。
- **影響**: 上流 3 工程を個別に回す。autonomous なので上流 4 文書は `aidev doccheck` の
  独立点検が必須。

## D2: 応急修正を作業ツリーに載せた状態から始める

- **背景**: 本 work を起こす前の調査で、`WsClient` の `close` が
  `session-controller` に伝わらず `busy` / `loading` が残る欠陥を特定し、修正とテストを
  作業ツリーに入れてある（未コミット。`feature/session-survives-disconnect` に載せた）。
- **決定**: この差分を**破棄せず、本 work の一部として扱う**。requirements の受け入れ基準に
  この分（表示側の復帰）も含め、tasks では「実施済み」として扱う。
- **理由・代替案**: 破棄して tasks から作り直す案もあるが、同じ差分を書き直すだけで
  情報が増えない。逆に**本 work の外でコミットする**案は、症状（ローディングが解けない）と
  原因（セッションが即閉じられる）が同じ事象の表裏で、PR を分けると片方だけ見た人が
  「まだ直っていない」と読むため採らない。
- **影響**: coding 工程の一部は着手時点で完了している。tasks でその旨を明示し、
  test / review は差分全体（応急修正を含む）を対象にする。

## D3: 3270 を対象外に narrow する（requirements の対象を修正）

- **背景**: requirements では対象を「表示セッション（5250 / 3270）」と書いたが、research で
  3270 には**セッションを共有・再取得する経路が無い**ことが分かった
  （`ws-handler.ts:1071-1074`「5250 のように MCP や HLLAPI が同じセッションを共有する経路が
  まだ無いので、残す理由が無い」。`WsOpen.sessionId` の attach も `SessionManager`＝5250 専用）。
- **決定**: 本 work の対象は **5250 表示セッションのブラウザ経路だけ**。3270 は VT と同じく対象外へ移す。
  requirements.md のスコープに、この判断への参照を添えて反映した（黙って変えない）。
- **理由・代替案**: 3270 も対象に含めるなら attach 相当の口を新設することになり、
  「転送断でセッションを失わない」という本題より**新機能の追加が主**になる。分けたほうが
  PR も review も読める。3270 で同じ要望が出たら別 work で attach から起こす。
- **影響**: AC1〜AC3・AC6・AC8 の検証対象は 5250 に閉じる。3270 / VT の `dispose` の
  既存の振る舞いは**変えない**ことが逆に不変条件になる（AC8）。

## D4: 復帰は「持ち主として戻る」— `resume` 付き attach

- **背景**: 既存の `attach` は `attached = true` を立て、以後そのハンドラは
  **どうやってもセッションを閉じない**（`ws-handler.ts:885` / `:1090`）。再接続にそのまま
  流用すると、復帰したタブがセッションを畳めなくなり孤児になる（research F4）。
- **決定**: `WsOpen` に `resume?: boolean` を足す。`resume: true` の attach は
  **`attached` を立てない**（＝閉じる責任を引き継ぐ）うえ、猶予タイマーを解除する。
  所有者検査（`sessions.get(id, user)`）はそのまま通す。
- **理由・代替案**: `attached` の意味を「繋いだ」から「持ち主か」へ変える案は、
  MCP が開いた画面をブラウザで覗く既存の使い方（見に来た人は殺さない）を壊す。
  別フラグを足すほうが既存の意味を保てる。
- **影響**: `WsOpen` のスキーマが 1 フィールド増える。`resume` を指定しない従来の attach は
  一切変わらない。

## D5: 猶予は SessionManager が自前の有限タイマーで持つ（既定 60 秒）

- **背景**: ブラウザ経路の既定アイドル上限は `"never"`（research F5）。その根拠は
  「WS の切断とハートビートが孤児を回収する」ことなので、**猶予保持はその前提を外す**。
  掃除役は `"never"` では何もしない。
- **決定**: `SessionManager` に猶予の口（保持・解除）を作り、**期限付きのタイマーで必ず畳む**。
  既定 **60 秒**。値は `SessionManagerOptions` で差し替えられるようにする（テストのため）が、
  **CLI オプションは足さない**。
- **理由・代替案**: 90 秒（サーバーの死判定 `HEARTBEAT_DEAD_MS` と同値）も候補だったが、
  猶予中は `maxSessions`（既定 8）の枠とホストの装置記述を掴み続ける。クライアントの
  再接続は 31 秒で打ち切る設計（D6）なので、その倍にあたる 60 秒で足りる。
  CLI オプションを足さないのは、設定面を増やす前に既定値で実地の様子を見たいため
  （必要になってから足すのは容易で、逆は難しい）。
- **影響**: 猶予中に**同じ設定で新しく開こうとすると装置名が使用中**になりうる。ただし既存の
  `retryWithNextDeviceName`（`session-manager.ts:767`）が装置名を繰り上げて接続するので、
  失敗ではなく別装置名での接続になる。最大 60 秒の一時的な現象。

## D6: 半開き検出は ws-client 層に置き、サーバーの `ping` を基準にする

- **背景**: サーバーは半開きを自分で畳む（90 秒無応答）が、**クライアント側には対応する
  見張りが無い**（research F7）。`close` イベントが来ない切れ方では今回の入口が発火しない。
- **決定**: `WsClient` が **`ping` の受信時刻**を見張り、`HEARTBEAT_DEAD_MS`（90 秒）来なければ
  自分から `ws.close()` する。**最初の `ping` を受け取るまで見張りを始めない**。
- **理由・代替案**: クライアント独自の周期（例: 自分から ping を打つ）を作る案は、
  サーバーに新しいメッセージを足すことになり、旧サーバーと繋いだときに黙って切れる。
  「`ping` が来なくなったら死」なら、**ping を送らないサーバーに対しては見張り自体が
  始まらない**ので後方互換になる。
- **影響**: 検知は最短 90 秒。即座ではないが、現状（永久に気づかない）からの改善は大きい。

## D7: 古いハンドラがセッションを殺さないよう、保持者トークンで判定する

- **背景**: 半開きでは、**クライアントが先に死を判定して繋ぎ直す**一方、サーバー側の
  古いハンドラは最大 90 秒後にようやく `dispose` する。素直に実装すると、
  **新しいタブが復帰した直後に古いハンドラの `dispose` がそのセッションを閉じる**。
- **決定**: `SessionManager` がセッションごとに**保持者トークン**を持ち、`open` / `resume` で
  更新する。`dispose` は「自分がまだ保持者か」を確かめてからでないと閉じない／猶予に入れない。
- **理由・代替案**: 時刻で新旧を見る案は時計に依存する。トークンなら単調増加の比較だけで済む。
- **影響**: 既存の「他に見ている人が居れば閉じない」判断とは**別軸の追加**で、既存判断は残す。

## D8: プリンターの保持者は「最後に開いた接続」になる（意図した副作用）

- **背景**: `openPrinter` は同じ保存済み定義（`ref`）なら既存エントリを返す。保持者トークン
  （D7）を `openPrinter` の直後にも打つので、**同じプリンターを 2 タブで開くと後のタブが
  保持者を奪う**。従来は先のタブが切れた時点で（非常駐なら）その場で閉じていた。
- **決定**: この変化をそのまま受け入れる。閉じるのは**最後の保持者が去ったとき**になる。
- **理由・代替案**: 表示セッションの「他に見ている人が残っていれば閉じない」と同じ方向の
  振る舞いで、**まだ使っている人が居るのに閉じる**という以前の挙動のほうが不自然だった。
  プリンターだけ `claim` を打たない案は、保持者照合が効かなくなり
  「古いハンドラが復帰済みを閉じる」を防げなくなる（D7 の目的そのものを失う）。
- **影響**: 非常駐プリンターの寿命がわずかに延びうる。猶予（D5）は表示セッション専用なので、
  プリンターは従来どおり転送断でも即座に閉じる（最後の保持者なら）。

## D9: 既存のサーバーテスト 3 件を、変えた振る舞いに合わせて更新した

- **背景**: `session-attach` / `ws-handler` / `ws-lifetime` の 3 件が「転送断で即座に閉じる」を
  固定していた。本 work はそこを変えるので、そのままでは赤くなる。
- **決定**: **緩めるのではなく、対比が残る形に書き換えた**——`close` メッセージ（利用者が閉じた）は
  従来どおり即閉じ、`onSocketClose`（転送断）は猶予に入る、という 2 つを並べて固定する。
  あわせて「猶予を無効にすれば従来どおり」のケースを 1 件足した。
- **理由・代替案**: 3 件とも `reconnectGraceMs: 0` を渡して素通しさせる案は、**本番が使わない
  設定でしか通らないテスト**になり、回帰資産としての価値が落ちる。
- **影響**: `isHeld` がテストから使われるようになった（公開 API の一部として維持する）。

## D10: 保持者の判定を「見るだけ」から「座を返す」に変えた（D7 の改訂）

- **背景**: D7 は `isHolder` で「交代済みなら何もしない」とだけ決めていた。T4 の独立点検で、
  **2 つの接続が続けて引き取ったあと、新しい持ち主が先に去るとどちらも閉じない**ことが分かった
  ——残った古い接続は「交代済み」として素通りするので、見る人ゼロのセッションが
  アイドル上限 `"never"` のまま残る。D4 が塞ごうとした孤児化が別経路で復活していた。
- **決定**: `isHolder`（読むだけ）を `releaseHolder`（自分が持ち主なら印を外して true）＋
  `hasHolder`（いま持ち主が居るか）に置き換える。`dispose` は
  **「自分が持ち主だった」か「いま持ち主が居ない」なら畳む**——手を出さないのは
  「交代済みで、その相手がまだ居る」ときだけ。
- **理由・代替案**: 「見ている人（`viewers`）が居るかどうかだけで判断する」案も検討した。
  表示セッションではそれで足りるが、**プリンターは `viewers` を数えない**
  （`subscribeSession` を通らない）ので、同じ判断ができない。座を返す形なら両方に効く。
- **影響**: D7 の「印を見る」は「印を返す」に変わった。`isHolder` は無くなった。

## D11: 繋ぎ直しでは打ちかけの入力を捨てる（design / research の記述を訂正）

- **背景**: research F11 と design「2. 復帰」は「差し替えるのは `client` だけなので、
  打ちかけの入力（`edits`）は保ったまま繋ぎ直せる」としていた。T10 のテストを書いて分かったが、
  **`sessionsStore.updateScreen` は新画面が来たら `edits` を捨てる**（既存の規則）ので、
  繋ぎ直しで `opened` の画面を反映した時点で消える。
- **決定**: **捨てる側を正とする。** 記述のほうを訂正し、テストでもその挙動を固定する。
- **理由・代替案**: 繋ぎ直しで返るのは**留守中にホストが書いた「いまの画面」**で、
  こちらが打っていた画面とは限らない。残したまま反映すると、**別の画面の欄に打鍵が載る**
  ——業務システムに違う値を送ることになる。画面が同一のときだけ残す案も考えたが、
  「見た目が同じ別の画面」をホストが書き直すことは普通にあり、判定を誤ったときの代償が
  大きすぎる。**安全側に倒す。**
- **影響**: 復帰後は打ち直しが要る。要件（AC2「直前の画面から操作を続けられる」）は満たす
  ——失われるのは未送信の打鍵だけで、ホストの対話ジョブは続いている。
  research F11 / design の該当箇所に訂正の参照を入れた。

## D12: 猶予を 90 秒にし、クライアントの再試行予算から導く（D5 の改訂）

- **背景**: D5 は「クライアントの再試行は累計 31 秒なので、その倍の 60 秒」としていた。
  T7 で**試行ごとの上限（10 秒）**を足した時点でこの足し算が崩れており、
  最悪ケースの壁時計は **37.2 秒（ゆらぎ込み）＋ 5 × 10 秒 ＝ 87.2 秒**。60 秒だと
  後ろ 1〜2 段が猶予切れに落ちるだけの空振りになる（cross 点検で判明）。
- **決定**: 既定の猶予を **90 秒**にする。値の根拠を「クライアントの再試行予算を覆う」と
  定義し直し、両側の定数コメントに足し算をそのまま書いた。
- **理由・代替案**: はしごを短くして 60 秒に収める案もあったが、繋ぎ直せる窓を狭める方向で、
  実機報告（回線の瞬断）に対しては逆。90 秒はサーバーの心拍の死判定と同値で、
  半開き経路での「両側が気づく時刻」とも桁が揃う。
- **影響**: 猶予中は `maxSessions`（8）の枠とホストの装置記述を最大 90 秒掴む。
  同じ設定で新規に開いた場合は既存の装置名の繰り上げが働く（D5 と同じ）。

## D13: 「見に来ただけのタブ」と「ホストが終わったセッション」は繋ぎ直さない

- **背景**: cross 点検で 2 つの破れが見つかった。(a) MCP / HLLAPI が開いた画面を後から
  覗くタブ（`sessionId` 指定の attach）も瞬断で `resume` を送ってしまい、**座を引き取って
  持ち主に昇格**する——次にそのタブを閉じると相手の作業ごと畳む。D4 が守ると宣言した
  不変条件の破れ。(b) ホスト側が終わった（サーバー発 `closed`）あとに転送も落ちると、
  区別が付かないままはしごを回し、「サーバーと繋がっていません」という**嘘の理由**を出す。
- **決定**: `SessionState` に `attachedOnly` と `endedByHost` を足し、`startReconnect` の門で
  どちらも弾く。`sendKey` 等の理由も `endedByHost` から出し分ける。
- **理由・代替案**: (a) は「`resume` を送る前にサーバーへ問い合わせる」案もあったが、
  往復が増えるうえ、**開いたのか繋いだのかはクライアントが最初から知っている**
  （`WsOpen.sessionId` の有無）。(b) は `reconnect` / `reconnectFailed` の有無から推測して
  いたが、推測が当たらない組み合わせが実在した。
- **影響**: `SessionState` に真偽値が 2 つ増えた。どちらも「なぜ `connected === false` なのか」
  を説明する印で、`connected` 自体の意味は変えていない。

## デバッグ D1: logic / stop_for_human（review round 1・2026-09-08T08:42:12Z）
- 根本原因: 「持ち主が居るか」「猶予中か」「繋ぎ直しの対象か」を単一の判定関数ではなく独立フラグの暗黙の連言として実装したため、1 つの規則を答える判定が 12〜15 か所へ散り、どこか 1 か所を直しても残りの写しが同じ規則に別の結論を返し続ける（設計の置き場所の問題）

- 確認方法: 判定に使うフラグの出現箇所が定義と導出関数の内側に限られること（rg の件数を CI で固定）。端末種別×切れ方×viewer×持ち主の全組合せを 1 つの表にし、サーバー・クライアント双方をその表から回す
- 確度: high
- 次の行動: stop_for_human
