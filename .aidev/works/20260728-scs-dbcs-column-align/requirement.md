# 要件: スプール（SCS）が DBCS ラン中に制御コードを食う不具合を直す

> 当初の題は「DBCS 桁勘定を 5250 画面に揃える」だったが、実採取データで方針が覆った。
> 経緯は下記「【重要】調査の結論」に残す（ユーザー承認済みで SO/SI 変更は廃止）。

## 背景 / 課題

利用者報告: **エミュレーター画面から WRKSPLF で見ると正しいのに、スプール画面では
DBCS を含む行の後続が詰まって表示される。**

調査で、同じ帳票バイト列が 2 経路で違う桁になることを実測した。

入力 `A + SO 機 SI + B`（EBCDIC `C1 0E 4579 0F C2`）:

| | 出力 | 桁数 |
|---|---|---|
| **5250 画面**（`wtd-applier`） | `A` `␣`(SO) `機`(2桁) `␣`(SI) `B` | **6 桁** |
| **スプール**（`scs.ts`） | `A機B` | **4 桁** |

**SO/SI が桁を消費していない。** 画面は `buf.setShift(addr++, "so")` で SO・SI にそれぞれ
1 桁を割り当てて桁位置を保つが、SCS デコーダは `if (b === SO) dbcsMode = true;` と
シフト状態を変えるだけで `col` を進めない。**DBCS ラン 1 つにつき 2 桁ぶん後続が左へ詰まる。**

`scs.ts` の冒頭にこう書かれている——

> SO/SI(0x0E/0x0F) は SBCS では出現しない前提（DBCS 対応時にシフト処理を追加する）。

tn5250 `lib5250/scs.c` から移植したのは SBCS 部分までで、**DBCS シフト処理は本 PJ が
後から足した部分＝原典照合を経ていない**。桁の勘定が画面と揃っていないのはそのため。

### 同時に見つかった 2 つ目の欠陥

DBCS ラン中、SCS デコーダは **SO/SI 以外のすべてのバイトを DBCS 先行バイトとして消費**する。
`wtd-applier` は `if (dbcsMode && codec.decodeDbcsPair && b >= 0x40)` と**0x40 未満を除外**しており、
制御コードは制御として処理される。SCS 側にこの判定が無い。

実測（CCSID 939、ホストが行末で SI を閉じない形）:

| 入力 | スプールの出力 |
|---|---|
| `SO 機 SI NL SO 能 SI` | `["機","能"]` ✅ |
| `SO 機 [SI無し] NL 能 SI` | `["機��"]` ❌ 化け＋**改行が消える** |
| `SO 機 [SI無し] CR 能 SI` | `["機��"]` ❌ |
| `SO 機 [SI無し] FF 能 SI` | `["機��"]` ❌ **改ページが消える** |
| `SO 機 0x40 能 SI`（奇数バイト） | `["機��"]` ❌ 以降ずっと化ける |

SCS の制御はすべて 0x40 未満（NOOP 0x00 / TRANSPARENT 0x03 / HT 0x05 / RNL 0x06 /
FF 0x0C / CR 0x0D / NL 0x15 / ORDER_2B 0x2B / PP 0x34 / RFF 0x3A）なので、
`b >= 0x40` を入れれば画面と同じ堅さになる。

### 調査で切り分けた「原因ではないもの」

- **文字コード変換は揃っている**。両経路とも同じ `codecForCcsid()` / 同じ表を使う。
  930 / 939 / 1399 × 6 サンプルで**同一 CCSID なら文字は完全一致**することを実測した。
- **フォントでもない**。`SpoolPane` / `PrinterPane` の帳票本文は既に `--screen-mono`
  （和欧 1:2 の一体フォント）を使っている。
- **全角空白（0x4040）の変換も正常**。`decodeDbcsPair(0x40,0x40)` は全 CCSID で U+3000 を返し、
  行中の全角空白は正しく 2 桁で出る。

## 【重要】調査の結論：SO/SI の桁勘定は**変えない**

当初は「SO/SI を 1 桁ずつ占めるようにして画面と揃える」方針で着手したが、
**実採取データがこれを覆した**。

`packages/scs/test/fixtures/scs-print-dbcs.bin` は PUB400 実機から採った DSPLIBL の帳票
（CCSID 1399）。現在の実装（SO/SI は桁を消費しない）でデコードすると:

| 行 | 説明欄の開始桁 |
|---|---|
| `PUB400SYS SYS  $ PUB400.COM global pr…` | **38** |
| `QSYS       SYS  System Library` | **38** |
| `TESTLIB      CUR  日本語テスト`（DBCS） | **38** |
| `QGPL       USR  General Purpose Librar…` | **38** |

**DBCS 行も SBCS 行と同じ桁 38 に揃っている。** SO/SI に 1 桁ずつ割り当てると DBCS 行だけ
39 桁目へずれ、**実帳票と食い違う**。

理由も筋が通る。**5250 画面と SCS 印刷はデータストリームの性質が違う**——
画面はホストがバッファアドレスでセルを指す固定グリッドなので SO/SI もバッファ位置を占める
必要がある（実機・ACS も空白として見える）。印刷は `PP`(AHPP/AVPP) で位置を明示する文字ストリームで、
SO/SI は印字位置を進めないシフト制御である。**両者が違うのは設計どおりで、どちらも正しい。**

利用者が「スプールでは後続が詰まる」と感じたのは、**画面側が SO/SI のぶん 2 桁ぶん広い**ため。
比較の基準が画面だと詰まって見えるが、帳票としては現在の出力が正しい。

AGENTS.md「規格どおりより既存クライアントと同じ挙動を優先」「実機検証を単体テストの代替にしない」
に従い、**SO/SI の変更は行わない**。

## 目的 / ゴール

SCS（スプール）の **DBCS ラン中に制御コードを食ってしまう欠陥**を直す。
判定式を `wtd-applier` と同じ `b >= 0x40` に揃え、ホストが SI を閉じない帳票でも
改行・改ページと以降の文字が失われないようにする。

## スコープ

### 対象

- **DBCS ラン中の `b >= 0x40` 判定**を入れ、0x40 未満は制御として処理させる。
  `wtd-applier` と同じ条件式にする。
- 上記を固定する回帰テスト（`packages/scs/test/`）。

### 対象外

- **SO/SI の桁勘定**（上記「調査の結論」。実採取データが現状を支持）。
- **CCSID の既定値**（画面 37 / スプール 273）の変更。スプールセッションにも正しい CCSID を
  設定するのが本来、というユーザー判断により今回は触らない。
- **1399 と 930/939 の DBCS 表の差**（波ダッシュ等 5 文字）。別々の DBCS 表（300 と 16684）を
  使う仕様どおりの挙動であり、実機 ACS の確認なしに寄せるとむしろ準拠が崩れる。
- SCS の他の未実装項目（HT のタブ停止など）。
- PDF レンダラ（`renderSpoolPdf`）の変更。`LogicalPage` を受け取るので**桁の修正は自動的に効く**。

## 機能要件

1. DBCS ラン中に制御コード（NL / CR / FF / PP / 2B 等）が来たら、**DBCS 先行バイトとして
   食わずに制御として処理**する。改行・改ページが失われない。
2. 全角空白（0x4040）は従来どおり 2 桁の U+3000 として出る。
3. **既存の帳票出力が変わらない**——とくに PUB400 実採取フィクスチャの桁が動かない。
4. SBCS のみの帳票の出力は一切変わらない（`isDbcs` が false の経路に影響しない）。

## 非機能要件 / 制約

- **判定式は `wtd-applier` と同一にする**（`b >= 0x40`）。片方だけ独自の閾値にしない。
- 行末の空白トリム（`flushPage` の `/\s+$/`）は据え置き。
- `packages/scs` は Node API 非依存のピュアロジック層。`node:*` を import しない。
- 変更ごとに回帰テストを追加する。

## 完了条件 (受け入れ基準)

- [ ] DBCS ラン中の NL / CR / FF が制御として効き、改行・改ページが失われない。
- [ ] 奇数バイトの DBCS ラン（`SO 機 0x40 能 SI`）でも、以降が延々と化け続けない。
- [ ] 全角空白が行中で 2 桁の U+3000 として出る。
- [ ] SBCS のみの既存フィクスチャの出力が変わらない（既存テストが通る）。
- [ ] `npm run build` / `packages/scs`・`core`・`web-ui` の `vitest` / `eslint` が通る。

## 未確定事項 / 確認したいこと

- **SO/SI が印字位置を占めるか**は PUB400 実採取フィクスチャで「占めない」を確認したが、
  これは 1 機種・1 帳票の実測である。別のホスト／帳票で桁が合わない事例が出たら再検証する。
- 0xFF（`IGNORE_FF`）は 0x40 以上なので、DBCS ラン中は先行バイトとして扱われる。
  `wtd-applier` も同じなので**両経路で一致**しているが、どちらが実機準拠かは未確認。
