# レビューガイド: 重なった窓から前面を選ぶ

## 変更概要 / 目的

> ウィンドウ画面表示後に Attn コマンド欄を表示すると、ウィンドウ画面のデザインが元に戻ってしまいます。

見た目の話として報告されたが、調べると**より重い問題**が同時に起きていた——後ろのヘルプ窓の
F キー凡例が押せるまま残り、前面が Attn の窓なので**押すとラベルと違う動作になる**
（#163 で塞いだ危険が、窓が重なると再発）。

## 重要ポイント

### 1. 実測が規則を決めた（推測していない）

実機の WRKMBRPDM で 5 パターン採った。「**前面の窓が後ろの窓の枠を上書きする**」という
原理がそのままデータに出ていた。

| 重なり方 | 罫線枠 | 反転枠 | 修正前の判定 | 正否 |
|---|---|---|---|---|
| ヘルプのみ（3 位置） | 健全 | なし | ヘルプ | ✅ |
| ヘルプ→Attn（file） | **下枠が消えた** | 健全 | Attn | ✅ |
| ヘルプ→Attn（lib） | 健全 | 健全 | **ヘルプ** | ❌ |
| ヘルプ→Attn（opt） | 健全 | 健全 | **ヘルプ** | ❌ |
| Attn→ヘルプ（逆順） | 健全 | **壊れている** | ヘルプ | ✅ |

**誤るのは「前面が後ろの内側に収まったとき」だけ。** 枠を壊す位置なら壊れた側が検出されず、
修正前から正しく前面が選ばれていた。

### 2. だから規則もその 1 ケースに絞った

```ts
if (border && reverse && containedIn(reverse, border)) return reverse;
return border ?? reverse;
```

「枠が健全な方を前面とみなす」という一般規則は**採らなかった**。原理としては正しいが、
罫線経路の許容度（端の記号のずれを吸収する重なり率 80%・縦罫の半数以上）を締める必要があり、
**実測で必要になっていない変更まで巻き込む**。あの許容度は F1 ヘルプで上下端が対にならない
問題を解くために入っている（既存コメントの経緯）。

### 3. 部分重なりは扱わない

どちらが前面か判断できないので、従来どおり罫線枠を返して挙動を変えない（安全側）。
実測できていないものを推測で決めない。

## 主要な変更箇所

- `packages/web-ui/src/composables/fkeyLegend.ts` — 両候補を見て前面を選ぶ／`containedIn`
- `packages/web-ui/test/fixtures/window-stack/` — **実機採取の 7 スナップショット**
  （生は 1.8MB なので、判定に要る情報だけのビット列に圧縮して 88KB）
- `packages/web-ui/test/stacked-window.test.ts` — 5 パターンの回帰（8 件）

## リスク / 確認してほしい点

- **3 枚以上の重なり**は未実測・対象外。2 枚の規則で足りるかは分からない
- **部分的に重なる**ケースも未実測。従来どおりの挙動に倒してある
- 反転枠の検出を**常に走らせる**ようになった。反転が無い画面は即 return するので実質コストは無く、
  実機 14 画面で誤検出が増えていないことを確認済み
- 見た目について: 前面が Attn の窓になるので、**後ろのヘルプ窓からは装飾が外れます**。
  「前面はこちら」という正しい表現ですが、ご報告の「デザインが元に戻る」という見え方自体は
  （対象が入れ替わる形で）残ります。装飾を両方に出すのは別の話（複数窓の同時装飾）で今回は対象外
