## D2: 自己点検欄（モジュラス10/11）の実装をこの work では見送る

- 背景: `research.md` F6 の通り、ACS の `Field5250` はモジュラス10/11の
  自己点検欄検証を実装している（`checkModulusField()`/`modulusCheck()`）が、
  当プロジェクトには対応する実装が無い。この検証は FCW（Field Control Word）
  経由でフィールドに付与される属性で、当プロジェクトの `wtd-applier.ts` は
  未知の FCW を安全に読み飛ばすため、パースが壊れるという実害は無い
  （feature gap であり bug ではない）。
- 判断: この work では実装しない。`.aidev/backlog/acs-parity.md` に、
  アルゴリズム概要・FCW 経由で伝わること・正確な FCW 値の確認に実機トレースが
  必要なことを記録し、次回以降の work（実機アクセスがある時）に引き継ぐ。
- 理由 / 代替案:
  1. **正確な FCW 値が今回のデコンパイルからは一意に確定できなかった**——
     ACS のコンパイル済みコードでは FCW カテゴリの判定が `int` に符号拡張
     された `short` 値に対する `& 0xFFFFFF00` というマスク演算で行われており、
     元の `short` としての正確な16進数（`0xB0xx`/`0xB1xx` 系と推測されるが
     未確定）を、デコンパイル結果の定数だけからは復元できなかった。当て
     推量の値で実装すると、無関係な FCW を自己点検と誤認する、または実際の
     自己点検 FCW を見逃すリスクがある——**この work のスコープ
     （実機起動不要な静的突き合わせ）を超える**。
  2. **検証の粒度が既存の `validateFieldContent()` と異なる**——モジュラス
     10/11 はフィールド全体の最終値（特にチェックディジット桁）に対して
     行う検証で、既存の「打鍵・貼り付けされた差分文字を1文字ずつ検証する」
     という構造にそのまま組み込めない。フィールド確定時に呼ぶ別の検証関数を
     新設する設計が必要になり、この work の想定規模（正規表現1箇所の変更）を
     大きく超える。
  3. 実際にモジュラス10/11欄を使うアプリがどの程度あるか（利用頻度）は、
     静的調査だけでは分からず、実装コストに見合うかの判断材料が不足している。
- 影響: `.aidev/backlog/acs-parity.md` に記録する（deliver 工程、T3 相当）。
  実装する場合の次の一歩は「実機で自己点検欄付きの画面を作り、生バイトを
  採取して正確な FCW 値を確認すること」——`.aidev/works/
  20260915-acs-field-validation-audit/research.md` F6 にアルゴリズムの詳細を
  残してあるので、次回の work はそこから始められる。

## D4: `research.md` F3 のコード抜粋に書き写し誤りがあった——結論は変わらないが
記述を訂正した

- 背景: T1・T3 のタスク点検（独立点検）で、`field-validate.ts`/
  `field-validate.test.ts` に追加したコメントの「ACS の `checkDigitsOnlyChar()`
  は空白を許容しない」という記述が、`research.md` F3 に転記したコード抜粋
  （`if (!Character.isDigit(c) && c != ' ')`）と矛盾すると2件（T1・T3）
  独立に指摘された——その抜粋の通りなら空白は許容されることになる。
- 判断: `Field5250.class` を再デコンパイルして直接確認したところ、実際の
  コードは `c != 'NUL(0x00)'`（NUL文字）であり、`c != ' '`（空白）ではなかった。
  つまり `research.md` F3 のコード抜粋自体が**当初の（この work 内での）
  最初のデコンパイル結果を正しく書き写せていなかった**（NUL文字を空白と
  誤記した）。加えて、`research.md` を Write ツールで書いた際、この誤記部分
  （`'NUL(0x00)'` のつもりで書いた文字列）が**エスケープされずに実際の NUL
  バイトとしてファイルに埋め込まれてしまっていた**——`grep`・`Read` ツール・
  今回のタスク点検の2エージェントいずれも、この不可視な NUL バイトを
  「空白」として読み違えた（NUL は多くのテキスト表示で空白と区別できない）。
  再デコンパイルで確認した正しい内容（NUL文字、空白ではない）に基づき、
  `research.md` F3・`field-validate.ts`・`field-validate.test.ts` のコメントを
  訂正し、`research.md` 内の不可視な NUL バイトを可読なエスケープ表記
  （`NUL(0x00)` という文字列）に置き換えた。
- 理由 / 代替案: この訂正によって**結論は変わらない**——`SHIFT_DIGITS_ONLY`
  は当初から「一致する・変更しない」という判断であり、NUL文字であれ空白で
  あれ、どちらの場合も「打鍵・貼り付けされた文字の検証には対応しない」という
  結論に影響しない。誤っていたのはコード抜粋の書き写しと、それに伴う
  不可視なバイト混入のみ。
- 影響: 今後 `research.md` 等のドキュメントにコード抜粋を転記する際、
  制御文字（NUL 等）はエスケープされた**文字列表記**（`NUL(0x00)` という
  4〜6文字のテキスト）で書き、実際の制御バイトをファイルに埋め込まない
  よう注意する——埋め込むと `grep` で検索できず、表示上も他の文字（特に
  空白）と区別が付かなくなり、今回のような誤読の連鎖を招く。
