# 決定記録

## D1: 打鍵で書き換えた欄の後ろは直さない

- 背景: 当 PJ は編集した欄の残りを NUL にし（送らない）、ACS はホストが書いた実空白が残る（送る）。
- 決定: この work では扱わない。
- 理由: ホストは欄長まで空白で埋めて受け取るので、プログラムに届く値の意味は同じ。直すには web-ui の編集の値にホストの原本の桁を残す作りが要る（O 欄の SO/SI の位置と同じ規模）。

## D2: 平坦な形の符号は原典で直し、0x42 のワイヤは未確認のまま

- 背景: DSM の READALT の画面に `QsnPutInpCmd(0x42)` を続けたところ、ACS のコアは施錠のままで応答がカーソル 1,1・全欄空白になり、畳み方を測れなかった（原因は未解明。以前の READINP の画面では 0x42 が通っている）。
- 決定: ACS `sendAll` の平坦な形の枝（case 66）は 0x82 の枝と**同じ文**で、その文は 0x52 で実測済み（`     -` → `40404040d0`）なので、原典に合わせる。0x42 のワイヤそのものは未確認と記録する。
- 代替案: 測れるまで据え置く——同じ文が別の枝で実測されており、据え置く根拠が無い。

## D3: 奇数長の G 欄は偶数へ丸めたまま

- ACS の奇数長の G 欄は未測定。組を割らないため、未編集でも従来どおり偶数へ丸める。

## D4: NUL だけの欄も原本として送る（review ラウンド 1）

- 背景: 構造の桁（SO/SI・全角）が無い G 欄（NUL だけ）は `hasDbcsStructure` が偽で、従来どおり 0x40 で欄長まで詰めていた。
- 決定: 実機の ACS のコア（READDBCS に NUL だけの G・O を足して測った）は **0 バイト**で送った。`dbcsRawCells` は NUL だけの欄も原本として返す。
- 影響: SBCS の欄でも NUL だけなら同じ経路になるが、結果は従来と同じ（末尾の NUL を落として 0 バイト・符号の桁が NUL なら畳まない）。

## D5: 工程記録の欠け（review ラウンド 1 の sent_back）

- review ラウンド 1 の指摘を `review.md` に書いた後で `aidev event review start` を打ったため、`sent_back` が「指摘行が増えていない」として CLI に拒まれ、記録されていない。
  その後の `unapprove test`・`unapprove coding`・`coding start`〜`approve review` は記録された。指摘と対応は `review.md` のラウンド 1 にある。ts を後から打ち直して辻褄を合わせることはしない。
