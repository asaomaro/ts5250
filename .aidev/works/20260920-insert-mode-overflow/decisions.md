## D3: 空きの計算を 1 つの純関数に集約し、全経路がそれを呼ぶ

- 背景: あふれの経路が **4 つ**あり（research F7）、うち ACS と同じ数え方をしているものは **0 個**。
  直前の work（`20260920-field-error-no-value`）は「同じ関数を呼ぶだけでは足りず、
  **呼ぶ位置まで揃える**必要がある」を**3 ラウンドかけて学んだ**（条項 `paired-artifact-sync`）。
- 決定: **`fieldEdit.ts` に純関数を置き、各経路が独自に「入るか」を判断しない。**
  - ~~`roomForInsert()` を 1 つ置き、打鍵・`paste()`・貼り付け・DBCS・IME の全経路がこれを呼ぶ~~
    → **design（改訂 2）で 2 つに割れた**: `trailingRoom()`（末尾の空白桁数）と
    `reservedTail()`（符号桁・DBCS 桁の取り置き）。**1 つにできなかった理由**は、
    `insertInto` が測る前に末尾空白を trim するので `trailingRoom` を流用できないこと
    （design「依拠する既存の事実」）。**共有できるのは `reservedTail` のほう**。
  - **`fieldEdit.paste()` は対象から外す**——本番の呼び出し元が無く、テストからしか呼ばれない
    （design の AC4 対応）。数えるのは**打鍵 / `insertInto` 経由の貼り付け / DBCS 打鍵 / IME** の 4 経路。
- 理由 / 代替案: 「各経路でそれぞれ直す」は、**今回また片方だけ直す**ことになる。
  数え方（末尾の連続空白・符号桁の取り置き）は 1 か所にあるべき事実で、
  分散させる理由が無い。
  **テストは「全経路に同じ入力を通して同じ答えになる」形で書く**（AC4）——
  関数を共有しているだけでは、呼ぶ位置がずれていても緑になる（前 work の実測）。
- 影響: `ScreenGrid.vue` の既存の `fitsBytes` / `absorbDbcs` / `insertInto` は、
  **置き換えではなく併用**する（バイト予算と桁の空きは別の判定）。
  design「インターフェース」§5 のとおり、`insertInto` が共有するのは `reservedTail` だけ。

## D4: 挿入モードでは「カーソルが最終桁の上」を拒否する（ACS に合わせる）

- 背景: design の「未確定事項 3」。ACS は `PS5250.insertChar` の入口で
  `cursorSBA == getEndPos()` なら**空きの有無に関係なく即座に拒否**する（research F2。デコンパイル）。
  当 PJ の `typeChar` は `cursor >= len` でしか弾かず（`fieldEdit.ts:31`）、
  `cursor` は 0..len なので**最終桁の上（`cursor === len-1`）は通ってしまう**。
  **推測で埋めずに実機で確かめた**（原則 2）。
- 決定: **挿入モードのとき `cursor === len-1` を拒否する**（値を変えず `MSG_NO_ROOM`）。
  **上書きモードは変えない**（ACS 側も `insertChar` の話であり、上書きは別経路）。
- 理由 / 代替案:
  - **実機で確定した**（research F11）。**46 桁目が空白＝空きが残っている**のに ACS は拒否し、
    同じ run の対照（45 桁目への挿入）は通った。**空きの数え方では説明できない独立した条件**。
  - デコンパイルの読み（F2）と実機が**一致**——条項 `measurement-sanity` の
    「別の経路でもう一度取る」を満たす。F4/F5 では読みが実機と食い違ったので、
    **一致したこと自体が確認の価値を持つ**。
  - 代替案「差として記録するだけで合わせない」は、`AGENTS.md` 判断の原則 1
    （ACS が正典。「当 PJ の構造では真似できない」で退けない）に反する。
    今回は構造上も素直に書ける（`typeChar` の早期 return を 1 つ広げるだけ）。
- 影響:
  - **副作用として「挿入モードでは最終桁に直接打ち込めない」**という規則になる。
    最終桁を埋めるには手前の桁から押し出す。**奇異に見えるが実測どおり**。
  - **既存テストは壊れない**——`field-edit.test.ts:34-41` は `initEdit("AB   ", 5, 1)` で
    `cursor=1`、`screen-grid.test.ts` の挿入モード群は貼り付けで `offset 0`。
    いずれも最終桁ではない（確認済み）。
  - **受け入れ基準を 1 つ足す**（design の AC 対応・requirements の完了条件）。
  - **貼り付け（`insertInto`）に同じ規則を掛けるかは未確認**——ACS の貼り付けが
    `insertChar` を繰り返すのかは測っていない。**この work では打鍵の経路にだけ掛け**、
    貼り付けは現状のままとする（埋めずに「未確認」と書く）。

## D5: `dbcsReserved` は `only` / `pure` だけを対象にし、`either` は取り置かない

- 背景: design の「未確定事項 2」。ACS は `insertChar` で `isDBCSOnlyField()` と
  **`isEitherFieldDBCSOn()`（either 欄が**いま**DBCS 側に倒れているか）**の両方で桁を取り置くが、
  **当 PJ の欄モデルには後者に当たる実行時状態が無い**
  （`DbcsFieldType` は静的種別のみ。`packages/tn5250/src/screen/types.ts:52,137`）。
- 決定: **静的に DBCS と分かる種別（`only` / `pure`）だけ取り置く。`either` は取り置かない。**
- 理由 / 代替案:
  - **無い状態を推測で作らない**（原則 2）。「いま DBCS 側か」を `chars` の中身から
    推定する案は、**推測を実装に埋め込む**ことになるので採らない。
  - 取り置かない側に倒すと、either 欄で**ACS より 1 桁多く入る**可能性が残る。
    これは**値を壊す向きではない**（`fitsBytes` がバイト予算で別途止める）。
    逆に倒す（常に取り置く）と、**SBCS しか入っていない either 欄で 1 桁損する**——
    こちらは利用者から見て明確な不具合になる。**害の小さい側を既定にする。**
  - **either 欄の実行時状態そのものを持つべきか**は、この work より広い設計問題。
    **台帳へ送る**（実測を添えて）。
- 影響: `reservedTail({ dbcsReserved })` の呼び出し側（`roomOptsOf(f)`）が
  `DbcsFieldType` を見て決める。**either は false**。この判断をコードにも注記する
  （条項 `comment-provenance`。「なぜ either を外したか」が後から読めるように）。

## D10: IME 経路の `base` / `e` の不整合は**この work では直さない**（範囲外・台帳へ）

- 背景: `onCompositionEnd`（`ScreenGrid.vue:3472` 付近）は
  `dbcs ? dbcsType(base, ch, f) : typeChar(e, ch, …)` と書かれている。
  `base` は「選択を消した直後なら挿入扱いにする」ための状態（`composeReplacedSelection`）だが、
  **SBCS 側は `base` ではなく `e` を渡している**。
- 決定: **直さない。** 記録して台帳へ送る。
- 理由: この work の受け入れ基準（AC1〜AC12）はどれもこの不整合を対象にしておらず、
  直すと**選択を置換したときの IME 確定の挙動が変わる**——別の回帰を呼ぶ。
