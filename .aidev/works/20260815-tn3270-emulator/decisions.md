# 設計判断の記録: 3270 エミュレータ

コードから参照される深い判断の背景。要点はコード側のコメントに、経緯と代替案はここに置く
（AGENTS.md「深い設計判断は decisions.md に切り出し、コードから参照する」）。

---

## D2: `transport/` を複製し、`@ts5250/base` へ降ろさない

**判断**: `Transport` インターフェースと `TcpTransport` は `@ts5250/tn5250` と同型だが、
`@ts5250/tn3270` に**複製**する。

**理由**: `base` へ降ろすと `base` が `node:net` / `node:tls` を持つことになる。
`packages/tn5250/test/dependency-direction.test.ts` は
**「`base` と `ebcdic` は外部にもワークスペースにも依存しない」を不変条件として検査**しており、
これを壊す。`base` の売りは「依存ゼロ・ブラウザで動く」ことなので、ここを崩す価値は無い。

**代替案**: `@ts5250/transport` を新設して両者から使う。**採らなかった**——
パッケージを 1 つ増やす費用に対し、得られるのは 130 行の重複解消だけ。
2 つの写しが**同じままだと分かってから**にする（そのときは tn5250 側も動かす必要があり、
この work のスコープ（5250 側は触らない）を超える）。

## D4: スナップショット型を tn5250 と意図的に重複させる

**判断**: `Cell` / `CellKind` / `Field` / `ScreenSnapshot` を `tn3270` に**新規定義**する。
ただし**フィールド名・列挙値を tn5250 と一致させる**。

**理由**: `tn3270` は `tn5250` に依存できない（同位・相互非依存）。`base` へ移す案は
tn5250 の既存型を動かすことになり、requirement の「5250 側の既存挙動は変更しない」に反する。

**なぜ形を揃えるのか**: 5250 の `CellKind` が持つ
`sbcs / dbcs-lead / dbcs-tail / so / si / attr` は、**3270 のバッファ構造とそのまま対応する**
（実測で確認: DBCS 1 文字＝2 桁、SO/SI＝各 1 桁、属性＝1 桁）。
将来 web-ui が両方を描くとき `base` へ括る候補になるので、**括りやすい形で置いておく**。

## D5: 標準サイズと代替サイズを両方持つ

**判断**: 画面は「標準 24x80」と「モデル固有の代替サイズ」の 2 段を持ち、
`Erase/Write`(F5) は標準・`Erase/Write Alternate`(7E) は代替に切り替える。

**根拠**: RFC 1576 の直読。

> The -2 following 3278 designates the alternate screen size. 3270 terminals have the ability
> to switch between the standard (24x80) screen size and an alternate screen size.
> Model -3 is 32x80, model -4 is 43x80 and model -5 is 27x132.

**5250 との違い**: 5250 は端末タイプを接続時にしか申告できず、**セッション中に画面サイズを
変えられない**（`docs/PROTOCOL.md` §2.1）。3270 は**コマンドで変わる**。
この差を画面モデルに織り込まないと、代替サイズの画面でバッファを作り直す経路が無くなる。

**照合上の注意**: **`s3270` はこの区別を報告に反映しない**——`EW` / `EWA` のどちらを受けても
モデルの代替サイズを返す（実測）。よって s3270 との桁単位照合は**代替サイズ側に揃える**。
「EW で標準サイズに戻る」ことは自実装の内部状態でしか検証できない。

## D7: `ByteReader` / `ByteWriter` を複製する

**判断**: `@ts5250/tn5250` の `protocol/bytes.ts` と同じものを複製する。

**理由**: D2 と同じ。`base` にしか依存しない純粋なユーティリティなので
AGENTS.md の「`base` に置く基準 2（複数パッケージが要るが、どれにも属さない）」に
**当てはまり得る**が、括るには tn5250 の import 書き換えが要る。
また 3270 側は `address.ts` と絡む読み取り（6 ビットコード表・可変長アドレス）が増える見込みで、
**2 つの写しが同じままとは限らない**。

**follow-up**: deliver 後に 2 つの写しが実際に同一なら `base` へ括る（retro で起票する）。

## D8: フィールドを保持せず `snapshot()` で導出する

**判断**: `Screen3270` はフィールド一覧を持たない。`snapshot()` のたびに属性桁を走査して組み立てる。

**理由**: 増分管理は `MF`（フィールド属性の書き換え）・`RA`（属性桁の上書き）・`EW`（全消去）が
絡むと**組み合わせが爆発する**。3,564 桁の線形走査は無視できる費用で、
**正しさを構造で担保できる**。`@ts5250/tn5250` の `screen/buffer.ts` が 1,047 行に膨らんだ
主因が増分管理なので、同じ轍を踏まない。

**MDT も同じ**: 別のフラグ配列を持たず、**属性桁の属性バイトのビット**に持つ（実機と同じ）。
真実が 1 箇所に閉じる。

## D9: `inbound` を状態を持たない純関数にする

**判断**: `applyInbound(screen, record)` はモジュールスコープの状態を持たない。
状態は `Screen3270` とセッションだけが持つ。

**理由**: パーサが状態を持つと、**trace の replay と実接続で挙動が分かれる余地**ができる。
無状態なら **replay がそのまま単体テストになる**——実際、照合で確かめたバイト列を
fixture に落とすだけで docker 無しの回帰資産になった（subtask 05）。

**例外の扱い**: DBCS 区間（`SO` 〜 `SI`）の追跡と `SA` の拡張属性は
**1 レコード内のローカル変数**で持つ。レコードをまたがないので無状態性は保たれる。

## D10: テストを 2 段に分ける

**判断**: `npm test` の既定は単体・replay のみ。s3270 / TK4- との照合は
`TN3270_E2E=1` で明示的に有効化する。

**理由**: 照合には docker が要る。docker の無い環境で `npm test` が落ちるのは避ける。
**照合で得た結果は fixture に落として単体段へ還元する**ので、
1 回照合すれば以後は docker 無しでも回帰が効く。

## 実測で覆した判断（記録として残す）

この work では**推測で書いた箇所が 3 回、実測で覆された**。いずれも
「原典を先に確認する・知識ベースで書き始めない」（AGENTS.md）を守り切れなかった箇所である。

### 1. 色とハイライトの割り当て

初稿で `COLOR.DEFAULT = 0xF0` などと標準知識で埋めていた。実測すると
**`0xF0` は「既定」ではなく `neutralBlack`**（既定は `0x00`）、
**ハイライトの `0xF3` は未定義**だった。
→ `s3270` に F0〜F7 を流して復号名を読み、実測値に置き換えた。

### 2. PA / Clear の短形式

`spec.md` に「PA1〜PA3 と Clear は AID とカーソルアドレスのみ」と書いた。
実測では **AID 1 バイトだけ**で、カーソルアドレスすら送らない。
→ spec を訂正し、実測値（`6c` / `6e` / `6b` / `6d`）をテストで固定した。

### 3. Read Modified の SBA（**最も危なかった**）

最初の探針で「s3270 は変更欄の前に SBA を置かない」と結論し、そう実装した。
**探針が誤っていた**——キーを総当たりする際、末尾で `Clear()` を押していた。
Clear は画面を消すので**以後は非フォーマット画面**になり、そこへの入力は
確かに SBA 無しで送られる。その状態を測っていた。

入力を伴う照合テストを足したところ `7d4b5d **1140c1** c1c2 **114b5b** e9e9` が出て発覚した。
正しくは「**フォーマット画面では欄ごとに SBA、非フォーマット画面では SBA 無し**」。

**教訓**: 実測は「何を測ったか」まで確かめないと、**推測より危険**になる——
数字が付いている分だけ信じてしまう。`outbound.ts` のコメントにこの経緯を残した。

## D11: コマンドコードの 2 系統を正規化して吸収する

**判断**: `normalizeCommand()` で SNA 系（`01`/`05`/`0D`/`02`/`06`/`0E`/`0F`/`11`）を
EBCDIC 系へ写してからパーサに渡す。**判定を 1 か所に閉じる**。

**根拠**: 実測（`artifacts/cmd.trc`）。両系統を s3270 に流したところ、同じコマンド名に復号された。
**Hercules は EBCDIC 系、IBM i は SNA 系**を使う。片方だけ実装すると、もう片方のホストで
「交渉は通るのに画面が来ない」という分かりにくい形で止まる（実際に踏んだ）。

**代替案**: 分岐を `switch` に両方書く。**採らなかった**——コマンドが増えるたびに
2 か所書く必要があり、書き忘れが静かに通る。

## D12: Query Reply は「実際に持っている機能だけ」申告する

**判断**: Summary / UsableArea / AlphanumericPartitions / CharacterSets / ImplicitPartition
＋（拡張属性ありなら）Color / Highlighting を申告する。
**DDM・RPQ Names・Reply Modes は申告しない**（実装していないため）。

**理由**: 申告は「これができる」という約束で、**無い機能を申告すればホストはそれを前提にした
データを送ってくる**。s3270 は 10 種を返すが、そのまま真似ると持っていない機能まで約束することになる。

**DBCS の申告は CCSID から導出する**（`codecForCcsid(ccsid).isDbcs`）。
**日本語 IBM i は DBCS 記述子が無いと画面を出さずに黙る**（実測）。
記述子の中身（SBCS 290 / DBCS 310 / 純 DBCS 300、3 件目は `SW=18` の全角セル）は
s3270 が同じホストへ返したものを**解析して事実として書き起こした**（バイトの丸写しではない）。

## D13: 検証環境を 1 つに絞ったことがスコープ判断を誤らせた（教訓）

**何が起きたか**: TK4-（MVS 3.8j）だけで検証していたため、
「WSF は今回のスコープ外」「コマンドコードは 1 系統」と判断した。
どちらも **IBM i に繋ぐには必須**で、deliver 後にユーザーの指摘（「実機確認は IBM i で可能か」）で発覚した。

**なぜ気づけなかったか**: TK4- は Query を撃たず、EBCDIC 系コマンドしか使わない。
**検証環境が要求しないものは、スコープから静かに落ちる。**

**教訓**: 「1 つのホストで通った」は「実装が正しい」ではなく
「**そのホストが要求する範囲では正しい**」でしかない。
`decisions.md` の「実測で覆した判断」と同じ構図——**測った範囲の外は分からない**。

## D14: IBM i 向けに NEW-ENVIRON でコードページを申告する

**判断**: `DO NEW-ENVIRON` を受理し、CCSID から導いた `KBDTYPE` / `CODEPAGE` / `CHARSET` を
`IS` で返す（RFC 2877）。素の 3270 ホストは NEW-ENVIRON を送ってこないので影響しない。

**理由（実測）**: 申告しないとホストはシステム既定のコードページで仮想デバイスを作る。
pub400 は `QCCSID=273`（ドイツ語）なので、こちらが CCSID 37 で送った `'@'`(0x7C) を
`'§'` と読む。結果 **`'@'` 入りパスワードが化けて `CPF1120`** で弾かれた。

**切り分けの経緯**: 3270 でサインオンが `CPF1120` で落ちたとき、
1. 送出レコードの構造（AID / カーソル / SBA アドレス / 各欄の長さ）が 5250 経路と一致することを確認
2. パスワードの符号化バイトが、**5250 経路が送った既知の正常バイト列と完全一致**することを確認
3. → 残る差は telnet の申告だけ、と絞り込んだ

**これは 5250 側に記録があった落とし穴**（`tn5250/src/session/terminal-type.ts` のコメント）。
**同じ製品の中に答えが書いてあったのに、3270 は別物という思い込みで参照しなかった。**
D13 と同じ形の失敗——「3270 だから」で 5250 の知見を切り離してしまった。

日本語機で先に成功したのは、**そちらのパスワードに variant 文字が無かった**ためで、
実装が正しかったからではない。**通った 1 例は正しさの証明にならない。**
