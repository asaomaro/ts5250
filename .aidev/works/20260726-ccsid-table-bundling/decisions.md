# 決定記録

## D1: 削減幅が想定（約 700 KB）を大きく超えたので、何が落ちたのかを実測で確認した

- 背景: T9 でバンドルを測ったところ **1,407,469 → 305,643 バイト（−1,101,826・78% 減）**だった。
  spec 段階の見積もりは「dist の `ibm930.js` 350,204 ＋ `ibm939.js` 350,202 ＝ 約 700 KB」で、
  実測はその 1.5 倍以上。**期待より良い結果は、期待どおりの結果より疑うべき**——
  必要なコードまで落としていれば、同じように「小さくなった」と見える。

- 決定: **数値で正体を確かめてから受け入れる**。`main` を worktree に取って baseline を再ビルドし、
  新旧のバンドルを 2 つの軸で突き合わせた。

  | 軸 | 旧 | 新 | 差 |
  |---|---|---|---|
  | サイズ | 1,407,469 バイト | 305,643 バイト | −1,101,826 |
  | 数値トークン（`\d+,`） | 187,881 個 | 2,063 個 | **−185,818** |
  | 旧のみに存在する識別子（7 文字以上） | — | — | **`d5d71879` の 1 個だけ**（チャンクのハッシュ） |

  減ったのは**ほぼ全部が数値データ＝変換表**であり、**機能を持つ識別子は 1 つも消えていない**。

- 理由 / 代替案:
  - 185,818 という数は表の構成と整合する。混在 CCSID 1 表あたりの数値は
    「マッピング数 × 4」（E2U と U2E に各 2 数値）で、
    930 と 939 が各 12,015 → 48,060 × 2 ＝ 96,120、1399 が 22,321 → 89,284。
    合計 **185,404** で実測 185,818 とほぼ一致する。
    つまり baseline には **930 / 939 に加えて 1399 の DBCS データも入っていた**——
    requirement 段階で名前文字列（`ibm-1399_P110-2003`）を検索したときに見つからなかったのは、
    bundler が外側のオブジェクトリテラル（`name` を含む）だけ落とし、
    参照されている Map 構築用の配列は残していたため。
    **識別子の検索だけでは表の在処を測り切れなかった**（数値トークン数の方が正確な尺度だった）
  - サイズだけ見て「78% 減った」と報告する案は採らない。
    削減幅が見積もりを超えたときに中身を確かめないのは、
    「テストが通ったから正しい」と同じ種類の油断になる

- 影響:
  - requirement の完了条件「baseline から 400,000 バイト以上小さい」は
    **1,101,826 バイト減**で大きく満たす
  - requirement には「バンドルに 930/939 の DBCS 表が含まれない」と書いたが、
    実際には **1399 の DBCS データも落ちていた**（当初の実測が name 文字列に頼っていたため
    見えていなかった）。受け入れ基準を下回る事象ではないので基準は変更しない
  - 残る表の識別子は `ibm-930_P120-1999_SBCS` のみ＝`katakanaChar` が使う 256 要素の表。狙いどおり

## D2: 削減の測り方は「識別子の検索」ではなく「数値トークン数」を主にする

- 背景: D1 のとおり、`grep "ibm-[0-9]*"` による識別子検索は
  **表のデータが残っていても名前が落ちていれば検出できない**。
  requirement 段階でこの手法を使ったため、baseline に ibm1399 のデータが
  入っていることを見落としていた。

- 決定: 回帰検査（T8）は import グラフの到達可能性で固定し、
  バンドルの検証では**数値トークン数**を主な尺度として報告する。
  識別子検索は「どの表か」を特定する補助として併用する。

- 理由 / 代替案: バンドルサイズだけでは何が入っているか分からず、
  識別子検索だけでは残骸を見逃す。**表はほぼ数値の羅列**という性質を使うのが最も直接的。

- 影響: walkthrough と PR 本文では両方の数値を併記する。
