# 決定記録

## D1: 補助条件（入力欄が矩形内に収まるか）は実装しない

- 背景: requirement の「対象」と spec の「web-ui: 補助条件」に、`snap.fields` が書き込み矩形に
  収まるかを見る条件を挙げていた。backlog も「安価なわりに効く」と書いている。
- 決定: **今回は入れない。** 判定は CLEAR / RESTORE / 矩形の下限・全画面一致の 4 条件のみ。
- 理由 / 代替案:
  - **本来の狙い（③ の誤検出を弾く）は CLEAR の条件だけで達成できた。** ③ は通常画面なので
    `cleared=true` が立ち、補助条件を足しても結果は変わらない（`window-write-extent.test.ts` で確認）。
  - 一方、`fields` を見る条件は**既存の前面判定（`containedIn`）と干渉する恐れがある**。
    窓が重なったときの前面選択は実機 5 パターンの採取に基づいて調整済みで
    （`stacked-window.test.ts` が担保）、実データの裏付けなしにここへ条件を足すと
    **担保済みの挙動を壊す側のリスクだけが増える**。
  - 本物の窓でも背景の欄が `fields` に残ることがある（ホストが様式を送り直さない場合）ため、
    条件としての確度も CLEAR より低い。
- 影響: requirement の完了条件は補助条件を要求していないため、受け入れ基準には影響しない。
  必要になれば別作業として足せる（backlog の window-detect.md に残す）。
- **【D5 による訂正】** 「③ の誤検出は CLEAR の条件だけで達成できた」という上の理由は**誤り**だった。
  実機検証で CLEAR による否定は罫線経路に掛けられないと判明し、**③ は未解決のまま残っている**。
  補助条件を見送る判断自体は変えない（前面判定との干渉リスクは依然あるため）が、
  **③ を直す候補として backlog に残す**。

## D2: `WriteExtent` を `packages/core/src/index.ts` からも export した

- 背景: spec の「対象範囲」表に `index.ts` を挙げていなかったが、web-ui 側のテストが
  `WriteExtent` を型として import するため、バレルに無いと `vue-tsc` が
  `TS2305: has no exported member 'WriteExtent'` で落ちた。
- 決定: `ScreenSnapshot` と同じブロックへ型 export を追加する。
- 理由 / 代替案: 画面モデルの共有型は既に `index.ts` から出しており、そこへ並べるのが素直。
  `browser.ts` へは**足さない**——web-ui は型としてしか使わず、型は実行時に消えるので
  ブラウザ入口を広げる理由が無い（AGENTS.md「狭い入口を使う」）。
- 影響: 対象範囲が 1 ファイル増えた。挙動への影響は無い。

## D3: `restoreScreen` は全画面書き込みとして記録する

- 背景: spec では「`restored=true` ＋ 全画面を矩形とする」と決めていたが、
  実装時に「矩形を付けずフラグだけにする」案も検討した。
- 決定: **フラグと矩形の両方**を立てる。
- 理由 / 代替案: 判定側は `restored` を先に見るので矩形は判定に効かないが、
  `WriteExtent` は「そのレコードで画面のどこが変わったか」を表す型であり、
  画面を丸ごと差し替えた事実を矩形にも反映しておかないと**型の意味と実体がずれる**。
  将来 `lastWrite` を別用途（差分描画・記録再生）に使うときに嘘の値を配らないため。
- 影響: なし（判定は `restored` で先に打ち切る）。

## D4: 実機での窓レコード採取は行えないまま進めた

- 背景: research F7 のとおり、実機（）へ接続はできるが**認証情報が無い**
  （`connections.json` にユーザー/パスワードが無く、`.env` は `AS400_SECRET_KEY` のみ）。
- 決定: 窓側は**合成データストリーム**で回帰テストを組み、実機採取は未了のまま進める。
- 理由 / 代替案: 通常画面側は**リポジトリ同梱の実機採取レコード**
  （`packages/core/test/fixtures/pub400-*.jsonl`）を再生して実測できており、判定の第一級条件
  （CLEAR の有無）はその実データが根拠になっている。窓側の「SAVE SCREEN → CLEAR なしの
  部分書き込み」も、リポジトリ内に実機由来の記録がある（`window-backdrop.test.ts` 冒頭の
  GRIDCL5/GRIDCL7 の受信バイト内訳）。合成で組む前提は既に実機で裏付いている。
- 影響: 「実機の窓で `lastWrite` が期待どおりか」は未検証のまま。
  認証情報が使えるようになれば `scripts/probe-window-signal.mjs` を直して確かめられる
  （同スクリプトは DBCS テール桁を空白へ置換しており、画面文字列の一致が全て外れるバグがある。
  未追跡ファイルなので本作業では触っていない）。

## D5: 実機検証で前提が半分崩れ、門を反転経路だけに絞った

- 背景: D4 のとおり認証情報が無く実機検証を保留していたが、利用者からパスワードの提供を受けて
  2026-07-29 に実機（IBM i 7.5）で `lastWrite` を実測した。**前提が半分しか成り立たなかった。**

  | 画面 | `lastWrite` |
  |---|---|
  | Attn の窓（ATNPGM。反転枠） | `cleared=false` / `rect=r18-24` / `cells=353` ＝**重ね書き** |
  | **F1 ヘルプ窓**（`.`／`:` の箱＝backlog の ①） | **`cleared=true` / `rect=r1-24` / `cells=1892`** |
  | 通常画面（メニュー・PDM・DSPLIBL） | `cleared=true` / `rect=r1-24` |
  | 窓を閉じた（F3 / F12） | `restored=true` / `rect=r1-24` |

  **ヘルプ窓はホストが画面をクリアしてから背景の見出しごと箱を描き直す。** つまり
  「本物の窓は背景を消さずに窓の領域だけ書く」は IBM i のヘルプ・パネルには当てはまらず、
  受信データ上は通常画面と区別が付かない。

- **回帰を実測で確認した**: 実機のヘルプ画面 fixture に対し、`lastWrite` 無しでは
  `{row1:3, row2:23, col1:3, col2:78}` と正しく検出されるのに、`lastWrite` を渡すと `null` になった。
  当初の門は**本物のヘルプ窓を落としていた**（backlog が「却下」した条件と同じ失敗の形——
  本物を弾いて誤検出を通す）。

- 決定: 門を**反転経路（`detectReverseFrame`）にだけ適用**する。罫線経路（ヘルプ窓が通る道）には掛けない。
  - `isOverlayWrite(snap)`＝`!cleared && !restored`。記録が無ければ true（従来どおり）
  - 直したのは **④ 反転バナーの誤検出のみ**。**③ 帳票の誤検出は残る**（回帰はしない）

- 理由 / 代替案:
  - **証拠のない否定はしない。** ③ とヘルプ窓は受信データ上で同一の形（CLEAR ＋ 全画面）をしており、
    ③ を切る条件は必ずヘルプ窓も切る。分ける材料がこの信号には無い。
  - 反転経路に限れば条件は実測で裏付く——Attn の窓は重ね書き、反転バナーが出る通常画面は CLEAR。
  - 「全部やめて plumbing だけ残す」も検討したが、④ は実測で安全に直せるので残した。

- 影響:
  - requirement の完了条件のうち「③ が窓と判定されない」を**満たさなくなった**。
    ④ は満たす。① ② は従来どおり（回帰なし）。
  - 実機のヘルプ画面を fixture 化して回帰資産にした
    （`packages/web-ui/test/fixtures/window-stack/real-help-menu.json` ＋ `test/real-help-window.test.ts`）。
    **同じ設計を再度試させないための証拠**として残す。
  - ③ の解決には別の材料が要る。backlog に差し戻す。
