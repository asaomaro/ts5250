# 要件: ウィンドウ判定を「受信データの書き込み範囲」で決める

出典: `.aidev/backlog/window-detect.md`（2026-07-28 の実測調査）。

## 背景 / 課題

ウィンドウ装飾（`windowFrame` / `windowBackdrop`）を出す範囲を、**画面に描かれた罫線から
推測**している。この推測に誤検出があり、2026-07-28 の実測で **2 経路とも誤る**ことが確認された。

| 画面 | 判定 | 誤りの経路 |
|---|---|---|
| ① 本物の窓（F1 ヘルプ相当。上下 `.`・左右 `:`） | 検出（正） | — |
| ② 一覧画面（PDM 風。`---` 区切り 2 本） | null（正） | — |
| ③ 表（左右に `:` が並ぶ帳票） | **誤検出** | 罫線経路 |
| ④ 反転バナー（見出し行＋末尾行が反転） | **誤検出** | 反転経路 |

推測条件が緩いことが直接の原因ではあるが（`fkeyLegend.ts:35-47`。`BORDER_H` が 8 桁以上連続する行が
2 本で 80% 以上重なり、間の行の**左右どちらか**に `BORDER_V` が**半数以上**）、条件を締めても
本物を弾くだけで根本解決にならない。

**根本原因は材料不足である。** 窓かどうかは描画結果ではなく**受信データ**に出ている
（本物の窓は背景を消さずに窓の領域だけ書く／通常画面は画面全体を書く）が、
この情報は現在**捨てられている**。実装で確認した事実:

- `ApplyResult`（`packages/core/src/protocol/wtd-applier.ts:10-32`）に書き込み範囲も
  「CLEAR したか」も無い
- `ScreenSnapshot`（`packages/core/src/screen/types.ts:185-196`）に dirty 領域が無い

判定が見た目しか見られないのは、そもそも材料が web-ui まで渡っていないためで、
**推測条件をいくら調整しても限界がある**。

## 目的 / ゴール

レコード適用ごとの**書き込み範囲（外接矩形）と CLEAR 有無**を core が記録して snapshot に載せ、
web-ui のウィンドウ判定の**第一級条件**をそれに置き換える。罫線検出・反転検出は
「窓かどうか」の判定から、「**枠がどこか**を詰める補助」へ降格させる。

これにより ③④ のような通常画面が窓と判定されなくなり、①（本物の窓）は引き続き検出される。

## スコープ

### 対象

- **core**: レコード適用ごとに書き込みの外接矩形を記録し、`CLEAR_UNIT` / `CLEAR_UNIT_ALTERNATE` を
  通ったかと併せて snapshot に載せる
  - セルへの書き込みは `packages/core/src/screen/buffer.ts` の
    `setChar`(425) / `setShift`(433) / `setDbcs`(441) / `setAttr`(449) / `eraseRange`(457) の
    **5 箇所に集約されている**ので、そこで外接矩形を更新すれば足りる
  - 矩形はレコードの頭でリセットする
- **web-ui**: 判定の第一級条件を「直近の書き込みが画面の一部に閉じた矩形か」にする
  （`fkeyLegend.ts:205` の `detectWindowRect`）
- **補助条件**: 入力欄が全て矩形内に収まっているか（`snap.fields`）を併用する
- 実測した 4 画面（①〜④）を回帰テストに起こす

### 対象外

- `snap.gui.windows`（`CREATE_WINDOW(51)` 構造化フィールド＝**ホストの宣言**）がある場合の経路。
  ホストが枠を送っているときに推測を止める現在の作りは**正しい**ので触らない
- ウィンドウ装飾の**見せ方**（`windowFrame` / `windowBackdrop` のデザイン候補）の変更
- 罫線検出・反転検出そのものの**削除**（降格させるが残す。枠位置の絞り込みに使う）

## 機能要件

- `ApplyResult` に、そのレコードで書き込まれたセルの**外接矩形**（行・桁の範囲。書き込みが
  無ければ無し）を持たせる
- 同じく `CLEAR_UNIT` / `CLEAR_UNIT_ALTERNATE` を通ったかを持たせる
- 上記を `ScreenSnapshot` に載せ、web-ui から参照できるようにする
- `detectWindowRect` は、書き込み矩形が**画面全体でない**ことを第一級の条件として判定する
  - 通常画面は 1 行目や F キー凡例まで書くので外接矩形が全画面になり、自然に外れる
  - 「メッセージ行だけ書き換えた」ような**小さすぎる更新**を窓と誤らないよう、高さ・幅の下限を置くか
    前回画面との差分を見るかを決めて実装する
- 罫線検出・反転検出は、窓と判定されたあとの**枠位置の特定**に用いる

## 非機能要件 / 制約

- **既存テストを壊さない**: `window-view` / `stacked-window` / `reverse-frame-window` /
  `pane-cursor-window` の 4 本が現行挙動を担保している
- 書き込み記録は全セル書き込みの経路に入るため、**走査を増やさない**
  （外接矩形の min/max 更新のみ。dirty ビットマップ等は持たない）
- snapshot はセッションごとに WS/MCP へ流れるため、追加フィールドは**小さく**保つ
- 既存の snapshot 消費者（MCP・printer 等）を壊さないよう、追加フィールドは**任意**とする

## 完了条件 (受け入れ基準)

- [ ] `ApplyResult` と `ScreenSnapshot` に書き込み外接矩形と CLEAR 有無が載る
- [ ] 既存 4 本（`window-view` / `stacked-window` / `reverse-frame-window` /
      `pane-cursor-window`）が**改修前と同じく通る**
- [ ] 実測 4 画面の回帰テストがあり、**③④ が窓と判定されない**ことが固定されている
- [ ] ①（本物の窓）は引き続き窓と判定され、枠位置も従来どおり得られる
- [ ] ② は従来どおり null
- [ ] テストが空振りでないこと（判定の切り替えを外すと ③④ のテストが落ちる）

## 段階的な着手（backlog 指定。順序を守る）

core 改修が入るので、いきなり判定を切り替えない。

1. 書き込み範囲を snapshot に載せるところまでやり、**既存テストが通ることだけ**確かめる
2. 実測 4 画面を回帰テストに起こす（③④ が窓と判定されないことを固定）
3. そのうえで判定を切り替える

## 未確定事項 / 確認したいこと

- **「小さすぎる更新」の下限**をどう置くか（固定値／画面比／前回画面との差分）。
  メッセージ行だけの書き換えを窓と誤らないための条件で、spec で決める
- **レコードの区切り**をどこで取るか（`ApplyResult` を返す単位＝1 レコードでよいか、
  複数レコードが 1 回の受信にまとまる場合の扱い）
- **CLEAR を通った直後**の扱い。全画面 CLEAR → 全画面描画は窓ではないが、
  CLEAR 無しで一部だけ書くのが窓、という整理でよいか
- ①〜④ の実測データが**どこに残っているか**（再現用のデータストリームがあれば回帰テストに使える。
  無ければテスト用に組み立てる）

## 却下済み（再検討しないこと）

**「枠の外に何も無ければ窓」は逆効果。** 実測で否定済み。

- 本物の窓ほど外側に内容がある（① は枠外の非空白 130 セル）。窓は背景の上に開くので当然
- 誤検出の ④ はむしろ外側が **0**

つまりこの条件で絞ると**本物を弾いて誤検出を通す**。
