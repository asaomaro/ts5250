# 決定記録

## D1: スコープを「設定モデルと軸の分離」に絞る（利用者の判断）

**背景**: requirement は状態機械（`stopped` の実装）と開始/停止まで含んでいた。
設定モデルと `resident` の作り直しが入った時点で、残りは
**`PrinterEntry.session` の省略可能化**という型の大改修になる
（`deliverReport` / `startRescue` / `close` / ws-handler が「エントリがある＝接続がある」に依存）。

**判断**: 利用者に選択肢を出し、**A（ここで一度 PR にする）**が選ばれた。
状態機械の実装と開始/停止は**次の work** に送る。

**理由**: 利用者が止めた目的は「見せ方の整理」。設定モデル（サービス ✅ / 自動で待ち受け開始）と
4 状態の語彙が先に着地すれば、**UI の設計を次の PR を待たずに進められる**。
また、設定モデル＋型の大改修＋操作を 1 つの差分に乗せると重くなる。

**この work で満たさない受け入れ基準**（requirement から次へ送るもの）:

- 停止しても一覧から消えず、再開できる
- 停止で接続を手放す
- 上限が「待ち受け中」の数で判定される
- 自動開始 ☐ なら開いても待ち受けない
- 実機での開始 → 受信 → 停止 → 再開

## D2: まだ使われていないものを 2 つ入れている（意図的）

**`ServiceState` / `holdsConnection`** と **`ResolvedTarget.autoStart`** は、
本 work のコードからは呼ばれていない。

**入れる理由**:

- **`ServiceState`**: 利用者はいま UI の見せ方を整理している。
  4 状態の語彙が確定していれば、**次の PR を待たずに画面の設計ができる**。
  `SessionManager` と `WatchRegistry` で語彙が割れるのを防ぐのが目的なので、
  実装より先に置く意味がある
- **`autoStart`**: 定義（スキーマ）と解決（`ResolvedTarget`）は
  **設定モデルの一部**。ここだけ次に送ると、設定 UI が参照する型が揃わない

**リスク**: 使われないコードを公開面に置くことになる（PR #246 の `freeLob` と同じ形）。
**次の work で必ず使う**ので、宙に浮いたままにはしない。PR に明記する。

## D3: `resident` の導出をやめる（PR #252 の作り直し）

`resident = (output !== undefined)` を `opts.service === true` に置き換えた。

**導出をやめた理由**（利用者との設計整理）:

- 「**開いている間だけ PDF に落としたい**」が表現できない
- 「**常駐して溜めるだけ**（出力なし）」も表現できない

**意図（サービス）と能力（出力設定）は別の軸**。両方をテストで固定した。

信頼境界は緩んでいない——`service` を受理するのは `config-resolver.ts` の 5 層目
（サーバー設定由来のときだけ）で、出力設定と同じ線に乗っている。
