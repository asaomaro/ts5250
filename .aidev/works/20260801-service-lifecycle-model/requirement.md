# 要件: 待ち受けの状態機械と、開始/停止

## 背景 / 課題

利用者との設計整理で、**セッション（WS に紐づく）とサービス（サーバー側で動く）**を
分けたうえで、**両者に同じ待ち受けの操作**を持たせる方針が決まった。

> 画面側で待機と停止を指示したい。定義に自動起動の設定を追加し、✅ されていれば
> サーバー起動で自動的に立ち上がる。WS 版のプリンターセッションも、
> ✅ されていなければ開いた直後に待ち受けを開始せず、開始ボタンを待つ。
> どちらでも停止ボタンで待ち受けを停止できる。**プリンターも待ち行列も同じ。**

### なぜこの形が成立するか

**待ち受けを止めても仕事は失われない。**

- プリンター: 停止＝装置を手放す。スプールは**ホストの OUTQ に残る**
  （`20260801-printer-session-residency` で `READY` のまま溜まるのを実測）
- 待ち行列: 停止＝読むのをやめる。エントリは**キューに残る**（読むまで消えない）

停止は「いま消費しない」であって「取りこぼす」ではない。だから利用者に停止を渡してよく、
**両者で同じ意味になる**。

### いまの実装が合っていないところ

| 箇所 | 問題 |
|---|---|
| `WatchRegistry.stop()`（`watch-registry.ts:211`） | **レジストリから削除する**。停止すると一覧から消え、**開始ボタンを押せない** |
| `PrinterEntry.session`（必須） | 「エントリがある＝接続がある」前提。**停止中のエントリを持てない** |
| `openPrinter` | 開いた瞬間に接続する。**待ち受けない状態で存在できない** |
| 状態の語彙 | `WatchRegistry` は `watching / reconnecting / error`。**`stopped` が無い**ので、明示停止と障害を状態として区別できない（`stopping` フラグで内部的にだけ区別している） |
| 上限 | `maxResidentPrinters` は**存在する数**を数える。停止中は資源を持たないのに枠を食う |

## 目的 / ゴール

**プリンターと待ち行列が、同じ状態機械と同じ開始/停止を持つ。**

その土台の上に、後続（定義ベースの一覧・サーバー起動時の自動開始・`ref` による attach）を
載せられるようにする。

## スコープ

### 対象

- **状態機械**: `stopped` / `listening` / `reconnecting` / `error` の 4 状態を両者で共有する
- **停止しても消えない**: 停止したエントリは一覧に残り、再開できる
- **停止は接続を手放す**: 装置・接続を解放する（仕事はホスト側に残る）
- **上限は「待ち受け中」で数える**
- **自動開始フラグ**を定義に足す（`printer` と `dtaqwatch`）。
  **開いた直後／起動直後に待ち受けを始めるか**を決める
- **サービス ✅** を `printer` 定義に足す（`dtaqwatch` は種別自体がサービスなので不要）
- WS から開始/停止を指示できる

### 対象外（後続の work）

- **定義ベースの一覧 API**（`/api/printers` は実行中しか出さない。作り直しが要る）
- **サーバー起動時の自動開始**（フラグは足すが、起動時に読む処理は次）
- **`ref` による attach**（開き直したら既存に繋がる）
- **待ち行列 UI の能動/受動の分離**（画面側）
- 待ち行列サービスの sink（コマンド実行等）——**独立した信頼設計が要る**

## 機能要件

- 停止したプリンター／監視は**一覧に残り、再開できる**
- **停止と再接続中を状態で区別できる**（前者は意思、後者は障害）
- 停止で**ホスト側の資源を手放す**
- 自動開始 ☐ の定義は、開いても待ち受けを**始めない**
- 自動開始 ✅ / ☐ のどちらでも**停止できる**
- **サービス ✅ は admin 限定**（既存の信頼境界に乗せる。新しい軸を作らない）
- 既存の対話型プリンター・既存の監視の**既定の挙動を変えない**
  （自動開始の既定を ✅ にすることで、いまと同じに保つ）

## 非機能要件 / 制約

- **信頼境界を緩めない**。サービス ✅ と出力設定は「サーバー設定 × canEditProfiles」限定
- `WatchRegistry` と `SessionManager` で**状態の語彙を揃える**
  （別々の言葉にすると UI が二重になる）
- 既存テストが通ること
- 実機で開始/停止の往復が確認できること

## 完了条件 (受け入れ基準)

- [ ] 4 状態が両者で共有されている
- [ ] 停止しても一覧から消えず、再開できる（両者）
- [ ] 停止で接続を手放す（両者）
- [ ] 上限が「待ち受け中」の数で判定される
- [ ] 自動開始 ☐ なら開いても待ち受けない
- [ ] 自動開始 ✅ / ☐ のどちらでも停止できる
- [ ] サービス ✅ が `printer` 定義にあり、admin 限定である
- [ ] 既定の挙動が変わらない（自動開始の既定 ✅）
- [ ] `npm run build` / `npm run lint` / `npm test` が通る
- [ ] 実機で開始 → 受信 → 停止 → 再開の往復を確認
- [ ] `20260801-printer-session-residency` で入れた `resident` 導出を、

  定義が消えたら落とすのか、明示的な破棄を用意するのか。**spec で決める**
- **待ち行列の「セッション」に定義が要るか**。現在の能動的 UI は定義を持たない
  場当たりの道具で、それで足りている可能性がある。**利用者に確認したい**
