## 課題 / 手戻り

### 1. 変異注入の 0 件を「テストの穴」と誤読した（D17。同じ誤りを 2 回）

AC5 で R4 の変異が 0 件だったのを「安全網の穴」と読み、**存在しない穴を埋めるテストを書いた**。
実際は**等価変異**で、`current === a && a.settled` という状態が到達しないため、どんなテストでも殺せない。
しかも「どのテストも覆っていなかった」という説明は、**自分の research F16 に書いた事実と矛盾**していた。
R1 でも同じ誤りをし、そちらは `cross` の次のラウンドまで残った。

**前段で防げたか**: design が変異の形を「項ごと」と指定した時点では実装の形が未定なので、design では防げない。
**防げるのは手順**——0 件が出たときに解釈が 2 通りある（穴／等価変異）ことと、
**門を丸ごと壊して切り分ける**という一手が、protocol にも design 指針にも無かった。→ ハーネス提案 H3。

### 2. 出所の書き方の誤りが 32 件（must 6 / should 12 / nit 14）

存在しない D 番号、同じ work で消える行を指す行番号、出所と食い違う数（`9` と `12` の取り違えは 3 回連続）、
読み手を数え切らない「読むのは X だけ」、work をまたぐ未修飾の参照。
**型検査も lint も変異注入も効かない領域**で、独立点検だけが見つけている。→ 条項 `comment-provenance`。

### 3. 対になる資産の片方だけが直る事故が 3 回（D15 / D16 / D18）

`settled` はクライアント側だけ走査集合から漏れ、`holdTimer` はサーバー側だけ漏れ、
コメント除去 helper の盲点は両側にあったのに片側ずつ直した。
**`holdTimer` はタスク単位の点検 13 タスクすべてを通り抜け、`cross` が拾った。**
→ 条項 `paired-artifact-sync`。

### 4. review の must が 215 件の独立点検を通り抜けた

AC1 は「導出の戻り値は列挙された状態で、呼び出し側が真偽値を組み合わせ直せない形」と定めるのに、
`isResumable` が真偽を返し、**`startReconnect` が門を規則の外で再評価**していた。
AC1 が防ごうとしている失敗そのものが起きている状態。

**なぜ通り抜けたか**（ここが本 work で最も示唆的）:
- **タスク点検の観点は「正確性・規約適合」に限定されている**（`protocol-check.md` が明示。
  要件適合・価値適合は work 全体の文脈が要るので review の担当）。設計どおりの棲み分けであり、点検の失敗ではない。
- **doccheck は「文書の内部一貫性」を見る。** design 単体は一貫していた——
  `resumable(s): boolean` と書き、それを実装した。**requirements の AC1 と食い違っていた**が、
  上流文書との整合は (a) の射程外。design は 2 ラウンドで 32 件の指摘を受けてなお、この行を残した。
- **`aidev coverage` は design=8/8(100%)・gap 0 と言った。** 被覆は**構造**（どの AC をどの節が扱うか）を見るもので、
  **AC の文言を実装の形が満たしているか**は見ない。100% は「全部の AC に担当が居る」であって
  「全部の AC が満たされている」ではない。→ ハーネス提案 H1。

### 5. タスク点検を 1 つ打ち漏らした（T10）

13 タスク中 T10 だけ点検が回っておらず、`cross` が記録を横断して初めて気づいた。
`approve coding` は `task_checks=13` / `tasks_done=13` を刻んで警告しなかった。→ ハーネス提案 H2。

### 6. 上限を使い切った後の修正が点検を受けられない（D21）

review の must を直した変更は T9 / T9-2 の scope だが、両者は点検ラウンド上限（2/2）を使い切っていた。
運用では review ラウンド 2 で見て済ませたが、**構造としては「差し戻しで直した箇所ほど点検が薄い」**。→ H4。

### 7. 記録の欠落について

この work では `metrics.yml` / `review.md` / `decisions.md` はすべて揃っており、記録漏れは無い。
ただし `aidev doctor` が **`harnessRev` を取れない**（ハーネスが git 管理下にない）と警告しており、
**版をまたいだ判定が成立しない**。また `.aidev/config.yml` に `docsRoots` が未設定のため、
起こした条項が既存 docs と重複していないかを**機械的に確認できていない**（目視では AGENTS.md
「コメントの残し方」と重ならないことを確認した——既存は「明記せよ」、条項は「検証できる形にせよ」）。

### 製品 / コード（→ backlog に起票済み）

  直し方の当たりと、直すときの注意（`updateScreen` の到達不能の根拠を検査し直す）まで書いてある
- **同一ファイル内の写しを CI が検知できない**（D19）——US3 がここだけ成立していない
- **R4 の `error` 経路と `lifetimeOf` が組合せ表に無い**（D17 の積み残し）
- **JSDoc が宙に浮くのを機械で検知する**——3 回起きた。ブロックコメントが 2 つ連続する箇所を落とす検査で止まる。
  **条項にしないのは、層を下げられるものを規約に置かないため**（protocol.md「12.」）
- **`sharedFiles` を宣言する**——doctor が未宣言の常連 4 件を挙げている。宣言すると
  タスク点検の発火条件「共有モジュール・公開 API に触れたタスク」が機械判定になり、T10 の打ち漏らしが減る

### PJ プロセス / 規約（→ `.aidev/conventions/` の条項）

- **`comment-provenance`**（新規・pending）——出所は検証できる形で書く。
  baseline 32 件。**既存の AGENTS.md「判断の出所を明記する」とは別物**——明記されていても
  間違っていたのがこの work の実態なので、足すのは「明記せよ」ではなく「検証できる形にせよ」。
  型検査・lint・変異注入のどれも効かないので、層を下げられない＝規約に置くのが妥当。
- **`paired-artifact-sync`**（新規・pending）——対になる資産は複製せず共有し、
  共有できないなら対応関係をテストで固定する。baseline 3 件。
- **「規約はあるのに守られていない」と判別したもの**: **JSDoc の宙吊り**（3 回）。
  AGENTS.md「関数の責務は JSDoc ヘッダで」は在るが、挿入位置の話ではない。ただし
  **機械で検出できる**ので条項ではなく検査に落とした（上記 backlog）。
- 索引は `AGENTS.md` の `<!-- aidev:conventions -->` ブロックに 2 行追加した（本体には書いていない）。

### ハーネス自体（→ `aidev-*` への提案。適用は人間）

- **H1: `aidev coverage` の 100% が「AC が満たされている」と読まれる。**
  この work では design=8/8・gap 0 のまま、design が AC1 の文言と食い違ったまま coding を通過し、
  実装に現れた。提案は 2 つのどちらか——(a) `coverage` の出力に「これは構造の被覆であって
  基準の充足ではない」を明記する、(b) **doccheck (a) の射程に「直前の上流文書との整合」を加える**
  （design なら requirements の AC 文言と、自分が定義した具体的なインターフェースを突き合わせる）。
  **(b) が本命**——この work の must は「AC1 の文言 vs `resumable(s): boolean`」を並べれば design 段で拾えた。
- **H2: `approve coding` が点検の打ち漏らしを検知できない。**
  `taskcheck` は id ごとの記録を持ち、`tasks.md` は `[x]` のタスク一覧を持つので、
  **両者の集合差を警告できる**（「`[x]` だが点検記録が無い: T10」）。
  いまは `task_checks` の件数しか見ておらず、13 と 13 が一致して見えた（実際は T10 欠落 / T9-2 追加で相殺）。
- **H3: 変異注入で 0 件だったときの手順が無い。**
  0 件には「テストの穴」と「等価変異」の 2 つの意味があり、**取るべき行動が正反対**。
  `aidev-50-test` か design の AC5 指針に「0 件なら、まず**門を丸ごと壊して**等価変異でないことを確かめる」
  の一手を入れる。この work では入れていなかったために、存在しない穴を埋めるテストを書き、
  同じ誤りを R1 でも繰り返した。
- **H4: 差し戻しで直した箇所ほど点検が薄い。**
  `maxTaskCheckRounds` を使い切ったタスクに review の must が当たると、その修正は独立点検を受けられない。
  提案: **review からの差し戻しで再開する coding には、対象タスクの点検ラウンドを 1 回戻す**
  （`unapprove` が後工程の承認を戻すのと同じ考え方）。いまは運用で review ラウンド 2 が肩代わりしている。
- **H5（記録）: `harnessRev` が取れない。** ハーネスが git 管理下にないため
  「版をまたいだ work」の層別ができない。条項の効果判定（`aidev-util-insights`）はこの層別を前提にするので、
  **条項を 2 件起こした今後は効いてくる**。置き場を git 管理下に置くのが前提条件。
