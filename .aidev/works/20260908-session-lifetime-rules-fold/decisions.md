## D1 三層判定を full とした（2026-09-08T10:43:00Z）

- **背景**: backlog `session-lifecycle.md` の 1 件目「判定の置き場所を 1 か所に畳む」から着手する。
  `20260908-session-survives-disconnect` のデバッグ D1 が出自で、「持ち主が居るか」「猶予中か」
  「繋ぎ直しの対象か」「この試行はまだ有効か」の 4 規則が独立フラグの組み合わせとして
  12〜15 か所に散っている状態を、**振る舞いを変えずに**定義と導出関数の内側へ畳む。
- **決定**: `profile: full`（light にしない）。`mode: autonomous`。
- **理由・代替案**: light の 4 条件のうち満たすのは「振る舞いを変えない」のみ。
  (a) 触る箇所が 12〜15 か所＋サーバー・クライアント両側で、`lightMaxFiles`（既定 3）を確実に超える。
  (b) `SessionManager` / `SessionState` という**共有モジュール**の内部構造そのものを差し替える。
  light を選ぶ代替案は coding で即昇格になる公算が高く、昇格の記録を増やすだけで得がない。
  mode は直前の `session-survives-disconnect` と同じ autonomous をユーザーが選択（PR で停止・auto-merge なし）。
- **影響**: 上流 3 工程をそれぞれのゲートで回す。責務の移動（散在フラグ → 導出関数）は
  `protocol.md`「4.5」の architecture 発火条件（モジュール間の境界を動かす／責務分割の選択）に
  当たりうるので、design 終了時に採否を自律判定する。autonomous なので上流 4 文書は
  `aidev doccheck`、coding の各タスクは `aidev taskcheck` の点検記録が必須。

## D2 backlog の 2 件目（全組合せ表）を同じ work に入れる（2026-09-08T10:49:53Z）

- **背景**: 着手対象は backlog `session-lifecycle.md` の 1 件目（判定の畳み込み）だが、
  2 件目「端末種別 × 切れ方 × viewer × 持ち主の全組合せを 1 つの表にし、サーバー・クライアント
  双方をその表から回す」に **「上の畳み込みと同時にやると効果が出る」** と自ら書かれている。
- **決定**: 2 件目を本 work のスコープに含める。**表は畳み込みの前に現行実装で埋める**
  （characterization test として先に書く）。
- **理由・代替案**: 1 件目の硬い制約は「振る舞いを変えない」で、それを示す唯一の手段が回帰テスト。
  既存テストは個別ケースの寄せ集めで、**組合せの穴がどこかを誰も知らない**——実際 PR #391 では
  3 ラウンドとも「テストが緑のまま別の組合せが壊れた」形で再発した。表を後に書くと
  **畳み込み後のコードに合わせた期待値**になり、安全網として機能しない。
  別 work にする案は、その場合 1 件目の完了判定が「既存テストが緑」だけになり、
  同じ失敗の再演を許す。
- **影響**: 作業量は増えるが、AC4 / AC5 として完了条件に載る。実機検証（3 件目）と
  既存フレーク（4 件目）は対象外のまま。

## D3 research（任意工程）を挟む（2026-09-08T10:59:10Z）

- **背景**: requirements を書き終えた時点で、`protocol.md`「4.5」の research 発火 5 条件のうち
  3 つに当たった——(1) 調査で解消すべき未確定事項が残る（AC2 の手段、`startReconnect` の
  docstring 訂正の可否）、(2) **未検証の既存挙動に依存する**、(4) 影響が横断的（server + web-ui）。
- **決定**: design の前に research を挟む。
- **理由・代替案**: 決め手は (2)。この work の硬い制約は「振る舞いを変えない」で、

  畳んだ後の形に合わせて期待値を推測することになり、安全網が安全網でなくなる（D2 と同じ理由）。
  `mode: autonomous` なので推奨ではなく自律判定（`protocol.md`「4.5」末尾）。
- **影響**: 工程が 1 つ増える。research の出力（全組合せの現行期待値）がそのまま
  AC4 のテストの入力になるので、design / coding の入力としても効く。

## D4 AC2 の対象集合から `connected` / `kind` / `meta.terminal` を外す（2026-09-08T11:32:33Z）

- **背景**: requirements は「表の 3 列目に挙げたフラグの出現箇所を定義と導出関数の内側に限る」と
  決めたが、design で読み手を数えたところ **この 3 つは表示にも使われていた**
  （`connected` 9 箇所・`kind` 4 箇所・`meta.terminal` 5 箇所。`research.md` 影響範囲）。
- **決定**: 3 つを AC2 の対象集合から外し、代わりに R3 の静的な性質を `resumability` に畳んで
  そちらを対象に含める。`connected` は `link` からの**読み取り専用アクセサ**にする。
  requirements の表を更新した（16 個 → 14 個）。
- **理由・代替案**: 表示側まで畳むと、この work の対象範囲が「寿命の判定」から
  「セッション状態の表示全体」へ広がる。**振る舞いを変えない**制約の下でそれをやると、
  `StatusBar` / `EmulatorPane` ほか 6 つの .vue を触ることになり、
  組合せ表（AC4）では守れない領域に手を入れる。得られるものより失うもののほうが大きい。
  代替案「`connected` も union に畳んで読み手を全部書き換える」は、退行リスクが
  この work の唯一の安全網の外にある。
- **影響**: `connected` への**書き込み**は getter 化によって型で塞がれる（web-ui はテストまで
  型検査される。`research.md` F19）ので、封じ込めとしてはむしろ強くなる。失うのは
  「読み手も `link` を直接読む」という見た目の統一だけ。

## D5 architecture で design を 3 点改訂した（2026-09-08T11:49:52Z）

- **背景**: design は畳み先の**形**を決めたが**置き場所**を決めていなかった。受け入れ先の

  「1 か所を読めば答えが分かる」というゴールに届かない（1720 行の中の 1 か所は、
  探す手間の点で 12 か所と大差ない）。
- **決定**: 規則を**依存ゼロの純粋モジュール 2 つ**（`server/src/session-lifetime.ts` /
  `web-ui/src/session-link.ts`）へ切り出す。あわせて design を 3 点改訂した:
  (1) `resumable()` / `sendToHost()` を `session-controller.ts` ではなく純粋側に置き、

  副作用（`SessionManager`）」に割る（**呼び出し側から見た形は design のまま**）。
  (3) `canSendToHost()` は文言ではなく `LostCause` を返す。
- **理由・代替案**: (3) は依存の向き——純粋な規則が表示文言（`opMessages.ts`）を引くと
  規則が表示に依存する。(2) は判断を引数だけで網羅できるようにするため。
  代替案「design のまま既存ファイルに足す」は差分が小さい代わりに**ゴールを満たさない**。
- **影響**: 新規ファイルが 2 つ増える（design の「対象範囲」に追加）。既存ファイルは
  判定が出ていくぶん**減る**見込み。AC5 の変異注入の対象がファイル単位で自明になり、
  AC2 の走査も「このファイル以外に出ない」で書ける。

## D7 表示セッションの `handedOverPresent` は座だけ譲って作る（2026-09-08T13:01:05Z）

- **背景**: 組合せ表の「交代済み・後任在席」を**実際の WS 接続**で組み立てると、
  表示セッションでは後任も `addViewer` される（`ws-handler.ts:879`）ため、
  表が `otherViewer: false` と言っている行なのに**在席 1 の状況**になる。
  結論（`keep`）は同じなので緑になるが、**在席の判定（ゲート1）が保持者ガードより先に効き、
  ガードの効き目を一切見ていない**。T2 のタスク点検が変異試験で実証した——
  `abandoned` を常に真にする変異を当てても、5250 の `handedPresent` 3 行は緑のまま通った。
- **決定**: 後任を接続で立てず、**`mgr.claim(id)` で座だけ譲る**（`handedOverAbsent` は
  続けて `releaseHolder`）。プリンターの行と同じ作り方に揃えた。
- **理由・代替案**: 表の軸「役割」が指しているのは**座の状態そのもの**で、
  後任がどう座を取ったかは軸に含まれない。接続で作ると 2 つの軸（役割と在席）が
  勝手に結びつき、片方しか検証できなくなる。代替案「表の `otherViewer` を `true` に直す」は、
  **在席 0 で保持者ガードだけが効く状況を表から失う**ので採らない。
- **影響**: 同じ変異で落ちる行が 3 → 6 に増えた。畳み込み（T5 / T6）で保持者ガードを
  壊した場合、5250 の行でも捕まる。

## D8 `ws-handler.sessionId` は読み替えずに getter として残す（2026-09-09T11:06:26Z）

- **背景**: design / architecture は `sessionId` / `attached` / `holderToken` の 3 フィールドを
  `link` に畳み、`this.sessionId` の参照 11 箇所を `this.link?.id` へ**読み替える**としていた。
- **決定**: 畳むのは同じだが、**`sessionId` を `link` からの private getter（読み取り専用）**
  として残し、読み手 11 箇所は 1 行も触らない。
- **理由・代替案**: クライアント側で採る手（`connected` を `link` からの読み取り専用アクセサに
  して表示側を触らない。design 方針3）と**同じ形**で、work 全体の一貫性が上がる。
  「振る舞いを変えない」制約の下では読み手を書き換えないほうが退行の余地が小さく、
  **代入が型で塞がる**ので「id はあるが役割が無い」状態も作れない（畳み込みの目的は達成）。
  読み替える案は差分が 11 箇所ぶん大きくなるだけで、得るものが無い。
- **影響**: 差分が小さくなった。**リスクは「getter への代入が残っていると実行時に黙って失敗する」**
  ——`src` は型検査が覆うが `packages/server` のテストは覆わない（`research.md` F19）。
  T6 のタスク点検にこの観点を明示的に渡した。

## D9 役割のリセットによる振る舞いの変化を受け入れる（2026-09-09T11:21:24Z）

- **背景**: T6 のタスク点検（ラウンド2）が、**畳み込みの副産物として実際の振る舞いが 1 点
  変わっている**ことを HEAD との比較プローブで実証した。旧実装は `dispose` で
  `sessionId` / `holderToken` を戻すが **`attached` は戻さない**（スティッキー）。
  `close` メッセージは `dispose` するだけで WS を閉じないので、
  `open{sessionId}`（viewer）→ `close` → 同じ接続で `open{host}`（持ち主）→ `close`
  という列が組める。**旧: 2 本目が閉じられず孤児（セッション数 2 のまま）／新: 正しく閉じる（1）**。
- **決定**: この変化を**受け入れる**。旧の振る舞いには戻さない。新しい振る舞いを
  回帰テストで固定する。
- **理由・代替案**: requirements の非機能要件は「バグに見えるものを見つけても直さない」と
  定めているが、これは**意図的な修正ではなく畳み込みの副産物**。旧に戻すには
  「役割をスティッキーにする」コードを新設計に**わざわざ書き足す**必要があり、
  前 work が D7 / D10 で 2 度戦った孤児化をあえて再導入することになる。
  `link` を 1 欄に畳んだ以上、id と役割が同時に消えるのが自然な帰結。
- **影響**: **製品の web-ui からは到達しない**——`send({type:"close"})` の直後に必ず
  `client.close()` する（`session-controller.ts:260` / `:392` / `:1152`）。到達しうるのは
  同じ WS を使い回す別のクライアント。AC3 の「既存テストの期待を緩めない」には反しない
  （緩めるのではなく、固定されていなかった振る舞いが良い方向に変わった）。
  review 工程での判断材料として明示する。

## D10 union は「到達しない組合せ」を表現できなくする（2026-09-09T11:37:27Z）

- **背景**: 現行の `endedByHost` には削除経路が 1 つも無い（`grep` で 0 件）ため、
  「繋がっているのにホスト終了の印が残る」という組合せが型の上で作れた。
  `SessionLink` の union に畳むと、`connected` / `reconnecting` へ遷移した時点で
  理由が消えるので、この組合せは**表現できなくなる**。
- **決定**: 表現力の差を受け入れる（union のまま進む）。
- **理由・代替案**: この組合せは**到達しない**——ホスト終了ではサーバーがエントリごと
  削除するので、以後 `opened` も `screen` も来ない。よって振る舞いは変わらない。
  表現力を保つ案（`endedByHost` を union の外に別フィールドで残す）は、
  **まさに畳み込みが消そうとしている「独立フラグの組み合わせ」を 1 つ残す**ことになる。
- **影響**: 「振る舞いを変えない」は満たすが、**型の表現力は狭まった**（狭めたのは
  到達しない側だけ）。もし将来サーバーがホスト終了でエントリを残すようになったら、
  ここが効いてくる——`session-link.ts` の `nextLink` にその旨を明記した。

## D13 繋ぎ直し成功後に画面が固まるバグを見つけた（直さず記録）（2026-09-09T14:08:46Z）

- **背景**: T9-2 の実装のため `tryResume` を読んでいて、`opened` の枝が
  `pendingResumes.delete(sessionId)` した後、同じハンドラ末尾のガード

  **以降の全メッセージを弾く**ことに気づいた。プローブで実測——繋ぎ直しに成功して
  `opened` の画面は反映されるが、**その後ホストが書いた `screen` は反映されない**。

- **決定**: **この work では直さない。** 振る舞いを保ったまま畳み、backlog に起票する（T14）。

  テストで示せなくなり、この work の唯一の安全網を自分で外すことになる」と定めている。
  D9（孤児化）は**畳み込みの副産物として不可避に変わった**ものだったが、これは
  **意図的に直さない限り変わらない**ので事情が違う。
- **影響**: 利用者から見ると「再接続したのに画面が固まる」。**深刻度は高い**が、
  修正は R4 の畳み込みとは独立に行える（ガードを「代表している試行か」から
  「現役の口か」に変えるだけの可能性が高い）。別 work で扱うべき——
  修正には「成功後も同じハンドラが使われ続ける」という前提の再確認が要り、
  本 work の「振る舞いを変えない」制約とは相容れない。
