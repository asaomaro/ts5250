# 要件: セッション寿命の判定を規則ごとに 1 か所へ畳む

## 背景 / 課題

`20260908-session-survives-disconnect`（PR #391）で「転送が落ちてもホストセッションを失わない」を
実装した際、review が **3 ラウンド続けて「直した項の隣が壊れる」** を出し、差し戻しの上限に達した。
まっさらなコンテキストへ委譲した原因究明（同 work の「デバッグ D1」）の診断は、個別の欠陥ではなく
**規則の置き場所**だった。

セッションの寿命は 4 つの規則で決まる。

| # | 規則 | いま判定に使っている下位フラグ（**AC2 の対象集合**） | 畳み先: 規則の**定義**（1 規則 1 つ） | 畳み先: そこから**導く関数** |
|---|---|---|---|---|
| R1 | **持ち主が居るか** | サーバー: `holderToken` / `hadHolder` / `attached` / `resident` | `SessionEntry` の持ち主状態（1 つの欄。いまは 2 つのフラグに割れている） | `SessionManager.disposition()` / `lifetimeOf()` |
| R2 | **猶予中か** | サーバー: `heldUntil` / `holdTimer` | `SessionEntry` の猶予状態（1 つの欄。いまは期限とタイマーに割れている） | `SessionManager.disposition()` / `lifetimeOf()` |
| R3 | **繋ぎ直しの対象か** | クライアント: `attachedOnly` / `endedByHost` / `reconnectFailed` / `reconnect`（保持値として） / `resumability`（D4 で畳み先として足した静的な性質） | `SessionState.link`（判別可能 union）＋ `resumability` | `resumeVerdict` / `sendToHost` |
| R4 | **この試行はまだ有効か** | クライアント: `settled` / `pendingResumes` / `reconnectTimers` | 進行中の試行を表す状態（`SessionState` の 1 つの欄。**R3 とは別の規則**） | `isCurrentAttempt` |

> **表の更新履歴**: `resumability` は D4 で対象集合に足したが表への反映が漏れていた（review ラウンド1 の指摘で追加）。
> `viewers` は D14 で対象外にした。R3 の導出は review ラウンド1 の must で `resumable`（真偽）→ `resumeVerdict`（列挙）に変えた。

**AC2 の対象集合は 3 列目に挙げた 14 個のフラグそのものだけ**（`design.md` 方針4 で確定。
当初は `connected` / `kind` / `meta.terminal` も含めていたが、**この 3 つは表示にも使われる**
ため定義の内側に閉じ込められない——代わりに R3 の静的な性質を `resumability` に畳み、
`connected` は `link` からの読み取り専用アクセサにして**型で書き込みを塞ぐ**。`decisions.md` D4）。
それを読むアクセサ
（`hasViewer` / `isResident` / `isHeld` / `hasHolder` / `holdForReconnect` / `cancelHold` / `reapHold` 等）は
**導出関数の側**なので集合に含めない——含めると「定義と導出関数の内側に限る」が自己矛盾する。
呼び出し側がフラグから組み立てているローカル変数（`ws-handler.dispose` の `wasHolder` /
`otherViewers` / `abandoned`）は、畳み込みで**消える側**なので集合に数えない（消えたことは
3 列目のフラグが `dispose` から消えることで確かめられる）。

**規則は 4 つ、定義も 4 つ、導出関数は 5 つ。** 1 つの定義から複数の答え（サーバーなら
「いま畳むか」と「いつまで生かすか」、クライアントなら「繋ぎ直してよいか」と「いま送ってよいか」）を
導くのは、**同じ 1 つの定義から導く限り**問題ない。数えるのは**規則ごとの定義の数**であって、
そこから生える導出関数の数ではない。

どの規則も**単一の判定関数を持たず、独立フラグの暗黙の連言**として書かれている。結果、1 つの規則を
答える判定が 12〜15 か所へ散り、**どこか 1 か所を直しても残りの写しが同じ規則に別の結論を返し続ける**。
実際に起きた再発は、`ws-handler.dispose` の 3 判断（`attached` / `otherViewers` / `isResident`）と
持ち主照合（`wasHolder` / `abandoned`）と猶予（`holdForReconnect` の `false` は「閉じてよい」ではない）が
同じ 1 つの if 文の中で絡み、`startReconnect` の **4 つの門**（1: `kind` / `meta.terminal` / `attachedOnly`、2: `endedByHost`、
3: `reconnectFailed`、4: `reconnect` ——**門は 4 つ、読むフラグは 6 つ**）がそれと独立に
書かれていることに由来する。

同じ形の欠陥はまだ埋まっていない。PR #391 の `walkthrough.md` と PR 本文にも「次に触る人が
隣の項を踏みやすい」と既知の制約として明記して着地させてある。

本 work は、そのとき起こした **`.aidev/backlog/session-lifecycle.md` の 1 件目「判定の置き場所を
1 か所に畳む」** から着手する（2 件目も同じ work に入れる。理由は `decisions.md` D2）。

## 目的 / ゴール

**セッションの寿命に関する 4 規則が、それぞれ 1 か所を読めば答えが分かる状態**にする。

- 規則の答えを知りたい呼び出し側が、下位フラグを組み合わせ直さなくてよい。
- 規則を変えたい人が、変える場所を 1 か所に特定できる（写しを探し回らなくてよい）。
- 写しが再び増えたら **CI が落ちる**（規約の口約束にしない）。
- **利用者から見た振る舞いは変わらない**——これは付随条件ではなく、この work の成立条件そのもの。

（`.aidev/charter.md` は無いため charter ゴールとの紐づけは行わない）

## ユーザーストーリー

- US1: **次にセッション寿命を触る開発者**として、規則の答えを 1 か所で読み・1 か所で変えたい。
  なぜなら、いまは 12〜15 か所の写しのうち 1 つを直すと隣が壊れ、レビューが 3 ラウンド続けて
  同じ性質の再発を出した実績があるから。（受け入れ: AC1, AC2, AC7）
- US2: **レビュアー**として、寿命の変更差分を「規則の定義」と「呼び出し側」に分けて読みたい。
  なぜなら、両者が同じ if 文に混ざっていると、変更が振る舞いを変えたのかどうかを差分から判断できず、
  指摘が推測になるから。（受け入れ: AC1, AC4）
- US3: **CI** として、判定の写しが定義の外に増えたことを機械的に検知したい。
  なぜなら、畳んだ直後だけ整っていても、次の変更で同じ状態に戻るなら投資が消えるから。（受け入れ: AC2）
- US4: **エミュレーターの利用者**として、この変更で操作感が一切変わらないでほしい。
  なぜなら、これは自分のために追加される機能ではなく、自分には見えない内部の整理だから。
  開いたままのタブとサーバーの版がずれることも普通に起きるので、そこも含めて変わらないこと。
  （受け入れ: AC3, AC4, AC5, AC6）

## スコープ

### 対象

- **サーバー**（`packages/server/src`）: `SessionManager` と `ws-handler` に散った R1 / R2 の判定を、
  規則ごとの導出関数に畳む。畳み先の当たりは backlog が挙げた
  **`SessionManager.disposition()`（後始末でどう処分するか）** と **`lifetimeOf()`（このエントリに効く寿命）**
  ——現行の `idleLimitOf` は後者に相当する。最終的な形は design で決める。
- **クライアント**（`packages/web-ui/src`）: `session-controller` と `stores/sessions` に散った
  R3 / R4 の判定を、**2 つの別々の定義**に畳む——R3 は **`SessionState.link` の判別可能 union**
  （そこから `resumable`（繋ぎ直してよいか）/ `sendToHost`（ホストへ送ってよいか）を導く）、
  R4 は **進行中の試行を表す状態**（そこから `isCurrentAttempt`（この試行はまだ有効か）を導く）。
  **R4 を `link` の中に入れない**——繋ぎ直しの可否と、走っている試行の新旧は別の問いで、
  混ぜると AC5 の変異注入で 2 規則を分けて壊せなくなる。
- **端末種別 × 切れ方 × viewer × 持ち主の全組合せを 1 つの表**にし、サーバー・クライアント双方を
  その表から回すテストを作る（backlog の 2 件目。畳み込みと同時に行う。理由は `decisions.md` D2）。
- **台帳（`.aidev/backlog/session-lifecycle.md`）の消し込み**——この work が閉じる 1・2 件目を、
  消し込みの根拠つきで閉じる（deliver の責務）。
- 上の畳み込みに伴う既存テストの追随。**期待している振る舞いは変えない**——変わりうるのは、
  テストが内部シンボルを直接呼んでいる箇所の**呼び出しの形だけ**（例: 消えた `isHeld` を
  導出関数越しに見る）。期待値そのものを緩める変更は AC3 が禁じる。

### 対象外

- **振る舞いの変更**。バグに見えるものを見つけても、この work では直さない
  （記録して backlog へ回す。理由は下の「非機能要件 / 制約」）。
- **実機（`.env.verify`）での瞬断復帰の確認**（backlog `session-lifecycle.md` の 3 件目）。
  別 work。この work は既存の自動テストの範囲で閉じる。
- **`packages/web-ui/test/tab-visibility.test.ts` の並列実行フレーク**（同 4 件目）。
  本件と無関係の既存フレークとして起票されている。**AC3 の判定からは除くが、除いた事実・
  再現条件・本件と無関係である根拠は、落ちたかどうかに関わらず `test-result.md` に残す**
  （黙って再実行で通さない）。
- **3270 / VT / プリンターの寿命の設計変更**。これらは 5250 と違う規則で動く（3270・VT は
  見ている人が閉じたら切る、プリンターは常駐という別の仕組みを持つ）ことが既に決まっており、
  その判断は畳み込みの対象だが**変更の対象ではない**。
- **WS プロトコル・公開 API の変更**（`WsOpen.resume` を含む）。
- **`SessionReservation.holder`（予約の持ち主＝表示名）の改名**。`holderToken`（接続の持ち主）と
  名前が似ているだけの別概念で、4 規則に含まれない。`holder` で grep したとき 2 概念が
  混ざるのは畳み込みの敵だが、**改名は振る舞いを変えない差し替えとは別の変更**なので分ける
  （気になったら backlog へ回す）。

## 機能要件

- R1〜R4 のそれぞれについて、**その規則の状態を表す定義が 1 つだけ存在する**
  （背景の表の 4 列目）。そこから複数の導出関数（5 列目）が生えるのは可。
- 呼び出し側は下位フラグを読まず、導出関数の戻り値だけで分岐する。
- **背景の表の 3 列目に挙げた下位フラグ**（この集合が対象のすべて。「等」で開かない）の
  出現箇所が、**その定義と導出関数の内側に限られる**。design で対象集合を増減させる場合は、
  表を更新してから行う。
- 規則の戻り値は**列挙された状態**として表され、呼び出し側が真偽値を組み合わせ直せない形にする
  （クライアントの `link` は判別可能 union、サーバーの処分は列挙）。
- 畳んだ各規則の定義に、それが引き継いだ既存の判断
  （`20260908-session-survives-disconnect` の D4 / D5 / D7 / D10 / D12 / D13）への参照が残る。
- **振る舞いが変わっていないことを示すテストが、実際に変化を捕まえられる**こと。
  緑であることだけでは「テストがその規則を見ていない」場合と区別が付かないので、
  **規則の判定を意図的に壊すと落ちる**ことまでを要求する（AC5）。

## 非機能要件 / 制約

- **既存の振る舞いを 1 つも変えない。** これは「なるべく」ではなく硬い制約で、
  振る舞いが変わったなら差し替えが失敗している。判定の集約中にバグらしきものを見つけても、
  **その場で直さず記録して backlog へ回す**——直すと「振る舞いが変わっていない」ことを
  テストで示せなくなり、この work の唯一の安全網を自分で外すことになる。
- **公開 API・WS プロトコル・永続データの形は変えない**（サーバーとクライアントは版がずれて
  繋がりうる）。型の内部表現の変更はよい。
- 性能上の要求は無い（判定はいずれも定数回の分岐）。
- 既存の言語・ツールのまま行う（**新規の外部依存を追加しない**）。

## 未確定事項 / 確認したいこと

- **現行の振る舞いが全組合せで何なのかが、どこにも書かれていない。** AC4 の表を埋めるには
  現行実装を読んで確定する必要がある（→ research 工程で行う）。
- AC2 を満たす手段。候補は (a) 封じ込め（フラグをエクスポートしない・型で外から読めなくする）、
  (b) lint ルール、(c) `rg` の件数を数えるテスト。**(a) で済むならそれが良い**——件数の固定は
  無関係な変更でも落ちて、やがて数字を上げるだけの作業になる。→ design で決める。
- `session-controller.ts` の `startReconnect` の docstring が
  「打ちかけの入力も残る（`edits` には触らない）」と書いているが、同 work の **D11 でこの記述は
  訂正済み**（繋ぎ直しでは `edits` を捨てるのが正）。畳み込みで同じ関数を触るので、
  **コメントの訂正だけ**をこの work に含めてよいか（振る舞いは変わらない）。
