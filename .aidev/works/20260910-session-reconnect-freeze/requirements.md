# 要件: 繋ぎ直しに成功したあと画面が固まるのを直す

## 背景 / 課題

`packages/web-ui/src/session-controller.ts` の**メッセージ共通ガード**（`:483`）は
`isCurrentAttempt(attempts.get(sessionId), a)` だけを見る。ところが繋ぎ直しが成功する
`opened` 枝（`:428`〜）は、その場で `a.settled = true` と `attempts.delete(sessionId)` を行う。
`isCurrentAttempt` は `current === a && !a.settled`（`packages/web-ui/src/session-link.ts:215`）なので、
**成功した瞬間から この判定は必ず偽**になり、以後この口に届くフレームは 1 つ残らず `:484` の
`applyDisplayMessage` に届かない。

落ちるのは `screen` / `key-done` / `reserved` / `pc-command` / `jobinfo` / `closed` / `error` の全種。
利用者から見ると **「再接続できたはずなのに画面が更新されず、応答待ちの覆いとスピナーが永久に残る」**
——`key-done` が落ちるので `setBusy(id, false)` が二度と来ず、覆いが消えないので Attn / SysReq の
逃げ道も押せない。`error` も落ちるので送信が拒否されても黙る。タブを開き直す以外に復帰の手が無い。

**打ちかけの入力（`edits`）は、この work では守られない**（review ラウンド1 で明確化）。
繋ぎ直しが成功しても `updateScreen` が `edits` を消す——サーバーの `attach` が返す「いまの画面」で
上書きするためで、`packages/web-ui/test/session-reconnect.test.ts` が
「設計の当初は残すとしていたが、繋ぎ直しで返るのは…」として**仕様**に固定している。
本 work が取り戻すのは**セッションの継続と画面の追従**であって、入力途中の内容ではない。

**畳み込み（`20260908-session-lifetime-rules-fold`）由来ではない**——旧実装の
`pendingResumes.get(id)?.client !== client` も同じ効果で、HEAD `657ad59b` でも同じ形で残っている。
前 work は「振る舞いを変えない」という非機能要件を負っていたため意図的に直さず、backlog へ起票した
（同 work の `decisions.md` D13）。

### 前提: R4 とは

前 work が、散在していたセッション寿命の判定を **4 つの規則**に畳んだ。**R1**「持ち主が居るか」と
**R2**「猶予中か」はサーバー側（`packages/server/src/session-lifetime.ts`）、**R3**「繋ぎ直しの対象か」と
**R4**「この試行はまだ有効か」はクライアント側（`packages/web-ui/src/session-link.ts`）。
本件が触るのは **R4** で、その唯一の答えが `isCurrentAttempt` である。

R4 に畳まれたのは「**この試行が代表か**」を問う判定だけで、「**この口がいま現役か**」
（`sessionsStore.get(id)?.client === client`）は**別の問い**として意図的に畳まれなかった
——成功した試行が退役したあとの `onClose`（繋ぎ直しを回し直す唯一の経路）を区別できなくなるため。
その `Attempt` の docstring（`session-link.ts:176-183`）自身が、**後者が必要なのに欠けている場所がある**
（＝本件のガード）と現在形で記している。したがって足りないのはこの 1 つで、**足す向きは
「通す条件を増やす」**——いまが厳しすぎるために固まっているのであって、緩すぎるのではない。

## 目的 / ゴール

**繋ぎ直しに成功したあと、利用者が何もしなくてもそのまま操作を続けられる状態**にする。
再接続後の画面更新・応答待ちの解除・通知が、初回接続のときと区別なく届く。

同時に、**「打ち切った試行からの更新は弾く」という既存の保証が保たれている**状態を保つ。
さらに、**`stores/sessions.ts:436` の `updateScreen` が「到達しない」と書いた根拠が、新しいガードの
もとでも成り立つかどうかが分かっている**状態にする——あの根拠が寄りかかっているのは
**この共通ガードの厳しさ全体**であって、「打ち切った試行を弾く」という一面だけではない。
崩れうる形は U2 に挙げた「成功したまま store に残っている口からの遅延」で、これは
打ち切った試行ではないため上の保証だけでは塞がらない。

（`.aidev/charter.md` は無い PJ のため、charter ゴールの紐づけは行わない）

## スコープ

### 対象

- `packages/web-ui/src/session-controller.ts` の繋ぎ直し経路のメッセージ共通ガード。
- そのガードが問う述語の置き場所（`packages/web-ui/src/session-link.ts` = R4 の定義側）。
- `packages/web-ui/src/stores/sessions.ts:436` の `updateScreen` に書かれた「到達しない」根拠の再検査
  （検査の結果として注記の更新、または実装の修正）。
- 上記を固定する回帰テスト（`packages/web-ui/test/` 配下）。

### 対象外

- ~~**初回接続（`open`）の経路**。あちらはガードを持たず現に正しく動いているので触らない~~
  **review ラウンド2 で対象に変更**（`decisions.md` D13）。除外の理由だった「現に正しく動いている」が
  本 work の調査で覆った——同じ経路で「はしごの最中に繋がっているへ戻る」が起きる。
  **1 回目のはしごを駆動するのは必ずこの口**なので、繋ぎ直しの口だけ塞ぐと非対称が残る。
- **サーバー側**（`packages/server/`）。本件はクライアント側の判定だけで閉じる。
- backlog の隣接項目——「同一ファイル内の判定の写しを CI が検知できない」（D19）、
  「R4 の `error` 経路と `lifetimeOf` が組合せ表に無い」（D17）、実機確認、
  `tab-visibility.test.ts` のフレーク。**本件で `error` 経路にテストが付くのは結果であって、
  D17 の消し込みではない**（`lifetimeOf` はサーバー側で本 work の対象外のため）。
- 繋ぎ直しの待ち時間の表・試行回数・タイムアウト値の変更。

## 機能要件

- 繋ぎ直しに成功した口から届くフレームを、初回接続と同じ経路（`applyDisplayMessage`）へ通す。
- 打ち切った試行の口から遅れて届くフレームは、いまと同じく捨てる。
- 繋ぎ直しに成功したあと再び切れたら、繋ぎ直しのはしごが従来どおり回る（`onClose` 経路）。

## 非機能要件 / 制約

- **振る舞いの変更は「繋ぎ直し成功後にフレームが届く」ことに閉じる。** 初回接続の経路と、
  打ち切った試行を弾く振る舞いは変えない。**唯一の例外は AC6**——新しいガードのもとで
  `updateScreen` の「到達しない」が崩れると分かった場合に限り、その到達を塞ぐ実装変更を本 work の
  対象とする（塞がないまま残すと、本件を直した副作用で US2 の保証のほうが落ちる）。
- 回帰のベースラインは前 work `20260908-session-lifetime-rules-fold` の test 工程の結果
  ——**5664 passed / 0 failed / 41 skipped**（AC8 の入力）。
- 起動確認（smoke）は `.aidev/config.yml` の `smokeCommand`＝`node launcher/smoke.mjs`。
  サーバーを起こして最初の使える状態まで到達するかを見るもので、クライアント側だけの変更でも
  配線が壊れていないことをここで確かめる（AC9 の入力。test 工程が通す）。
- **判定の写しを増やさない。** 「この試行が代表か」「この口が現役か」は R4 の語彙として
  `session-link.ts` に置き、コントローラ側で組み立て直さない
  （`packages/*/test/lifetime-flag-containment.test.ts` が緑のままであること）。
- 公開 API・WS プロトコル・永続スキーマは変えない。
- 新規の外部依存を足さない。
