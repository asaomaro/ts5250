## 実機（attach の部分）

```
### 6. 開き直す（同じ ref）
  1 回目 id=a3489159-… / 2 回目 id=a3489159-…
  PASS **同じエントリが返る（二重接続しない）**
  PASS 一覧も 1 本のまま
  PASS 閉じている間に届いた帳票が読める
```

同じ id が返っており、**二本目の接続を張っていない**。装置名がホスト上で排他なので、
張っていれば断られていた。

## 受け入れ基準ごと

| 基準 | 結果 |
|---|---|
| 同じ `ref` ＋ owner で二度開くと同じエントリ・接続 1 本 | 合格（単体＋実機） |
| attach で状態が変わらない | 合格（停止中のものを開いても `stopped` のまま） |
| attach 時にバッファ済みの帳票が届く | 合格（`printer-opened.reports`） |
| 帳票バッファに上限があり古いものから落ちる | 合格（50 件） |
| 累計が落ちた分も含めて数えられる | 合格（`receivedTotal`） |
| `ref` 無し（直接接続）は毎回新規 | 合格 |
| 既定の挙動が変わらない | 合格 |

## 常駐が持ち込んでいた漏れを塞いだ

`entry.reports` に**上限が無かった**（`push` するだけ）。WS 切断でセッションごと
消えていた頃は自然に頭打ちになっていたが、**サービスとして何日も動く**ようになった以上、
無制限だと伸び続ける。`20260801-printer-session-residency` /
`20260801-service-start-stop` が持ち込んだ副作用で、**この work で見つけて塞いだ**。

警告には上限（20）があったのに帳票には無い、という非対称が手掛かりだった。

## 未検証の穴

  （単体テストは `deliverReport` を直接叩いている）
- **画面が無い**。`printer-opened.reports` を受け取る側は未実装
- **サーバー起動時の自動開始は未実装**。`autoStart` は「開いた直後」にしか効かない
- **定義ベースの一覧 API も未実装**。`/api/printers` は実行中しか出さない
- **監視側には attach 相当が既にある**が、`ref` の一致条件が
  プリンターと同じかは**照合していない**（別実装のまま）
