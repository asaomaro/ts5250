# 要件: 開き直したら常駐中のプリンターに繋がる（＋帳票バッファの上限）

## 背景 / 課題

### 1. 「開き直すと繋がる」が未達

利用者の要件:

> ブラウザを閉じた後も、そのプリンターセッションを開くとサービスとして
> 起動していたプリンターセッションと繋がる仕様とする

いまは `openPrinter` が**毎回新しいエントリを作って接続する**。常駐中のものがあっても、
同じ定義を開くと**二重接続**になる。同じ装置名なのでホストに断られるはず
（実機で `8903`／装置使用中を踏んでいる）。

**監視側には前例がある**（`watch-registry.ts:178`）——同じ `ref` ＋ 同じ owner の監視が
あれば、それを返す。コメントが判定をサーバーに置く理由も書いている:

> 画面側だけで見ると、リロード直後はまだ一覧が届いておらず（`watch-list` 待ち）すり抜ける

プリンターにも同じ規則を入れる。理由は監視（消費が競合する）とは違い、
**装置名がホスト上で排他**だから。

### 2. 常駐化が持ち込んだ漏れ: 帳票バッファに上限が無い

`deliverReport` は `entry.reports.push(report)` するだけで**上限が無い**
（`session-manager.ts:745`）。

**常駐化する前は問題にならなかった**——WS が切れればセッションごと消えたので、
自然に頭打ちになっていた。サービスとして**何日も動く**ようになった以上、
**無限に伸びる**（`20260801-printer-session-residency` / `20260801-service-start-stop` が
持ち込んだ副作用）。

警告には上限がある（`OUTPUT_WARN_LIMIT = 20`）のに、帳票には無い。

## 目的 / ゴール

**開き直したら常駐中のものに繋がり、閉じている間に届いた帳票が読める。**
そのバッファが**無制限に伸びない**。

## スコープ

### 対象

- **同じ `ref` ＋ 同じ owner のプリンターがあれば、それに繋ぐ**（新しく接続しない）
- attach したとき、**閉じている間に届いた帳票**が画面に届く
- **帳票バッファに上限**を設ける（超えたら古いものから落とす）
- **累計受信数**を持つ（落ちた分も含めて「何件来たか」が分かる）

### 対象外

- 画面（UI）——利用者が設計中
- サーバー起動時の自動開始
- 定義ベースの一覧 API
- 待ち行列 UI の分離、サービスの sink

## 機能要件

- 同じ定義を二度開いても**接続は 1 本**（エントリも 1 つ）
- **attach では状態を変えない**——利用者が止めたものを、開き直しただけで勝手に再開しない
- attach したブラウザに**バッファ済みの帳票**が届く
- 帳票バッファは**上限を超えたら古いものから落ちる**。累計は落ちた分も数える
- `ref` を持たない（直接接続の）プリンターは**従来どおり**毎回新規

## 非機能要件 / 制約

- 判定は**サーバー側**で行う（画面側だけだとリロード直後にすり抜ける。監視の前例）
- 所有が違うものには繋がない（`owner` も一致条件）
- 既存の対話型プリンターの挙動を変えない
- 実機で二重に接続しないことを確認できること

## 完了条件 (受け入れ基準)

- [ ] 同じ `ref` ＋ owner で二度開くと、**同じエントリが返り接続は 1 本**
- [ ] attach で**状態が変わらない**（停止中のものを開いても停止中のまま）
- [ ] attach 時にバッファ済みの帳票が `printer-opened` で届く
- [ ] 帳票バッファに上限があり、超えたら古いものから落ちる
- [ ] 累計受信数が落ちた分も含めて数えられる
- [ ] `ref` 無し（直接接続）は従来どおり毎回新規
- [ ] `npm run build` / `npm run lint` / `npm test` が通る
- [ ] **実機で「二度開いても 1 本」**を確認
- [ ] 既定の挙動が変わらない

## 未確定事項

- **上限の値**。警告は 20。帳票は 1 件が数十 KB になりうるので同じではない。**spec で決める**
- **attach 時に全部送るか**。上限まで溜まっていると `printer-opened` が大きくなる
