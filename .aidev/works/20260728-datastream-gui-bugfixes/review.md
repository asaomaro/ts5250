- **[should] 修正F の「次の ESC まで読み飛ばす」は、オーダーの引数バイト 0x04 で誤停止しうる**
  / 対応: **許容（原典どおり）＋ 挙動を記録**

  原典は「ESC(0x04) は表示データ（0x40 以上）にも他のオーダーにも現れないので安全」としている。
  **オーダー識別バイトとしては確かに 0x04 は使われない**が、`SBA` の行番号のような
  **引数バイトが 0x04 になることはある**（例 `ORDER.SBA, 0x04, 0x10` ＝ 4 行 16 桁）。
  読み飛ばし中は長さが分からず引数を識別できないため、ここで早期に止まる可能性がある。

  ただし**退行にはならない**ことを確認した。誤停止した場合、`applyDataStream` の外側ループが
  その 0x04 を ESC として読み、次のバイトを未知コマンドとして警告してレコードを打ち切る
  ——これは修正前の挙動（レコードの残りを捨てる）と同じ着地である。正しく停止できた場合だけ
  後続の WRITE/READ が救われるので、**期待値としては常に改善で、悪化する経路が無い**。

- **[nit] 修正I の DBCS ペア読み取りは、レコードが対の途中で終わると `PROTOCOL_ERROR` を投げる**

### 確認した点（指摘なし）

- **修正A の波及範囲**: `resize()` の呼び出し元は `clearUnitAlternate()`（:282）と
  `clearUnit()`（:342）の **2 つだけ**。`clearUnit()` 側で `clearGui()` を呼び直しているので、
  GUI が消える経路は修正前と変わらない。
- **修正D の等価性**: 旧実装が 24x80 のときに行っていた `cells.fill(null)` は、
  `resize(24,80)` の `new Array(...).fill(null)` と結果が同じ。`saveScreen()` は
  `cells.map(c => c === null ? null : {...c})` で**深いコピー**を取るため、配列を作り直しても
  退避済みスナップショットに影響しない（別名参照の問題なし）。
- **修正F の再同期位置**: 読み飛ばしは ESC を**消費せずに**止まり `return` するので、
  外側ループの `r.u8()` がその ESC を読む。`applyWtd` 冒頭の `if (b === ESC) return;` と同じ流儀。
- **修正E の退行なし**: 既存テスト（green / red の桁区切り）が通り続けている。
  黄・青緑で**本当に** DSPATR(CS) を頼んだ場合は区切りが出なくなるが、属性バイトから区別する
  手段が無い以上避けられない（`decorAttrClass` が既に同じ割り切りをしている）。
- **`.win-frame` と `.gui-window-border` の二重指定**: `hostBorderSegments()` は
  `"win-frame gui-window-border …"` と**両方のクラスを同一要素に**載せる。どちらのルールにも
  同じ `margin: 8px 0 0 10px` を書いたが、CSS は同一プロパティを加算しないので二重補正にならない。
- **AGENTS.md 準拠**: `console.*` を追加していない。core に `node:*` の import を足していない。
  原典の doc コメント（実機トレース・ACS 突き合わせ・利用者報告の出所）をすべて取り込んでいる。
  `.aidev` 成果物に実資格情報を書いていない（トレース例はホスト由来のバイト列のみ）。
- **`ORDER.UNKNOWN_1C` の命名**: 正体未確認を名前で明示しており、doc コメントに
  「要再確認」と残っている。原典の残課題をそのまま引き継げている。
