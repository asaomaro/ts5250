# 要件: SEU でカーソルを保護欄に置いた状態で PageUp/PageDown すると、
カーソルがヘッダーの入力欄へ強制移動してしまう不具合の修正

## 背景 / 課題

利用者から、`.aidev/backlog/acs-parity.md`「SEU の PageUp/PageDown で境界ページに到達した
ときカーソル位置を維持する」目標について、**具体的で再現性の高い手順**が提供された
（2026-09-15）:

1. 任意のソース（SEU、`STRSEU` でメンバーを開く。browse・edit いずれでも可）を表示する。
2. 10列10行目など、**入力不可（保護欄）の位置**にカーソルを設定する
   （矢印キー等、クライアント側のみの操作でホストへは送らない）。
3. PageUp を押下する。
4. **元のカーソル位置から、ヘッダー部分の入力可能エリアへフォーカスが勝手に移動する。**

利用者の報告: **ACS ではこの操作でカーソル位置が変わらない**（保護欄に置いたままの
位置を維持する）。

`.aidev/works/20260914-seu-page-cursor-hold` で取り組んだ「境界ページでのカーソル
保持」（Rule1/Rule2）は、ACS のコア実装に専用ロジックが見当たらなかったため撤去済み
（`decisions.md` D7）。しかし今回の報告は**境界ページに限定されない**（PageUp/PageDown
一般で、保護欄にいるときに発生する）——**現在残っている `session.ts` の既存分岐
（`PR#387`、`.aidev/works` 無し・コミット `c82e2b34`）が原因である可能性が高い**。

`PR#387` の分岐（`packages/tn5250/src/session/session.ts:642-659`）は
「画面が変わったのにカーソルが1桁も動かず、そこが入力できない桁なら、最初の入力欄へ
寄せる（ACS と同じ）」という条件で、**Enter キーで確定した際に上の欄が保護化され
カーソルが取り残される**シナリオ（`PR#387` のコミットメッセージ）向けに実機検証済みで
導入された。しかし、この分岐は**AID キー種別を問わず**発火する——今回の利用者報告は
**PageUp/PageDown** で同じ条件（「動いていない」「保護欄」）を踏んだ場合に、
`PR#387` と同じ条件で誤って発火している可能性が高い。既存の回帰テストは
`packages/tn5250/test/cursor-stale-on-protected.test.ts`（`PR#387` 本来のシナリオ）・
`packages/web-ui/test/screen-grid-cursor-restore.test.ts`（SEU 走査検索でカーソルが
`SEU==>` へ飛ばないシナリオ）にある。

**WTD（Write To Display）**: ホストから届く画面描画データストリーム。5250 プロトコルの
基本単位で、`cursorSet`（WTD 中にカーソル位置指定があったか）はここから導出される
（`applyDataStream` の戻り値）。

## 目的 / ゴール

SEU でカーソルを保護欄（入力不可な位置）に置いた状態で PageUp/PageDown を行っても、
ACS と同様にカーソル位置が変わらない状態。かつ、`PR#387` が実機検証済みの本来の
シナリオ（Enter で確定した際に上の欄が保護化されカーソルが取り残されるケース）は
引き続き正しく動作する状態。

## ユーザーストーリー

- US1: SEU でソースを読む利用者として、保護欄（コメント行や本文行）にカーソルを
  置いた状態でページ送りしても、カーソル位置が変わらないでほしい。なぜなら、
  カーソルがヘッダーへ強制移動すると、読んでいた位置を見失い、都度カーソルを
  戻す操作が余計に必要になるから。（受け入れ: AC1）
- US2: 開発者として、修正が既存の実機検証済みの正しい挙動——`PR#387`（Enter で確定後、
  上の欄が保護化されカーソルが取り残されるケース）と SEU 走査検索
  （見つけた保護欄の位置へカーソルを飛ばし、`SEU==>` へは戻さないケース）——を
  壊さないことを確認したい。なぜなら、どちらも実機検証済みの既存の正しい挙動であり、
  これを壊すと別の不具合を再発させることになるから。（受け入れ: AC2, AC5）
- US3: 開発者として、原因を実機トレースで確認してから修正したい。なぜなら、
  `.aidev/works/20260914-seu-page-cursor-hold` の教訓（推測のみで直すと的外れに
  なりうる）があり、また `PR#387` の条件を安易に狭めると別の既知シナリオを
  壊すリスクがあるから。（受け入れ: AC3, AC4）

## スコープ

### 対象

- SEU で保護欄にカーソルがある状態から PageUp/PageDown した際のカーソル確定
  ロジック（`packages/tn5250/src/session/session.ts` の `PR#387` 分岐、642-659行）。
- 実機トレースによる原因特定（利用者の再現手順に沿って、PageUp 送信前後の
  `cursorAddr`（カーソルのアドレス）・`cursorSet`・`cursorIsUnenterable()` の値を
  確認する）。
- `PR#387` の既存シナリオ（Enter で確定後の保護化）の回帰確認。
- SEU 走査検索（見つけた保護欄の位置へカーソルを飛ばすシナリオ。`PR#387` の
  コミットメッセージにある「2/9 → 11/53（動く）」ケース）の回帰確認——本 work の
  修正が「動いていない」ことを条件に加える／変える場合、この「動く」ケースの扱いに
  影響しないことを確認する対象として明示的に含める。

### 対象外

- `.aidev/works/20260914-seu-page-cursor-hold` で撤去した Rule1/Rule2（境界ページ
  でのカーソル維持専用ロジック）の再実装。今回の課題は境界ページに限定されないため、
  別のアプローチが必要（別課題として扱う）。
- ACS の UI 描画層の調査（今回は利用者自身の実機操作による確認で足りるため、
  この work では ACS を直接操作しない）。
- SEU 走査検索の既存シナリオ（`PR#387` のコミットメッセージにある「2/9 → 11/53
  （動く）」ケース）以外の、カーソルが移動する一般的なケースの網羅的な見直し。

## 機能要件

- PageUp/PageDown 送信時、保護欄でカーソルが動かなかった場合に `PR#387` の分岐が
  発火しないようにする（AID キー種別による除外条件を追加する、または実機トレースの
  結果に基づく別の条件を設計する）。
- Enter 等、`PR#387` が本来対象とするシナリオでは、引き続き分岐が発火する。
- SEU 走査検索で保護欄へカーソルが移動する（動く）シナリオでは、`PR#387` 分岐が
  そもそも発火しない（既存の「動いていない」という条件で排他済み）ことを維持する。

## 非機能要件 / 制約

- 修正は `packages/tn5250` 内部実装に閉じ、公開 API・型シグネチャの破壊的変更を
  伴わない見込み（設計段階で確認する）。
- **実機トレースでの裏付けを取ってから設計判断を行う**（推測のみでの修正をしない。
  `.aidev/works/20260914-seu-page-cursor-hold` の教訓）。利用者自身の実機・ACS操作に
  よる証言（「ACS ではカーソル位置が変わらない」）を ACS 側の実機確認として扱い、
  この work では自クライアント側の実機トレース（PageUp 送信前後の WTD・カーソル状態）
  を取得して原因を特定する。

## 未確定事項 / 確認したいこと

- `PR#387` の分岐に「直前に送信した AID キーが PageUp/PageDown なら発火しない」
  という除外条件を追加するのが妥当か、それとも実機トレースで別の判別方法
  （例: ホストが実際に IC を送っているか否か）が見つかるかは、research で確認する。
- 「直前に送信した AID キー」を `Session5250` が保持する仕組みは
  `.aidev/works/20260914-seu-page-cursor-hold` で一度実装（`lastSentAid`）した後に
  撤去済み。同じ仕組みが必要になった場合、撤去した経緯（D7: ACS のコアに
  専用ロジックが無かったため）とは**別の目的**（AID キー種別による除外条件）で
  再度必要になる可能性がある——design で判断する。
