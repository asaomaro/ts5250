# レビュー: サービス一覧の画面

## ラウンド 1（自己レビュー）

### 実装中に気づいて直したもの

**`watches.history(w.id, user)` を無条件に呼んでいた。**
`history` は所有者を検査して**投げる**ので、起動時に上がった監視（所有者なし）を
一般利用者が見ると **500 になる**。`detail` のときだけ数えるようにした。
一覧を一般に開くという変更が、**既存の所有者検査と衝突する**典型で、
「見せる範囲を広げる」ときは呼び先の検査を 1 つずつ確かめる必要がある。

**`listPrinters(user)` で絞ったままだった。**
絞ると**起動時に上がったサービス（所有者なし）が一般利用者から消える**——
それでは「動いているか」が分からず、この画面の目的が果たせない。
絞らずに突き合わせるようにした。安全なのは**定義の一覧が既に認可済み**で、
`ref` が保管場所ごとに一意だから（他人の実体には当たらない）。

**`printer-service-start` が停止中の常駐に効かなかった。**
`openPrinter` は `ref` で既存を返して終わるので、そのままでは
「押しても動かない」。`autoStart: false` で開いて**明示的に `startPrinter`** を呼ぶ形にした。
1 通で「一度も開いていない定義」と「停止中の常駐」の両方に効く。

## 判断の記録

### なぜ `listSessions` を緩めず新しい口を作ったか

「サーバー設定は admin だけ」は**信頼設定（パス・コマンド・資格情報）の置き場**を守る規則で、
これは残す価値がある。一方で「いま何が動いているか」は運用の情報で、秘密ではない。

`listSessions` に `includeX` を足して分岐させると、**規則が条件付きになる**——
足し忘れ 1 つで信頼設定が漏れる。`ServiceDef` という**別の狭い型**にすれば、
漏れようがないものしか通らない（型が境界になる）。

テストで `listSessions` が同じ相手に 0 件を返すことを**併記**してある。

### なぜ状態は push で受けないか

真実はサーバー側にあり、**押した結果が効いたかは画面の記憶ではなくサーバーに聞く**のが
この画面の性格。push を積み上げると「画面には出ているがサーバーにはない」ずれが生まれる。

代償は反応の遅さ（操作後 1.2 秒＋定期 4 秒）。一覧画面なので許容できる。

## nit（直していない）

- **状態の色分けが 3 か所目になった**（`PrinterPane` / `WatchPane` / `ServicesPane`）。
  レビューの前回で「3 か所目が出たら畳む」と書いたので、**次に触るときに畳む**。
  今回畳まなかったのは、語が 3 通り（監視中 / 待ち受け中 / 未起動）に増えており、
  共通化すると引数で分岐する層のほうが大きくなるため。
- **定期取得の間隔が固定（4 秒）**。定義が増えたときに調整できるとよい。
