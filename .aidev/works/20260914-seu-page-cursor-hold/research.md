# 調査: SEU の PageUp/PageDown で境界ページに到達したときのカーソル制御

## 調査の問い

- Q1: 境界ページ（先頭ページ・最終ページ、それ以上スクロールできない状態）に到達したとき、
  ホストは実際に IC/MC（カーソル位置指定オーダー）を省略するのか。
- Q2: 上記の結果を踏まえ、`packages/tn5250/src/session/session.ts:613-616` の
  「IC/MC が無ければ無条件に先頭入力欄へ寄せる」分岐は、今回の不具合の原因か。
- Q3: 修正方針はどうあるべきか（AID キー種別による除外か、一般化した条件か）。

## 判明した事実

**実機（`.env.verify` の実機・IBM i 7.3、CCSID 5035）に接続し、80行のダミーソース
（`ASAOLIB/QCLSRC(PAGECURS)`、`* LINE 0001`〜`* LINE 0080`、`scripts/build-pagecurs.mjs` で作成）
に対し `STRSEU` の browse（OPTION 5）・edit（OPTION 2）両モードで PageUp/PageDown を送り、
`Session5250` の `traceRecords: true` で受信レコードの生バイトを採取して IC(0x13)/MC(0x14) の
有無を直接確認した。**（診断スクリプト: `scripts/diag-seu-page-cursor.mjs`（browse）、
`scripts/diag-seu-page-cursor-edit.mjs`（edit、非境界→末尾境界）、
`scripts/diag-seu-topboundary.mjs`（edit、先頭境界の反復確認））

- F1: **cursorSet（IC/MC の有無）は、観測した全ケース（browse/edit、非境界/境界、
  先頭/最終、合計 40 回超の PageUp/PageDown）で常に `true` だった。** ホストが IC/MC を
  省略したケースは一度も観測されなかった。
  根拠: 各スクリプトの実行ログ（`IC含む=true MC含む=true` が全行）。
- F2: **したがって、`session.ts:613-616`（`readRequested && !cursorSet` の分岐）は、
  この不具合のいずれの再現手順でも一度も発火していない。** cursorSet が常に true である以上、
  この分岐は無関係であり、requirements.md の当初仮説（この分岐が誤発火の原因）は**実機の
  証拠によって否定された**。
  根拠: F1 と `session.ts:613`（`if (result.readRequested && !result.cursorSet)`）の条件式。
- F3: browse モード（OPTION 5）では、**唯一の入力欄が `SEU==>`（コマンド行、row2/col9）
  であり**、走査検索（`F '<文字列>'`）で本文中に一時的にカーソルを移動させても、
  その直後の PageDown/PageUp では**必ず**（境界かどうかに関わらず）カーソルが
  `SEU==>`（2/9）へ戻る。ホストが明示的に IC で row2/col9 を指定している（cursorSet=true）。
  根拠: `scripts/diag-seu-page-cursor.mjs` ケースA/B/Cの全ログ（走査検索直後の非2/9カーソルが、
  次の PageDown/PageUp 1回で必ず2/9に戻る）。
  → **browse モードでは「本文中にカーソルが留まる」場面自体が実質無い**ため、
  ユーザー報告の「まだ続きのページがある場合はカーソル位置が維持される」は
  **browse モードの挙動とは一致しない**。次の F4 が示す edit モードの方が報告と整合する。
- F4: **edit モード（OPTION 2）では、各ソース行が個別の入力欄であり、`sendAid` の
  `cursor` オプション（後述 F7）で本文行にカーソルがある状態を作れる。** この状態から
  PageDown した場合:
  - 非境界（続きのページがある）遷移: **カーソルは送信時と同じ画面行・桁に維持される**
    （例: 8/9 → 8/9、7回連続で確認）。ACS の期待挙動（ユーザー報告の「まだ続きのページが
    ある場合はカーソル位置が維持される」）と一致する。
  - **最終ページ手前から最終ページ（まだ何行かソースが見えている状態）への遷移でも、
    ほぼ維持される**（例: `LINE 0072`〜`LINE 0080` + データの終わりマーカーが見えるページでも
    8/9 のまま）。
  - **さらに1回 PageDown すると（画面はまだ変化する＝マーカーだけの空ページへ）、
    カーソルは 8/9 から 4/9 へ移動する**（本文行の入力欄がその画面には存在しないため）。
  - **さらにもう1回 PageDown すると（画面はもう変化しない＝真の境界）、カーソルは
    `SEU==>`（2/9）へ移動する。** このときも IC/MC は明示的に付与されている
    （cursorSet=true。F2 参照）。
  根拠: `scripts/diag-seu-page-cursor-edit.mjs` ケースD のログ（D-PageDown #1〜#8 は
  「送信カーソル 8/9 → 受信後カーソル 8/9」、#9 で「8/9 → 4/9」、#10 で
  「画面変化=false、8/9 → 2/9」）。
- F5: **先頭ページ側の境界は、末尾側と非対称。** 先頭ページを開いた直後、本文行
  （8/9）にカーソルがある状態を明示して PageUp を送ると、画面は変化しない
  （既に先頭ページで、それ以上遡れない）にもかかわらず、**カーソルは 8/9 のまま維持される**
  （6回連続で確認、一度も 2/9 へ戻らない）。
  根拠: `scripts/diag-seu-topboundary.mjs` の実行ログ（top-PageUp #1〜#6 すべて
  「cursor 8/9」のまま、IC/MC は毎回 true）。
  → **末尾側の「境界でカーソルが飛ぶ」不具合は、先頭側では実機上は再現しなかった。**
  ユーザー報告は「先頭ページや最終ページでは」と両方に言及しているが、少なくとも
  今回作った素朴なテスト条件（本文行にカーソルがある状態を `sendAid` の `cursor` で明示） では
  非対称という実機の事実が観測された。
- F6: F4 の「4/9 への移動」「2/9 への移動」は、いずれもホストが**明示的に IC で
  その位置を指定した結果**であり、クライアント側が IC/MC の欠落を補って推測した
  ものではない（cursorSet は常に true。F2）。**つまりこの挙動は SEU プログラム自身が
  意図して行っている**（少なくとも、このクライアントが受け取るデータストリームの上では）。
- F7: `Session5250.sendAid(key, opts)` は `opts.cursor?: {row, col}` を受け付け、
  ホストへ送信するレコードのカーソル位置だけを一時的に上書きできる（`buf.cursorAddr` 自体は
  変えない）。web-ui は実際にこの経路を使っている——ブラウザ側でクリック/フォーカスした位置を
  ローカルの `cursorOverride`（`EmulatorPane.vue`）として保持し、次の AID 送信時に
  `sendKey(..., cursor)` → WS `{type:"key", cursor}` →
  `packages/server/src/ws-handler.ts:999` `session.sendAid(key, {cursor})` として
  そのつど渡す。**`Session5250` 自体はカーソル位置を継続的に「今どこにあるか」として
  保持する public API を持たない**（`buf` は private。`cursorAddr` は内部の WTD 処理からのみ
  更新される）。
  根拠: `packages/tn5250/src/session/session.ts:86,336,383`、
  `packages/tn5250/src/protocol/read-response.ts:358-367,233-241`、
  `packages/web-ui/src/components/ScreenGrid.vue:3580-3595,2780-2828`、
  `packages/web-ui/src/components/EmulatorPane.vue:115-124,539`、
  `packages/web-ui/src/session-controller.ts:1122-1160`、
  `packages/server/src/ws-handler.ts:999-1000`。

## 影響範囲

- F2 により、当初 requirements.md が疑っていた `session.ts:613-616` は**今回の不具合の
  発火経路ではない**ことが実機で確認された。この分岐（F1ヘルプ/27x132切替時の既定動作）は
  **今回のスコープからは事実上外れる**——触る必要も、回帰を心配する必要も無くなった
  （ただし design で最終確認する）。
- 一方で `session.ts:617-634`（`PR#387`、保護欄からの退避、`cursorSet===true` かつ
  「動いていない」場合に発火）は、**F4 の「4/9 へ移動」「2/9 へ移動」のケースと
  条件が重なる可能性がある**（cursorSet=true という条件は満たすが、カーソルは
  「動いている」ので `cursorAddr === cursorBefore` は満たさない見込み——`cursorBefore` は
  クライアントの `buf.cursorAddr`（8/9 相当）で、IC後は 4/9 や 2/9 に変わるため、
  この分岐自体もおそらく無関係。design で厳密に確認する）。
- 今回の事実（F4〜F6）を踏まえると、**修正はホストの IC 指定を「常に信用する」現在の実装から、
  特定の条件下でクライアントが IC を無視して直前のカーソル位置を保持する、という
  方向へ変わる可能性が高い**。これは「ホストの指示に従う」という現在の設計原則からの逸脱であり、
  影響範囲は `session.ts` 内に閉じる見込みだが、**どの条件で無視するかの線引き**が
  設計上の主眼になる（下記「design への申し送り」参照）。

## 実現性 / リスク

- 技術的には、`sendAid` 呼び出し前後で「画面が変化したか」「カーソル対象の欄が
  引き続き存在するか」を比較する材料はクライアント側に揃っている
  （`applyDataStream` 前後の `ScreenBuffer` 比較、`cursorIsUnenterable()` 等の既存ヘルパー）。
  「ホストの IC を無視する」条件を狭く保てば（例: PageUp/PageDown の AID 応答に限定する等）、
  他の AID キー・他の画面（F1ヘルプ等）への影響は避けられる見込み。
- リスク: **F5 の非対称性**（先頭境界は問題なし、末尾境界のみ問題あり）の原因が
  クライアントとホストのどちらの「境界の詰め方の違い」に起因するのか、
  design 段階でもう一段掘り下げないと、「末尾だけ効く条件」を正しく書けない
  （雑に「画面が変化しなければ無視」にすると、F4 の #9→#10 のような
  「画面はわずかに変化するが実質もう境界」のケースを取りこぼす）。
- **IBM ACS との直接比較ができていない**（この環境に ACS が無く、実機への同時接続による
  横並び比較は実施していない）。requirements.md の前提「ACS ではカーソル位置が維持される」
  は今回未検証のまま design へ引き継がれる。F4〜F6 で観測された「ホストが明示的に
  SEU==> へ IC を送る」という事実に対し、ACS がその IC を額面通り受け入れているのか、
  独自に無視しているのかは、**今回の実機トレースだけでは判別できない**
  （データストリームは同一クライアントで採取したものであり、ACS 側のログは無い）。

## 実装アンカー

- A1: 今回の現象を再現するための実機診断スクリプト一式（今後の design/coding/test で
  再利用可能）:
  - `scripts/build-pagecurs.mjs` — 80行のダミーソース `ASAOLIB/QCLSRC(PAGECURS)` を作る。
  - `scripts/diag-seu-page-cursor.mjs` — browse(OPTION 5) での境界挙動確認（ケースA/B/C）。
  - `scripts/diag-seu-page-cursor-edit.mjs` — edit(OPTION 2) での境界挙動確認（ケースD/E、
    `sendAid` の `cursor` オプションで本文行にカーソルがある状態を明示的に再現）。
  - `scripts/diag-seu-topboundary.mjs` — edit(OPTION 2) 先頭ページでの反復 PageUp 確認。
- A2: 修正候補の分岐（`packages/tn5250/src/session/session.ts:613-634`）——
  ただし F2 によりこのままでは無関係と判明したため、**新しい分岐（または既存分岐の拡張）を
  どこに置くかは design で決める**。挿入位置の候補は `session.ts` の `handleRecord()`
  （`session.ts:532-634` 付近、IC/MC 適用後・カーソル確定前）。
- A3: 「PageUp/PageDown の AID 応答であること」をクライアントが知る手段——
  `session.ts` は直前に送った AID キー種別を保持していない（`pendingAid` は
  resolve/timer のみ保持。`aidev-00-start` の事前調査で既出）。この分岐を
  「PageUp/PageDown 限定」で作るなら、**新規に「直前に送信した AID キー」を
  保持する小さな状態追加が必要**（未特定 — design で決める）。
- A4: 画面変化の比較対象——`ScreenBuffer` のセル内容比較、または
  `session.snapshot().cells` のテキスト化比較（診断スクリプトの `text()` 関数と同等の
  比較を `session.ts` 内で行うのは重い可能性があるため、より軽量な比較手段
  （例: WTD の CLEAR_UNIT の有無、書き込まれたセル数）が使えないか design で検討する
  ——未特定。

## 実装時の注意

- **`sendAid` の `cursor` オプションは `buf.cursorAddr` を変えない一時的な上書きである**
  （F7）。実機診断スクリプトを書く／読む際にここを勘違いすると、「クライアントの内部状態」と
  「その回だけ送信レコードに載る値」を混同する。設計・実装でも、`session.ts` 内部の
  `cursorAddr` を「直前にクライアントが主張したカーソル位置」の唯一の真実として
  扱ってよいのか（web-ui の `cursorOverride` の方が実態に近いのでは）は、
  design で明確にする必要がある。
  **[解決済み・decisions.md D5]**: この懸念を design 時点で解消せずに実装した結果、
  deliver（PR #395）後に実機で「クリックで別の欄へ移してから PageUp すると
  無関係な位置へ戻る」という回帰として顕在化した。修正は `sendAid()` が
  `opts.cursor` を受け取った時点で `buf.cursorAddr` をそれに同期させるというもの
  （`decisions.md` D5 参照）。**教訓**: research が「design で明確にする必要がある」と
  残した懸念は、design.md 側で実際に解消したことを確認してから coding へ進むべきだった
  （このケースでは design.md にこの懸念への言及が引き継がれず、宙に浮いていた）。
- **browse モード（OPTION 5）は本文中にカーソルが留まる状況が作れない**（F3）ため、
  この不具合の再現・自動テストは **edit モード（OPTION 2）を主軸に据えるべき**
  （AC1〜AC3 の受け入れ確認、AC8 の自動テストとも、edit モードでの検証が中心になる）。
- **末尾境界の「4/9 への移動」（F4 の #9）は、真の境界（#10）の1つ手前の中間状態**であり、
  実際のユーザー操作でも「終わりのマーカーが見えたのにもう一度 PageDown する」という
  ありがちな操作で踏む。修正の受け入れ基準（AC1）を検証する際、**#10（完全な境界）だけでなく
  #9 相当（マーカーは見えるが微妙に画面が変わる境界）も見落とさないこと**。
- ダミーソース `PAGECURS` は 80 行・1画面 16〜17 行相当で、境界まで PageDown 約 9〜10 回、
  PageUp も同程度。test 工程で再利用する場合はこの行数・境界到達回数を踏まえる。

## design への申し送り

- **当初仮説（`session.ts:613-616` が原因）は実機の証拠により否定された。** design は
  この分岐の削除・条件変更ではなく、**「ホストが明示的に送ってきた IC を、特定条件下で
  クライアントが無視し、直前のカーソル位置を保持する」という新しい仕組み**を設計する
  必要がある（F2, F4, F6）。
- **設計判断が必要な論点**:
  1. 「無視する条件」をどう定義するか（例: 直前に送った AID が PageUp/PageDown であり、
     かつ画面内容が実質変化していない／本文行の入力欄が消えた、等）。F4 の #9・#10 の
     両方を拾える条件にすること。
  2. 「直前に送信した AID キー種別」をどう保持するか（A3）。
  3. F5 の非対称性（先頭境界は問題なし）をどう解釈するか——「先頭は既に正しいので
     何もしなくてよい」のか、「今回のダミーソースだからたまたま出なかっただけで、
     本当は対称に直すべき」なのか、design で追加検証するか、それとも requirements の
     AC2（先頭ページでの維持）を「現状も問題なし」として扱うか。
  4. **ACS の実際の挙動が未検証**（実現性/リスク参照）。設計の正しさの最終的な物差しは
     「ユーザーが求める見た目の挙動」（PageUp/PageDown でカーソル位置が変わらない）であり、
     ACS の内部実装を完全に模倣する必要はない、という前提で進めてよいか、
     requirements のオーナー（ユーザー）に確認する余地がある。
- 上記1・2は tasks 分解の起点になる。3・4 は **decisions.md に判断根拠を残すこと**
  （特に4は、この work の受け入れ基準の解釈に関わるため）。
