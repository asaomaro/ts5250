# 判断記録

## D5: deliver（PR #395 マージ）後、利用者から「改善していない」と報告——`cursorBefore` が
`buf.cursorAddr` を直接参照していたための取りこぼしを修正

- 背景: PR #395 マージ後、利用者が実機（web-ui 経由）で PageUp を試したところ、
  「カーソルが移動してしまう」ままだった（スクリーンショット2枚での報告）。
  research.md「実装時の注意」に**未解決のまま残していた懸念**（「`session.ts` 内部の
  `cursorAddr` を『直前にクライアントが主張したカーソル位置』の唯一の真実として
  扱ってよいのか——web-ui の `cursorOverride` の方が実態に近いのでは」）が、
  実際に踏まれた。
- 根本原因: `Session5250.sendAid(key, opts)` の `opts.cursor`（web-ui がマウスクリック等で
  ローカルに移したカーソル位置を伝える経路。`research.md` F7）は、**送信レコードの値を
  一時的に上書きするだけ**で `this.buf.cursorAddr` 自体は更新しない
  （`packages/tn5250/src/protocol/read-response.ts:240,366`
  `const cur = cursor ?? buf.rowColOf(buf.cursorAddr);`）。
  一方、今回追加した新分岐は `cursorBefore = this.buf.cursorAddr`（`handleRecord()` 冒頭）を
  「送信直前のカーソル位置」として扱っていた。利用者がクリックで別の欄へカーソルを移し、
  その状態のまま（別の AID を経由せずに）直接 PageUp/PageDown を押すと、
  `buf.cursorAddr` は**クリック前の古い位置のまま**——境界に達すると、新分岐が
  「送信前の位置」として復元するのはこの**古い**位置になり、利用者がクリックした
  実際の位置とは無関係な場所へカーソルが飛んで見える（報告された症状と一致）。
- 判断: `sendAid()` で `opts.cursor` が渡された時点で `this.buf.cursorAddr` を
  その位置へ同期する（範囲外の値は例外を投げず黙って無視——`buildFieldResponse` 側も
  検証せずそのまま送るのと同じ扱いにする）。これにより `buf.cursorAddr` が
  「クライアントが最後に申告したカーソル位置」を常に正しく反映するようになり、
  新分岐（および将来 `buf.cursorAddr` を参照する他のロジック）が古い値を掴む余地を
  構造的に閉じる。Attn/SysReq は対象外（`lastSentAid` の更新と同じ理由・同じ条件）。
- 理由 / 代替案: 新分岐だけに個別のパッチ（`lastSentCursorAddr` を別途持つ等）を
  当てる案もあったが、design.md がそもそも指摘していた懸念は「`buf.cursorAddr` を
  唯一の真実として扱ってよいか」という**より根本的な**ものであり、既存の `PR#387`
  分岐（保護欄退避）も同じ `cursorBefore` を参照している以上、同種の取りこぼしを
  抱えていた可能性がある。個別パッチではなく `buf.cursorAddr` 自体を正しく保つ方が、
  今回の新分岐に閉じない、より一般的な修正になる。
- 検証: `packages/tn5250/test/cursor-page-boundary.test.ts` に、クリック（`opts.cursor`）で
  別の欄へ移してから境界ページで PageDown する回帰テストを追加。修正前はこのケースのみ
  失敗することを確認済み。既存 595 件（monorepo 全体では tn5250:595, web-ui:2035 等）は
  すべて green のまま。
- 影響: `Session5250` の `opts.cursor` を使う全ての呼び出し経路（web-ui のクリック直後の
  キー送信全般）に及ぶ変更だが、**直接検証したのは PageDown 境界のケースのみ**
  （タスク点検で指摘）。既存 595〜596 件は全通過しているが、非ページキー×
  `opts.cursor` の組み合わせ（例: `PR#387` の保護欄退避分岐との相互作用）を狙って
  検証するテストは追加していない——既存テストが偶然そのケースを踏んでいなければ、
  「悪影響が無い」の根拠は「未検証」であって「確認済み」ではない。
  実機（web-ui + 実ホスト）での再確認は、この PR のレビュー・
  マージ後に利用者側で行う。

## D6: ACS（`acsbundle.jar`）のデコンパイル調査——コア WTD 処理には
「PageUp/PageDown 境界でカーソルを保持する」専用ロジックが見当たらなかった

- 背景: D1 で「ACS との実機同時比較ができていない」としていたが、ユーザーから ACS の
  実体（`/mnt/c/tool/IBMiAccess_v1r1/acsbundle.jar`、IBM i Access Client Solutions）を
  教示された。`plugins/emulator/acshod2.jar`（Host On-Demand 系譜の emulator コア、
  `com.ibm.eNetwork.ECL.tn5250.*`）を CFR（OSS デコンパイラ）で逆コンパイルし、
  `DS5250`（データストリーム処理）・`PS5250`（プレゼンテーション・スペース）を確認した。
- 判明した事実:
  - `PS5250.setDefaultInsertCursor()` は fft（フォーマットテーブル）を走査して
    最初の非バイパス（入力可能）欄の先頭へ `homePos` を置く——**「IC/MC が無ければ
    最初の入力欄へ」という当プロジェクトの既存ロジック（`session.ts:613-616` 相当）と
    同じ設計**。ここは相違点ではない。
  - `DS5250.preprocessWCC2()`（WTD 確定時にカーソル位置を決める中核ロジック）は
    「`WTD_IC_addr` が無ければ `setDefaultInsertCursor()` → 最初の入力欄／
    あれば IC の位置／`WTD_MC_addr` があれば MC が優先」という、当プロジェクトの
    613-634 相当とほぼ同じ組み立てだった。**「PageUp/PageDown 直後に限りホストの
    IC より送信前のカーソル位置を優先する」という、今回追加した Rule1/Rule2 に
    相当する専用ロジックはコア（`DS5250`/`PS5250`）には見当たらなかった**
    （唯一の例外は「ENPTUI selection field」——GUI 選択ウィジェット——が同じ欄のまま
    なら戻す、という狭い特殊ケースのみ。プレーンな SEU テキスト欄には当たらない）。
  - `AvoidThrashingWTD`（`DS5250` 内部クラス）は「250ms 以内に同一 WTD が
    大量（100回以上）届く」ホスト側の暴走を検知して間引く防御機構で、
    利用者操作としての PageUp/PageDown（人間の打鍵間隔）とは無関係。
- 解釈 / 未解決: コアの WTD 処理だけを見る限り、ACS も「ホストが明示的に送ってきた
  IC をそのまま受け取る」という点では当プロジェクトと同じ構造に見える。
  したがって、ユーザーが観察した「ACS は境界でもカーソル位置が変わらない」という
  現象は、(a) ACS 側のキー送信時にクライアントが申告するカーソル位置が
  当プロジェクト（修正前）と異なり、その違いがホスト側（SEU）の応答判断に
  影響している、(b) UI 描画層（Swing、今回は未調査）に protocol 状態とは別の
  見た目上のカーソル位置保持がある、(c) ユーザーの観察自体が
  `decisions.md` D5 で直した「クリック起因のズレ」と同種の要因を含んでいた、
  のいずれか（複合もありうる）で、**コアの逆コンパイルだけでは断定できなかった**。
  UI 描画層（`com.ibm.eNetwork.HOD.gui` 相当、または ACS 独自の Swing 拡張）の
  追加調査、または実機での ACS 側トレース採取（`tap-proxy.mjs` が使える）が
  次の手がかりになる。
- 判断: D1 の「ACS の実挙動は未検証」という前提は、コアロジックの限りでは
  **当プロジェクトの設計と大きく矛盾しないという弱い追加根拠**を得たが、
  「境界でカーソルが動かない」という具体的な観察を完全に説明する専用ロジックは
  見つからなかったため、D1 の判断（ユーザーの要望どおりの挙動を正として実装する）は
  変更しない。この調査結果は次回 ACS 差分調査の出発点として残す。

## D1: ACS の実挙動が未検証のまま、ユーザーの要望どおりの挙動を正として設計する

- 背景: `research.md` の通り、この環境には IBM ACS が無く、実機への同時接続による
  横並び比較ができない。ホストは境界ページで明示的に IC を `SEU==>` へ送っており
  （`research.md` F4/F6）、これは SEU 自身の意図的な挙動である可能性が高い。
  ACS がこの IC を額面通り受け入れているのか、独自に無視しているのかは不明。
- 判断: `requirements.md` に明記されたユーザーの要望（PageUp/PageDown でカーソル位置が
  変わらない）を正として design を進める。ACS の内部実装の完全な再現は目的にしない。
- 理由: この製品の受け入れ基準はユーザーの利用体験であり、ACS の実装詳細そのものではない。
  ACS の挙動を確認する手段が無い以上、要望を字義通り満たす設計に進むのが唯一の実行可能な道。
  将来 ACS 実機比較の機会があれば、review/test で追加確認する余地を残す（下記 D2）。

## D2: PageUp/PageDown 以外の AID キーで境界に至る類似ケースは今回のスコープに含めない

- 背景: 本設計の新ルールは AID キー種別を PageUp/PageDown に限定する
  （`design.md`「対象範囲」「振る舞いの詳細」）。SEU 以外のプログラムが別のロールキー
  （例: F7/F8 に割り当てた ROLL 相当）で同様の境界挙動を持つ可能性は実機で確認していない。
- 判断: 今回は PageUp/PageDown のみを対象とする。他のロールキーでの類似不具合が
  実機で確認された場合は、別途 backlog へ追記して次回以降の課題とする。
- 理由: requirements.md のスコープが PageUp/PageDown に限定されており、無関係な
  AID キーにまで一般化すると検証範囲が際限なく広がる（`research.md`「実現性/リスク」）。

## D4: 2件の既知の残存リスクは、この work のスコープでは直さないと確定する

- 背景: T3（`session.ts` の新分岐）のタスク点検（2ラウンド）と、全タスク完了後の
  タスク横断点検（cross）の両方で、同根の2件の指摘が繰り返し出た。
  1. `cellsSignature()` はセルの文字・属性バイトのみを比較し、フィールドの
     FFW（保護ビット等）は比較に含まない。理論上、画面の文字・属性が完全一致したまま
     FFW だけが変わる（同じ表示属性のまま保護状態が変わる）という5250上あり得る
     パターンでは、`cursorBeforeWasEnterable` による排他が効かず、`PR#387` 分岐との
     重なりが再発しうる（cross 点検では「Rule2 適用**後**に戻す先＝`cursorBefore` が、
     その応答で保護化されていないかを再検証していない」という切り口でも同じ穴を指摘）。
  2. `lastSentAid` から Attn/SysReq を除外した副作用として、PageDown 応答待ち中に
     Attn/SysReq を挟んだ場合、その後に届く**無関係な**レコードに対しても `isPageKey`
     が "PageDown" のまま誤って true 判定されうる（1ラウンド目で直した「取りこぼし」の
     裏返しの誤判定。方向が逆なだけで、根はどちらも AID とレコードの対応付けを
     `lastSentAid` という単純な最新値でしか追えないことに起因する）。
- 判断: **どちらもこの work では対応しない、と確定する**（「60 review へ判断を委ねる」
  という先送りではなく、ここで close する）。実機トレース（`research.md`）では
  いずれも観測されておらず、`protocol-check.md` の方針（上限で止まったら深追いしない）
  にも合致する。コード側にも残存リスクである旨のコメントを追加済み
  （`session.ts` の新分岐コメント）。
- 理由 / 代替案:
  - 1点目を直すには `cellsSignature()` に FFW も含める設計変更が要り、
    「軽量な比較」という design.md の前提を再検討することになる（今回のスコープを超える）。
  - 2点目を直すには AID 送信とその応答レコードを 1:1 で対応付ける仕組み
    （リクエスト ID 相当）が要り、既存の `pendingAid`/`readCommand` の設計全体に
    影響する大きな変更になる。
  - どちらも「表示属性を変えずに保護状態だけ変える」「PageUp/PageDown応答待ち中に
    Attn/SysReqを挟む」という、SEU の境界ページ問題という当初のスコープからは
    外れた入力が必要で、実機で観測されるまでは投機的な作り込みになる。
- 影響: 将来、実機でこれらのパターンが実際に踏まれた場合は、新規の backlog 項目として
  切り出す（この work の再オープンではなく別 work とする）。review 工程はこの2件を
  「未解決の指摘」として再度上げるのではなく、この決定記録を踏まえて close 済みとして扱う。

## D3: 先頭ページ側の非対称性に、方向別の特別扱いを入れない

- 背景: `research.md` F5 の通り、先頭境界は現状のダミーソースでは問題が再現しなかった
  （ホストが既に正しく維持している）。末尾境界とは非対称。
- 判断: 方向（PageUp/PageDown）ごとに異なる条件を作らず、`design.md` の Rule1/Rule2 を
  両方向に対称に適用する統一ルールとする。
- 理由: 先頭境界で新ルールが（現状すでに正しい動作と）同じ結果を出すことを
  `research.md` F5 の実機データで確認済みであり、方向別の特別扱いを持ち込むと
  条件が複雑化し、将来別のソース内容（先頭境界でも Rule1 相当の中間状態が起きる場合）で
  かえって非対称な不具合を生む恐れがある。対称な単一ルールの方が保守しやすい。
