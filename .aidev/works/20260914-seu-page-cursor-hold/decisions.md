# 判断記録

## D1: ACS の実挙動が未検証のまま、ユーザーの要望どおりの挙動を正として設計する

- 背景: `research.md` の通り、この環境には IBM ACS が無く、実機への同時接続による
  横並び比較ができない。ホストは境界ページで明示的に IC を `SEU==>` へ送っており
  （`research.md` F4/F6）、これは SEU 自身の意図的な挙動である可能性が高い。
  ACS がこの IC を額面通り受け入れているのか、独自に無視しているのかは不明。
- 判断: `requirements.md` に明記されたユーザーの要望（PageUp/PageDown でカーソル位置が
  変わらない）を正として design を進める。ACS の内部実装の完全な再現は目的にしない。
- 理由: この製品の受け入れ基準はユーザーの利用体験であり、ACS の実装詳細そのものではない。
  ACS の挙動を確認する手段が無い以上、要望を字義通り満たす設計に進むのが唯一の実行可能な道。
  将来 ACS 実機比較の機会があれば、review/test で追加確認する余地を残す（下記 D2）。

## D2: PageUp/PageDown 以外の AID キーで境界に至る類似ケースは今回のスコープに含めない

- 背景: 本設計の新ルールは AID キー種別を PageUp/PageDown に限定する
  （`design.md`「対象範囲」「振る舞いの詳細」）。SEU 以外のプログラムが別のロールキー
  （例: F7/F8 に割り当てた ROLL 相当）で同様の境界挙動を持つ可能性は実機で確認していない。
- 判断: 今回は PageUp/PageDown のみを対象とする。他のロールキーでの類似不具合が
  実機で確認された場合は、別途 backlog へ追記して次回以降の課題とする。
- 理由: requirements.md のスコープが PageUp/PageDown に限定されており、無関係な
  AID キーにまで一般化すると検証範囲が際限なく広がる（`research.md`「実現性/リスク」）。

## D4: T3 の taskcheck 上限（2ラウンド）到達時点の残存する2件の指摘は、直さず記録に留める

- 背景: T3（`session.ts` の新分岐）の2回目のタスク点検（`maxTaskCheckRounds` の上限）で
  2件の指摘が残った。
  1. （should）`cellsSignature()` はセルの文字・属性バイトのみを比較し、フィールドの
     FFW（保護ビット等）は比較に含まない。理論上、画面の文字・属性が完全一致したまま
     FFW だけが変わる（同じ表示属性のまま保護状態が変わる）という5250上あり得る
     パターンでは、`cursorBeforeWasEnterable` による排他が効かず、`PR#387` 分岐との
     重なりが再発しうる。
  2. （nit）`lastSentAid` から Attn/SysReq を除外した副作用として、PageDown 応答待ち中に
     Attn/SysReq を挟んだ場合、その後に届く**無関係な**レコードに対しても `isPageKey`
     が "PageDown" のまま誤って true 判定されうる（1ラウンド目で直した「取りこぼし」の
     裏返しの誤判定。方向が逆なだけで、根はどちらも AID とレコードの対応付けを
     `lastSentAid` という単純な最新値でしか追えないことに起因する）。
- 判断: どちらも実機トレース（`research.md`）では観測されておらず、`protocol-check.md`
  の方針（上限で止まったら深追いしない・残った疑問を記録して次工程へ委ねる）に従い、
  この work では追加の作り込みをしない。判断は 60 review に委ねる。
- 理由 / 代替案:
  - 1点目を直すには `cellsSignature()` に FFW も含める設計変更が要り、
    「軽量な比較」という design.md の前提を再検討することになる（今回のスコープを超える）。
  - 2点目を直すには AID 送信とその応答レコードを 1:1 で対応付ける仕組み
    （リクエスト ID 相当）が要り、既存の `pendingAid`/`readCommand` の設計全体に
    影響する大きな変更になる。
- 影響: 将来、実機でこれらのパターンが実際に踏まれた場合は、新規の backlog 項目として
  切り出す（この work の再オープンではなく別 work とする）。

## D3: 先頭ページ側の非対称性に、方向別の特別扱いを入れない

- 背景: `research.md` F5 の通り、先頭境界は現状のダミーソースでは問題が再現しなかった
  （ホストが既に正しく維持している）。末尾境界とは非対称。
- 判断: 方向（PageUp/PageDown）ごとに異なる条件を作らず、`design.md` の Rule1/Rule2 を
  両方向に対称に適用する統一ルールとする。
- 理由: 先頭境界で新ルールが（現状すでに正しい動作と）同じ結果を出すことを
  `research.md` F5 の実機データで確認済みであり、方向別の特別扱いを持ち込むと
  条件が複雑化し、将来別のソース内容（先頭境界でも Rule1 相当の中間状態が起きる場合）で
  かえって非対称な不具合を生む恐れがある。対称な単一ルールの方が保守しやすい。
