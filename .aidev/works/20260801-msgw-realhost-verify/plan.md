# 計画: MSGW の実機検証

## subtask 分割の判定

**分割しない**。実装 1 ファイル・テスト 1・スクリプト 1。

## 実装方針

**まず MSGW を作れるようにする**（そこが本題）。作れて初めて
`retrieveMessage` / `answerMessage` が測れる。欠陥が出たらそこで直す。

## 作業順序と依存関係

1. **T1** MSGW を誘発する道を探す（自動構成 → 自作 → 既存装置を借りる）
2. **T2** 実機スクリプトで MSGW を作り、取得と応答を通す（依存: T1）
3. **T3** 見つかった欠陥（本文の CCSID）を直す（依存: T2）
4. **T4** 単体テスト（依存: T3）
5. **T5** 実機で再実行して全項目が通ることを確かめる（依存: T4）
6. **T6** build / lint / test ＋ **実機に残留が無いことの確認**（依存: 全部）

## リスク / 留意点

- **共有の実機を汚さない**。ライターは必ず止め、スプールは消す。
  装置は借りるだけ（作らない・消さない）。**他人の OUTQ・装置には触らない**
- **`finally` で後始末する**。途中で落ちてもライターが残らないように
- **確かめていない経路を巻き込んで直さない**。`decodeNpString` の既定は 37 のまま
- 用紙タイプの上書きは**スプールの名前**（`QPRTLIBL`）に掛ける。
  間違えると MSGW にならず、そのまま印刷されて気づきにくい

## テスト方針

- **実機**: MSGW の誘発 → 状態 → ID・本文・ハンドル → 応答 → 解除 → 印刷到達（8 項目）
- **単体**: CCSID を渡すと日本語が読める / 37 だと化ける /
  **英数字はどちらでも読める**（ID では気づけないことの明示） / 既定は 37
- **残留の確認**: ライター 0 件・OUTQ のスプール 0 件を SQL で確かめる
