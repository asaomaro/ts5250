# 要件: IFS ペインの上限表示・プレビューの競合対策・プレビューの先回り判定

## 背景 / 課題

`.aidev/backlog/hostserver.md` の「IFS ファイルブラウザからの積み残し」から 3 件を消化する。
いずれも `20260720-ifs-file-browser`（PR #117 系）で spec に含みながら実装しなかったもので、
各 work の decisions に見送りの理由が残っている。

### 1. プレビューの競合（`hostserver.md:210` / 03 review S3）

`packages/web-ui/src/composables/usePreview.ts` の `show()` は**発行順を管理していない**。

```
利用者が A.txt を選ぶ → readFile(A) 発行（大きい / 遅い）
すぐ B.txt を選ぶ     → readFile(B) 発行（小さい / 速い）
B が先に返る → state = B
A が後で返る → state = A   ← 選んでいない A が表示される
```

`state.value` を上書きするだけで、**自分が最新の要求か**を見ていない。
IFS は実効 100KB/s なのでファイルサイズ差で順序が入れ替わるのは現実的に起こる。
`error` / `loading` も同じ経路を通るので、古い失敗が新しい成功を潰す形もありうる。

なお同じ work の review で `S2 操作中に別の操作ができる（busy を使っていない）` は解消済みだが、
**S3（プレビューの競合）は残っている**。

### 2. zip 上限「値」が UI に出ない（`hostserver.md:207`）

**サーバーは既に上限値を送っている。使っていないのはクライアント側**である。

| 応答（`host-ifs.ts`） | 送っている値 | `ifsApi.ts` の `messageFor` |
|---|---|---|
| zip `TOO_LARGE`（`:775-790`） | `files` / `bytes` ＋ **`maxFiles` / `maxBytes`** | 実測値だけ表示（「501 ファイル以上 / 20.1 MB 以上」） |
| zip `TOO_MANY_DIRECTORIES`（`:792-803`） | `directories` のみ。**上限を送っていない** | 実測値だけ表示 |
| read `TOO_LARGE`（`:372-400`） | `bytes` ＋ **`maxBytes`** | 実測値だけ表示 |
| 削除 `TOO_MANY` | `entries` ＋ `max` | **`上限 ${b.max} 件` を表示している** |

削除だけが上限を出しており、**同じファイルの中で扱いが不揃い**になっている。
クライアントの `IfsError` 型（`ifsApi.ts:11-27`）には `maxFiles` / `maxBytes` の口が既にある。

利用者から見ると「20.1 MB 以上で大きすぎる」とだけ言われ、**どこまでなら通るのか分からない**。
対象を絞る操作（フォルダを分ける）の当てが付かない。

### 3. プレビューのサイズ上限とヌルバイト判定（`hostserver.md:202` / 03 D11）

`20260720-ifs-file-browser` の spec 193-207 は「プレビューは 5MB 上限」「テキスト判定は拡張子
**＋ヌルバイトが無いこと**」を定めたが、`kindOf()` は**拡張子しか見ておらず**、サイズ判定も無い。
03 D11 が「今回は実装しない」と記録している。

- **サイズ**: `readMaxBytes`（既定 5 MiB）を超えるテキストを開くと、**サーバーが 413 を返すまで待つ**。
  一覧が持っている `entry.size` を `show()` に `sizeHint` として渡しているのに使っていない。
- **ヌルバイト**: 拡張子がテキスト（`.log` 等）で中身がバイナリのファイルを開くと、
  復号できず `content: null`（「文字コード未対応」の案内）に落ちる。壊れた表示にはならないが、
  **原因の案内が実態とずれる**（文字コードの問題ではなく、そもそもテキストではない）。

## 目的 / ゴール

**IFS ペインで「今どれが表示されているか」と「どこまでなら通るか」が利用者に分かる状態にする。**

- 選んだファイルだけが表示される（古い応答に上書きされない）。
- 上限に当たったとき、**超過値だけでなく上限値**が示され、次の一手（対象を絞る）が打てる。
- 明らかに開けないものは**読みに行く前に**断り、理由を正しく述べる。

## 機能要件

### 競合対策

- `show()` / `reload()` は**自分が最新の要求のときだけ** `state` / `error` / `loading` を更新する
- 古い応答は**破棄する**（blob URL を作った場合は解放し、漏らさない）
- 連続して選んだとき、**最後に選んだファイルが表示される**

### 上限値の表示

- zip の `TOO_LARGE` / `TOO_MANY_DIRECTORIES`、read の `TOO_LARGE` で、
  **超過値と上限値の両方**を文言に出す（削除の `TOO_MANY` と同じ書き方に揃える）
- サーバーが上限値を送っていない `TOO_MANY_DIRECTORIES` は、**送るようにする**
- 上限値が欠けている応答でも文言が壊れない（古いサーバーとの組み合わせ）

### プレビューの先回り判定

- 一覧から分かるサイズ（`sizeHint`）が上限を超えるテキスト／PDF／画像は、**読みに行かずに断る**
- 断り方は「大きすぎます（実測 / 上限）。ダウンロードしてください」——**ダウンロード手段は残す**
- 拡張子がテキストでも**中身にヌルバイトがあればバイナリとして扱う**（文字コードの問題と混同しない）

## 非機能要件 / 制約

- **`AGENTS.md` の UI 規約に従う**（配色は CSS 変数経由・生色を書かない、二重スクロールを作らない）
- プレビューに失敗しても**操作は消さない**（既存方針。`usePreview` の `reload` が既に守っている）
- blob URL を漏らさない（解放は「次を表示する直前」と「破棄時」の 2 箇所、という既存の設計を壊さない）
- 型検査・lint・テストが monorepo 全体で従来どおり通る
- ピュアロジック層（core）には触れない

## 未確定事項 / 確認したいこと

autonomous のため、判断は `decisions.md` に根拠つきで記録し、PR をレビュー地点とする。

- **クライアントが `readMaxBytes` を知る手段**。サーバーは 413 の応答にしか上限を載せていないので、
  「読みに行く前に断る」には上限を先に知る必要がある。
  (a) `GET /api/host/ifs/limits` を新設 / (b) 413 から学習してキャッシュ /
  (c) クライアント側に定数を持つ（サーバー設定とずれる）——research で決める
- **ヌルバイト判定をどこで行うか**。復号後のテキストに `U+0000` が混ざるかを見るのか、
  base64 で読んで生バイトを見るのか。前者は 1 往復で済むが、復号に失敗した場合は判定できない
- 上限値の**単位と丸め**（バイトのまま出すか MB に直すか）。既存の `TOO_LARGE` は
  `(b.bytes / 1024 / 1024).toFixed(1)` で MB 表示、削除の `TOO_MANY` は件数をそのまま出している
