## 実機で分かったこと（検査の期待値を直した）

**応答つきのメッセージは対で消える。** `REPLY` を消すと組の `SENDER` も一緒に消える
（IBM i の仕様）。最初「1 件だけ減る」と書いて落ちたので、
**通知（1 件だけ減る）と応答つき（2 件減る）を分けて**固定した。

## `QSYSOPR` に対する実操作（2026-08-04 に追加）— 26/26

**共有の本番資源なので、自分が作ったメッセージだけを触った。**
送る → 応答する → **自分の分だけキー指定で消す**に限定し、**全消しは一切していない**。

```
OK  **QSYSOPR を読める**（共有の待ち行列） — 365 件
OK  **QSYSOPR へ送れる** ／ **QSYSOPR へ照会を送れる**
OK  **送ったものが一覧に出る** — 3 件（自分の分だけ）
OK  **QSYSOPR の照会に応答できる**（利用者 USER）
OK  **自分が作った分を消し切った** — 2 件消した / 残り 0
OK  **他人のメッセージが減っていない** — 365 → 365
```

**一般利用者（`USER`）でも `QSYSOPR` の照会に応答できた。** 権限次第で断られる環境も
ありうるので、検査は**断られた場合もその理由を記録する**形にしてある。

「3 件作って 2 回の削除で消し切った」のは、**応答つきが対で消える**挙動どおり。

### 検証の作り方

**他人のものに触れないことを検査で担保した**——開始時のキー集合を控え、
`fromUser` が自分のものだけを対象にし、最後に**他人の件数が変わっていないこと**を確かめる。
共有資源を触る検証は、これを書かないと安心して回せない。
