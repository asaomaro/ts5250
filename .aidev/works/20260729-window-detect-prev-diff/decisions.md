# 決定記録

## D1: 表示設定（SO/SI マーク・表示コード）は watch しない

- 背景: `decoWindow` は元は computed で、`displayChar` 経由で `showShiftMarks` / `sbcsView` に
  反応していた。判定を watch へ移すにあたり、これらも watch 対象に含める案を spec に書いた。
- **実装中に見つけた不具合**: 含めると設定変更時にコールバックが走り、そのとき
  `prev === snap`（同じ snapshot オブジェクト）になる。素直に前画面として渡すと
  **画面を自分自身と比較**することになり、枠外は当然無変化なので裏取りが素通りして
  **③ が窓に化ける**。
- 決定: **`props.snapshot` だけを watch する。** 表示設定は次の画面更新から反映される。
- 理由 / 代替案:
  - 窓かどうかは画面の中身で決まり、SO/SI マークの表示切替で窓であることは変わらない。
  - 「設定変更時は前画面なしで引き直す」案も検討したが、それは ③ を弾いている唯一の材料
    （前画面との差分）を捨てることなので不可。
  - 「設定変更時は前回の結論を保つ」なら安全だが、それは watch に含めない場合と同じ結果で、
    余分な分岐が増えるだけ。
- 影響: 表示設定を切り替えた直後、次の画面更新までウィンドウ装飾の矩形が更新されない。
  罫線文字（`.` `:` 等）は SO/SI や表示コードの影響をほぼ受けないので実害は小さい。

## D2: 先行作業の `WriteExtent` 経路（反転の裏取り）はそのまま残す

- 背景: 前画面差分は Attn の窓も正しく通すので、`isOverlayWrite` による反転経路の裏取りは
  重複しているとも言える。
- 決定: **残す。**
- 理由: 二つの材料は独立で、どちらも実測で裏付いている。前画面が無い状況
  （接続直後・`prev` を渡さない呼び出し）では `isOverlayWrite` だけが効く。
  片方を消す積極的な理由が無い。
- 影響: なし。

## D3: 先行作業と同じブランチ・同じ PR に載せる

- 背景: `protocol.md` は「1 works = 1 作業ブランチ = 1 PR」を原則としている。
- 決定: `20260729-window-detect-write-bounds` と同じ `feat/window-detect-write-bounds` /
  PR #206 に載せる（利用者の指示「このまま進めて」）。
- 理由: 同じ `detectWindowRect` を触るため別ブランチにすると確実に衝突する。
  また backlog の同一項目（③④ の誤検出）を完結させる変更で、レビュー単位としても一体。
- 影響: 原則からの逸脱。works フォルダは 2 つ、PR は 1 つになる。

## D4: 前画面差分は「表示設定」ではなく「画面モデル」で比べる

- 背景: 利用者から「浮き出し表示設定なのに `WRKMBRPDM` のヘルプ窓が窓に見えない」と報告
  （別の画面では出ている）。
- **調査の経過（2 回外した）**:
  1. 最初に `WRKOBJPDM` の fixture で測って「検出できている＝設定が none だから」と答えたが、
     **画面を取り違えていた**（出ないのはメンバー一覧 `WRKMBRPDM` の方）
  2. 次に「判定を computed から watch へ移したので、スナップショットが同一オブジェクトのまま
     更新されると発火しない」と見当を付けたが、`sessions.ts:200` は毎回**新しいオブジェクトを
     代入**しており外れ
- **原因**: 実機画面は **SO/SI マーク表示が ON** で、`detectWindowRect` に渡る `charOf` が
  SO/SI セルを `{` `}` として返す。窓の枠が背景の DBCS を分断すると SO/SI の片割れが残り、
  それが**「新しい内容が現れた」と数えられて** `introducedOutside` が窓を弾いていた。
  D2 で入れた「`文字→空白` は無視」の除外を、マーク表示がすり抜けていた。
  - 実測: 既定 charOf → 検出 / マーク表示 charOf → **null**（実機 fixture 2 つとも再現）
- 決定: `introducedOutside` に**表示用 `charOf` を渡さない**（既定＝画面モデルで比較する）。
- 理由: この差分が答えるべきは「**ホストがそこへ新しい内容を置いたか**」であって、
  こちらの表示設定は関係ない。表示の都合を混ぜたのが誤りだった。
- 影響: 実機 `WRKMBRPDM` のヘルプを fixture 化し（`win-wrkmbrpdm-f1`）、
  「表示設定を変えても窓を落とさない」を回帰テストに固定した。


## D5: 大きい窓から小さい窓へ戻る遷移は制限事項として受け入れる

- 背景: 利用者報告——ヘルプ窓 → `F2` 拡張ヘルプ（より大きい窓）→ 元のヘルプ窓、と戻ると
  窓判定が外れる。
- 決定: **直さない。制限事項として文書化し、テストで固定する**（利用者判断）。
- 理由: この判定は「窓は背景の上に開く＝**枠の外は前の画面のまま**」という前提に立っている。
  窓が縮むと、大きい窓が占めていた領域が背景で描き直され、それが小さい窓の枠外に当たる。
  **通常画面への遷移とまったく同じ形**になるので、前画面 1 枚では原理的に区別できない。
  直すには窓の履歴（スタック）を持つ必要があり、費用に見合わない。
- 影響:
  - `introducedOutside` の JSDoc に理由つきで明記
  - `window-prev-diff.test.ts` に「既知の制限」節を置き、**現在の挙動を固定**した
    （誰かが挙動を変えたら落ちて気づける）。併せて「広がる方向は判定できる」も対で置いた
  - backlog の `window-detect.md` に制限事項として記載。将来やるなら
    `WriteExtent.restored`（RESTORE SCREEN）を「1 つ前の窓へ戻った」合図に使える可能性がある、
    という手掛かりも残した（未検証）


## D6: RESTORE SCREEN を合図に使う案は実機で否定された

- 背景: D5 で「将来やるなら `WriteExtent.restored` を『1 つ前の窓へ戻った』合図に使える
  可能性がある（未検証）」と手掛かりを残した。利用者から「実機で検証し使えるなら対応して」と指示。
- **実測**（実機・IBM i 7.5 / `WRKMBRPDM` → `F1` → `F2` 拡張ヘルプ → `F12` で戻る）:

  | 段 | cleared | restored | rect | cells |
  |---|---|---|---|---|
  | 1) 一覧 | true | false | 全画面 | 3053 |
  | 2) ヘルプ窓 A | true | false | 全画面 | 1702 |
  | 3) 拡張ヘルプ B | true | false | 全画面 | 1921 |
  | 4) **戻る** | true | **false** | 全画面 | 1702 |

- 決定: **使えない。制限事項のまま据え置く。**
- 理由: **4 段すべて `restored=false`**。ホストは毎回クリアしてから全画面を描き直しており、
  この遷移で RESTORE SCREEN は送られてこない。合図が存在しない以上、実装しようがない。
  （窓を閉じるときの RESTORE は別の場面では観測済み——Attn の窓を F12 で閉じたときは
  `restored=true` だった。**ヘルプの階層移動は別の作り**、という事実が分かった）
- 影響:
  - 実機の遷移を fixture 化（`win-help-shrink-back`）し、合成データだった制限テストを
    **実機データに差し替えた**。「判定が外れる」と「`restored` が false」の両方を固定
  - backlog の手掛かりを**「却下: 実機で否定済み。再検討しないこと」**へ書き換えた
