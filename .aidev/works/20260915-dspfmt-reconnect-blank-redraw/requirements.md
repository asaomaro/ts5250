# 要件: DSPFMT 等、複数レコードに分かれた応答で初回表示が罫線のみになる不具合の修正

紐づく charter ゴール: なし（`.aidev/charter.md` 未整備のプロジェクトのため対象外）。

## 背景 / 課題

利用者から「DSPFMT FILE(ASAOLIB/COMPLIST) OUTPUT(*) を実行すると、初回表示が罫線のみになり、
その後 Enter を1回押下すると正常に表示される」という不具合報告（20260915、スクリーンショット添付）
を受けた。追加のヒアリングで次の情報を得た:

- ほとんどの場合に再現するが、まれに正常なこともある（タイミング依存）。
- 一瞬罫線以外の内容が見えてから消えることもある（＝一度正しく描画された後に、何かが
  上書きして消している）。
- 再接続や寸断への対応の後に発生している可能性がある、との申告。

`.aidev/backlog/acs-parity.md` の既存項目（`20260914-dspfmt-field-underline-instability`）で
同じ症状の再現・原因特定を試みたが、その work では実機トレース（WRKOBJPDM の Opt 欄 + F1ヘルプ窓
開閉 + PageDown）で再現できず、代わりに見つかった別の確実な欠陥（WEA オーダー未実装）を修正して
終えていた。本 work は、利用者から得られた新しい具体的な再現手順（`DSPFMT FILE(ASAOLIB/COMPLIST)
OUTPUT(*)` を直接コマンド入力）を使って再挑戦する。

## 予備調査で判明した事実（本 work 開始前、requirements 起票時点で確認済み）

- DSPFMT の応答は3つの5250レコードに分かれて届く。1つ目・2つ目は
  `unlockKeyboard=true, readRequested=false`（キーボード解放はするが Read 要求を伴わない
  Write to Display）で、3つ目だけが `readRequested=true`（実際の Read コマンドを伴う、
  本当のデータと最終カーソル位置を含む）。この事実は
  `.aidev/works/20260915-dspfmt-reconnect-blank-redraw/research.md` に再現手順ごと記録する。
- `packages/tn5250/src/session/session.ts` の `handleRecord()` は、**`unlockKeyboard`
  （どのレコードにも独立に立ちうる WCC のビット）が立った時点で `pendingAid`（`sendAid()` が
  返す Promise）を解決してしまう**。DSPFMT のように「キーボードだけ先に解放し、続けて複数の
  Write to Display でデータを埋めていく」ホストプログラムでは、**1つ目のレコード（罫線の骨格
  だけ）の時点で解決してしまう**。
- **この欠陥はコア層（`packages/tn5250`）単体、web-ui/server 層を一切経由しない状態で、
  100%決定的に再現する**（`session.sendAid("Enter")` が返す Promise の解決値を直接調べる
  診断で8回中8回、罫線のみの画面を観測。同じ瞬間の `session.snapshot()`——ライブのバッファ
  状態を都度読む API——は8回とも正常）。**「コア層では再現しない」という当初の見立ては
  誤りだった**——最初に作った診断（`scripts/diag-dspfmt-reconnect-blank.mjs`）は
  `session.snapshot()` をポーリングするだけで `sendAid()` の解決値そのものを見ておらず、
  3レコードが届き終わった後の正しいライブ状態しか観測できていなかった（本
  work 内の doccheck ラウンド1指摘で発覚・訂正。詳細は research.md F1/F1'）。
- **利用者に見える最終表示（ブラウザの画面）としてこの欠陥が現れるかどうかは、上記の
  コア層の欠陥とは別の、タイミング依存の要因が絡む**: `packages/server`（ws-handler）を
  実サーバーとして起動し、ブラウザと同じ `/ws` プロトコルで接続する診断
  （`scripts/diag-dspfmt-ws-e2e.mjs`）では、8回中5回、罫線のみの状態が最終的にブラウザ側へ
  届くメッセージ列の中に現れた（残り3回は正常）。ブラウザ側
  （`session-controller.ts` の `applyDisplayMessage`）は `"screen"` と `"key-done"` の
  どちらも無条件に `sessionsStore.updateScreen()` で上書きするため、**後から届いたほうが
  常に勝つ**。3つのレコードそれぞれが発火する `"screen"` イベントは同期送信されるのに対し、
  `"key-done"`（コア層の欠陥により常に古い画面を運ぶ）は Promise の解決を経て非同期
  （マイクロタスク）で送信されるため、TCPセグメントの分かれ方次第で `"key-done"` が
  正しい `"screen"` より後に届くことがある。**これが「ほとんど再現するが、まれに正常」
  「一瞬正しく見えてから消える」という利用者申告のタイミング依存の症状と一致する**
  （詳細は research.md F2, F7）。
- **利用者申告「再接続や寸断への対応の後に発生している可能性がある」について**:
  `packages/tn5250` のコアには reconnect ロジックが存在しない（再接続の概念があるのは
  ブラウザ↔ローカルサーバー間の `packages/web-ui/src/session-link.ts` だけ）。上記の通り
  コア層の欠陥はフレッシュな接続でも100%決定的に発生するため、**この仮説（再接続が原因）は
  反証されたと判断する**——再接続ロジックのバグではなく、再接続を誘発するような不安定な
  ネットワーク状況が、上記のタイミング競合（TCPセグメント分割）にも影響し、たまたま
  「罫線のみ」側に倒れやすかった、という相関が最も単純な説明である（research.md F9）。
- **単一レコードで完結する応答（大多数のケース）への影響は無い**: Read コマンドは常に
  `readRequested` と `unlockKeyboard` を**同じレコードの同じ処理内で同時に**立てる
  （`packages/tn5250/src/protocol/wtd-applier.ts:253-263`）。応答が1レコードで完結する
  場合、どちらを見ても同一レコードの同一呼び出しで真になり、解決タイミングは変わらない
  （research.md F3）。

## 目的 / ゴール

ホストの応答が複数の5250レコードに分かれて届き、かつ先行するレコードが「Read 要求を伴わない
キーボード解放」だけを行う場合でも、利用者に最終的に表示される画面が常に**最後まで処理された
正しい内容**になっている状態を達成する（`key-done` が運ぶ画面が、後続の `"screen"` イベントに
よって上書きされる／取り違えられることがない状態）。

## ユーザーストーリー

- US1: 利用者として、DSPFMT のような複数レコード応答を返すホストプログラムを実行したとき、
  最初から正しい内容（罫線だけでなく見出し・データも含む）が表示されてほしい。なぜなら、
  現状は罫線だけの画面が表示され、何が起きたのか分からず、Enter を押すという追加操作を
  強いられているため。（受け入れ: AC1, AC2）
- US2: 開発者として、`sendAid()` が返す Promise（および `key-done` メッセージ）が運ぶ画面が、
  ホストの応答が完全に処理された後の内容であると信頼できる状態にしたい。なぜなら、現状は
  「キーボード解放」と「ホストが本当に応答を完結させたこと（Read 要求）」を同一視しており、
  複数レコードに分かれる応答全般で同種の取り違えが起きうるため（DSPFMTだけの局所修正では
  再発を防げない）。（受け入れ: AC3, AC4, AC5）

## スコープ

### 対象

- `packages/tn5250/src/session/session.ts` の `handleRecord()`（`pendingAid` の解決条件）。
- 上記変更に伴う `sendAid()`／`onceReady` 等、関連ロジックの整合性確認（`design.md` で判断）。
- 回帰テスト（複数レコードに分かれた応答を合成して `sendAid()` の解決内容を検証する単体テスト）。

### 対象外

- `packages/server`／`packages/web-ui` 側の変更（原因はコア層の `pendingAid` 解決条件にあり、
  そちらを直せば web-ui 側の無条件上書きロジック自体は変更不要と見込む——ただし design で
  再確認する）。
- DSPFMT というコマンド自体の実装・ホスト側プログラムの是非（当プロジェクトの管轄外）。
- `20260914-dspfmt-field-underline-instability` で見送った自己点検欄・色符号化の調査
  （別テーマであり、本 work の対象外）。

## 機能要件

- `sendAid()` が返す Promise（および、それを使う `key-done` メッセージ）が運ぶ画面は、ホストの
  応答（1つのAIDキー送信に対する一連のレコード群）のうち、**実際に Read が要求された時点**
  （＝ホストが「これ以上書かない、入力を待つ」と表明した時点）の内容を反映する。
- キーボード解放（`unlockKeyboard`）だけが立ち、Read 要求（`readRequested`）を伴わないレコード
  では `pendingAid` を解決しない。
- 上記変更後も、単一レコードで完結する（従来の大多数の）応答では現状と同じタイミングで
  解決される（回帰が無い）。

## 非機能要件 / 制約

- **推測のみでの修正をしない**: 実機トレースで実際の DSPFMT のレコード列・各レコードの
  `unlockKeyboard`/`readRequested` の値を確認済みの上で設計する。
- **確認できていないことを確認済みと書かない**: web-ui（Vue コンポーネント・ブラウザでの
  実際の描画）は本 work のコア層の修正で解消される見込みだが、**実際のブラウザでの目視確認は
  この開発環境では出来ない**（`packages/server`+WSプロトコルでの diag スクリプトでの再現・
  非再現の確認に留める）。

## 未確定事項 / 確認したいこと

- `readRequested` を伴わない `unlockKeyboard` のレコードの後、**最終的に `readRequested` が
  一度も来ないまま**セッションが別の状態（切断等）に至った場合に `pendingAid` が永久に
  解決されない（ハングする）リスクがあるかどうかは、design で検討する。
- `this.state = "ready"`／`onceReady` の遷移タイミングも同じ理由（`unlockKeyboard` 単独での
  早すぎる遷移）で影響を受けうるかは、design で判断する（本 work のスコープに含めるかどうかも
  含めて）。
