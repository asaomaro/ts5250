# 要件: HLLAPI / EHLLAPI 対応（Rust の薄い接続層 ＋ TypeScript のロジック）

autonomous 実行。**起動時に与えられた指示を requirement とする**（protocol「10.」）。

> 「HLLAPI と EHLLAPI への対応を進める。**Rust で薄い接続層**を作り、**ロジックは TypeScript** による
> 実装を想定している。」

## 背景 / 課題

ts5250 は 5250 セッションを操作する入口を 3 つ持っている——**画面**（web-ui）、**MCP**
（`open_session` / `send_key` / `get_screen` / `set_fields` …）、**WebSocket**。
いずれも「このアプリのために書かれた」入口で、**既存の資産からは呼べない**。

IBM i の現場には **HLLAPI / EHLLAPI で書かれた自動化資産**が大量にある。
これは 3270/5250 エミュレーターを外部プログラムから駆動する業界標準の API で、
IBM Personal Communications や ACS が提供してきた。VB / C / C# / Excel VBA / RPG(PC 側) などから、
`hllapi(func, data, length, rc)` という**単一の入口**に数値の機能コードを渡して
「画面を掴む」「キーを送る」「画面を読む」「ホスト待ち」を行う。

**この API を話せれば、既存の自動化資産をエミュレーターごと載せ替えられる。**
逆に話せない限り、ts5250 に移るには自動化を全部書き直すことになる。

## 目的 / ゴール

**既存の HLLAPI / EHLLAPI プログラムが、書き換えずに ts5250 のセッションを駆動できる**状態にする。

## スコープ

### 対象

1. **HLLAPI / EHLLAPI の入口を提供する**——標準の呼び出し規約（C ABI・単一エントリ＋機能コード）で
   受け、ts5250 のセッションへ橋渡しする。
2. **接続層は Rust で薄く作る**。ネイティブの呼び出し規約・引数のバイト列・文字コードの
   出し入れだけを担い、**セッションの状態も画面の解釈も持たない**。
3. **ロジックは TypeScript**（既存の `packages/server` / `packages/tn5250`）に置く。
   機能コードごとの意味づけ・画面の走査・キーの解釈は既存実装を使う。
4. **中核の機能コードを実装する**（何を入れるかは research で確定する。最低限、接続・切断・
   キー送信・画面読み出し・文字列書き込み・検索・ホスト待ち・セッション一覧）。
5. **未対応の機能コードは、そうと分かる戻り値で断る**（黙って成功を返さない）。
6. **動く証拠を残す**——実際の HLLAPI 呼び出し規約でこちらのライブラリを叩き、
   実機のセッションが動くところまで確かめる。

### 対象外

- **HLLAPI の全機能コードの網羅**（40 種以上ある）。中核から始め、残りは follow-up。
- **ファイル転送（Send File / Receive File。機能 90 / 91）**。別プロトコルで、単独で大きい。
- **3270 の対応**。ts5250 は 5250 のエミュレーターで、3270 のセッションは持たない。
- **既存の入口（MCP / WebSocket / 画面）の仕様変更**。HLLAPI は**追加の入口**。
- **HLLAPI 経由でのプリンターセッション操作**（表示セッションに閉じる）。

## 機能要件

- **FR-1** 標準の HLLAPI エントリポイントを公開し、機能コードで分岐する。
- **FR-2** セッションへの接続・切断ができる（Connect / Disconnect Presentation Space）。
- **FR-3** キーを送れる（Send Key。機能キー・AID キーを含む）。
- **FR-4** 画面を読める（Presentation Space の全体および指定位置からの読み出し）。
- **FR-5** 文字列を書き込める（Presentation Space / 入力欄への設定）。
- **FR-6** 画面内を検索できる（Search Presentation Space）。
- **FR-7** ホストの応答を待てる（Wait）。
- **FR-8** セッションの一覧・状態を問い合わせできる。
- **FR-9** **未実装の機能コードは、規約上の「未対応」を示す戻り値で返す**。
- **FR-10** 戻り値（`rc`）は HLLAPI の規約に従う（成功 0、種類ごとの誤り番号）。
- **FR-11** **Rust 側に状態を持たない**。セッションの同一性・寿命は TypeScript 側が持つ。

## 非機能要件 / 制約

- **文字コード**: HLLAPI の伝統的な入口は**バイト列**でやり取りする。日本語（DBCS）を含む画面を
  どう渡すかを決める必要がある（既存の CCSID 処理は TypeScript 側にある）。
- **プラットフォーム**: HLLAPI の実利用者は**ほぼ Windows**（`EHLLAPI32.DLL` 等を動的リンクする）。
  開発環境は WSL2 の Linux で、配布は Electron（Windows/Linux）。**どこで動く形にするかを
  research で確定する**。
- **依存を足さない規律**（AGENTS.md「パッケージ分割と入口」）。Rust 側も同様に、
  必要最小限のクレートに留める。
- **既存の非退行**: MCP / WebSocket / 画面の挙動を変えない。
- **秘密の扱い**: HLLAPI は資格情報を扱いうる（サインオン画面への入力）。ログに値を出さない。
- **ログは stderr のみ**（`console.*` は lint で禁止）。

## 完了条件 (受け入れ基準)

- [ ] HLLAPI の呼び出し規約で中核の機能コードが動く（接続 → キー送信 → 画面読み出し → 切断）
- [ ] **実際の HLLAPI クライアント側の呼び出し方**（C ABI での動的リンク）で叩いて動く
- [ ] **実機のセッション**に対して一連の操作が通る
- [ ] 未実装の機能コードが**規約どおりの戻り値**で断られる（黙って成功しない）
- [ ] 日本語（DBCS）を含む画面の読み書きが壊れない
- [ ] Rust 側がセッションの状態を持っていない（TypeScript 側が単一の真実）
- [ ] 既存の MCP / WebSocket / 画面が退行していない
- [ ] ビルド・lint・全テストが通る

## 未確定事項 / 確認したいこと

**research で潰すもの**

- **HLLAPI / EHLLAPI の正確な仕様**——エントリポイントの名前と署名、機能コードの割り当て、
  戻り値の規約、`data` バッファの形式。**一次情報に当たる**（推測で API を作ると資産が動かない）。
- **どの機能コードを中核とするか**（既存資産が実際に使うもの）。
- **Rust ↔ TypeScript の橋渡し方法**。候補: ローカル HTTP / WebSocket（既存サーバーに乗る）、
  Unix ドメインソケット / 名前付きパイプ、stdio。**同期呼び出しである HLLAPI を、
  非同期のサーバーへどう写すか**が要点。
- **プラットフォーム**——Windows DLL が本命だが、この環境（WSL2 Linux）でどこまで検証できるか。
  クロスコンパイルの要否。
- **Rust ツールチェーンがこの環境に無い**（`cargo` 未導入）。導入の要否と方法。
- **文字コードの受け渡し**（バイト列と CCSID／UTF-8 の境界をどこに置くか）。
- **セッションの同定**——HLLAPI は「短縮名」（`A`〜`Z` の 1 文字）でセッションを指す。
  ts5250 のセッション ID とどう対応付けるか。
