| 指示 | 実現 |

### 層をまたぐ確認

| 観点 | 結果 |
|---|---|
| 依存の向き | `crates/hllapi → HTTP → packages/server → SessionManager`。逆流なし |
| **外部依存を足していない** | Rust は `std` のみ。TypeScript も新規パッケージなし（CP932 表は `TextDecoder` から組む） |
| 既存の認可を迂回していない | **`assertWritable` / `assertKeyAllowed` を通す**（01 の must で塞いだ）。<br>読み取り専用セッションへ HLLAPI から書けない |
| 秘密の扱い | バッファの中身をログに出さない。**サインオン画面への入力が通る経路**なので必須 |
| 上限 | `data` 8KB、Wait / Pause 30 秒、HTTP 45 秒。**無限に待たない** |
| 一次資料に基づく | 機能番号・戻り値・ニーモニックの出所（SunLink EHLLAPI Programmer's Manual）を明記 |
| **推測で番号を置かない** | `Start Host Notification` は目次に誤植があり確定できないので**入れていない** |
| 既存の非退行 | ルート登録 1 行のみ。3,846 件緑 |
| この環境固有の回避策 | **リポジトリに焼き込んでいない**（`.cargo/config.toml` を置かず環境変数で渡す） |

### 設計判断の妥当性（振り返り）

- **1 呼び出し = HTTP 1 往復**——同期 API を非同期サーバーへ写す最も単純な形。
  Rust に相関も接続プールも要らず、「状態を持たない」を構造で担保できた。
  実機で**別プロセスから叩き直せる**ことも確認した。
- **CP932 を選んだのは正しかった。** UTF-8 のままだと日本語画面が 1920 バイトの器に収まらず、
  既存資産の前提を壊していた。実機で `バイト=1920 セル=1920` を確認。
- **PS をバイト配列で扱う**のは、CP932 を選んだ結果として必然だった。
  文字列で持っていたときに `サイン・オン` が `サ イ ン ・ オ ン` になり、
  **日本語で検索できない**という致命的な欠陥が出ていた（02 の must）。

### 残る弱点（`test-result.md` にも記載）

- **Windows でビルドも動作確認もしていない。** 実利用者はほぼ Windows なので、
  **これが最大の未検証点**。クレートは OS 非依存に書いてあるが動作は主張しない。
- **実際の HLLAPI 資産で試していない**（手元に無い）。
- 未実装が 15 機能ある（`rc=10` で断る）。
- 画面を書き換えるローカル操作（Erase EOF 等）はカーソルを動かすだけ。

いずれも「できた」と書いていないので**この作業としては通過**とし、follow-up に送る。

### 判定

**通過。** subtask で must 3 件・should 2 件を潰し、統合 test で `Send Key` の疑いも
実機で切り分けた（製品側の欠陥ではなく検証側のキー選択の誤り）。

## ラウンド 2（2026-08-03・差し戻し後）

deliver 済みだったものを **coding へ差し戻した**。理由は 3 つとも利用者との対話で出たもの。

| | 指摘 | 対応 |
|---|---|---|
| C | **同じセッションに 2 人が書ける**（`Reserve`/`Release` 未実装） | 実装 |
| — | **どのシステムのどのセッションかを指定できない** | `Connect` を拡張 |
| — | DLL → ブラウザまでの E2E が無い／VBA から使えない | Playwright E2E ＋ `.bas` ＋ 生成スクリプト |

### 予約（`Reserve`/`Release`）の置き場所

**`SessionManager.assertWritable` / `assertKeyAllowed` の内側に置いた**のが要点。
書き込みの経路は WebSocket・MCP・HLLAPI の 3 つあり、経路ごとに検査を書くと足し忘れる。
`readOnly` ゲートと同じ場所に同居させたので、**新しい経路が増えても自動で効く**。
`ws-handler` には予約を見るコードが 1 行も無い——それでも締め出しは効き、
`ws-handler.test.ts` が経路側から確かめている。

期限（2 分）を置いたのは、**接続層が状態を持たない＝落ちた自動化は `Release` を送れない**から。
それでも詰まるときのために `forceRelease`（画面の「解除して操作する」）を用意した。
**TTL の値を勘で詰めるより、人が取り戻せるほうが確実**という判断。

### セッション指定

標準の `Connect` は短縮名 1 文字なので**開いた順**でしか指せない。
自動化にとってこれは危うい——順番が変われば別のシステムの本番画面を操作しうる。
`"A <指定>"` を足し、**当たらなければ繋がない**（`rc=1`）・**曖昧なら断る**（`rc=11`）ようにした。
`"A"` だけなら従来どおりなので、既存資産は影響を受けない。

安定した名前を出すために `SessionEntry.target` を足した（どの設定から開いたか）。
実行中の id は起動のたびに変わるので、それだけでは自動化が書けない。

### 呼び出し規約の誤り（この差し戻しで一番効いた発見）

エクスポートが `extern "C"`（cdecl）だった。**WinHLLAPI と VBA の `Declare` は `stdcall`** なので、
32bit Office から呼ぶとスタックが壊れる。`extern "system"` に変えた
——32bit Windows で `stdcall`、他は `C`。

**VBA サンプルを書こうとして初めて気づいた。** ドキュメントに「Windows 未検証」と
書いてあっても、具体的な呼び出し側を書くまで見えない類の欠陥だった。

### 薄さは保たれているか

**保たれている。** `hllapi-bridge-thinness.test.ts` は無改変で通る。
機能を 2 つ足し、`Connect` の意味を拡張したが、**Rust は 1 行も変えていない**
（呼び出し規約の宣言を除く）。これが「薄い層」の狙いそのもの。

### 残る弱点

- **Windows でビルドも動作確認もしていない。** 規約は直したが**直したことを確かめていない**
- **VBA の `Declare` を通した動作は未検証**。`.bas` は書いたが動かしていない
- **`.xlsm` を生成していない**（Linux 側では VBA プロジェクトを組めないため、
  Windows 上の Excel に作らせるスクリプトを用意した。それも未実行）

いずれも「できた」と書いていない。

### 判定

**通過。** 指摘 3 件すべてに対応し、実機 33/33・E2E 14/14・自動テスト 3,883 件緑。
