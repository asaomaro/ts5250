# 計画: SAVE PARTIAL SCREEN に応答し、QSH を通す

## 実装方針

実装は research の途中で最小限を入れて実機で確かめた（それが唯一の判定手段だった）。
ここからは**テストで固定し、未実測の部分を明示し、回帰手段を残す**。

## 作業順序と依存関係

1. 定数・分岐・応答・`roll`（実装済み。研究で実機確認）
2. 単体テスト（応答の形・後続が生き残ること・ROLL の境界）（依存: 1）
3. 実ブラウザ＋実機の回帰スクリプト（画面を撮る）（依存: 2）
4. 空振り検証（依存: 3）
5. 文書（PROTOCOL.md・backlog・decisions）（依存: 4）

## リスク / 留意点

- **`0x13` / `0x23` は未実測**。docstring と backlog で区別する
- ROLL でフィールドを動かさない（動かすと入力欄がずれる）
- 直列化の共有（`writeScreenAsWtd`）で SAVE SCREEN の既存挙動を変えない
- 退避スタックを `0x02`/`0x12` と共用している点は仕様として明記

## テスト方針

- `applyDataStream`: `0x03` でパラメータを消費し、**同じレコードの後続 WTD/READ が生きる**
- 応答レコード: opcode・先頭 2 バイト・写した 5 バイト・後続が WTD であること
- `0x13`: 退避から戻る／空なら警告
- `roll`: 上へ・下へ・境界（0 行・範囲外・範囲超え）・フィールドを動かさない
- 実機: `verify-browser-qsh.mjs`（起動・コマンド実行・出力・スクリーンショット）

## 空振り検証（mutation）

- `0x03` を default に戻す（QSH が固まる＝後続が消える）
- 応答を送らない
- パラメータを消費しない（後続がずれる）
- 応答の先頭を `0x12` にする（保管物の識別が変わる。実機で確認できないので**空振り想定**）
- ROLL の方向ビットを反転／行数のマスクを外す
- ROLL でフィールドも動かす
