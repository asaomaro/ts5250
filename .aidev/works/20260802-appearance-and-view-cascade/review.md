# レビュー: 「外観」と「表示」／表示設定の 2 段カスケード

## ラウンド 1

### 見た観点

要件適合 / 正確性 / 規約適合 / 保守性。差分は 13 ファイル（うち新規 3）。

### 確認したこと

- **利用者の判断がそのまま入っているか**: `表示`／`外観` の名前、全項目カスケード、
  タブ名トグル（既定 ON・2 システム以上のときだけ）、テーマはペインの中のみ、
  スキンのセッション個別は無し——すべて反映。
- **移行で見え方が変わらないか**——今回いちばん壊しやすいところ。
  CSS の選択子から `:root` を外すので**特定度が下がる**。**変更前のビルドで基準値を実測**し、
  変更後と突き合わせた（`rgb(247, 248, 244)` で一致）。jsdom では見えない検査。
- **テーマがペインの外へ漏れないか**: 画面は変わり、**タブ帯とヘッダーは動かない**ことを
  実測。タブ帯は `.tabs`（透過で測れない）ではなく `.tab`（`var(--crt)`）で測っている。
- **従来の使い勝手を黙って変えていないか**: メニューの初期の層を `全体の既定` にした。
  ここを `このセッション` にすると、「開いて変えたら全画面に効く」という従来の挙動が
  無言で変わる（既存テスト 6 件が落ちて気づいた）。
- **`set()` の意味を変えていないか**: キー設定からの順送り（`cycle`）は**全体の既定**へ。
  セッション上書き側へ流すと、キー 1 つで挙動が分岐して分かりにくくなる。テストで固定。
- **上書きが増え続けないか**: セッションを閉じたら捨てる（`closeSession`）。
- **箱の分け方**: タブ名トグルは `viewSettings` ではなく新しい `appearance` に置いた。
  あちらはペインの中の見え方（しかも 2 段）で、こちらはクローム。同じ箱に入れると
  「この項目はセッションごとに変えられるのか」が箱から判断できなくなる。
- **秘密の混入**: ステージ済み差分をパスワード・内部 IP で機械走査（陽性対照つき）。0 件。

### 指摘

**must**: なし
**should**: なし

**nit（対応済み）**:
- メニューの初期の層が `このセッション` だった → `全体の既定` へ（従来の使い勝手を保つ）。
- 検証スクリプトで実効テーマと同じ側を選んでいて色が動かず、**検査になっていなかった** →
  逆側を選ぶようにした。
- `hasText` がテンプレート由来の改行で当たらなかった → ページの中で探して押す形へ。

### 残した制限（PR 本文にも書く）

- **スプールの `表示`** は対象外（利用者の明示）。項目一覧は差し替えられる形にしてある。
- **スキンのセッション個別は無し**（利用者の判断）。Web アプリ風スキンを当てた状態で
  セッションのテーマを個別指定すると、そのペインだけ端末パレットが表示モード側の値になる。
- 上書きは保存しない（セッション ID は接続のたびに変わるため）。

## 判定

指摘なし（nit のみ・対応済み）→ deliver へ。
差分は複数レイヤに跨るが、構造の芯は「2 段のカスケード」1 点。判断は spec に集約済みなので
walkthrough は挟まない。
