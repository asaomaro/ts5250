# 計画: ペインの実体を 1 か所に置き、置き場所だけを動かす

## 実装方針

先に「一度開いた」の記録を共有へ出し、次に実体をプールへ移し、最後に最大化の描き方を替える。
逆順だと、実体がグループにある状態で最大化の描き替えをすることになり、
「最大化で消える」不具合を残したまま検証することになる。

## 作業順序と依存関係

1. `composables/openedPanes.ts` — 「一度でも開いたアプリ系タブ」の共有記録（依存: なし）
2. `stores/workspace.ts` — `groupOf(tab)` を足し、`displayRoot()` を消す（依存: なし）
3. `components/PanePool.vue` — 実体＋Teleport（依存: 1, 2）
4. `WorkspaceNode.vue` — 受け皿だけを描く（依存: 3）
5. `WorkspaceNode.vue` — 分割段で最大化を表現（依存: 4）
6. `App.vue` — `root` を描き、`<PanePool>` を置く（依存: 3, 5）
7. テスト更新・追加（依存: 1-6）
8. build / lint / web-ui スイート（依存: 7）
9. 実機で実ブラウザ検証（依存: 8）

## リスク / 留意点

- **Teleport の行き先は `to` が変わったときだけ引き直される。** 目印にグループ id を含めないと、
  タブを移したときに外れた古い要素へぶら下がったままになる（spec に明記）。
- **描画の順序**: 受け皿（`<main>` の中）がプールより先に描かれること。
  同じテンプレートで `<main>` → `<PanePool>` の順に置いて担保する。
- **最大化の見た目**: `flex-basis` の切替を誤ると 1 枚が全面にならない。
  jsdom では計算できないので、**実ブラウザで寸法を測る**。
- 既存テストが `displayRoot()` を検査している（`pane-maximize.test.ts` の 3 か所）。
  「木は書き換えない」という本来の不変条件へ書き換える。

## テスト方針

- 単体（jsdom）: `App` をマウントして、**入力してから**最大化／解除・タブ移動・分割を行い、
  値が残ることを見る。受け皿の位置（どのグループの下に居るか）も確認する。
- 実ブラウザ（実機）: `verify-pane-state.mjs` に**最大化とタブ移動**を足し、
  **5250 の画面が 1 枚で全面になる**ことを寸法で測る（jsdom では見えない）。
