# レビュー: 純 DBCS と BLOB の 64KB 超を実測で閉じる

## ラウンド 1

### 見た観点

要件適合 / 正確性 / 規約適合 / 保守性。差分は 10 ファイル（うち新規 2 ＝ スクリプト）。
本体の変更は **3 ファイル各 1 行と、そこに寄せる関数 1 つ**。

### 確認したこと

- **「押した判断」を事実に置き換えたか。** PR #289 は純 DBCS と BLOB を
  「`isTwoByteCcsid` が同じ枝だから同じはず」で押していた。今回は実機で測り、
  **純 DBCS は推論どおり／BLOB は推論の外に事実があった**（CCSID 65535）。
  推論が当たっていたかどうかに関係なく、**測るまでは事実ではない**という点が要点。
- **作れないと思っていたものが作れた。** `20260801-pure-dbcs-dbclob` は
  「1200 経由の二段キャストが要る」とだけ書いており、大きな値の作り方は未知だった。
  **連結（`P || P`）は同じ CCSID どうしなので変換が要らない**——種だけ二段キャストで
  作れば倍々に伸ばせる。requirement の未確定事項として挙げ、research で潰した。
- **BLOB の CCSID が 65535 だったこと。** `decodeLobBytes` は `0` しか見ておらず、
  **`catch`（未知の CCSID はバイト列で返す）に落ちて偶然正しかった**。
  65535 に codec を足した瞬間に BLOB が黙って文字列へ化ける形だった。
  doc（`@param ccsid 0 なら BLOB`）も嘘だった。
- **同じ判定が 3 か所にあり、1 か所だけ欠けていた**（`db-reply.ts` / `marker-encode.ts` は
  正しかった）。`20260801-dbclob-locator-decode` が「根は判定の重複」で集約したのと
  **まったく同じ形**なので、同じ扱い（`isBinaryCcsid` に集約）にした。
- **振る舞いを変えていないか。** `isBinaryCcsid` の導入で結果は変わらない
  （今もバイト列が返る）。変わるのは「偶然」から「明示」へ。
  `db-reply.ts` / `marker-encode.ts` は条件が同値なので影響なし——既存 702 件が緑。
- **テストが循環していないか。** 偽ホストの `perChar` を `isTwoByteCcsid` から導くと
  **自分の判定で自分を試す**ことになる。引数で渡す形（`charCountingHostFor`）にし、
  実機で測った値をそのまま書いた。既存の呼び出しは薄い包み（`charCountingHost`）で従来どおり。
- **`decodeLobBytes` の戻りが同一配列のままか。** 既存テストが `toBe` で見ているので
  コピーしていないことを確認（`isBinaryCcsid(ccsid)` なら `return bytes`）。
- **秘密の混入。** ステージ済み差分をパスワード・ホスト・内部 IP で機械走査
  （陽性対照つき）。パスワード 0 / ホスト 0 / 私的アドレス 0。
  利用者名の当たりは `TESTLIB`（ライブラリー名）のみ——既存スクリプトに以前からある公開識別子。

### 残した制限（PR 本文にも書く）

- **CCSID 16684 は測れていない。** `20260801-pure-dbcs-dbclob` で
  **この実機に変換表が無い**ことを実測済み（1200 経由でも `-332`）。
  作れないものは測れないので、別の実機が要る。**これは「押した判断」ではなく
  「測れないと分かっている」状態**なので、backlog には戻さず制限として記す。
- `MAX_LOB_BYTES` いっぱいでの実測はしていない（往復数が増えるだけで単位の扱いは同じ）。
