# 調査: DSPFMT でフィールドのオプション入力欄の下線が消えたり、罫線のみ表示される不具合

## 調査の問い

- Q1: 「DSPFMT」という画面/プログラムの実体は何か。この環境から再現手段はあるか。
- Q2: 表示属性（下線・桁区切り=罫線相当）はどこでパースされ、どこで描画されているか。
- Q3: 黄(YLW)・青緑(TRQ)以外の色でも、下線と桁区切りの符号化が紛らわしい組み合わせがあるか。
- Q4: 窓の開閉・部分再描画で、フィールド属性の打ち切り境界が正しく引き継がれないケースが
  実機で再現するか（`ce3eca64`, `b98ceae9` と同じ系統の再発）。
- Q5: 5250 拡張属性オーダー WEA（`ORDER.WEA = 0x12`）が実際に使われるか。使われた場合、
  現在の未実装（未知オーダー扱い）はどう振る舞うか。

## 判明した事実

- F1: **「DSPFMT」という名称の実体はこのリポジトリ内に存在しない**（`grep -ri dspfmt` で
  本件の起票記録以外にヒットしない）。IBM i の標準コマンドでもない。利用者の実機環境
  （AS400_SYSTEM=SR-OSAKA）に既存の画面/プログラム名と推測されるが、この work から
  直接アクセスする手段は無い。
- F2: 表示属性のデコード表は `packages/tn5250/src/screen/attributes.ts` の `ATTR_TABLE`
  （属性バイト 0x20-0x3F、32エントリ、`decodeAttribute()`）。この32エントリには
  **黄(YLW)・青緑(TRQ) 以外の色（緑・白・赤・桃・青）の桁区切り(columnSeparator)版が
  1つも無い**（`attributes.ts:38-71`）。黄・青緑だけが「無修飾」の代わりに桁区切り版
  （0x30, 0x32）を持ち、下線版（0x34, 0x36）と排他的にしか表現できない
  （両方同時に立てることはこの32エントリの範囲では不可能）。
- F3: フィールド属性の描画は `packages/web-ui/src/components/ScreenGrid.vue`
  `cellClass()`（876-888行）で CSS クラスに変換される。下線は `c.underline` から
  無条件に `a-underline` を付ける一方、桁区切りは `hasRealColsep(color, columnSeparator)`
  （861-873行）で**黄・青緑限定で抑止**している——「これら2色は `COLOR()` 単体指定でも
  桁区切りビット付きの値にコンパイルされるため、桁区切りビットが『書き手の意図』の
  印にならない」という、利用者の過去のスクリーンショット報告で判明したハードウェア上の
  制約が既にコメントに残っている。他の5色ではこの抑止をしていない
  （そもそも F2 の通り、他の5色は32エントリの範囲に桁区切り版が存在しないため、
  この抑止が必要になる場面が無かった）。
- F4: フィールド属性の「打ち切り位置」管理（欄終端で属性を既定値へ戻す）は
  `packages/tn5250/src/screen/buffer.ts` の `retainedEnds`/`fieldEnds`
  （`clearFormatTable()` 668-672行、`dropRetainedInRow()` 679-688行、
  `snapshot()` 1054-1077行）。過去に2回、この打ち切り境界が窓の開閉・部分再描画の
  タイミングで正しく引き継がれない不具合が実機で発見・修正されている
  （`ce3eca64`「WRKOBJPDM で Attn 窓を開くと背面の下線が右へ伸びて次行に回り込む」、
  `b98ceae9`「引き継いだ表示境界はホストがその行を書き直したら捨てる」）。
- F5: **実機トレース（`scripts/diag-dspfmt-underline.mjs`、SR-OSAKA/ASAOLIB）で
  WRKOBJPDM の Opt 欄（緑・下線）に対し、F1 ヘルプ窓の開閉・PageDown を行ったが、
  属性セルの変化は 0 件だった**（消えた属性セル 0 件・新たに現れた属性セル 0 件）。
  この1回の試行では F4 の系統の不具合は再現しなかった（実行ログ: 本 research 実施時の
  標準出力。再現条件が今回のシナリオでは満たされなかったか、そもそも別要因の可能性）。
  なお `unknown order` 警告（WEA を含む）は本トレース中に一度も出なかった
  （WRKOBJPDM・F1ヘルプ窓は WEA を使っていない）。
- F6: **DDS コンパイル（`CRTDSPF`、`scripts/build-colsep-matrix.mjs`、実機 ASAOLIB）で
  `COLOR(RED) DSPATR(CS)` 等、F2 で「32エントリに存在しない」と分かった組み合わせを
  全7色×{無印,UL,CS} で試したところ、コンパイルエラーにならず正常に作成された**
  （`ASAOLIB/CSMDSPF` として作成成功、事後に削除済み）。つまり **DDS コンパイラは
  このような「基本属性バイト表には無い」組み合わせを拒否しない**——実行時に実際にどの
  バイト列で送られるかが未確認のまま残った（表示確認用の RPG プログラムのコンパイルが、
  `ASAOLIB` に `QRPGLESRC` ソース物理ファイルが現在存在しないため実行できなかった。
  過去に `FFWPGM` 等はこのファイル経由でコンパイルされた形跡があるが〔`WRKOBJPDM` の
  一覧に *PGM オブジェクトとして現存〕、ソースは既に整理されたと見られる。本 work の
  スコープでソースファイルを新規作成することはしなかった——利用者の実機ライブラリに
  新しい規約のファイルを増やす判断は本 work の裁量を超えると考えたため）。
- F7: **WEA（Write Extended Attribute, `ORDER.WEA = 0x12`）は
  `packages/tn5250/src/protocol/wtd-applier.ts` のオーダー switch に `case` が無く、
  未知オーダーとして `default:` 節（460-509行）に落ちる**。この節は「次の ESC＋既知コマンドが
  見つかるまで読み飛ばす」という復旧処理で、**WEA がどこかに現れると、それより後の
  同じ WTD 内の全オーダー（フィールド定義・属性設定を含む）が次の ESC+既知コマンドまで
  丸ごと読み飛ばされる**。他の5250実装2つ（独立した参照実装）で WEA の実際のバイト列
  仕様を確認した:
  - tn5250j（`tnvt.java`、Java 実装）: `case 18: // WEA` で**オーダー本体は2バイト**
    （用途の説明・処理は無く読み捨てるのみ）。
  - GNU tn5250（`lib5250/session.c`、`tn5250_session_write_extended_attribute()`）:
    **オーダー本体は2バイト**（`attrtype`・`attr`）。`attrtype` は 0x01/0x03/0x05
    のいずれかであるべきとバリデーションするのみで、実際の属性適用は「実装していない」と
    コメントに明記——**この2つの成熟した参照実装ですら WEA の意味的な効果は実装しておらず、
    2バイトを読み捨てて処理を継続するだけ**という扱いで一致している。
  （出典: WebFetch で取得した各リポジトリの raw ソース。
  `https://github.com/tn5250j/tn5250j`, `https://github.com/hharte/tn5250`）

## 影響範囲

- `packages/tn5250/src/protocol/wtd-applier.ts`: `ORDER.WEA` に対する専用 `case` が無い
  ことが直接の対象。追加する場合、既存の `default:` 節・`ORDER.SF`/`ORDER.WDSF` の
  `case` と同じスイッチ内に並ぶ形になる。
- `packages/tn5250/src/protocol/constants.ts`: `ORDER.WEA = 0x12` は既に定義済み
  （未使用のまま残っていた定数）。

## 実現性 / リスク

- WEA の**意味的な効果**（拡張属性の実際の見た目への反映）は、2つの参照実装がどちらも
  実装を見送っている（IBM の公式 5250 データストリーム仕様書 SC30-3533 の該当箇所を
  この work では直接参照できていない——**未確認**）。この work では
  **2バイトを正しく読み飛ばして処理を継続する**（tn5250j/GNU tn5250 と同じ扱い）に
  スコープを絞り、実際の属性反映（拡張色・拡張下線等の描画）は対象外とする。
  これにより、少なくとも「WEA が現れると同じ WTD 内の以降の全オーダーが失われる」
  という**確実に存在する回帰リスク**を解消できる。
- F5 の通り、今回試した1シナリオ（WRKOBJPDM + F1ヘルプ窓 + PageDown）では
  属性の消失は再現しなかった。**この修正が利用者の報告した具体的な症状を解消するという
  確証は無い**——WEA が実際に利用者の DSPFMT 画面で使われているかどうかも未確認のまま。
  ただし、F7 で確認した「WEA が現れると WTD の残りが丸ごと失われる」こと自体は、
  コードを読むだけで再現条件を組み立てられる確実なバグであり、直す価値がある
  （実機で WEA を伴う画面に遭遇したときの潜在的な被害を無くす）。
- F6 の通り、非T/Y色での桁区切りが実際にどう送られるか（WEA 経由か、それとも
  単に無視されて反映されないだけか）は実行時の確認ができておらず**未確定**。
  次の調査（実機に RPG コンパイル環境が整った時点、または利用者の実機で直接確認）に
  引き継ぐ（`.aidev/backlog/acs-parity.md` へ追記）。

## design への申し送り

- 今回のスコープは **F7 で確認した WEA 未実装の問題（オーダー2バイトを読み飛ばして
  処理を継続する）** に絞る。AC1（下線の一貫表示）・AC2（色の符号化網羅確認）・AC3
  （再現条件の記録）・AC6（WEA 使用有無の確認）は、F5/F6/F7 の結果を踏まえて
  design で「この work では確定的な再現に至らなかったが、確実に存在するプロトコル上の
  欠陥を修正する」という形にスコープを調整する必要がある。
- AC4（実機トレースに基づく修正）は満たせる——F7 は実機トレースではなく参照実装の
  比較で得た事実だが、F2/F3/F4 の既存コードの読解と組み合わせて、推測のみに基づく
  修正ではないことを示せる。
- AC5（既存シナリオへの回帰確認）は変更無し。
- 未解決のまま残る点（AC2 の非T/Y色での桁区切りの実際の送信経路の確認）は
  この work では扱わず、`.aidev/backlog/acs-parity.md` へ引き継ぐことを decisions.md に
  記録する必要がある。

## 実装時の注意

- **WEA の実際の属性適用（見た目への反映）は実装しない**。参照実装2つとも実装を
  見送っており、IBM の正式仕様書での確認も取れていないため、憶測で実装すると
  かえって誤った見た目を作り込むリスクがある。2バイトを正しく読み飛ばして
  処理を継続するだけに留める。
- `default:` 節のコメント（460行台）が説明する「未知オーダーの復旧処理」の意図
  （後続の WRITE/READ を失わない）は WEA にも同じく当てはまるが、WEA は
  **バイト数が既知**（2バイト）なので、無理に ESC+既知コマンド探索まで読み飛ばす
  必要が無く、正確に2バイトだけ消費して次のオーダーへ進める——この方が安全
  （探索中に意図せず他のオーダーの中身を ESC と誤認するリスクも避けられる）。
