# 計画: DBCS 欄の埋め込み属性を編集・送信で失わない

## split 判定

**分割しない**。core 3 点・web-ui 2 点の小さな変更が 1 本の因果でつながっており、
途中状態に意味が無い（値にセンチネルを載せるだけでは web-ui が長さを誤る）。

## 実装方針

**落ちるテストを先に書く。** 原因は実測で特定済みなので、テストが先なら
「本当にその原因か」の確認と回帰防止が同時に片づく。

core → web-ui の順に直す。core が値にセンチネルを載せない限り web-ui 側は検証できないため。

## 作業順序と依存関係

1. **T1** core の round-trip テストを書く（落ちる）
2. **T2** core を直す（D1・D2・輸出）→ T1 が緑
3. **T3** web-ui のテストを書く（落ちる）
4. **T4** web-ui を直す（D3・D4）→ T3 が緑
5. **T5** 通し確認

## リスク / 留意点

| # | リスク | 対応 |
|---|---|---|
| R1 | 送信バイトが変わり**既存の実機挙動を壊す** | DBCS 構造つき欄（`dbcsRawFieldValue` 経路）の送信バイトが**変わらない**ことをテストで固定する。触るのは構造なしの一般経路だけ |
| R2 | 属性が全角ランの途中に来る場合の SO/SI | spec D1 の実測根拠に基づく。テストで実際のバイト列を確認する |
| R3 | `dbcsByteLength` の変更が入力検証を緩める/きつくする | センチネルは**ホスト由来の値にしか現れない**（利用者は打ち込めない）。既存の入力検証テストが通ることを確認 |
| R4 | `Cell.rawByte` を属性セルにも載せることで、既存の `rawByte` 利用箇所が誤動作 | `rawByte` の既存利用は「表示できない SBCS バイト」の復元。属性セルは `kind === "attr"` で分岐済みなので混ざらない。利用箇所を確認する |
| R5 | web-ui は root の `tsc -b` に含まれない | T5 で `vue-tsc` 込みビルドを実行 |

## テスト方針

**core**（`packages/core/test/` に追加）
- DBCS 欄（構造なし）: 値 → 制御コードに触れない編集 → `setFieldValue` → **属性セルが残る**
- DBCS 欄: 送信バイト列に**属性バイト 0x28 が桁位置ごと含まれる**
- 属性より前を 1 文字削ると**属性の桁が 1 つ左へ動く**
- **DBCS 構造つき欄の送信バイトが変わらない**（R1）
- SBCS 欄の挙動が変わらない（既存テスト）

**web-ui**
- `dbcsByteLength(センチネル)` が 1
- 既存の入力検証・DBCS 編集テストが通る（R3）

**全体**: `npm run build` / `npm test` / `npm run lint` / `npm run build -w @as400web/web-ui`

**ガードの検証**: T1 / T3 は修正を戻して**落ちることを確認**する。
