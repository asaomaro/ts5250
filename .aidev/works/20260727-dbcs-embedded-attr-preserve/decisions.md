# 決定記録

## D1: 元コメントの「送信エンコードが壊れる」懸念は成り立たないと判断した

- 背景: `fieldValue` の `dbcs ? " " : attrSentinel(c.byte)` には
  「DBCS 欄は SO/SI・2 バイトの都合でセンチネルを混ぜると送信エンコードが壊れる」
  という理由が書かれていた。これを外すのが本作業の中心なので、根拠を確かめた。

- 決定: **外す**。懸念は現状に当てはまらない。

- 理由（すべて実測・コード確認）:
  1. `dbcsRawFieldValue`（未編集で DBCS 構造を持つ欄）は**既に `attrSentinel` を返している**。
     実測値 `e0c1 e0c2 e028 e00e e045 e0e2 e00f e0c3 e0c4` に属性 0x28 が載る。
     つまり「DBCS 欄の値にセンチネルが載る」状態は既に本番で動いていた
  2. 送信（`read-response.ts:39-45`）は `isRawSentinel` なら生バイトを 1 つ書き、
     前後を**別の run として `codec.encode`** する。DBCS/SBCS を区別しない
  3. 属性は **SBCS モードの 1 バイト**なので、全角の間に来たときに
     「SI で閉じる → 属性 → SO で開く」となるのが正しい。`flushRun` の分割がそれを満たす
     （web-ui 側の `dbcsByteLength` でも同じ数え方になることをテストで固定した）

- 影響: 取り残されていたのは「DBCS 宣言はあるが DBCS 構造を持たない欄」の一般経路だけ。
  SEU のソース行は日本語を含まない行が多く、**その多数派がこの経路**だった。

## D2: snapshot の属性セルに `rawByte` を載せた（新フィールドは足さない）

- 背景: web-ui が編集の種値（`logicalFromCells`）を作るとき属性をセンチネルへ戻す必要があるが、
  `snapshot()` の属性セルは色だけを持ち**バイトを落としていた**。

- 決定: 既存の `Cell.rawByte`（表示できない SBCS バイト用）に属性バイトを載せる。

- 理由 / 代替案:
  - 新しいフィールドを足すより、**同じ意味（このセルが運ぶ生バイト）**の既存欄に乗せる方が概念が増えない
  - 既存の `rawByte` 利用箇所を全数確認した: web-ui は `kind === "sbcs"` で、
    core は `type === "char"` で守られており、属性セルと混ざらない。
    `save-screen.ts` は**内部セル**（`type === "attr"` を先に分岐）を使うので影響なし

## D3: `dbcsByteLength` と `displayCols`（PR #172）を共通化しない

- 背景: どちらも「センチネルを `isFullWidth` に渡すと私用領域＝全角と誤判定される」問題。
  今はどちらも「センチネルは 1」と答えるので、1 つにまとめたくなる。

- 決定: **別々に持つ**。

- 理由: 一方は**画面の桁数**、他方は**送信バイト数**で、たまたま今の答えが同じなだけの別概念。
  1 つにすると、片方の都合（例: 桁の描き方を変える）で他方（送信長）が動く事故を招く。
  `MIN_BORDER_RUN` と `MIN_REVERSE_FRAME` を別名で同じ値にしたのと同じ判断。

- 影響: 同種の修正が 2 箇所に残るが、それぞれの JSDoc に理由を書いた。
