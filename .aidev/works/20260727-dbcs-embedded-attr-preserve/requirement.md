# 要件: DBCS 欄（SEU ソース）の埋め込み属性を編集・送信で失わない

## 背景 / 課題

PR #172 で SEU ソース欄の色が**表示されるように**なったが、利用者から
「**編集すると色が消える。行を離れても戻らない**」との報告を受けた。

調べた結果、これは表示の問題ではなく **データが壊れている**。

### 実測（`ScreenBuffer` に SF＋埋め込み属性 0x28 を流し、制御コード桁に触れない編集を書き戻した）

| 欄 | 編集後のセル色 | 属性セルの残存 |
|---|---|---|
| SBCS 欄 | `green/red` | **true** |
| DBCS 欄（SEU ソース相当） | `green` のみ | **false** |

**DBCS 欄では編集を書き戻した時点で属性セルが消える。**

### 原因の連鎖

1. `ScreenBuffer.fieldValue`（`buffer.ts:462`）は
   `} else if (c?.type === "attr") s += dbcs ? " " : attrSentinel(c.byte);`
   ——**DBCS 欄では属性を「ただの空白」として返す**
2. `ScreenBuffer.setFieldValue`（`buffer.ts:424`）は値を 1 文字ずつセルへ書き戻す。
   属性センチネルなら属性セルを復元するが、**空白はただの文字セル**として書く
   → **属性セルが消える**
3. 送信（`read-response.ts:39-45`）は値の中のセンチネルを生バイトで書き出す。
   属性が値に無い以上、**送信データからも制御コードが落ちる**

つまり `e9ab19e`（センチネル方式）が「編集で属性が元の桁に残り、**送信でソースが壊れ得た**」
として直した問題が、**DBCS 欄では直っていなかった**。

### 影響（表示より重い）

- 色が消える（報告された症状）
- **SEU で行を編集して保存すると、その行から色制御コードが失われる**——
  利用者のソースが書き換わる。表示の不具合ではなく**データ損失**

### web-ui 側にも同じ穴が 2 つある（実測で確認）

| 箇所 | 現状 | 問題 |
|---|---|---|
| `logicalFromCells`（`ScreenGrid.vue:685`） | 属性セルを **空白 1 桁**にする | 編集開始時の種値から属性が落ちる。コメントは「core の SBCS fieldValue と同じ扱い」とあるが、**core は空白ではなくセンチネルを返す**ので記述が誤り |
| `dbcsByteLength`（`fieldValidate.ts:43`） | `isFullWidth` で幅を見る | `isFullWidth` は**私用領域を全角として含む**ため、センチネルを **2 バイト＋SO/SI** と数える。長さ予算が壊れる |

### 送信経路はセンチネルを既に扱える（確認済み）

- `read-response.ts:39-45` は `isRawSentinel(ch)` なら生バイトを 1 つ書く。**DBCS/SBCS を問わない**
- `dbcsRawFieldValue`（未編集で DBCS 構造を持つ欄の経路）は
  **既に `attrSentinel(c.byte)` を返している**（`buffer.ts:510`）
  ＝ DBCS 欄の値にセンチネルが載ること自体は既に成立している

したがって、直すべきは「DBCS 構造を持たない欄が通る一般経路」だけ。
SEU のソース行は日本語を含まない行が多く、**その多数派がこの経路に落ちる**。

## 目的 / ゴール

DBCS 欄でも、埋め込み属性が**編集を経ても・ホストへ送っても失われない**ようにする。
SBCS 欄と同じ round-trip の保証を DBCS 欄にも与える。

## スコープ

### 対象

- `packages/core/src/screen/buffer.ts` の `fieldValue`（DBCS 欄でも属性をセンチネルで返す）
- `packages/web-ui/src/components/ScreenGrid.vue` の `logicalFromCells`（属性をセンチネルで残す）
- `packages/web-ui/src/composables/fieldValidate.ts` の `dbcsByteLength`（センチネルは 1 バイト）
- 上記の round-trip 回帰テスト（**修正前に落ちること**を確認して追加する）

### 対象外

- 埋め込み属性の**新規入力**（利用者が画面から制御コードを打ち込む機能）
- SO/SI の再構成規則・DBCS の入力検証規則そのもの
- 反転枠の窓判定（PR #172 で対応済み）
- 表示側のオーバーレイ経路（PR #172 で対応済み。本件が直れば値にセンチネルが載るため、
  将来は表示も値由来へ寄せられるが、**本作業では表示の経路を変えない**）

## 機能要件

- DBCS 欄の `fieldValue` が埋め込み属性を**センチネル**で返す
- 編集値を `setFieldValue` で書き戻したとき、**属性セルが復元される**
- 送信データに**属性バイトがそのまま含まれる**（桁位置も保たれる）
- 編集で属性より前の文字を増減させたとき、**属性が値の中を一緒に動く**（SBCS 欄と同じ）
- `dbcsByteLength` がセンチネルを **1 バイト**として数える
- SBCS 欄の挙動は変わらない
- 未編集で DBCS 構造を持つ欄（`dbcsRawFieldValue` 経路）の挙動は変わらない

## 非機能要件 / 制約

- ピュアロジック層の Node API 非依存を維持する
- 既存テスト（core 806 / web-ui 901）を減らさない
- `vue-tsc` 込みの web-ui ビルドが通る
- **実機で確認された事実に基づく**。SO/SI の扱いは推測で変えない

## 完了条件 (受け入れ基準)

- [ ] DBCS 欄で「値を取得 → 制御コードに触れない編集 → 書き戻し」を行っても
      **属性セルが残る**（実測で `false` だったものが `true` になる）
- [ ] DBCS 欄の送信データに**属性バイト 0x28 が含まれる**（桁位置も一致）
- [ ] 属性より前の文字を 1 つ削ると、**属性の桁が 1 つ左へ動く**（SBCS 欄と同じ追従）
- [ ] `dbcsByteLength(センチネル)` が 1 を返す
- [ ] SBCS 欄の既存挙動が変わらない（`errors-compat` 等の既存テストが無変更で通る）
- [ ] 未編集の DBCS 構造つき欄（SO/SI・全角を含む行）の送信バイトが変わらない
- [ ] 上記を固定する回帰テストがあり、**修正前のコードでは落ちる**ことを確認済み

## 未確定事項 / 確認したいこと

spec で決める（完全自律のため `decisions.md` に根拠つきで記録し、PR をレビュー地点とする）。

- **`fieldValue` の `dbcs ? " " : attrSentinel(...)` を単純に外してよいか。**
  元のコメントは「SO/SI・2 バイトの都合でセンチネルを混ぜると送信エンコードが壊れる」と
  述べているが、`dbcsRawFieldValue` は既にセンチネルを返しており、送信側も
  センチネルを生バイトで書き出せる。**この懸念が今も成り立つ場面があるか**を確かめる
- 属性が**全角文字の途中**（SO..SI ラン内）に来る場合の送信バイト列。
  属性は SBCS モードの 1 バイトなので SI で閉じてから出す必要があるが、
  `codec.encode` の分割（`flushRun`）がそれを満たすか実測する
- `dbcsByteLength` の修正は `displayCols`（PR #172 で追加）と**同じ性質の問題**。
  共通化するか、それぞれの層に置くか
