# 設計判断の記録: 基本 TN3270E

## D1: 5 バイトヘッダは telnet 層で付け外しする

**判断**: `TelnetLayer` が送信時に付け、受信時に剥がす。上位（`protocol/` / `screen/` / `session`）は
基本 TN3270 と同じものを扱う。

**理由**: ヘッダは「どの種別のメッセージか」を運ぶ**封筒**であって、3270 データストリームの一部ではない。
封筒は封筒を開ける層で扱う。

**この判断の実利は「既存コードを触らないこと」**。`protocol/inbound.ts` /
`protocol/outbound.ts` / `screen/*` は**1 行も変更していない**。基本 TN3270 は
TK4- と IBM i（英語・日本語）で実機検証済みなので、そこに手を入れない設計は
**退行の余地を構造的に無くす**。実際、TN3270E 追加後も TK4- / IBM i の E2E は緑のまま通った。

**代替案**: セッションでヘッダを扱う。**採らなかった**——`applyInbound` の前後に条件分岐が増え、
経路が 2 本に割れる。

## D2: 交渉の状態機械を `telnet/tn3270e.ts` に分け、純粋に保つ

`Tn3270eNegotiator` は**ソケットに触らない**。バイト列（サブネゴシエーション本文）を受けて
返すべきバイト列を返すだけ。`telnet.ts` は出し入れだけを担う。

これで交渉の全経路（正常・REJECT・対案の往復・上限超過・要求外の IS）が
**単体テストで固定できる**。`protocol/inbound.ts` を無状態にしたのと同じ思想。

## D3: device-type は基本 TN3270 と別に組み立てる

| 経路 | 型名 | 関数 |
|---|---|---|
| 基本 TN3270 | `IBM-3279-<model>[-E]` | `terminalTypeFor()` |
| TN3270E | **`IBM-3278-<model>[-E]`** | `deviceTypeFor()` |

**根拠**: RFC 2355 §7.1 が挙げる有効な端末 device-type は `IBM-3278-*` 系だけで、
`IBM-3279-*` は載っていない。RFC は「3278 を使うのは呼称の都合で能力を制限する意味ではない。
クライアントの能力は **Read Partition Query と Query Reply** で示される」と明記している。

**実測が裏付けた**——同じ s3270 が、基本 TN3270 では `IBM-3279-2-E`、TN3270E では
`IBM-3278-2-E` と名乗り分けていた。

**関数を分けたのは型で取り違えを防ぐため**。1 つの関数に引数で分岐を持たせると、
呼び出し側の 1 文字の間違いが実行時まで見つからない。

## D4: LU 名は経路ごとに渡し方を変え、`TelnetLayer` が振り分ける

| 経路 | 渡し方 |
|---|---|
| 基本 TN3270 | 端末タイプ文字列に `@<名前>`（慣行。実測で Hercules / IBM i が受理） |
| TN3270E | `DEVICE-TYPE REQUEST <型名> CONNECT <名前>`（RFC §7.1.2 の正式な手段） |

**どちらの経路になるかは交渉が始まるまで分からない**ので、`TelnetLayer` が `deviceName` を
保持し、**発火した側でだけ使う**。二重指定を構造的に防ぐ。

これに伴い `session` は端末タイプに `@` を含めなくなった（telnet 層が付ける）。

## D5: `FUNCTIONS` は空集合を要求し、減らすときは `REQUEST`（対案）

**根拠**: RFC 2355 §7.2.1。

> it may respond in the positive … it sends the FUNCTIONS IS command
> **with the function-list exactly as it was received.**
> it may respond in the negative by sending **a FUNCTIONS REQUEST command** …

**`IS` は「受け取ったリストをそのまま」返す場合にしか使えない。**
減らすなら `REQUEST` で対案を出す。空リストでの合意＝**basic TN3270E**（§9）。

**プロトタイプでこれを間違えた。** 部分集合を `IS` に載せて返し、**s3270 が寛容に受理したので
気づけなかった**。実装とハーネスの両方をこの規則に直してある。

> **教訓**: 参照実装が受理したことは仕様準拠の証明にならない。
> 前 work の D13（検証環境が要求しないものはスコープから落ちる）と同じ形の罠。

**往復には上限（既定 5）を設けた**。§7.2.1 は対案の往復を許すが、双方が譲らないと
無限に続きうる。RFC の impasse 条項に相当する打ち切りを実装で持つ。

## D6: `tn3270e: false` で後退経路を踏めるようにする

実ホストで TN3270E を提示するものが手元に無い（TK4- も IBM i も基本 TN3270 止まり）。
**切り替えを人為的に起こせないと分岐を検証できない**ので、明示的に無効化する口を設けた。

これにより「TN3270E を提示するサーバに、基本 TN3270 で繋ぐ」という組み合わせを
テストで踏める。ハーネス側も後退を扱えるようにしてある。

## D7: `onNegotiated` は TN3270E の `ready` と BINARY/EOR の**両方**が揃うまで発火しない

BINARY / EOR の合意だけで発火させると、セッションが使える気になった直後に送信して
ホストに弾かれる。TN3270E のときは交渉器が `ready` になるまで待つ。

## 検証方法の記録

**s3270 を独立オラクルにする三段構え**:

1. **ハーネスの正しさを先に確かめる**——RFC 準拠の TN3270E サーバに **s3270** を繋ぎ、
   `connected-tn3270e` と画面表示を確認する
2. **同じサーバに自実装を繋ぐ**——画面・LU 名・device-type を確認する
3. **交渉列を突き合わせる**——サーバが受け取ったサブネゴシエーション本文を
   s3270 と自実装で比べる（`DEVICE-TYPE REQUEST` は完全一致。`FUNCTIONS` は
   s3270 が機能を並べるのに対しこちらは空＝基本 TN3270E）

**順序が大事**。ハーネスが仕様違反だと 2 と 3 が誤検証になる。実際、
BIND-IMAGE を合意してしまうハーネスでは s3270 が `connected-unbound` のまま画面を描かず、
「s3270 がモードに入らない」という紛らわしい失敗になった。

## D8: 属性バイトは**送るときに CODE 表で引き直す**（そのまま返さない）

`Read Buffer` の属性桁は、受け取ったバイトの写しではない。
**意味を持つ 6 ビット（`ATTR.MEANINGFUL` = 0x3d）だけを残し、
バッファアドレスの 12 ビット形式と同じ CODE 表**で引いた値を送る。

0x00〜0xff の 256 通りを実測して確かめた（`artifacts/s3270-readbuffer-attr-256.hex`）。
アドレスと属性で同じ表が効いているのは偶然ではなく、
**制御コードと衝突しない図形文字だけを流す**という 3270 の一貫した作りによる。

## D9: `GE` の代替文字は**バッファに書かず、描画で引く**

`GE` に続くバイトは生のまま `chars` に置き、`geMark` という並行配列で印だけ立てる。
描画（snapshot）の段で代替文字集合を引く。

**理由は `Read Buffer`**——ホストは書いたバイトがそのまま返ることを期待する。
バッファの時点で Unicode に置き換えると戻せない。
「バッファは受け取ったバイトのまま、解釈は上の層」は 5250 側と同じ方針。

## D10: 端末は**直前の AID を覚える**。忘れるのは**キーボード復旧のとき**

ホスト起因の読みの先頭バイトは 0x60 固定ではなく、直前に押されたキーの AID。
`Read Modified` / `Read Modified All` / `Read Buffer` の**3 つとも**この値を使う。

**記憶を捨てる条件は「キーボードが復旧したとき」**——`WCC` の復旧ビット付きの書き込みと
`EAU`。復旧ビットの無い書き込みでは捨てない（実測で切り分けた）。
`applyInbound` は元から `keyboardRestored` を返していたので、
**セッション側はこの 1 つの合図だけを見る**——条件を 2 か所に書き分けない。

**意味づけ**: キーボードの復旧は「ホストが操作者に入力を返した」＝新しい取引の始まり。
そこで前の取引の AID を持ち越さない、という一貫した読み方ができる。

## D11: `Read Modified All` との違いは**短形式の扱いだけ**

`buildReadModified` に `all` フラグを 1 つ足して分けた。
`PA1`〜`PA3`・`Clear` の後、`Read Modified` は AID 1 バイトで答えるが、
`Read Modified All` は欄まで返す。**それ以外は完全に同じ**。

当初 `hostInitiated`（AID を 0x60 にする）というフラグを持っていたが、
**AID を覚えるようにしたら不要になった**ので消した。
操作者の押下もホストの読みも「覚えている AID で組み立てる」で一本化できる。

## D12: DBCS の入口は **3 本**として扱う（SO/SI だけではない）

`SO`/`SI` 小区間・**DBCS 欄**（`SFE` の文字セット属性 `0xf8`）・**`SA` 指定**の 3 通り。
x3270 が `enum dbcs_why` でこの 3 つを区別していたのを見て、こちらにも入れた。

桁ごとの文字セットは `Screen3270` の**並行配列**（`extCharset`）に持つ。
色・ハイライト・GE 印と同じ持ち方で、**バッファは受け取ったバイトのまま**という方針を崩さない。

## D13: DBCS の対は **区間の先頭からの偶奇**で決める（行では決めない）

行ごとに判定していたのを、画面全体を 1 本の通し番号として数える形に変えた。
その結果**DBCS 1 文字が行末で割れる**のを正しく描けるようになった。

判定は `snapshot()` の中で**画面 1 周を先に走査**して桁ごとの状態表を作る方式にした
（x3270 の `ctlr_dbcs_postprocess` と同じ位置づけ）。
セルを作りながら判定すると、行またぎと dead position を同時に扱えない。

## D14: x3270 の「先頭の欄が DBCS にならない」取りこぼしは**真似しない**

x3270 の後処理はアドレス 0 を支配する属性桁の次から一周するため、その属性桁自身を処理せず、
**画面の先頭に置いた DBCS 欄が対にならない**。実測 3 通りで確かめた。

規格から外れているのではなく回り込みの取りこぼしなので、真似ない。
**利用者に見える日本語が壊れる**方の挙動を写す理由が無い。
差は単体テストに期待値として書き、比較テストはこの配置を避けている。
