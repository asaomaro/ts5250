# 要件: 基本 TN3270E（RFC 2355 §9）

## 背景 / 課題

`@ts5250/tn3270` は**基本 TN3270（RFC 1576）**を実装済み（`20260815-tn3270-emulator`、PR #330）。
docker の TK4-（MVS 3.8j）と IBM i（英語・日本語）に接続し、画面の組み立て・入力・AID 往復・
日本語 DBCS まで実機で確認できている。

一方、**本命の z/OS メインフレームは TN3270E（RFC 2355）が前提**になる。
TN3270E は基本 TN3270 に対して次を足す:

- **LU 名（device-name）の指定**——どの端末として繋ぐかをクライアントが要求できる
- **5 バイトのメッセージヘッダ**——データ種別・応答要求・順序番号を運ぶ
- 任意機能（RESPONSES / BIND-IMAGE / SCS-CTL-CODES / DATA-STREAM-CTL / SYSREQ）

基本 TN3270 には LU 指定の仕組みが無く、端末タイプ文字列に `@<装置>` を付ける慣行で代用していた
（実測で Hercules / IBM i が受理）。TN3270E ならこれが仕様として使える。

## 目的 / ゴール

`@ts5250/tn3270` に **基本 TN3270E**（RFC 2355 §9 "BASIC TN3270E"）を実装する。
**任意機能は一切合意しない**——`FUNCTIONS IS` を空で返し、素の 3270 データストリームだけを扱う。

TN3270E を提示するホストとは TN3270E で、提示しないホストとは**従来どおり基本 TN3270 で**繋がること。

## スコープ

### 対象

- **telnet オプション TN3270E（40 / 0x28）の交渉**——`DO` に `WILL` で応じる
- **DEVICE-TYPE 交渉**（§7.1）
  - `SEND DEVICE-TYPE` に `DEVICE-TYPE REQUEST <型名>` で応答
  - **`CONNECT <device-name>` で LU 名を要求できる**（任意指定）
  - `DEVICE-TYPE IS <型名> CONNECT <名前>` の受理、`REJECT` + `REASON` の処理
- **FUNCTIONS 交渉**（§7.2）——**空集合を要求し、空集合で合意する**。
  ホストが機能を提示してきたら**部分集合（空）で返す**
- **5 バイトメッセージヘッダ**（§8.1）の付与と解釈
  - DATA-TYPE / REQUEST-FLAG / RESPONSE-FLAG / SEQ-NUMBER
  - 受信: `3270-DATA` のみ処理。他の種別は**記録して読み飛ばす**
  - 送信: `3270-DATA` ＋ `NO-RESPONSE` で送る
- **基本 TN3270 への後退**——ホストが TN3270E を提示しなければ従来経路をそのまま使う
- 検証: `mini3270` を TN3270E 対応に拡張し、**s3270 を独立オラクル**として照合

### 対象外

- **任意機能の実装**: RESPONSES / BIND-IMAGE / SCS-CTL-CODES / DATA-STREAM-CTL / SYSREQ
- **プリンターセッション**（3287 / LU type 3）
- **NVT モード**（§9.1）・**ATTN キー**（§11）・**装置プール**の細かい規則
- web-ui / MCP への露出（別 work）
- 5250 側（`@ts5250/tn5250`）の変更

## 機能要件

- ホストが `DO TN3270E` を送ってきたら `WILL TN3270E` で応じ、TN3270E で接続できる。
- ホストが TN3270E を提示しない場合、**基本 TN3270 で従来どおり接続できる**（退行なし）。
- 接続オプションで **LU 名を指定できる**（指定しなければホストに任せる）。
- ホストが要求を `REJECT` した場合、**理由（REASON）を添えて失敗する**。
- 受信したメッセージのヘッダを解釈し、`3270-DATA` の本体だけをデータストリームとして適用する。
- 送信時に 5 バイトヘッダを付ける。
- 未知の DATA-TYPE を受け取っても落ちない（記録して読み飛ばす）。

## 非機能要件 / 制約

- 既存の**基本 TN3270 の経路を壊さない**——TK4- / IBM i への接続が従来どおり通ること。
- 層規約（AGENTS.md）: `node:*` は `transport/` のみ。ピュアロジックは Node API 非依存。
- 依存方向: `tn3270` は `base` / `ebcdic` のみに依存（変更なし）。
- テストは 2 段構成を維持（既定は docker 不要、照合は `TN3270_E2E=1`）。
- **推測で書かない**——コードは RFC 2355 の直読と `s3270` との照合で裏を取る。

## 完了条件 (受け入れ基準)

- [ ] TN3270E を提示するサーバに対し、`connected-tn3270e` 相当まで到達し画面を組み立てられる
- [ ] **s3270 と同じ交渉列**（DEVICE-TYPE / FUNCTIONS）を送ることを、同一サーバ相手に突き合わせて確認
- [ ] LU 名を指定した接続で `CONNECT <名前>` を送り、ホストの `IS … CONNECT` を受理できる
- [ ] `REJECT` + `REASON` を受けたとき、理由付きのエラーになる
- [ ] 5 バイトヘッダの付与・解釈が単体テストで固定されている（境界値・未知の DATA-TYPE 含む）
- [ ] **TN3270E を提示しないホスト（TK4- / IBM i）で従来どおり動く**（退行なし）
- [ ] trace fixture の replay で TN3270E 経路が docker 無しで回帰する
- [ ] `npm run build` / `npm run lint` / 全パッケージの `npm test` が通る

## 未確定事項 / 確認したいこと

- `FUNCTIONS` を**空集合**で要求したときの実ホストの反応（s3270 は既定で 3 機能を要求するので、
  空要求が一般的かは未確認）。研究で s3270 の `-tn3270e` 関連オプションと RFC §7.2.1 を突き合わせる。
- `DEVICE-TYPE REQUEST` で送る型名を、基本 TN3270 と同じ組み立て（`IBM-3279-2-E`）でよいか。
- 基本 TN3270 で使っていた **`端末タイプ@装置名` の慣行**を TN3270E 時にどう扱うか
  （二重指定を避ける必要がある）。
