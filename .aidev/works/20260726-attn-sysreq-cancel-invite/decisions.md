## D1. research 工程を挟まない（2026-07-26 / requirement 終了時）

**判断**: 任意工程 research を実施しない。

**理由**: 本件の事前調査は requirement 起票前に**実機で完了済み**で、結果は requirement.md の
「背景 / 課題」に事実として畳み込んである。

- ホスト挙動は実機（system `S1234567`）で採取済み。ack 有無の**対照実験まで実施**して
  「返さないと止まる／返すと流れる」を確定させた
- 原典（tn5250j 0.8.0-beta2 `org.tn5250j.framework.tn5250.tnvt`）は javap で逆アセンブルして直読済み。
  `cancelInvite()` = `writeGDS(0, 10, null)` / `systemRequest(String)` = `writeGDS(4, 0, ebcdic(str))`
- 採取手順は `scripts/probe-sysreq.mjs` として再現可能な形で残してある

requirement.md の「未確定事項」に残る 3 点は**調査ではなく設計判断**（当実装の構造にどう嵌めるか）であり、
spec で解消するのが適切。protocol「4.5」の research 推奨条件（未検証の既存挙動への依存・実現性の仮定）には
当たらない。

## D2. Esc の既定キーバインドを足さない（2026-07-26 / requirement）

**判断**: 出荷時の既定バインド（`DEFAULT_BINDINGS`）に Esc を追加しない。

**理由**: 利用者の明示的な選択。Esc は現在「ヘッダーメニューを閉じる」「ブロック選択を解除」に使われており、
既定を足すと既存の操作感を壊す。キー設定画面（⌨ キー）で任意のコンボを Attn へ割り当てる機構は既にあるため、
機能欠落にはならない。

## D3. ボタンの置き場を「トップバー」から「CRT フッター（StatusBar）」へ変える（2026-07-26 / spec）

**判断**: 利用者が選んだ「トップバーに Attn / SysReq ボタン」を、`StatusBar` の `.fk` キー行に置き換える。

**理由**: PJ の明文規約に反するため。

- AGENTS.md「UI デザインガイド」: **ボタンは設置面の系統に合わせる**（トップバー `.theme-btn`＝固定高 28px /
  CRT ペイン＝`.fk` 意匠）
- `App.vue` のヘッダー冒頭コメント: **「ヘッダーに置くのは『いまどのシステムに繋いでいるか』と、
  このアプリ自身の管理だけ。IBM i の機能はランチャー（本体）に並ぶ」**

Attn / SysReq は IBM i の機能（5250 の AID キー）であってアプリ管理ではない。`StatusBar` には既に
`F1 ヘルプ / F3 終了 / F4 プロンプト / F5 更新 / F12 取消 / ⏎ 実行` の `.fk` ボタン行があり、
AID を押す導線としてはそこが正規の置き場。ペインごとに描かれるためアクティブペイン連動の配線も要らない。

**利用者の意図**（「キー設定を触らない人向けの導線」）は置き場が変わっても損なわれない。
選択肢を提示した時点で `StatusBar` に既存のキー行があることを把握していなかったのが原因なので、
**この逸脱は報告時に明示する**（利用者が元の選択を通したければ移設は容易）。

## D4. design 工程を挟まない（2026-07-26 / spec 終了時）

**判断**: 任意工程 design を実施しない。

**理由**: protocol「4.5」の推奨条件のうち「複数コンポーネントにまたがる」だけが該当するが、
core / server / web-ui の各変更は独立かつ局所的（core=opcode 分岐 1 箇所＋レコード組み立て、
server=任意項目 1 つの受け渡し、web-ui=新規小コンポーネント 1 つ）。インターフェースは
`sysReqText` という任意文字列 1 個のみで、データモデルの追加は無い。spec に変更ファイル表と
シーケンス図まで落ちており、plan で作業分解できる粒度に達している。

## D5. キーボードロック中の SysReq 送信は対象外（2026-07-26 / spec。requirement 未確定事項 3 の解消）

**判断**: ホスト応答待ち（`locked` / `busy`）の最中に SysReq を送れるようにするのは、今回やらない。

**理由**: 実現には AID 送信の中核を 3 箇所同時に崩す必要がある——`Session5250.pendingAid` が 1 本しか
持てない（2 本目で `key-done` の対応付けが壊れる）／`session-controller.sendKey` の `busy` 早期 return
（多重送信プロテクト）／`sendAid` 入口の `assertReady()`。

一方、本 work の目的（Esc でコマンド入力欄）は ack の修正だけで達成でき、そもそも**「固まる」原因が
今回直す欠陥そのもの**。切り離して別 work とするのが妥当。

## D6. tn5250j の「先頭が 2 なら受信キューを捨てる」は移植しない（2026-07-26 / spec。未確定事項 1 の解消）

**判断**: `systemRequest(String)` 冒頭の `dsq.clear()` 相当は入れない。

**理由**: あちらは受信データストリームを `BlockingQueue` に積む設計であり、前の要求を終了させるときに
積み残しが害になるための処置。当実装は `telnet.onRecord` → `handleRecord` で到着順にその場で処理しており
**キューが存在しない**。移植対象そのものが無い。

## D7. システム要求行のキー横取りは「行が開いているか」ではなく「行の中で起きたか」で判定する（2026-07-26 / coding）

**背景**: 実装中のコンポーネントテストで、**Esc を SysReq に割り当てると行を二度と閉じられない**という
欠陥が出た（利用者の想定用途そのもの）。

**原因**: 入力欄は `.pane` の子なので keydown がペインまでバブルする。取り消しの Esc は
`SysReqLine` のハンドラが先に走って `sysReqOpen` を false にし、**その後**同じイベントがペインへ届く。
ペイン側の歯止めが `if (sysReqOpen) return` だけだと、そのときには既に false なのですり抜け、
カスタムバインド（Esc → SysReq）が解決して行が即座に開き直る。

**決定**: 歯止めを `sysReqOpen.value || ev.target.closest(".sysreq")` にする。
「行が開いている間」に加えて「**行の中で起きたキーは行が閉じた後でも**ペインが触らない」を条件に足す。

**代替案**: `ev.defaultPrevented` を見る案は退けた。`ScreenGrid` は欄内 Shift 移動を preventDefault して
**ペインへ委譲する**設計（矩形選択）なので、defaultPrevented で一律に止めるとブロック選択が壊れる。

## D8. システム要求行は開いている間フォーカスを手放さない（2026-07-26 / review R1 の対応）

**背景**: review で「ホスト画面のプッシュでフォーカスを奪われると端末が固まって見える」を検出した。
`ScreenGrid` は新しい画面が来るたび `focusCursorField()` で入力欄へフォーカスを移す
（`ScreenGrid.vue` の `watch(() => props.snapshot)`）。行を出している最中にホスト発の非同期プッシュ
（メッセージ表示灯・ブレークメッセージ・遅延応答）が来ると caret が行の外へ飛ぶ一方、
`EmulatorPane` は行が開いている間 5250 のキー処理を止めるため、キーボードがどこにも効かなくなる。

**決定**: `SysReqLine` に `@focusout` を置き、開いている間はフォーカスを取り戻す。併せて
`EmulatorPane` の snapshot watcher は行が開いている間ペインへ focus しない（取り合いを避ける）。

**代替案**: 「行が開いていてもペイン側のキー処理を止めない」案は退けた。止めるのは ACS 準拠
（システム要求行がキーボードを保持する）で、実行キーの二重解釈も防いでいる。**止めること自体は正しく、
誤っていたのは『止めている間にフォーカスが外へ出られる』こと**なので、そちらを塞ぐ。

**回帰**: `sysreq-line.test.ts`「ホスト画面がプッシュされてもシステム要求行がフォーカスを保つ」。
`@focusout` を外すと落ちることを確認済み（テストが実際に欠陥を捕まえる）。

## D9. Attn / SysReq を README に載せる（2026-07-26 / review R1 の対応）

**背景**: review で「利用者向け文書に無い」を検出した。既定のキーバインドを付けない方針（D2）なので、
**文書に書かないと利用者が機能に辿り着けない**（キー設定で自分で割り当てる前提のため）。

**決定**: README の機能一覧と「使い方 2.（キー操作）」に追記する。ACS の既定に合わせるなら
`Esc → Attn` である旨、SysReq 行はオプション専用で CL コマンドは Attn 側である旨も明記した。

## D10. ペインがフォーカスを失ったらシステム要求行を畳む（2026-07-26 / review R2 の対応）

**背景**: D8 のフォーカス保持が、タブ・ペイン切替と喧嘩することが review R2 で分かった。
Alt+PageUp/Down（タブ切替）と Alt+矢印（ペイン移動）は**ペインではなく `App.vue` のグローバル
ハンドラ**が担うため、行を開いていて `onKeydown` が早期 return していても発火する。
切替後に離れたペインの `@focusout` がフォーカスを引き戻すと、切替先のペインがキーボードを取れない。

**決定**: `props.focused` が false になったら `sysReqOpen` を false にする（＝取り消し扱い）。
**まだ何も送っていないので副作用は無い**。切断時に畳むのと同じ考え方（送り先・操作主体が居なくなったら畳む）。

**回帰**: `sysreq-line.test.ts`「ペインがフォーカスを失ったら行を畳む（＝取り消し扱い・何も送らない）」。
