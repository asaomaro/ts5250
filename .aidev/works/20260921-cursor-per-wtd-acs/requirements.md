# 要件: カーソルの位置を WTD ごとに決め、READ では動かさない（ACS と同じ）

## 背景 / 課題
- 台帳「READ だけのレコード（WTD 無し）でも、カーソルを先頭の入力欄へ動かす」（要実機測定）。当 PJ は READ のとき、そのレコードで
  位置が指されていなければ先頭の入力欄へ置く。ACS は位置を WTD の終わり（`preprocessWCC2`）で決め、READ では触れない。
- WTD と READ が別のレコードで来る画面が作れず、差を測れていなかった。CL の SNDF → RCVF で作れる（`scripts/build-ulktest.mjs` の SPLIT）。

## 目的 / ゴール
- どの画面でも、カーソルの初期位置が ACS と同じになっている状態。

## ユーザーストーリー
- US1: 5250 の利用者として、画面が出たときのカーソルが ACS と同じ位置にあってほしい。なぜなら、IC で指された欄から打ち始める前提の画面で
  別の欄に打ってしまうから。（受け入れ: AC1, AC2）

## スコープ
### 対象
- カーソルの初期位置の決め方（コア）。IC / MC の持ち越し。
### 対象外
- 原典にある「解錠中に来てキーボードの状態を変えない WTD はカーソルを動かさない」（実測と合わない。decisions D2）。

## 完了条件 (受け入れ基準)
- [ ] AC1: WTD と READ が別のレコードで来る画面で、IC があれば IC、無ければ先頭の入力欄（ACS と同じ）。
- [ ] AC2: 実機の画面 9 つ（メインメニュー・DSPFMT・WRKOBJ・SNDMSG のプロンプト・WRKSPLF・分かれたレコード 2 つ・窓・QSH の出口）で ACS と同じ位置。
- [ ] AC3: 各判定を外すとテストが落ちる（`verify-by-mutation`）。
