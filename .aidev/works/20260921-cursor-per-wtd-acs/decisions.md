# 決定記録

## D1: 既定位置は WTD の終わりで置き、READ では触れない（旧実装の「READ のときに先頭の入力欄」を破棄）

- 原典（research F1）と実測（F3・F4）の両方で裏が取れた。台帳が心配していた「WRITE と READ が別のレコードで来る画面で既定位置が
  一度も置かれなくなる」は、既定位置を WTD の終わりへ移したので起きない（SPLITN で ACS と同じ 5,20）。

## D2: 原典の「解錠中に来てキーボードの状態を変えない WTD は動かさない」は入れない（未確認）

- 背景: `preprocessWCC2` の頭の条件（research F2）を入れると、DSPFMT の 3 つ目のレコード（前のレコードの CC2 で解錠済み・CC1 0・SOH なし・
  IC 7,4）では動かないことになるが、実機の ACS は 7,4 に置いた（F5。ACS 側のレコードも中継で確かめた）。
- 決定: 実測と合わない条件は入れない。ACS がレコードの終わりにキーボードを開く時機（`WCC2_unlock_pending` と `endOfRecord` の順序、
  出力だけのレコードでの扱い）の読みが確かめられていないので、**未確認**として残す。9 画面すべてが ACS と一致した。
- 影響: 解錠中に届く WTD（利用者が打っている最中の書き換え）でもカーソルが IC / ホームへ動く。ACS が本当に動かさないなら差になる。
  測るには、解錠の後に CLEAR も SOH も無い WTD を送る画面を作る（DSM など）。

## D3: SAVE / RESTORE SCREEN で IC も退避・復元する（独立点検の指摘）

- IC をレコードをまたいで持ち越すようにした（D1）ので、窓を開いて F12 で戻ると窓の IC が残るようになっていた。ACS `Save5250Net` は `WTD_IC_addr` と `homePos` を退避・復元する（MC は退避しない）ので、`icAddr` を退避の段に入れた。
