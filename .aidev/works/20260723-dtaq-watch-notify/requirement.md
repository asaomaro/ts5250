# 要件: データ待ち行列の常駐監視と到着通知

## 背景 / 課題

データ待ち行列（DTAQ）パネルは、いま**要求ごとに接続を開いて閉じる**方式でしか動かない。

- 受信の待機秒は HTTP 側で 0〜60 秒にクランプされ、無限待ち（core の `wait=-1`）は
  HTTP/MCP から使わせない歯止めが入っている（`packages/server/src/host-dtaq.ts:26-31`, `:73`）。
- そのため「いつ来るか分からないエントリ」を捕まえるには、利用者が 60 秒ごとに受信ボタンを
  押し続けるしかない。押していない間に届いた分は、押した時点でまとめて出てくるだけで、
  **届いた瞬間が分からない**。

一方で、プリンターセッションは常駐セッション＋WebSocket push＋未読バッジ（`sessionsStore.markSpoolRead`）
という形が既にあり、「放っておくと勝手に届いて、気づける」体験が成立している。DTAQ にも同じ体験が要る。

## 目的 / ゴール

指定したデータ待ち行列を**常駐して待ち続け**、エントリが届いたら
**画面に触れなくても気づける**状態にする。

## 既存「データ待ち行列」タブとの関係（分離する）

既存の `dtaq:entries` タブとは**別のアプリ（別タブ）**として作る。既存タブには手を入れない。

このリポジトリには同じ判断の前例がある——スプール（pull 型）とプリンターセッション（push 型）は
別タブに分けてある（`packages/web-ui/src/paneLabels.ts:30`）。DTAQ も同じ対比になる。

| | 既存「データ待ち行列」タブ | 待ち行列監視（本作業） |
|---|---|---|
| 型 | pull（押したときだけ要求） | push（届いたら来る） |
| 接続 | 要求ごとに開いて閉じる | 張りっぱなし |
| 状態の持ち主 | 画面（リロードで消える） | サーバー（リロードしても残る） |
| 対象 | 1 本を都度指定 | 複数本を同時に |
| 未読 | 概念なし | 要る |

同居させると、ステートレスな要求と常駐状態が 1 コンポーネントに混ざり、
「今どのキューを見ているか」を表す単一の入力欄の意味が二重化する。

## スコープ

### 対象

- サーバー常駐の DTAQ 監視（ブラウザを閉じても待ち続ける）
- 監視中に届いたエントリを**受信して取り出し**、履歴として保持・表示する
- **複数キューの同時監視**（個別に開始／停止）
- **監視コンソール 1 タブ**に監視中のキュー一覧と、選択したキューの履歴を収める
- **起動口はセッション段**：監視対象をセッション設定として登録し、そこから接続＝監視を開始する
- 到着の通知＝**タブの未読バッジ（全キュー合計）＋一覧の行ごとの未読件数＋履歴への追記**
- 接続断からの復帰（再接続して監視を続ける）

### 対象外

- ブラウザ通知（OS 通知）・通知音（今回は入れない。将来の追加余地は残す）
- 非破壊監視（ピーク／SQL ポーリングによる観測モード）——今回は受信＝消費方式のみ
- 受信したエントリの自動処理（外部への転送・スクリプト起動・ファイル保存）
- 監視設定のサーバー永続化（プロセス再起動をまたいだ自動復元）
- MCP ツールからの監視操作

## 画面の構成

監視コンソール 1 タブに、次の 2 段を収める。

```
タブ帯:
[データ待ち行列] [待ち行列監視 ●5] [SQL]
                  ↑ 全キュー合計の未読

タブの中身:
  監視中          受信  未読
  ▶ TESTLIB/ORDERQ   12    3      ← 選択中。行ごとに停止できる
    TESTLIB/LOGQ      7    2
  [＋監視を追加]
  ── TESTLIB/ORDERQ の履歴 ──
  #12 22:41:03 "ORD-1043" 18B
```

## 機能要件

- 監視の**開始**: ライブラリー・キュー名・符号化（utf8/base64/ebcdic）を指定して監視を始められる。
  キー付きキューの場合はキーと検索条件を指定できる。
  指定はセッション設定として登録し、ランチャーのセッション段から接続＝監視開始できる。
  監視コンソールが未オープンなら開き、開いていればそこに監視が 1 本増える。
- 監視の**停止**: 監視中の各キューを個別に止められる。タブを閉じても監視は止まらない
  （常駐はサーバー側にあるため。止めるのは明示的な停止操作）。
- **待ち続ける**: エントリが無い間は無通信でブロックして待つ（ポーリングしない）。
- **受信して蓄積**: 届いたエントリは取り出し、到着順に履歴として保持する。
  履歴には本文（指定符号化）・バイト数・受信時刻・送信者情報（有効なキューのみ）を含む。
- **一覧**: 監視中のキューを一覧し、キューごとの受信件数・未読件数・状態（監視中／エラー）が分かる。
  行を選ぶとそのキューの履歴が出る。
- **通知**: 到着したら、監視タブを見ていなくてもタブの未読バッジ（全キュー合計）で気づける。
  タブを開いたら未読は解消する（プリンターと同じ挙動）。どのキューに来たかは一覧の行の未読で分かる。
- **消費することの明示**: 監視は**エントリを取り出して消す**（本番のコンシューマの取り分を奪う）。
  開始時に画面上で明示し、誤って本番キューに掛けないようにする。
- **失敗の可視化**: 接続断・権限エラー・キュー削除などで監視が続けられない場合、
  その監視の状態としてエラーを表示する（黙って止まらない）。
- **復帰**: 一時的な接続断は自動で再接続して監視を続ける。復帰できない場合は上記のエラー表示に落とす。

## 非機能要件 / 制約

- 監視 1 本につきホストサーバー（`QZHQSSRV` / 0xE007）へ接続を 1 本張り続ける。
  同時監視数には上限を設け、無制限に接続を張らない。
- 監視は**開始した利用者の資格情報**で動く。他の利用者の監視や履歴は見えない。
- 履歴はサーバーのメモリ上に保持し、キューごとに保持件数の上限を設ける（無制限に溜めない）。
  プロセス再起動で失われてよい。
- 既存の DTAQ パネル（送信・受信・ピーク・一覧・属性・管理）の挙動を壊さない。
- 既存の HTTP ルートの歯止め（HTTP からの無限待ち禁止）は維持する。
  無限待ちは常駐監視の内部でのみ使う。

## 完了条件 (受け入れ基準)

- [ ] 登録した監視設定からセッション段で接続すると、監視コンソールが開いて監視が始まる
- [ ] 監視中であることと、対象キューが一覧で分かる
- [ ] 監視中のキューにエントリを送ると、画面操作なしで**数秒以内**に履歴へ現れる
- [ ] 監視タブを見ていないときに到着すると、タブに未読件数（全キュー合計）が付く。タブを開くと消える
- [ ] どのキューに何件届いたかが一覧の行で分かる
- [ ] 複数キューを同時に監視でき、それぞれ個別に停止できる
- [ ] タブを閉じても監視は止まらず、開き直すと閉じていた間の到着が履歴にある
- [ ] ブラウザを閉じて再度開いても監視は続いており、閉じている間に届いた分が履歴にある
- [ ] 監視は取り出し（消費）であることが開始前に画面で分かる
- [ ] 権限が無いキューを監視しようとすると、その監視がエラー状態として一覧に表示される
- [ ] 履歴が保持件数の上限を超えても、古いものが落ちるだけで監視は続く
- [ ] 既存の「データ待ち行列」タブは変更されず、そのテストが通り続ける

## 未確定事項 / 確認したいこと

- 履歴の保持件数の上限（キューあたり何件か）
- 同時監視数の上限（利用者あたり／サーバー全体）
- 監視の寿命：利用者がログアウトしたら止めるか、そのまま続けるか
- セッション設定モデルへの載せ方：既存のセッション設定は**装置名**を前提に組まれている
  （装置名の重複判定・1 装置 1 接続の制約）。装置名を持たない監視種別をどう表すか
- 監視コンソールのタブが「セッションを持つタブ」「持たないタブ」のどちらに属するか
  （`paneLabels.ts` の `PANE_PREFIXES` は後者の一覧。閉じたときの扱いが変わる）
