# 決定記録

## D1: 監視は独立したレジストリが所有する（`SessionManager` に相乗りしない）

- 背景: research が「監視の寿命を WS から切り離す必要がある」（F1・R1）と結論し、
  相乗りするか独立させるかを spec に投げていた（申し送り 2）。
- 決定: **独立した `WatchRegistry`**。
- 理由 / 代替案:
  - `SessionManager` の寿命の規則は「WS 切断＝破棄」「アイドルで掃除」で、
    `20260729-session-lifetime-timeout` で整理したばかり。監視は
    **何も来ない状態が正常**・**WS と無関係に生きる**・装置名も画面も持たないので、
    同じ箱に入れると規則に例外が生える。**寿命の異なるものを同じ箱に入れない**
  - 上限 8 の共有も避けたい（監視が表示セッションの枠を食う）。監視は `maxWatches`（既定 4）を持つ
- 影響: 管理画面のセッション一覧（`listAll`）には出ない。必要になれば別途足す。

## D2: 長時間アイドルは TCP キープアライブ＋自動再接続で守る

- 背景: `wait=-1` は read タイムアウトを無効にするので**相手が黙って消えても永久に待つ**。
  `host-connection.ts` は `setKeepAlive()` を呼んでいなかった（research R3）。
- 決定: core に `socket.setKeepAlive(true, 60_000)` を入れ、切れたらレジストリが
  指数バックオフ（1→2→5→10→30 秒）で張り直す。**`wait` を区切って張り直す方式は採らない**。
- 理由: 区切り方式は「無通信で待つ」要件から離れ、再接続のたびに認証往復が増える。
  keepalive は要求ごとの短い接続に実害が無く、切断の検出が早くなるだけ。
- **実測（A/B）**: `scripts/probe-dtaq-longwait.mjs --minutes 45` を keepalive の有無で回した。
  - **無し: エントリが失われた。** キューからは消えたのに待機中の `read` は返らない
    （50 分時点でも待機のまま）＝接続は死んでいるのにこちらは気づかず、
    **ホストが死んだソケットへ払い出して捨てた**
  - **有り: 45 分を越えて受信できた**（`受信: "after-45min"`）
  - つまり **keepalive は保険ではなく必須だった**。research R3 の懸念は現実だった。

## D3: 停止の印をループの `catch` が見る（順序には依存しない）

- 背景: 停止は接続の `close()` で行うが、待機中の `read` は reject される。
- 決定: `stopping` を立て、ループの `catch` がそれを見て黙って抜ける。
- 理由: 印が無いと**停止操作が `error` 状態として表示される**（「黙って止まらない」の逆で、
  止めたのに障害に見える）。テストで固定した。
- **訂正（空振り検証で判明）**: 当初「`close()` より先に立てる」ことを要点として書いていたが、
  **順序には依存していない**。Promise の reject ハンドラは必ずマイクロタスクで走るので、
  `stop()` の同期処理が終わった時点で印は立っている。順序を入れ替えるミュータントが
  落ちなかったことでそれが分かった——**効いているのは「`catch` が印を見ること」だけ**。
  コメントが保証していない性質を語っていたので直した。

## D4: 再接続できた時点で `watching` に戻す（受信できた時点ではない）

- 背景: 最初の実装は「`read` が成功したら `watching`」にしていた。
- 決定: **接続が張れた時点**で戻す。
- 理由: 受信で戻す形だと、**張り直せたのにエントリが来ないキューが永久に `reconnecting` に見える**。
  監視は「何も来ないのが正常」なので、それは嘘の表示になる。**単体テストが先に捕まえた**
  （`reconnecting` のまま `watching` イベントが出なかった）。

## D5: 待っても直らない失敗は再試行しない

- 決定: `ACCESS_DENIED` / `FORBIDDEN` / `NOT_FOUND` / `UNAUTHENTICATED` / `CONFIG_ERROR` /
  `HOST_SERVER_UNSUPPORTED` は `error` に落として**ループを抜ける**。
- 理由: 権限が無い・キューが無いは何度張り直しても同じ結果。無限に再試行すると
  ホストへ無駄な接続を打ち続ける。
- 影響: `error` になった監視も明示停止で消せる（消し方が無いと残骸になる）。

## D6: 同じ設定の監視を二重に始めない。判定は**サーバー**に置く

- 背景: 実機 E2E で、リロード後に「接続」を押すと**同じキューに監視が 2 本**掛かった。
  監視は消費するので、2 本掛かると 1 本ぶんのエントリを取り合って**両方が欠ける**。
- 決定: `WatchRegistry.start()` が同じ `ref` ＋ 同じ所有者の監視を見つけたら
  **既存を返す（冪等）**。画面側の判定は最適化として残すだけ。
- 理由: 画面側だけで見ると、**リロード直後は一覧が届いていない**（`watch-list` 待ち）ので
  すり抜ける。実機で踏んで初めて分かった——**真実を持っている側で判定する**しかない。
- 影響: 「別の設定で同じキューを 2 本」は依然できる（設定が 2 つあれば別物と見なす）。
  そこまで塞ぐと「同じキューを違う符号化で見たい」を禁じることになる。

## D7: `watch-*` は `open`（5250 セッション）を要さない

- 背景: 既存の WS メッセージはすべて `requireSession()` を通す。
- 決定: 監視のメッセージだけは通さない。
- 理由: 監視コンソールは pane タブで**セッションを持たない**（research F6）。
  `requireSession()` を通すとコンソールから一切使えない。
- 影響: `dispose()` は購読を外すだけにした（**レジストリに触らない**）。
  ここを間違えると「ブラウザを閉じたら監視が止まる」に戻るので、テストで固定した。

## D8: `.superRefine()` を付けたスキーマとは別に素のオブジェクト版も公開する

- 背景: 種別（`dtaqwatch`）と設定（`dtaqWatch`）の整合を parse で強制するため
  `.superRefine()` を足したところ、既存の `config-routes` のテストが 6 件落ちた。
- 決定: `serverSessionObject` / `personalSessionObject`（素）と
  `serverSessionSchema` / `personalSessionSchema`（`superRefine` 付き）を分け、
  CRUD 入力用に `sessionInputSchema(source)` を用意する。
- 理由: `.superRefine()` は `ZodEffects` を返すので **`.omit()` が使えない**。
  `ConfigStore.parseSessionInput` は `id` を除いて検証するため `.omit()` が必要だった。
  型キャストで隠れていたので**実行時に初めて壊れた**（テストが捕まえた）。
- 影響: 整合チェックは**ファイル読み込みと API 入力の両方**で掛かる（片方だけだと
  API 経由で不整合な設定を作れてしまう）。
