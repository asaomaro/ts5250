# 要件: `CONNECT_FAILED` の意味を取り戻す

## 背景 / 課題

`.aidev/backlog/library-extraction.md` の「先に返すべき負債」の 1 項目。

元の記述は「`ErrorCode` の整理（19 種に … ホストサーバーに無縁のものが混在）」だったが、
**2026-07-19 の実測でこれは事実と食い違っていた**——実際は 21 種で未使用のコードは 0 件。
「無縁のものを消す」作業は存在しない。

代わりに実在する問題として記録されたのがこれ:

> **`CONNECT_FAILED` の意味が壊れている**——server 側で「限度到達」「参照不正」
> 「users ファイルが読めない」など**接続と無関係な用途に 11 箇所**流用されている。
> やるなら「core の型を整理する」ではなく「**server の 11 箇所の意味を決め直す**」作業。
> HTTP ステータス写像（`host-api.ts`）にも波及するので、独立した作業として起こすこと。

`CONNECT_FAILED` は本来「IBM i へ繋げなかった」を指す（core の `transport/tcp.ts` が投げる）。
サーバーがそれを「セッション上限に達した」「設定ファイルが壊れている」にも使っているため、
**受け取った側が「ホストが落ちているのか、こちらの設定が悪いのか」を区別できない**。
これは `statusOf` が 502 を「上流との通信失敗」に限っている方針（`host-api.ts`）と同じ思想で、
コード名そのものが同じ役目を果たせていない。

## 目的 / ゴール

**`CONNECT_FAILED` を「IBM i へ繋げなかった」だけに戻す。** 流用されている箇所は、
それぞれの実際の意味に合ったコードへ移す。受け取った側（HTTP クライアント・MCP・ブラウザ）が
コードだけで「誰が直せる問題か」を判別できる状態にする。

## スコープ

### 対象

- `packages/server/src/` で `CONNECT_FAILED` を接続以外の意味に使っている箇所すべて
- 「セッション上限に達した」の扱い（接続の失敗ではなく**資源の上限**。閉じれば通る）
- `host-api.ts` の `statusOf`（HTTP ステータス写像）への波及
- `ws-handler.ts` の `fatal` 判定——**エラーコードの列挙で「致命的か」を決めている箇所**。
  今回のような改名で意味が黙って変わる形になっているので、判定の根拠を状態に置き換える
- `ErrorCode` の JSDoc（コードの意味が書かれていないものに意味を書く）

### 対象外

- core が投げる `CONNECT_FAILED`（`transport/tcp.ts` / `host-connection.ts`）。**これは正しい用途**
- 偏りの是正そのもの（`PROTOCOL_ERROR` 65 / `CONFIG_ERROR` 33 …）。
  件数を平すことが目的ではない。**意味が合っているかだけを見る**
- 既存コードの削除・統合。未使用のコードは 0 件なので消すものが無い
- 同じファイルにある他の負債（CCSID テーブルの同梱単位・ライブラリ切り出し 3/4）

## 機能要件

1. `CONNECT_FAILED` は「IBM i へ繋げなかった」ときにだけ投げられる
2. 「セッション上限に達した」は**それ専用のコード**で表され、
   「繋げなかった」「設定が悪い」と区別できる
3. 設定ファイルの読み込み失敗・スキーマ違反・指定不足は設定系のコードで表される
4. HTTP ステータスが**利用者の対処に合っている**（502＝ホストが落ちている、を汚さない）
5. `ErrorCode` の各コードに「どういうときに使うか」が書かれている
6. `fatal` 判定がエラーコードの列挙に依存しない

## 非機能要件 / 制約

- **外部に見える契約を壊さない**。`As400Error` は npm 公開候補のライブラリの型なので、
  既存コードを消さず、必要なら足す
- HTTP ステータスが変わる箇所は**変わる理由が説明できる**こと（400 → 409 など）
- `statusOf` の戻り型（`400 | 403 | 404 | 409 | 502`）を安易に広げない
- テストが「どの意味でそのコードなのか」を語る形にする（コード名の羅列にしない）

## 完了条件 (受け入れ基準)

- [ ] `packages/server/src/` に接続以外の意味の `CONNECT_FAILED` が残っていない
- [ ] セッション上限が専用コードになり、HTTP ステータスが対処に合っている
- [ ] 設定系（ファイル読めない・スキーマ違反・指定不足）が設定系コードになっている
- [ ] `statusOf` の写像が新しいコードを含めて説明つきで整っている
- [ ] `fatal` がコードの列挙ではなく状態で決まる
- [ ] `ErrorCode` の全コードに用途の JSDoc がある
- [ ] 既存テスト（`CONNECT_FAILED` を期待している 4 件）が新しい意味で通る
- [ ] `.aidev/backlog/library-extraction.md` の当該項目にチェックが付く

## 未確定事項 / 確認したいこと

- セッション上限に**新しいコードを足す**か、既存の `RESOURCE_BUSY` を使うか
  （後者は IFS のロック競合と区別できなくなる）
- 「host or profile required」（指定不足）は設定エラーか、別の意味か
- `fatal` を状態で決めると、`open` 前の `key` など既存の分類が変わる箇所があるか
  （現在 `fatal` を読んでいるクライアントがあるか）
