# 決定記録

## D1: セッション上限には新しいコード（`SESSION_LIMIT`）を足す

- 背景: backlog は「core の型を整理するのではなく server の意味を決め直す」作業と規定していた。
  上限に合う既存コードがあれば足さずに済む。
- 決定: `SESSION_LIMIT` を追加する。既存コードの流用はしない。
- 理由 / 代替案:
  - `SESSION_REJECTED` は core の `printer-session.ts:205` が「**ホストが**起動応答で拒否した
    （8925 等）」に使っている。断ったのがホストか自分かは、利用者の次の一手が変わる
  - `RESOURCE_BUSY` は IFS の rc=1/32/33（**ホスト上の対象**が他に掴まれている）専用で、
    `ifsApi.ts:52` が「他の処理が対象を使用中です」という文言に写している。流用すると UI が嘘を言う
  - `CONFIG_ERROR` は不適。`--max-sessions` の設定は正しく、問題は**今の状態**
- 影響: `ErrorCode` に 1 つ増えた（既存は消していないので外部契約は壊れない）。
  `statusOf` に 409 として足した。

## D2: 上限の HTTP ステータスは 400 → 409

- 背景: 以前は `CONNECT_FAILED` 経由で 400 だった。
- 決定: 409。
- 理由: `statusOf` には既に **409 の棚**がある（`ALREADY_EXISTS` / `RESOURCE_BUSY` / `NOT_EMPTY`）。
  共通するのは「**時間や対象を変えれば通りうる**ので 502（ホストが落ちている）に落とさない」。
  上限も**どれか閉じれば通る**ので同じ棚。400 は「要求が間違っている」だが、要求は正しい。
  429/503 は `statusOf` の戻り型を広げることになるので採らない（棚が増えるほど呼び出し側が困る）。
- 影響: MCP・ブラウザは本文の文言を見せるだけなので実害は見当たらない。写像表テストで固定した。

## D3: 「指定不足」に専用コードを作らず `CONFIG_ERROR` にまとめる

- 背景: `host or profile required` / `system, session, or host required` は
  「設定ファイルが壊れている」とは別種にも見える。
- 決定: `CONFIG_ERROR` にまとめる。
- 理由: 利用者の対処が同じ（**こちら側の指定を直す**）で、`statusOf` も同じ 400 になる。
  **区別できても誰も使わない区別**を作ると、呼び出し側の分岐だけが増える。
  代わりに `CONFIG_ERROR` の JSDoc に「設定・指定の不備（利用者が直せる）」と範囲を書いた。
- 影響: `CONFIG_ERROR` の意味が少し広い。JSDoc で範囲を明示して歯止めにした。

## D4: `fatal` はエラーコードの列挙をやめ、状態で決める

- 背景: `ws-handler.ts:122` が `fatal = code === "SESSION_CLOSED" || code === "CONNECT_FAILED"`。
  今回 `open` の失敗が `CONFIG_ERROR` / `SESSION_LIMIT` に分かれるので、
  **列挙のままなら「開けなかった」が致命的でなくなる**（意味が黙って変わる）。
- 決定: `fatal = code === "SESSION_CLOSED" || this.sessionId === undefined`。
- 理由 / 代替案:
  - 新しいコードを列挙に足す案は、次に名前が変わったときに同じことが起きる。
    **この作業そのものが「列挙で意味を持たせる危険」の実例**なので、根を直す
  - `fatal` を読んでいるクライアントは無い（research F5。`packages/web-ui/src` に 0 件）。
    web-ui は `sessionId` が未確定かで自前に判断している——**それと同じ判定を server 側でも使う**形になった
- 影響: `open` 前の `key`（`SESSION_NOT_FOUND`）が `fatal: false` → `true` に変わる。
  「この接続にセッションが無い」は事実で、読んでいる側も無いため実害なし。テストで固定した。

## D5: `ErrorCode` 全種に用途の JSDoc を書く（範囲外に見えるが本体）

- 背景: requirement のスコープは「server の意味を決め直す」。型のコメントは付随作業に見える。
- 決定: 全 26 種（追加後）に「どういうときに使うか」＋**似ているコードとの使い分け**を書く。
- 理由: 腐りの原因の半分がこれ（research F7: 意味が書かれているのは後半 9 種だけだった）。
  意味の無いコードには呼び出し側が「近そうなもの」を選ぶ。**移し替えだけして
  コメントを書かないなら、同じことがまた起きる**。
- 影響: `errors.ts` の差分が大きい（型 1 行 → JSDoc 付き）。振る舞いは変わらない。
