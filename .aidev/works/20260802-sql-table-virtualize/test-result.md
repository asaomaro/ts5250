### 計測でつまずいた点（すべて直したうえでの値）

1. **古いバンドルを測っていた。** `npm run build`（root）は `tsc -b` ＋ 型検査だけで、
   **web-ui の `dist` を作らない**。1 回目の検証は変更前のコードを測っており、
   「仮想化が効いていない」という結果が出た。`npm run build -w @as400web/web-ui` が要る。
2. **応答本文の読み終わりを `res.clone().text()` の `.then` で拾っていた。**
   アプリが描き終えたあとに解決することがあり、**200 行が「0 ms」**になった。
   自分で読み切ってから時刻を刻み、読んだ中身で `Response` を作り直す形に変えた。
3. **前後で待ち方が違うと比べられない。** 基準線は「全行が出揃った時刻」。
   仮想化後に「窓が確定するまで」を待つと **rAF 2 枚ぶん**余計に乗る。
   「行が 1 つでも見えた時刻」＝利用者が表を見た瞬間で比べ、確定までは別に出している。
4. **窓の更新は rAF で間引いてある**ので、スクロール直後に読むと前の窓を見る
   （行番号の検査が「中間でも 1 から」と出た）。1 フレーム待ってから読む。
5. **全角は半角の 2 倍ではなかった。** 節 7 を足して測ったところ、
   半角 8.00px に対し全角 13.00px＝**1.625 倍**。`IBM Plex Mono` は CJK の字形を持たず、
   **代替フォントが描く**ため。2 と決め打っていた `displayWidth` に重みの引数を足し、
   **実測した比を渡す**ようにした——直す前は日本語の列だけ 2 割ほど広くなっていた。
   この穴は「未検証」として記録するつもりだったが、確かめたら実際に外れていた。

### 残った差の正体

200 行が 123 → 88 ms（−28%）にとどまるのは、**残りが表ではない**から。
1000 行（112 ms）と 200 行（88 ms）の差は 24 ms ＝ 幅の走査（40,000 対 8,000 セル）ぶんで、
共通の ~80 ms は**応答の解析と反応性の設定**。仮想化では減らない。

検査の閾値は**動機に合わせた**——1000 行（0.6 秒固まる）を潰すのが目的で、
200 行は元から実用域。全部に「半分以下」を課すのは的外れな検査になる。
