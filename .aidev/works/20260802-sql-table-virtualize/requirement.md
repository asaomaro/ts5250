# 要件: SQL 結果表の行を仮想化する（表示範囲だけ描く）

## 背景 / 課題

`.aidev/backlog/hostserver.md:347` の未着手項目。

> **SQL 結果表の行を仮想化する（表示範囲だけ描く）**
> 1 タブぶんの初回描画（200 行 × 40 列 ＝ 8,000 セル）が今も 100ms 前後かかる。
> `pageSize` を 1000 にすると 40,000 セルになる。
> **`table-layout: auto` のままだと描画範囲で列幅が揺れる**ので、幅の決め方とセットで設計が要る
> （`20260723-sql-multi-statement` の decisions D1）。

`SqlResultTable.vue` の冒頭コメントにも実測が残っている:

> 切り替えのたびに表を作り直すと、200 行 × 40 列（8,000 セル）で
> **Vue の再生成に 220〜280ms** かかり、描画後に操作を受け付けない時間が出る。

`pageSize` は画面から **50 / 200 / 1000** を選べる（`SqlPane.vue:590`）ので、
40,000 セルは**利用者が普通に到達できる**設定。

### 幅の問題が本体

行を間引いて描くと、`table-layout: auto` は**いま描いている行だけ**から列幅を決める。
スクロールのたびに幅が変わり、**表が横に踊る**。だから仮想化は
「幅をどう決めて、いつ固定するか」と**同時にしか解けない**。

いまの幅の決まり方（`useColumnWidths.ts` ＋ `SqlResultTable.vue` の CSS）:

- 既定は **中身に合わせる**（`table-layout: auto` ＋ `th, td { max-width: … }` で打ち切り）。
- ドラッグで手動指定すると `width` / `min-width` / `max-width` を同時に当てる
  （`max-width` も動かさないと打ち切りが既定のままで、広げても隠れた文字が見えない）。
- ダブルクリックで**既定（中身に合わせた幅）へ戻す**。

## 目的 / ゴール

- **大きな結果でも初回描画が待たされない。** 1000 行を選んでも実用的であること。
- **スクロールで列幅が動かない。**
- 既存の使い勝手（手動リサイズ・ダブルクリックで戻す・行番号列・LOB 表示・
  下端で読み足し・タブを戻したときのスクロール位置）を**壊さない**。

## スコープ

### 対象

- `SqlResultTable.vue` の行描画（表示範囲だけ描く）。
- 列幅の決め方（測って固定する方式への移行）と、`useColumnWidths` との噛み合わせ。
- 実ブラウザでの**前後の実測**。

### 対象外

- **データ転送ペインの表**。`useColumnWidths` を共有しているので幅の扱いが変われば
  波及しうるが、あちらは行数が少なく仮想化の動機が無い。**壊さないことだけ**確かめる。
- サーバー側のページング・取得量（`pageSize` / `maxRows` の意味は変えない）。
- 列の並べ替え・絞り込みなど新機能。

## 機能要件

- **表示範囲＋前後の余白だけを描く。** 行数が増えても描画コストが一定に近いこと。
- **スクロールしても列幅が変わらない。**
- スクロールバーの長さが**全行数を反映**する（掴んだ位置と中身が一致する）。
- **手動リサイズが効く**（ドラッグ中も含む）。ダブルクリックで既定へ戻せる。
- **下端での読み足し**（`load-more`）と End / PageDown が効く。
- タブを切り替えて戻ったとき、**スクロール位置が保たれる**（現行の約束）。
- 行番号（`#`）が**通し番号**であり続ける（間引いてもずれない）。
- **キーボードと選択・コピー**の使い勝手を著しく損なわない
  （範囲選択が画面外の行に及ばなくなる点は、仮想化の避けられない代償として記録する）。

## 非機能要件 / 制約

- **追加の依存を入れない**（仮想スクロールのライブラリを入れない）。
- 実ブラウザで**前後を測り、数字で示す**（jsdom では描画コストも列幅も測れない）。
- 実機は共用の本番機。作った表は消す。
- 検証スクリプトに内部 IP を書かない。資格情報は `.env` のみ。

## 完了条件 (受け入れ基準)

      （200 行 × 40 列、および 1000 行 × 40 列）。
- [ ] スクロールしても**列幅が変わらない**ことを実ブラウザで確かめている。
- [ ] スクロールバーの長さが全行数を反映している。
- [ ] 手動リサイズ・ダブルクリックで戻す・読み足し・スクロール位置の保持が
      **すべて従来どおり**動く。
- [ ] データ転送ペインの表が壊れていない。
- [ ] 単体テストで、間引き（表示範囲の計算）と行番号の対応が固定されている。

## 未確定事項 / 確認したいこと

- **列幅をどう決めるか**——(a) 先頭の一部を描いて測って固定、(b) 全行の文字数から
  見積もる、(c) 現状どおり全行を描いて測る（＝初回の重さは残る）。
  **設計で決める**。それぞれ「幅の正しさ」と「初回の速さ」の取り合いになる。
- **本当に 100ms かかっているか。** backlog の数字は `20260723` 時点のもの。
  **まず現状を実ブラウザで測る**（改善を主張するには基準線が要る）。
- 仮想化しても**十分速くならない**なら、やらない判断もありうる
  （その場合は測定値を残して backlog を閉じる）。
