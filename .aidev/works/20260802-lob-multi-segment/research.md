# 調査: 64KB を超える LOB の分割受信（実機 / IBM i 7.3）

再現: `scripts/research-lob-multi-segment.mjs`

フィクスチャ（`TESTLIB.LOBSEG`。倍々に伸ばして作る——SQL 文の長さ制限に当たらない）:

| 列 | 型 | 実測 |
|---|---|---|
| `C` | `CLOB(1M)`（ジョブ既定＝**混在 5035**） | 262,144 バイト / 262,144 文字（中身は ASCII） |
| `G` | `DBCLOB(1M) CCSID 1200` | **524,288 バイト / 262,144 文字** |

## F1〜F3: 単位はすべて「文字」だった

`0x1816`（`retrieveLobData`）の往復を生で覗いた結果:

| 項目 | CP | 単位 | 根拠 |
|---|---|---|---|
| `lobRequestedSize`（要求量） | `0x3819` | **文字** | `want=65535` に対し `body=131,070` バイトが返った（1200） |
| `lobStartOffset`（開始位置） | `0x381a` | **文字** | 下記 F4 |
| `lobData` の長さフィールド | `0x380f` | **文字** | `lenField=65535` / `body=131,070` バイト |
| `lobDataLength`（総長） | `0x3810` | **文字** | `declared=262,144`（バイトなら 524,288） |

**長さ 2 つ（`lenField` / `declared`）は既に `* perChar` していて正しい。**
`20260801-dbclob-locator-decode`（PR #248）が直したのはここ。

## F4: 分割の 2 周目でデータが飛ぶ（**silently wrong**）

`G` を `maxBytes=200000` で取ったときの往復:

```
want=65535 offset=0      → lenField=65535 body=131070B   [30 42 30 44 …]（あいうえ…）
want=65535 offset=131070 → lenField=65535 body=131070B   [30 4d 30 4f …]（きく…）
```

**2 周目の `offset` が 131,070。** これはバイト数（1 周目で受け取った `body.length`）だが、
ホストは**文字**で解釈するので、実際には**文字 131,070 目 ＝ バイト 262,140 目**から読まれる。

結果、取れた値は

- 文字 0〜65,534（1 周目）
- 文字 131,070〜196,604（2 周目）

で、**文字 65,535〜131,069 の 65,535 文字が丸ごと欠けている**。
スクリプトの出力:

```
最初に食い違う位置: 65535 文字目 = 131070 バイト目
```

**穴が空いた値に `too-large` が付く**のが最悪の点。`too-large` は「先頭から順に取れて
末尾で切れた」と読ませる印なので、**利用者は中抜けに気づけない**。

`C`（混在 5035・中身 ASCII）は `perChar=1` なのでオフセットが一致し、**正しく取れる**。
——**SBCS だけで測ると通ってしまう**という、この LOB 実装で 3 度目の同じ罠。

## F5: メモリ上限（`maxBytes`）が守られていない

`retrieveLob(conn, loc, { maxBytes: 200_000 })` の戻り:

```
bytes=262140 totalLength=524288 ccsid=1200 truncated=true
```

**262,140 バイト**——上限の **1.31 倍**。`want` をバイトのつもりで
`min(SEGMENT, maxBytes - received)` と計算しているが、返るのはその 2 倍のバイト数だから。

上限で打ち切る場合も同じ: `maxBytes=40000` で `want=40000` 文字 →
**80,000 バイト**が返る（2 倍）。**大きな LOB でメモリを掴まない**という
`DEFAULT_LOB_MAX_BYTES` の目的が、2 バイト CCSID では効いていない。

## F6: 「進まなくなったら打ち切る」歯止めが死んでいる

```ts
if (body.length < want) break;   // want は文字、body.length はバイト
```

2 バイト CCSID では `body.length ≒ want * 2` なので**この条件は成立しえない**。
無限ループを防いでいるのは実質 `want <= 0`（上限到達）と `offset >= totalLength` の 2 つだけ。
`totalLength` の比較も**文字とバイトを突き合わせている**ので、当てにならない。

## F7: 既定値では分割経路をほぼ通らない

`SEGMENT_BYTES = 0xffff`（65,535）に対し `DEFAULT_LOB_MAX_BYTES = 64 * 1024`（65,536）。
差が 1 なので、既定のままだと 2 周目の `want` が **1**。
**分割受信は `lobMaxBytes` を明示的に上げないと実質通らない**——だから
PR #248 / #251 の実機確認をすり抜けた。API（`/api/host/sql` の `lobMaxBytes`）と
MCP からは上げられるので、本番で到達しうる。

## F8: 打ち切りの先頭連続性は保たれている（1 セグメントで収まる場合）

`maxBytes=40000` の打ち切りは 1 往復で終わるので、`C` / `G` とも**先頭から連続**。
飛びが出るのは**2 周目以降だけ**。

## 直し方（spec で確定させる）

**ループをホストの単位（文字）で回し、上限（バイト）は換算して当てる。**

- `offset` は**受け取った文字数**で進める（`body.length / perChar`）。
- `want` は**文字**で出す（`perChar` 判明後は `remainingBytes / perChar`）。
- 進捗の歯止めも**文字どうし**で比べる。
- `perChar` は最初の応答まで分からないので、**1 周目だけ上限を超えうる**
  （最大 1 セグメント＝131,070 バイト）。**最後にバイト上限へ切り詰める**ことで、
  戻り値としての約束（`maxBytes` を超えない）は守る。
  切るのは `perChar` の倍数の位置——UTF-16 を奇数バイトで切ると末尾が化ける。

## 積み残し

- **純 DBCS（CCSID 300）の 64KB 超は作れなかった**——`20260801-pure-dbcs-dbclob` の
  二段キャストは小さな値では通るが、倍々に伸ばす経路では試していない。
  `isTwoByteCcsid` は 1200 と同じ枝なので、**1200 で押さえれば同じ道を通る**と判断した
  （型の分岐が同じことは単体テストで固定する）。
