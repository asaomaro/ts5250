# レビュー: LOB の分割受信をホストの単位（文字）で回す

## ラウンド 1

### 見た観点

要件適合 / 正確性 / 規約適合 / 保守性。差分は 6 ファイル（うち新規 3）。
本体の変更は `retrieveLob` 1 関数と、そこから呼ぶ `trimToBytes` だけ。

### 確認したこと

- **backlog の言い分を鵜呑みにしていない。** 「未検証」と書かれていたが、
  現物を読んだ時点で**壊れている疑いが濃かった**ので requirement に仮説として書き、
  research で実測して**確定させてから**直した。推測で直していない。
- **本当に壊れていたか。** 実機で `offset=131070`（バイト）を送り、
  ホストは**文字 131,070 目**から読んでいた。欠落は 65,535 文字ちょうど。
  `research.md` F4 に往復の生ログがある。
- **穴の空いた値に `too-large` が付いていた**——これが最も悪い点。あの印は
  「先頭から順に取れて末尾で切れた」と読ませるので、**中抜けに気づけない**。
  だから検査は件数ではなく**先頭からの連続性**で書いた（単体・実機とも）。
- **直す前に落ちることを確かめた。** 偽ホストが吐いた `131070` / `262140` は
  **実機で採った値と一致する**——模写が正しいことの裏取り。ここが一致しない模写は、
  直したつもりで別のものを直すことになる。
- **元から正しい経路を壊していないか。** 混在 CLOB（`perChar=1`）は往復も結果も
  従来どおり。単体（SBCS・混在の 2 件）と実機（節 3）の両方で見た。
  混在が `perChar=1` で正しいことは `20260801-dbclob-locator-decode` で確認済み
  （申告長が SO/SI 込みのバイト数）。
- **申告値で進めていないか。** `offsetUnits += gotUnits` の `gotUnits` は
  **届いたバイト数から割った**値。申告どおり進めると、応答が途中で切れたときに
  届いていない分を飛ばす（＝今回直した不具合と同じ形の穴が別経路で開く）。
- **短い応答を終端と決めつけていないか。** 従来の `body.length < want` は
  2 バイト CCSID で成立しえない死んだ歯止めだった。直すにあたり
  **総長が分かっているときは短い応答で止めない**ようにした——止めると
  「ホストが返せた分」を全部だと思い込む。総長が不明なときだけ終端と見なす。
- **上限が守られているか。** `maxBytes=200,000` に対し従来は 262,140 バイト（1.31 倍）、
  `40,000` に対し 80,000 バイト（2 倍）を保持していた。`perChar` は最初の応答まで
  分からないので**1 周目だけ超えうる**——最後に切り詰めることで戻り値の約束を守る。
- **切り詰めで末尾を壊していないか。** `perChar` の倍数で切り、
  **末尾が上位サロゲート単独なら 1 単位落とす**。落とさないと孤立サロゲートが残り、
  「打ち切られた」ではなく「壊れた」ように見える。
- **名前が単位を偽っていないか。** `SEGMENT_BYTES` → `SEGMENT_UNITS`。
  **この誤名がバグの入口**なので、直したあとに同じ名前を残さない。
- **公開の形を変えていないか。** `RetrievedLob` はそのまま。`opts.startOffset` の
  意味だけバイト→文字に変わるが、呼び出し元（`fillLobs`）は常に省略している。
  doc に単位を明記した。
- **秘密の混入。** ステージ済み差分をパスワード・ホスト・内部 IP で機械走査
  （陽性対照つき）。パスワード 0 / ホスト 0 / 私的アドレス 0。
  利用者名は 5 件当たったが、**すべて `TESTLIB`（ライブラリー名）の部分一致**——
  既存の `research-dbclob-locator.mjs` に以前から入っている公開済みの識別子。

### 指摘

**must**: なし
**should**: なし

**nit（対応済み）**:
- 本体が空の応答（`rawData.length <= 6`）で **CCSID を読む前に抜けていた**。
  総長は申告されているのに単位が分からず、2 バイト CCSID の総長が**半分**（文字数のまま）
  で返る。CCSID を読んでから抜けるようにし、テストを 1 件足した（14 → 15 件）。
  従来の実装でも同じ穴があったが、`totalLength` を loop 内で立てていたため
  「0 で返る」形に化けていて表に出なかった。
- `if (wantUnits <= 0) break;` が現在の式では到達しない。消さずに残し、
  **「刻み方を変えたときの空回りを塞ぐ」**という意図をコメントにした。

### 残した制限（PR 本文にも書く）

- **純 DBCS（CCSID 300）の 64KB 超は作れなかった。** 二段キャスト（1200 経由）は
  小さな値では通るが、倍々に伸ばす経路で試していない。`isTwoByteCcsid` は
  1200 と同じ枝なので同じ道を通る（型の分岐はテストで固定）。
- **BLOB（CCSID 0）の 64KB 超は測っていない。** `perChar=1` なので混在 CLOB と同じ経路。
- **既定値（`lobMaxBytes` 未指定）では分割経路を通らない**（`SEGMENT_UNITS` 65,535 に対し
  既定上限 65,536）。**これが PR #248 / #251 の実機確認をすり抜けた理由**なので、
  今後 LOB を実機で測る人向けに `scripts/README.md` に明記した。

## 判定

指摘なし（nit のみ・対応済み）→ walkthrough を挟んで deliver へ。
差分は 1 関数だが、**単位という目に見えないものが芯**で、diff からは読み取りにくい。
実機の往復ログを添えて示す価値がある。
