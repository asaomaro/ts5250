# 要件: 64KB を超える LOB の分割受信と `too-large` を実機で確かめる

## 背景 / 課題

`.aidev/backlog/hostserver.md:459` の未着手項目。

> **64KB を超える LOB の分割受信と、LOB の打ち切り（`too-large`）を実機で確かめる**
> PR #248 / #251 で長さの単位を直したが、**1 応答に収まる値でしか測っていない**。
> 分割受信が跨ぐ場合と、`too-large` が正しく立つかは未実測（UTF-16・純 DBCS の両方）。

着手前に現物（`packages/hostserver/src/db/lob.ts`）を読んだところ、**未検証というより
壊れている疑いが濃い**。以下は仮説であって、実機で確かめるまで事実ではない。

### 仮説 1: オフセットの単位が食い違っている（最有力）

`retrieveLob` のループは、ホストへ送る `lobStartOffset` を**バイトで進めている**:

```
const dataBytes = view.getUint32(2) * perChar;   // 応答の長さは【文字数】→ バイトへ換算
…
offset += body.length;                            // ← バイトで進める
```

しかし応答の長さフィールドを `* perChar` している時点で、**ホストは 2 バイト CCSID の
LOB を「文字」で数えている**と認めている。だとすれば要求側の `lobStartOffset` も
文字のはずで、バイトで進めると **2 セグメント目以降が 2 倍の位置から読まれる**
——中身が飛ぶか、範囲外で空が返って途中で切れる。

**1 応答に収まる LOB では `offset` が二度と使われないので、この食い違いは現れない。**
PR #248 / #251 が「1 応答に収まる値でしか測っていない」というのは、
まさにこの分岐を一度も通していないということ。

### 仮説 2: 分割の終了条件が 2 バイト CCSID で効かない

```
if (body.length < want) break;   // want は【バイト】、body.length も【バイト】
```

`lobRequestedSize`（`want`）もホストが文字で解釈するなら、返るのは最大 `want` 文字
＝ **`want * 2` バイト**。すると `body.length < want` は**まず成立しない**ので、
この歯止め（進まなくなったら打ち切る）が働かない。

### 仮説 3: 既定値では分割そのものが起きない

`SEGMENT_BYTES = 0xffff`（65,535）に対し `DEFAULT_LOB_MAX_BYTES = 64 * 1024`（65,536）。
差は 1 バイトなので、既定のままだと 2 周目の `want` が **1** になる。
**分割受信の経路は、`lobMaxBytes` を明示的に上げない限り実質通らない。**
API（`/api/host/sql` の `lobMaxBytes`）と MCP からは上げられるので、本番で到達しうる。

### なぜ今やるか

LOB の長さの単位は**同じ罠を 2 回踏んでいる**（PR #245 のインライン経路、PR #248 の
ロケーター経路）。backlog にも「**SBCS だけで試すと文字数＝バイト数で一致し、
取り違えが結果に出ない。LOB の長さは必ず全角で確かめること**」と警告が残っている。
分割受信は**その罠が 3 度目に出る場所**として最も可能性が高い。

## 目的 / ゴール

- **64KB を超える LOB が正しく取れることを、実機で確かめる**。
  取れないなら直す。
- **`too-large`（打ち切り）が正しく立つ**ことを確かめる。
- 確かめるのは **SBCS / 混在 CLOB / UTF-16 DBCLOB / 純 DBCS DBCLOB** の 4 系統。
  **SBCS だけで通しても意味がない**（文字数＝バイト数で一致してしまう）。

## スコープ

### 対象

- `packages/hostserver/src/db/lob.ts` の `retrieveLob`（分割受信のループ）。
- 分割が跨ぐときのオフセット・要求サイズ・終了条件の単位。
- `truncated` → `too-large` の判定（`query.ts` の `fillLobs`）。
- 実機（）での再現スクリプトと、単体テスト。

### 対象外

- **まとめ取り**（`20260801-lob-batch-retrieval-research` で「道は無い」と結論済み）。
- LOB フィールドしきい値（インライン経路）。あれは別の行で扱う。
- `DEFAULT_LOB_MAX_BYTES` の既定値そのものを上げること。
  大きな LOB でメモリを掴まない方針は変えない（**上げられること**は確かめる）。
- 書き込み（`0x1817`）。読みだけ。

## 機能要件

- **2 バイト CCSID の LOB でも、要求した長さぶんが欠けずに揃う。**
  取れた中身が、書き込んだ内容と**バイト単位で一致**すること。
- **上限で打ち切ったときに `truncated` が立ち、`too-large` として画面に出る。**
  打ち切られた側の中身も**先頭から連続**していること（飛びや重複が無い）。
- 分割が何周しても**無限ループにならない**（進まなくなったら止まる）。
- 単位が食い違っていたら**単体テストで再現できる**形にする
  ——実機が無い環境でも回帰を止められるように。

## 非機能要件 / 制約

- 追加の依存を入れない。
- **実機（）は共用の本番機。** 作った表は必ず消す（`finally`）。
  他人のオブジェクトに触らない。大きな LOB を扱うので、**表は自分のライブラリーに作る**。
- 検証スクリプトに内部 IP を書かない（`process.env.AS400_HOST`、既定値なし）。
- 資格情報は `.env` のみ。`.aidev` 成果物・コード・コミット・PR 本文に書かない。
