# 要件: 待ち行列サービスの実行内容（Webhook 転送）

## 背景 / 課題

待ち行列の常駐監視（`20260723-dtaq-watch-notify`）は、いま**画面に出すだけ**である。
利用者の当初の言葉:

> データ待ち行列について … サービスとして利用する場合、**サーバー側で指定のコマンドを
> 実行させたりすること**などが考えられます。

サービスとしての値打ちは「ブラウザが居なくても動く」ことなので、**届いたときに
サーバー側で何かが起きる**のでなければ、常駐させる意味が半分しかない。

利用者の選択は **Webhook（HTTP へ転送）**。コマンド実行より危険が小さく、受け手を
別プロセスにできる。

## 目的 / ゴール

**待ち行列に届いたエントリを、設定した URL へ転送する。** ブラウザが居なくても。

## スコープ

### 対象

- `dtaqwatch` 定義に **Webhook の設定**（URL・秘密・タイムアウト・再試行）
- 届いたエントリの **HTTP POST 転送**（到着順）
- **失敗の扱い**——監視は消費するので、落とした分が黙って消えない仕組み
- 画面への露出（設定欄・失敗の表示）

### 対象外

- **コマンド実行**（今回は採らない。必要になったら別途、独自の信頼設計で）
- 受け手側の実装
- 複数宛先への転送（1 定義 1 宛先）
- 転送の永続キュー（プロセスが落ちたら未送分は失われる。下記「未確定事項」）

## 機能要件

- 定義に URL を設定すると、届いたエントリがそこへ POST される
- **到着順に送る**（1 監視につき直列）
- 失敗したら**再試行**し、諦めたら**画面に出す**
- 秘密（認証ヘッダー）を設定でき、**平文で保存されない**
- 転送を設定していない監視は**従来どおり**（画面に出すだけ）

## 非機能要件 / 制約

- **信頼境界**: Webhook は**サーバー設定だけ**が持てる（`printer` / `pcCommand` と同じ 5 層目）
  ——サーバーからの**外向きのデータ経路**であり、個人設定に置けてはならない
- 遅い受け手が**監視そのものを止めない**（読み取りを塞がない）
- 溜まった未送分が**無限に増えない**

## 完了条件 (受け入れ基準)

- [ ] 設定した URL にエントリが届く（実機のキュー → 実際の HTTP 受け口）
- [ ] 受け手が落ちていても**監視は止まらない**
- [ ] 諦めた分が**画面で分かる**
- [ ] 個人設定に Webhook を送ると 400
- [ ] 秘密が設定ファイルに平文で残らない

## 未確定事項 / 確認したいこと

- **プロセスが落ちたときの未送分**をどう扱うか（永続キューを持つか、失うと割り切るか）
- **URL の制限**をどこまで掛けるか（内部ネットワークへの到達をどう考えるか）
