## 実機で測ったこと

```
  PASS **秘密が復号されて解決に載る**
  PASS 転送ありとして立ち上がる
### 1. 届く
  PASS **実キューのエントリが実際の HTTP で届く**
  PASS 本文が載る（ORD-0001）/ キュー名が載る
  PASS **秘密が設定したヘッダーで届く** / 本文の署名が付く / 配送 id が付く
### 2. 受け手を落とす
  PASS **受け手が落ちても監視は止まらない**（実際: listening）
  PASS キューからは読めている（受信 2 件）
### 3. 諦める
  PASS **諦めた分が「未達」として一覧に出る**（黙って消えない）
### 4. 受け手を戻す
  PASS **受け手が戻れば、その後のエントリは届く**
### 5. 受け手が 400 を返す
  PASS 1 回は送る / **4xx は再試行しない**（実際: 1 回）

OK — 14 passed, 0 failed
```

受け口はスクリプト内に立て、待ち行列（`TESTLIB/DTQHOOK`）は**自動で作って消す**。

## 実機検証が見つけたもの

**「未達」の数が次の到着まで古いままだった。**

到着時（`push`）に `w.view.undelivered` へ写し取っていたので、受け手が落ちて諦めても
**キューが静かなら「未達 0 件」に見え続けた**。3 番目の検査がそこで落ちた。

`viewOf()` で**読むたびに実体へ聞く**形に直した。**失敗は「何も起きない」ときにこそ起きる**
ので、写しを持つと一番見たい場面で嘘になる。単体テストにも起こしてある
（「次の到着を待たずに未達が数に出る」）。

## 未検証（穴）

- **プロセスが落ちたときの未送分は失われる**（design D1 で「割り切る」と決めた）。
  設定画面に明記してある。
- **画面の通し確認をしていない**（設定欄と「未達」表示は型と描画までで、
  実ブラウザで操作していない）。実機 E2E は API とレジストリの層で測った。
- **転送先が遅いときの背圧**を実測していない（上限 500 件で落ちることは単体で確認）。
- **`secretEnv` 経路を実機で通していない**（`secretEnc` で通した）。
