# 計画: 待ち行列サービスの Webhook 転送

## 実装方針

**設定 → 転送の実体 → 配線 → 画面**の順。転送の実体（`WebhookSink`）を独立に作り、
`WatchRegistry` には**差し替え可能な口**だけを開ける——レジストリの責務は
「ホストの待ち行列を読む」ことで、HTTP の再試行が混ざると両方読みにくくなる。

## 作業順序と依存関係

1. `webhookSchema`（**サーバー設定にだけ**足す）＋ 種別との整合
2. `WebhookSink`（キュー・再試行・未達の記録）
3. `WatchSink` を `WatchRegistry` に差す（`push` から待たずに渡す）
4. 解決器で秘密を復号 → 3 か所（起動時・WS・反映）から `makeWatchSink`
5. 保存時の URL 検査 ＋ **秘密の据え置き**（`system.password` と同じ約束）
6. 画面（設定の信頼設定欄・一覧の「未達」表示）
7. 単体テスト → 実機 E2E

## リスク / 留意点

- **秘密が保存で消える。** 編集フォームには返らないので、そのまま送り返すと認証が外れる
  ——printer 出力で実際に起きていた壊れ方と同じ形。`toWebhookRecord` で据え置く。
- **`stop` で未送分を捨てない。** 読み取り済みのエントリはホスト側から消えているので、
  捨てれば**ただのデータの喪失**になる。捨ててよいのはプロセスを畳むときだけ。
- **読み取りを塞がない。** `deliver` は待たない・投げない。
- 実機の待ち行列は**自動で作って消す**（`TESTLIB/DTQHOOK`）。

## テスト方針

- **単体**: 2xx/4xx/3xx/5xx の扱い・順序・上限・配送 id・秘密の解き方・URL 検査・
  信頼境界（個人設定に置けない／秘密が返らない）・**秘密の据え置き**
- **実機 E2E**: 実キュー → 実 HTTP／**受け手が落ちても監視が止まらない**／
  諦めた分が未達に出る／受け手が戻れば届く／4xx は再試行しない
