## うまくいった点

- **plan の「赤い区間を最短にする」順序が機能した。** `git mv` した瞬間に core が壊れるので、
  テスト移設や lint 設定を間に挟まず「移設 → 付け替え → 緑に戻す」を一続きにした。
  結果、ビルドが通らないのは T3〜T5 の 3 タスクだけで、T6 で緑に戻った。
  中断可能点を `tasks.md` に明記したことで、途中で止まっても復帰できる状態を保てた。
- **plan で挙げたリスクが実際に当たった。** R3（バンドル膨張）・R4（lint ガードが外れる）・
  R8（web-ui は root の `tsc -b` に含まれない）の 3 つは、すべて現実に起きるか、
  起きうる状態だった。**リスク列挙が儀式ではなく検出装置として働いた**のは今回の再現したい成果。
- **推測せず `main` を worktree に取って同一条件で比較した。** バンドルが 628 バイト増えた件は、
  ベースラインを再現して突き合わせなければ「誤差」で片付けていた。
  実測の結果、最終的にコンテンツハッシュまで一致する状態に戻せた。
- **rename 検出で「変更行 0」を証明したことが、レビュー負荷を実質的に下げた。**
  18,900 行のテーブル移動を「読む必要がない」と機械的に示せたので、
  walkthrough で「設計判断が入っているのは 9 ファイルだけ」と言い切れた。

## 課題 / 手戻り

### 1. requirement の影響範囲調査で `.vue` を取りこぼした（decisions.md D1）

`grep --include=*.ts --include=*.tsx` で影響範囲を測り、「web-ui は codec を import していない」と
requirement に**断定形で書いた**。実際は `ScreenGrid.vue:41` が `katakanaChar` を使っていた。
Vue プロジェクトなのに `.vue` を検索対象から外していた。

**前段で防げたか**: requirement 工程の調査手法の問題。**research 工程を挟んでも防げない**——
同じ grep を打てば同じ穴が開く。工程の有無ではなく「網の張り方」が原因。

**より重い教訓**: backlog には「web-ui が import しているのは `katakanaChar` の 1 関数だけ」と
正しく書いてあった。**既存の記録を「古いかもしれない」と疑って実測で上書きしたら、
実測の方が雑だった。** 記録と実測が食い違ったときに真っ先に疑うべきは自分の測り方の方だった。

### 2. spec の「後方互換」の定義が足りず、通ってしまう劣化を招いた（decisions.md D2）

spec D4 で後方互換を「`exports` マップを変更しない」と定義し、それは守った。
にもかかわらず互換ファサードの参照先が ebcdic の**バレル**になっていたため、
`pure-dbcs` が module graph に入り web-ui のバンドルが 628 バイト増えた。

**前段で防げたか**: spec で防げた。後方互換の不変条件は
「**利用側から見た到達可能なモジュール集合が広がらない**」であるべきで、
`exports` マップはその一部の表現に過ぎなかった。定義が狭かったので、
定義を満たしたまま性質が壊れた。

### 3. 新設した「守り」を壊して確かめたのが 3 つ中 1 つだけだった

review の should 2 件は、どちらも**この作業で自分が新設したガードの穴**だった。

| 新設した守り | 壊して確認したか | 結果 |
|---|---|---|
| eslint の Node 非依存ガード拡張 | **した**（`node:fs`/`Buffer`/`process` で 5 件発火） | 問題なし |
| `catalog-no-tables.test.ts` | 部分的（`from "…"` 形だけ試した） | **副作用 import と動的 import を素通し**（should） |
| tsconfig の `types` 設定 | **していない**（ebcdic からコピー） | **scs に不要な `types:["node"]`**（should） |

同じ作業の中で、同じ原則の適用に**ばらつき**があった。
lint については `20260719-core-debt-payoff` の先例が頭にあったので実施したが、
「先例のある対象」にしか適用していなかった＝原則ではなく事例の模倣になっていた。

### 4. 差し戻し後の工程記録が 0 秒になった（記録不備）

`metrics.yml` の 23:26:42 に **coding② approved / test② start / test② approved / review② start**
の 4 イベントが同一 ts で並んでいる。protocol「8.」は
「複数工程を続けて実行する場合も、各工程の start/approved は実際にその工程を行った時刻で記録する。
まとめて同一 ts にすると工程別の所要時間が失われる」と明記しており、**これに違反した**。

原因は、差し戻し後の修正検証を coding の中で完結させ、test 工程を形式的に通したこと。
検証自体は行っている（ビルド・lint・テスト・バンドル・gen:tables を通し直した）が、
**その実施時間が coding に埋もれ、test 工程は 0 秒として記録された**。
このデータのまま insights で集計すると「差し戻し後の test は一瞬で終わる」という誤った傾向が出る。

## 改善提案

### 製品 / コード（→ issue 候補）

- **`ScreenGrid.vue` の `katakanaChar` 1 関数のために EBCDIC 表がバンドルに入り続けている。**
  今回は「悪化させない」ことだけを保証した。削るには backlog の
  「CCSID テーブルの同梱単位を見直す」に着手する必要がある。
  **今回の分割で `@as400web/ebcdic/codec` という狭い入口ができたので、
  当時より打ち手が取りやすくなっている**（サブパス分割は選択肢の (b) に相当）
- **`packages/server` の `zip-writer.test.ts` が `unzip` 不在の環境で 4 件落ちる。**
  外部コマンド依存のテストがスキップではなく失敗になるため、
  `npm test` の緑/赤が環境で変わる。`unzip` の有無を検出して skip する形にすれば、
  「失敗 0・skip N」として正直に出せる（今回この 4 件のせいで、
  自分の変更による回帰かどうかを worktree で切り分ける手間が発生した）
- **新パッケージに README が無い。** publish は今回のスコープ外だが、
  切り出しの価値（SBCS 止まりでない・依存ゼロ）を書き残す場所が無い状態

### PJ プロセス / 規約（→ AGENTS.md）

- **「守り（ガード・検査・lint ルール）を新設したら、必ず壊して落ちることを確認する」を明文化する。**
  AGENTS.md には `no-restricted-globals` について
  「追加したうえで、違反コードを実際に書いて lint が落ちることを確認している」と
  **実例としては書かれているが、原則としては書かれていない**。
  そのため今回、lint には適用され tsconfig と検査テストには適用されなかった。
  対象を「lint ルール」に限定せず「ガード全般（型設定・検査テスト・CI チェックを含む）」に広げる
- **影響範囲を grep で測るときは、検索対象の拡張子をリポジトリの実態から決める。**
  `git ls-files | sed 's/.*\.//' | sort -u` で実在する拡張子を確認してから `--include` を組む。
  この PJ は `.ts` / `.vue` / `.mjs` が混在しており、`.ts` だけでは web-ui を丸ごと見落とす
- **「後方互換」を宣言するときの不変条件を、シンボルの有無だけでなく到達可能性まで含めて定義する。**
  ライブラリ境界を動かす変更では「同じ名前が取れる」だけでは足りず、
  「利用側から到達できるモジュール集合が広がらない」まで見ないと、
  ビルドもテストも通ったままバンドルが膨らむ
- **既存の記録（backlog・decisions・retro）と自分の実測が食い違ったら、まず自分の測り方を疑う。**
  今回は backlog の方が正しく、実測を根拠に requirement へ誤った断定を書いた

### ハーネス自体（→ aidev-* への提案・適用は人間）

- **`aidev approve <工程>` で、同一 phase の直前 start と ts が同一なら警告する。**
  今回 test② が 0 秒で記録された。protocol「8.」は散文で禁じているが、CLI は素通しする。
  「散文の約束を CLI で機械的に弾く」のは protocol「2.8」が既に採っている方針なので、
  同じ考え方をメトリクス記録にも広げられる。少なくとも `aidev verify` で
  「所要 0 秒の工程」を検出して retro/insights に上げるだけでも、
  集計の歪みに気づける
- **差し戻し後の再検証を、どの工程の記録にするかを protocol に明記する。**
  「review → coding へ差し戻し → 修正 → 再検証」の再検証は、
  coding の一部なのか test 工程のやり直しなのかが protocol「3.」から読み取れない。
  今回は coding 内で終わらせて test を形式的に通したが、
  逆に「必ず test 工程として通し直す」と決めれば 0 秒問題も起きない
- **`aidev status` に「backlog の項目と works の対応」を持たせることの検討。**
  今回、backlog の項目 1・2 を消化したのに `.aidev/backlog/library-extraction.md` の
  チェックボックスは未着手のままで、deliver 後に手で消し込む必要があった。
  `state.yml` に `backlogRef`（ファイル+行）のような参照を持てば、
  deliver 時に消し込み漏れを検知できる（**提案のみ。適用は人間**）
