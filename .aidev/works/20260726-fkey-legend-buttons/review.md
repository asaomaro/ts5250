## ラウンド 1（2026-07-26）

観点: requirement の完了条件 / spec との整合 / AGENTS.md（コメントは意図中心・桁揃えの前提）/ 正確性 / 保守性。

- **[should]** `src/composables/fkeyLegend.ts:170-174` **ラベルからは末尾の罫線を除くのに、
  ボタンの占有幅（`width`）からは除いていない。**
  `label` は `TRAILING_BORDER` で罫線・句読点を落としているが、`endIdx` は
  「末尾の空白だけを落とした `raw`」から計算しているため、`width` に罫線が残る。
  描画はラベルではなく**桁（width）で切り出す**ので、**ボタンが隣の罫線を飲み込む**。
  - 実測: `|F3=終了|` → `label="終了"` なのに `width=8`（桁 2〜9＝末尾の `|` を含む）。
    `F3=終了 :` → `width=9`（`:` を含む）。
  - spec B1-3「末尾の罫線文字を除去する」との不整合。表示だけの問題で AID は正しく飛ぶが、
    窓が狭くラベルの直後に罫線が来る画面で見た目が壊れる。
  - 対応: **差し戻し**（幅もラベルと同じ切り出しにする）
- **[nit]** `src/composables/fkeyLegend.ts:99-102` `charAtCol` が `colOf.indexOf()` の線形探索で、
  窓検出の二重ループから呼ばれる。24x80 では実害が無く、検出は snapshot 単位の computed で
  1 回しか走らないため、現状は許容。
  - 対応: 許容（将来 132 桁×大量の罫線行で重くなるようなら見直す）
- **[nit]** `ScreenGrid.onFkeyClick` と `EmulatorPane.onFkeyAid` で `busy` / `keyboardLocked` を
  二重にチェックしている。防御的で害は無く、どちらか一方が将来消えても安全側に倒れる。
  - 対応: 許容

### 確認したが問題なかった点

- コピー・語頭ジャンプは `columnCharAt`（cells＋編集モデル）を参照しており、**DOM を読んでいない**。
  ボタン化しても矩形コピーや Ctrl+矢印に影響しない。
- `legendsByRow` は `props.snapshot` のみに依存する computed で、打鍵のたびに再検出しない（decisions D1）。
- 意匠 `none` では `legendsByRow` が空 Map を返し、描画側は従来どおりの `linkParts` 経路になる。
- `gui.selectionFields` は 1 フィールド 1 行のデータ構造で、行単位の除外と描画（横並び）が整合している。
- コメントは意図・根拠（spec / research / decisions）を参照しており AGENTS.md に沿う。

## ラウンド 4（2026-07-26・拡張5250 の窓矩形）

ユーザーの質問「拡張5250 でない WINDOW 属性の DSPF を表示した場合は？」を機に、
`gui.windows` 経路を実データで点検した。

- **[must] `detectWindowRect` が拡張5250 の窓を 1 行/1 桁ずつ余計に削っていた。**
  罫線文字の窓に合わせて上下左右を内側へ寄せていたが、**拡張5250 の窓は枠を「線」として
  描く**（クライアントが `.gui-window` を絶対配置し、文字セルを消費しない）。したがって
  宣言された矩形がそのまま使用領域であり、削ると**窓の先頭行・最終行の凡例が落ちる**。
  - 実測（TESTLIB/EXTPGM の WINDOW）: 宣言 `row=6 col=17 46桁×10行`。
    枠線の内側に `Row 1`(r6) と `Row 10`(r15) の両方が入っていることを画面で確認。
    旧計算は 行 7〜14 / 桁 18〜61 に縮んでいた。
  - 対応: **修正済み**（`row1=w.row, row2=w.row+height-1, col1=w.col, col2=w.col+width-1`）。
    実機の実測値を使った回帰テストを追加し、旧計算では落ちることを確認した。
  - 実機再確認: WINDOW 画面でボタンは `F12=Cancel` の 1 個のみ＝窓の中だけが対象で、
    下の画面の `F3=exit`（1 行目）は除外される。

> 見つかった経緯: 「アプリの WINDOW DSPF はどう判定されるのか」という問いに答えるため
> 実データを見直したところ判明した。EXTPGM の凡例がたまたま窓の中ほど（r14）にあったため、
> 既存のテストでも実機確認でも露見していなかった。
