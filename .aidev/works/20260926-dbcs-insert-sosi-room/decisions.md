# 決定記録

## D1: full で進め、(a) と (c) の両方を対象にする（着手時の判断）

- 背景: `aidev-util-batch` で `acs-parity.md` の先頭の未着手項目「挿入モードの余地の残り（DBCS）」を autonomous で起こした（利用者の指示「acs-parity を autonomous で進めて」。2026-09-27）。
  人間の確認が入らないので、三層の判定は安全側（full）に倒す（`aidev-00-start` 手順0）。
- 決定: profile は full。項目の (a) O 欄の SO/SI を含む必要桁と、(c) 継続欄への IME 確定の余地の両方を扱う。
- 理由: (a) は ACS 側が実機で測定済み（`20260921-dbcs-insert-room` の C3・C4 が 0012）で、当 PJ の差だけが残る。
  (c) は ACS 側が未測定とされていたが、原典（`PS5250.insertChar` → `processCharWithDBCSOpenContField`）を読めば手順は確定でき、
  必要なら `scripts/acs-probe.mjs` で実機の ACS のコアに当てられる（AGENTS.md「判断の原則」2）。どちらも ScreenGrid の DBCS の挿入という同じ箇所に閉じる。
- 影響: (c) を調べて「当 PJ と同じ」と分かれば、実装せずに台帳の記述を直すだけにする（その判断は research の結果で決め、ここに追記する）。

## D2: (a) は「入るか・0012 か」だけを ACS に合わせ、入ったあとのバイト列の差は別項目に割る

- 背景: research F5・F6。ACS と当 PJ の必要桁が違うのは 2 つの場合（(i) 並びの直後の半角の字の桁へ全角、(ii) 並びの最初の全角の桁へ半角）だけだが、
  入ったあとの ACS のバイト列（別の並び・空の SO/SI）は、当 PJ の DBCS 欄の編集の値（論理値。SO/SI は送信時に付け直す）では表せない。
- 案:
  - A) 必要桁の判定だけ ACS に合わせる（0012 になる場合が一致する）。入ったあとは当 PJ の正規化した並び（桁を 2 つ／2 つ少なく使う）のまま。
  - B) DBCS 欄の編集の値に SO/SI の位置を持たせ（センチネル）、判定も結果も ACS と同じにする。core の送信・web-ui の全編集操作（Backspace・Delete・Erase EOF・貼り付け・IME）に及ぶ。
- 決定: **A**。B は項目の規模（優先度 低・深さ △）を大きく超え、全 DBCS 編集操作の回帰リスクを負う。
  **「当 PJ の構造では真似できない」として退けたのではない**（AGENTS.md「判断の原則」1）——B は実現できるので、差を事実つきで backlog に起票して残す。
- 影響: requirements の AC2（入ったあとのバイト列が ACS と同じ）はこの work では満たさない。完了条件から外し、対象外に理由つきで移す。
  A のままだと、(i)(ii) で入ったあと当 PJ は ACS より 2 桁（(i)）・2 桁（(ii)。空の SO/SI の分）多く空きが残るので、続けて打つと ACS では 0012 になる挿入が入りうる。これも起票に書く。

## D3: (c) 継続欄への IME 確定は、ACS の手順を記録して別項目に割る

- 背景: research F7。ACS の継続の O 欄は、隣り合う SI・SO を併合して鎖全体へ語単位で詰め直して判定する。当 PJ は区間の中で数える。数え方が根本から違い、実機での測定もまだ無い。
- 決定: この work では直さない。F7 を根拠に、実機の ACS のコア（`scripts/acs-probe.mjs`）での測定から始める別項目を起票する。
- 理由: 推測で合わせない（AGENTS.md「判断の原則」2。測れるので測ってから）。規模も (a) と切り離して検証できる。
- 影響: AC4 は「根拠つきで記録し、差があれば直す or 割る」なので、記録と起票で満たす。

## D4: T3（別項目の起票）は deliver で消化する

- 背景: T3 は `acs-parity.md` への起票で、本項目の消し込み（deliver の責務。`aidev-70-deliver`「3.5」）と同じ行を書き換える。
- 決定: coding では消化せず、deliver で消し込みと同じコミットに入れる。coding の承認時に T3 は未チェックのまま残る。

## D5: 生き残る変異のうち 3 つは等価変異として残す

- 背景: coding の mutation（T1・T2）で、次の 3 つは結果が変わらず生き残る。
  - (i) の「前が全角」を外す: 前が半角なら当 PJ の既存の判定（字を入れて収まるか）も SO・字・SI の 4 桁を数えるので、同じく 0012 になる（research F5）。
  - (ii) の「前が半角か無い」を外す: 並びの中ほどの全角へ半角は、当 PJ も SI・字・SO の 3 桁になる（同 F5）。
  - 「O 欄に限る」を外す: J・G 欄は全角だけ（全角と半角の境目が無い）ので (i)(ii) が起きない。E 欄は全角・半角を混ぜられる差が別項目にある（`acs-parity.md`「E 欄で SBCS と DBCS を混ぜられる差」）ので、混ぜた E 欄は作らない。
- 決定: テストで区別できる形が無い（結果が同じ）ので等価変異として記録し、条件はコードに残す（ACS の表の場合分けと対応させて読めるように）。
