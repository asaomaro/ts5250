# 振り返り: STRPCO / STRPCCMD 対応

## うまくいったこと

- **実機捕捉を最初に置いたのが効いた。** `Session5250` の `traceRecords` を warn で拾うだけで
  ACS タップ（[[acs-tap-proxy-capture]] の手順）を立てずに済んだ——**こちらがクライアントとして
  再現できる機能は、自前セッションで捕まえるほうが速い**。タップが要るのは
  「ACS だけが出せる応答」を見たいときに限られる。
- **対照実験でプロトコルを確定した。** `PAUSE(*NO)` と `PAUSE(*YES)` の 2 レコードを
  バイト比較して「差は 1 バイト」と言い切れた。`STRPCO` も「メニュー再描画と完全一致」で
  実装不要と確定できた。**推測なら「たぶん何かしている」で終わっていた**。
- **参照実装（tn5250j / xtn5250）を答え合わせに使った。** 先に実測して、後から定数が一致することを
  確かめる順序にしたので、逐語移植にならずに済んだ（AGENTS.md のライセンス方針とも整合）。
- **判定を「ホストが進んだか」ではなく「こちら側で実行できたか」に置いた。**
  research D5（ホストは実行の有無を検証しない）が分かっていたので、E2E の設計を最初から
  ファイル生成の確認にできた。ここを外していたら**何も実行しなくても緑になる E2E**を書いていた。

## つまずいたこと（次に活かす）

- **CL のコンパイルが `CPF0820` だけで落ち続けた。** 原因は `ADDPFM` の `SRCTYPE(CLP)` 漏れ。
  ジョブログにも理由が出ず、コンパイル・リストのスプールも見つけられず、
  切り分けに 5 本の使い捨てスクリプトを費やした。
  **既にリポジトリ内に動く前例（`build-gridtest3.mjs`）があったのに、先に読まなかった**のが敗因。
  実機に何かを作るときは、**まず同じことをしている既存スクリプトを探す**。
- **`QSYS2.OUTPUT_QUEUE_ENTRIES` は重い。** 全出力待ち行列を走査するため、DB 接続の
  ソケットタイムアウト（20 秒）に当たった。スプールを探すなら対象を絞るか、別の手段を使う。
- **`CALL` の文字リテラルは 32 バイトに詰められる。** CL のパラメーターで長い文字列を渡す設計に
  しかけて、宣言長との食い違いで領域を踏むところだった。**データ域経由に変えて回避**した
  （5250 のコマンド行が 100 桁しかない問題も同時に解けた）。
- **同じジョブで `STRPCO` を 2 回実行すると `IWS4010`。** 1 セッションに複数ケースを詰め込む
  E2E を書きかけて気づいた。実機の状態を持つ機能は**ケースごとにセッションを分ける**。

## 設計上の判断で迷ったところ

- **中間画面を見せるか。** tn5250j に倣って見せない（`screen` イベントも `pendingAid` の解決も
  しない）ことにした。利用者からは「CALL したら次の画面が出た」だけに見える。
  デバッグ時は「何も起きていないように見える」欠点があるので、通知とセッション情報で補った。
- **信頼設定の露出を `printer` と変えた。** `printer` は値を API に返さないが、`pcCommand` は
  編集できる相手に**値ごと返す**。更新がオブジェクトごと置き換えなので、返さないと編集のたびに
  許可リストが黙って消え、**設定の消失が安全側に倒れない**（`enabled` だけ残ると、むしろ緩くなる）。
  なお `printer` 側も同じ問題を抱えているはず——今回は触っていないが、要確認。
