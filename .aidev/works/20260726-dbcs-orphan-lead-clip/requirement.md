# 要件: 相方を失った DBCS 前半セルを 1 桁に切り詰めて描く（ACS 準拠）

## 背景 / 課題

ホストが**既に全角文字が書かれている桁に、属性バイトや別のデータを重ねて書く**ことがある。
5250 の全角文字は **lead（前半）＋ tail（後半）の 2 桁**を占めるので、tail の桁が上書きされると
**lead だけが取り残される**（逆に lead が潰されて tail だけ残ることもある）。

このとき ACS は**その文字を 1 桁ぶんに切り詰めて**描く（見た目は文字が縦に割れた形になる）。
一方こちらは lead を必ず 2 桁の箱（`.wide-cell { width: 2ch }`）で描くため、**上書きされたはずの隣の桁まで
食い込み、以降の見た目が 1 桁ずれる**。

### 実機で確認した再現例（CCSID 939）

Attn でホストの ATNPGM が「コマンド入力」窓を 23 桁目から重ねたとき、背面の 19 行目
「選択項目またはコマンド」（2 桁目から DBCS 11 文字＝2〜23 桁）の**最後の「ド」の tail が
窓の左端の属性バイトに潰される**。桁ごとの種別（`L`=lead / `T`=tail / `A`=属性）:

```
      ....+....|....+....|      ← 桁の目盛り
行19  .LTLTLTLTLTLTLTLTLTLTLA.  ← 22 桁目が lead、23 桁目が属性（tail が消えている）
```

- **ACS**: 「選択項目またはコマン」＋切り詰められた文字。窓は 23 桁目から始まって見える
- **こちら**: 「選択項目またはコマンド」と 2 桁ぶん描くので、窓の左端に 1 桁食い込み**全体が 1 桁右へずれて見える**

利用者から「ACS 側は DBCS を途中で分断する形で表示しているのに対して、WEB 画面側は分断をしていない結果、
1 桁分ずれているのでは？」と指摘があり、実データで裏が取れた。

なお同じ画面で 23 行目の「の設定」は 17〜22 桁にきれいに収まり属性は 23 桁目なので跨がらない。
**跨がっている行だけがずれる**ため、画面全体ではなく一部の行だけが崩れて見える。

## 目的 / ゴール

ホストが全角の片割れを潰した桁でも、**ACS と同じ桁位置**で描けるようにする。
「1 セル = 1 桁」という当実装の原則を、相方を失った全角セルにも貫く。

## スコープ

### 対象

- **tail を失った lead** を 1 桁ぶんの幅に切り詰めて描く（グリフは左半分だけが見える＝ACS と同じ）。
- **lead を失った tail** も 1 桁ぶんを占有させる（現在は読み飛ばしていて桁が消える＝逆方向のずれ）。
- 上記が反転・下線・色などの属性表示と桁数計算（カーソル位置・選択範囲・コピー）と矛盾しないこと。

### 対象外

- **core（`packages/core`）の変更**。バッファは既に「lead の tail が属性で潰された」状態を正しく保持しており、
  スナップショットは事実を忠実に返している。直すのは**描画側の解釈**だけ。
- ホストが送るデータ自体への介入（潰された tail を補完する等の推測）はしない。
- 全角の**入力欄**内での分断（`dbcsType` 付きフィールドの編集）は今回対象外。今回直すのは
  **表示（保護領域・背面テキスト）**で起きる桁ずれ。入力欄で同じ状況が起きうるかは spec で確認し、
  波及するなら明記して切り分ける。

## 機能要件

- `dbcs-lead` セルの次の桁が `dbcs-tail` **でない**場合、そのセルは **1 桁ぶんの幅**で描画する。
  グリフは切り詰め（クリップ）で、隣の桁を侵さない。
- `dbcs-tail` セルの前の桁が `dbcs-lead` **でない**場合、そのセルは**空白 1 桁**として桁を占有する
  （読み飛ばして桁を詰めない）。
- 切り詰めたセルにも、そのセルの属性（反転・下線・色）が 1 桁ぶん正しく乗る。
- 通常の（対になっている）全角セルの描画は**一切変わらない**。

## 非機能要件 / 制約

- 変更は `packages/web-ui` に閉じる（AGENTS.md の「core はピュアロジック」を崩さない）。
- 既存の桁計算（`fieldSlices` / カーソル位置 / 矩形選択 / コピー）と齟齬を出さない。
- `docs/UI-DESIGN.md` に従い、切り詰めの見せ方は CSS で行い生色を使わない。
- web-ui のビルドは `vue-tsc` を含めて通す。テストは `cd packages/web-ui && npx vitest run`。
- **ACS の見た目を正とする**（AGENTS.md「規格どおりより既存クライアントと同じ挙動を優先する」）。

## 未確定事項 / 確認したいこと

- **切り詰めたグリフの見せ方**。ACS は文字の左半分をそのまま描いて分断された形にする。CSS の
  `overflow: hidden` で同じ見た目になるか、あるいは空白に置き換える方が読みやすいかを spec で決める
  （**ACS に合わせるのが原則**だが、可読性を著しく損なうなら記録のうえ判断する）。
- **入力欄（`dbcsType` 付きフィールド）内で同じ状況が起きるか**。起きるなら同じ規則を適用すべきか、
  それとも別 work に切るか。
- **桁計算への波及範囲**。`ScreenGrid` には lead/tail 対を前提にした箇所が複数ある
  （`fieldSlices` の桁数え・コピー・カーソル移動）。表示だけ直して計算がずれると新たな不具合になるため、
  spec で洗い出す。
