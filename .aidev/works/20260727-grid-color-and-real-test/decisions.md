# 決定記録

## D1: グリッド線の色は 5250 の属性バイトではなかった（PR #178 の誤りを修正）

- 背景: PR #178 は `decodeAttribute(g.color).color` で色を決めていた。
- 判明: DDS リファレンス（GRDATR の Table 14）が**専用の色コード**を定めている
  （`BLU=X'01' … WHT=X'07' … NONE=X'FF'`）。属性バイト（0x20–0x3F）とは別の符号体系で、
  そのまま `decodeAttribute` に渡すと**全部緑になる**。
- 決定: `GRID_COLOR` 表を持ち、描画側はそれで引く。X'FF' と未知は白へ。
- **なぜ気づけたか**: 実機に当てるために DDS 構文を調べ、その過程で色表に行き当たった。
  ワイヤ仕様（Wireshark）だけ見ていては**分からなかった**——ディセクタは
  「default_color」というフィールド名を出すだけで、値の意味までは示さない。

## D2: マイナー構造は 11 バイトだった（長さを決め打たない）

- 背景: Wireshark の `deg_ms_fields` は 10 フィールドで模している。
- 判明: 実機は `length=0x0b`＝**11 バイト**で送ってきた。増えているのは**項目ごとの線種**。
  `(*LINTYP DSH)` を指定した箱の実データが `… 01 08 02 08`
  （色=BLU / 線種=DSH / 横罫 2 / 縦罫 8）と並ぶことから確定した。
- 決定: **先頭の length に従って進む**。足りないフィールドは 0xFF（既定）に倒し、
  未知の追加フィールドがあっても長さぶんスキップする。
- 理由: 原典（ディセクタ）のフィールド並びは**モデルであって保証ではない**。
  同じ轍を PR #178 でも踏んでいる（Border Presentation と主構造の可変長）。
  **長さを持っている構造は長さに従う**のが唯一ずれない読み方。

## D3: 実機検証を諦めずにやり直した価値

PR #178 では「DDS 構文が確定できない」として未検証のまま出した。
今回 IBM の DDS リファレンスを取得して構文を確定し、実機に当てたところ、
**D1・D2 の 2 件の誤りが見つかった**。どちらも単体テストは通っていた。

- 構文の壁は「原典を探しに行く」ことで越えられた（推測でコンパイルを繰り返す必要はなかった）
- 未検証のまま出した機能は、**動いているように見えて誤っていた**
