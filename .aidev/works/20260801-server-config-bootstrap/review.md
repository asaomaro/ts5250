# レビュー: サーバー設定を画面から作り始められるようにする

## ラウンド 1（自己レビュー）

### 利用者の指摘がそのまま正解だった

> profiles.json がなくても管理者ユーザーであることは分かっているなら、画面から新規システム
> 追加して、結果を profiles.json に保存するようにするだけなのでは？

調べたら、**個人設定は元からそうなっていた**（`PersonalConfigStore.fromFile` が ENOENT で
空＋`setPath`）。サーバー設定だけが取り残された**非対称**で、設計上の理由は無い。

`persistable` を条件に入れたこと自体は正しい（保存できないボタンを出さない）。
**結論が「機能を隠す」になっていたのが誤り**で、正しくは「保存できるようにする」だった。
条件は 1 文字も変えていない。

### 途中で気づいて直したもの

**`start.sh` が「無ければ profiles.local.json を指す」だけでは壊れる。**
`--profiles` に渡す以上、`fromFile`（無ければ投げる側）に入るので**起動しなくなる**。
渡す前に作るように直した。`.env`（master key）を既に自動生成しているので、扱いは揃っている。

**`.gitignore` を同時に直す必要があった。** 既定の保存先には接続先・ユーザー名・
暗号化パスワードが入る。`connections.json` は無視されているのに `profiles.json` は
されていなかった——既定にした瞬間、**公開リポジトリの作業ツリーに実運用の設定が置かれる**。

## 判断の記録

### なぜ明示指定は投げたままにするか

`--profiles /path/typo.json` で空の設定が立ち上がると、**既存の設定が全部消えたように見える**。
明示指定は「そこにあるはず」という意思表示なので、無ければ黙らない。

`fromFile` と `fromFileOrEmpty` を**呼び分けで意味を表す**形にした（引数のフラグにしない
——呼び出し側を読んだときに、どちらの意味かが名前で分かる）。

### セキュリティ上の変化を過小評価しない

`canEditServer` が true になる場面は**広がる**。ただし:

- 認証あり: admin だけが得る。admin は元よりサーバー設定を管理する役
- 認証なし: 単一利用者・ローカル前提。ポートに到達できる相手は既に保存済み資格情報で
  セッションを張れるので、**新しい種類の力ではない**

信頼設定を書ける相手の**条件は変えていない**。変えたのは「保存先が決まっているか」だけ。

## nit（直していない）

- **`fromFileOrEmpty` と `PersonalConfigStore.fromFile` に同じ ENOENT 分岐が 2 か所ある。**
  基底クラスへ寄せられるが、エラーメッセージ（`profiles` / `connections`）と
  スキーマが違うので、まとめると引数で分岐する層が増える。3 つ目が出たら畳む。
